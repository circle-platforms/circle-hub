# 测试脑图评审（初评）

你是初评方：按团队的评审方法（test-list-review）评审一份测试脑图，写出每个用例的评审发现和整份的等级。结论不由你签：初评交给 Hub 后，要由另一个会话、另一个模型用复核任务包 case-review-verify 独立复核（前驱写这次运行）。不要添加方法以外的评审维度、发现名称或等级。

## 1. 评审对象

- 评审对象由 start_run 的输入 subject 指定：敏捷平台的脑图 `agile:mindmap:<文档编号>`，或上传的 KityMinder 导出。没有给出时先问，不要猜。
- 要对照某个构建时，build 和 version 写在 start_run 顶层，与 pack、product、inputs 并列，不写进 parameters。
- 条目就是用例：默认认带标签（resource 不为空）或按团队模板带标记（带优先级 2 且有子节点）的节点；它的子节点是期望结果。条目编号是 `<文档编号>:<节点编号>`。需要限制为只认带标签用例时，用参数 `case_rule: "tagged"`。
- 一次运行最多 100 个条目。用例更多时开始运行会被拒，修正说明给出分法：优先按分组用参数 `block`（子树）分块；分组超过 100 例、没有更小的分组或用例不在分组下时，用参数 `slice`（`{"from": 1, "to": 100}`，下一段 from 101）按用例顺序分段，可以和 block 一起写。每块单独开始一次运行，各块独立初评、独立复核；每次评审最后一步都开终稿运行；不分块也开 case-review-report（verifications 只写一条）。Hub 按各块最差给出结论和等级，并按测试子项排出原始用例与评审意见的对照表；最终回答原样贴表，再写简短总体意见，详见该包 SKILL。分块和分段二选一，不要重叠。

## 2. 证据，按顺序读六组

Hub 在 start_run 时把能找到的来源绑定到运行，回答里的“来源”列出每个来源的引用和角色。原文用 `get_nodes`（参数 reference）读，命令目录和手册在锁定的知识根里用 `get_nodes`（参数 root、paths）读，要引用的原文用 `resolve_reference` 找到精确的引用。

1. **需求与缺陷**（期望来源，`plm:story:<编号>`、`plm:bug:<编号>`）：开发改了什么——参数、行为、影响的版本、涉及的命令。编号取自标题和上级目录，或参数 stories、bugs。编号没有标明是需求还是缺陷时（如标题开头的“31057-”），两种都会读到；需求和缺陷分开编号，其中一种可能与这份文档无关：先核对记录的标题，只引用相关的那一种；知道是哪一种时用参数 stories 或 bugs 重新开始运行。
2. **产品设计文档**（期望来源，`manual:spec-search:<功能词>` 找到的规格书，最多五份）：功能定位、与其他功能的耦合、设计边界。
3. **CLI 手册与命令目录**（期望来源，锁定构建的知识根）：参数表、合法取值、默认值、依赖、示例。不熟悉的命令一律先在手册或目录里查。
4. **测试策略文档**（线索，`manual:qa-search:<功能词>` 找到的同类功能的测试策略）：同类功能用了哪些维度和方法。
5. **相似功能的历史测试清单**（线索，`agile:search:<功能词>`，不含被评审的这份文档）：覆盖面、设计思路、模块划分。
6. **被评审对象本身**（被判对象）：整份读完，不要只看摘要；命令的已验证测试事实（足迹）在这一版还没有，算证据缺口。

产品行为只以被评审对象、需求、缺陷、产品文档、手册和命令目录为根据。历史测试清单和测试策略只是线索：它们能帮你判断该覆盖什么，不能作为“产品是这样工作的”的根据——只引用线索的发现会被 Hub 退回修复。读不到、没有绑定、检索为空或“对你不可用”的组都是证据缺口，在等级的陈述里逐一写明，不要跳过不说。

## 3. 每个用例的评审发现（槽位 findings）

每个处理过的条目都要给出 `findings` 列表；没有问题就写空列表 `[]`。每条发现：

- `code`：七类问题之一——`literal_issue` 字面问题（重复的行、空字段、错别字、字段格式不一致）、`coverage_gap` 覆盖缺口（缺陷或需求引入的功能或参数没有用例测到）、`differentiation_gap` 区分缺口（两个功能都只测正向、从没有对照着测）、`edge_case_gap` 边界用例缺口（空值、超长字符串、Unicode、大小写）、`negative_gap` 反向用例缺口（缺陷修复的错误路径没有反向用例）、`block_structure_mismatch` 分块结构不符（分组标题与其中用例描述的行为不一致）、`self_contradiction` 业务自相矛盾。
- `rank`：`critical` 严重（对应等级 P6-P7）、`major` 主要（P3-P5）、`minor` 次要（P0-P2）。
- `text`：中文说明，写清楚问题是什么、为什么是问题、应该怎么改。
- `location`：发现落在被评审脑图的哪个节点，写那个节点的 `src:` 引用（通常就是条目自己的位置；缺少的用例写它应该归属的分组或文档节点）。期望来源和线索的原文不写在这里。
- `quotes`：至少一段逐字引文 `{reference, text}`，text 必须一字不差地出现在 reference 所指的片段里；空白、换行、大小写、标点、字符宽度和 Unicode 规范化形式都不能改，否则整份提交不被接受；没有引文的发现会被退回修复。
- `grounds`：其他根据的引用（`src:`、`tree:`、`rec:`）。grounds 只是引用，不能代替引文。
- `commands`：发现提到的命令。照用例原样引用的命令行写 `{"command": "<命令行>"}`：必须是用例文字里整条的那一行（只忽略空白和大小写，不删参数、不加参数、不改取值），Hub 按目录核对参数，结果算用例自己的事实；用例里没有的命令行会被退回修复。说某个命令存在写 `"present": true`，说不存在写 `"present": false`，Hub 按锁定构建的目录核实，说反了会退回修复。反向用例（Negative 类标签）请引用用例里那条带非法输入的命令行，Hub 会确认它确实越界（预期的反驳）；未引用时 Hub 从该用例自身的文字行取命令；自身也没有可核验的行首目录命令时记提示档反驳，请修正原用例后重开评审。

Hub 自己判定字面问题（空字段、取值、重复用例、节点编号、标签写法），结果和你的发现分开列出；你仍可以报告 Hub 判定不了的字面问题（如错别字）。

## 4. 等级（跨条目主张，码 level）

整份（或这一块）给一个等级，写在 `cross_item` 里，只写一条：

`{"nature": "judgment", "statement": "等级理由：……；证据缺口：……", "grounds": ["<所依据的引用>"], "code": "level", "rank": "P3"}`

- P0：覆盖全部功能细节，兼容性、反向、压力、边角用例和极端场景非常丰富
- P1：覆盖全部功能细节，兼容性、反向、压力用例丰富
- P2：覆盖全部功能细节，兼容性、反向、压力用例比较丰富
- P3：覆盖全部功能细节，有一些兼容性、反向、压力用例
- P4：覆盖全部功能细节，有一些反向和压力用例，兼容性不足
- P5：覆盖全部功能，有一些反向和压力用例，功能细节的深度不够
- P6：覆盖基本功能，有反向和压力类型，功能细节覆盖不完整
- P7：没有覆盖基本功能，没有反向和压力类型

等级和发现的严重程度要一致：最重发现为严重（critical）时等级只许 P6-P7，主要（major）时只许 P3-P5，次要（minor）时只许 P0-P2。Hub 只核这个区间，不按发现数量自动定级；没有发现时也不由脚本推定等级。初评投影会冻结源摘要、完整识别参数、整份预期条目和本块选定条目，供独立复核与终稿做整份覆盖对账。

## 5. 提交与修复

用 `submit_result` 一次提交全部条目（start_run 回答的最后给出示例）。每个处理过的条目写 `context`：你为这个条目读过的上下文（用例原文和所引原文）的 SHA-256，64 位十六进制，可以用 shell 的 sha256sum 算；写了 context 的发现，文档以后改了别处时可以沿用。

整份不被接受时（引文不逐字、引用解析不出、结构不对）按回执逐条改正后重交；单条发现被退回修复时（说反了命令是否存在、命令行不在用例里、没有引文、只引用线索、没有写位置），回执给出修正说明和剩余轮数（每个要求项两轮），改正后再交。

文档改过以后重新评审：开始新运行时 `predecessor` 写上一次初评运行的编号。内容没变的条目，start_run 的条目行带“可沿用 rec:…”；提交时这样的条目写 `reuse`（`{"item": "<编号>", "handling": "handled", "reuse": "<那个 rec: 引用>"}`），不写 slots，Hub 核对条目和所引原文没变后沿用原来的发现，检查照常重跑。

## 7. 报告

每次评审（单块或分块）复核结束后，都由初评方开 case-review-report 终稿运行：verifications 每块给一条已受理的验证结果 rec: 引用，target 绑定同一份脑图；precondition_priority 与初评保持一致。结论和等级照 Hub 算出的整体结果，不改判。终稿按初评冻结的整份预期清单对账，未进入任何块和未交付的条目都必须先补齐；只交付输入块里出现过的条目不等于整份完成。

按终稿包 SKILL 用 get_nodes 读取运行记录的 #/items/0/fields/review_tables；有下一页就读完，表按原样逐页贴入最终回答，不改字、不重排。回答或上下文放不下时，按终稿包 review_counts.characters 的冻结边界只贴完整子项，空行结束表格并明确标“部分”、已贴表数和字符数；完整内容交给控制台和原记录续读，不声称未贴或未读部分已完成。随后写“## 评审意见”，给出简短总体意见和等级理由及证据缺口，不重抄逐条用例、发现，也不再另写建议主张。最后一行给出控制台运行页。


## 参数

stories、bugs（直接给需求和缺陷编号）；id_ranges、bare_ids（标题里没有标明类型的编号怎么读）；spec_search、strategy_search、history_search、max_terms（检索规格书、测试策略和历史测试清单）；case_rule、case_priority、group_priority、precondition_priority（哪些节点是用例）；block、slice（分块、分段）。

本包的跳过不是完成：handling=skipped 必须附 reason，列入待续做清单，按回执继续本条目或以当前运行为前驱续做；不能因跳过而省略发现、处置、结论或等级。缺判定时按修正说明补齐并重交；初评缺等级、报告缺块或有未交付条目时先修复所列块或条目，再用新回执重开后续运行。


命令引用须逐字给出本用例的一条完整原文行，不能省略参数、擦除提示符或改大小写/空白；是否为命令及类型是否合法由锁定目录完整核验。不要凭 show/config/no 等前缀或自由文字猜测。

喂入层：这个包读到的用例、缺陷、构建、规格凡经 Hub 读的都由程序自动进喂入层（带锁定树苗和冻结序号），视图按"锁定树苗 + 冻结序号之前的喂入层"读；版本未声明和矛盾的对象单列计数，不进版本差。Circle 只经 knowledge-contribution 回注补程序填不了的语义（带逐字引文），运行中不问人；结构契约见该包 tables/knowledge-structure.json 或 get_nodes 根路径。
