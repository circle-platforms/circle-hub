# packs/workflow/traceability

The defect-to-case traceability matrix (capability 6a): a fact-only workflow pack, computed by the Hub at start_run
(a production run, no model submission needed). For every defect the build's release notes list, the matrix says which
indexed cases carry its id — or that none do, which is an UNKNOWN, never a failure, because the case index is incomplete
by construction (absence is not proof).

## The answer

- **Items** are the defects of the build: id = system plus the normalised bug id when the system is known (plain id when unspecified), label = the defect summary
  from the entry statement, summary = status and case count (`已修复；2 个用例`, `已知（未修复）；无已索引用例（未知）`);
  the defect entries naming more than one system append the systems and the collision note
  (`系统 bugzilla、plm 已确认同号撞号`).
- **traced** (per item): the claim statement uniformly starts with `缺陷 X（发布说明：…；缺陷系统：…）：…`.
  Support when at least one case entry carries the id — the claim statement lists up to the first 5
  cases (`<document>:<node> <title>`, sorted by numeric document then string case id, with `另有 M 个` when > 5), all cases
  are in the claim data and in the complete result references via `get_nodes`, and the grounds are the tree references of the defect entry
  and the case entries. Otherwise
  unknown (missing input): the reason says no indexed case names the defect, that the index is incomplete by construction,
  and how many listed sources were not read / whether the index view was cut. When the defect system status cannot be read
  or verified (unspecified defect system, source unavailable, record without status, unreturned id), it is recorded as unknown with a distinct reason, never assumed unclosed. Two advisory refutations guard integrity:
  `status_conflict` (the same bug is listed as fixed in one entry and known in another — this happens in real release notes;
  the cases are still listed, the status is left to the defect system) and `join_mismatch` (a listed case's raw defect ids do
  not carry the bug — the check re-verifies the join against the raw ids instead of trusting the frozen fields).
- **counts** (run level): the counts (defects, traced, untraced, closed defects and their traced/untraced partition, status unknown defects, conflicts)
  as a fact, with the two views' stated totals, truncation and skipped-source counts. Closed statuses are defined in
  `tables/closed-statuses.json` (default `["closed"]`). A view that declares itself complete (not truncated) but lists fewer keys or entries
  than its stated totals contradicts itself, and the counts are refuted (`count_mismatch`) instead of stated.

## Decisions

- **Id normalisation** (`ids.ts`): a pure run of ASCII digits loses its leading zeros (`0074001` = `74001`, `000` = `0`);
  anything else compares exactly as written. Bug and story numberings never meet: the case view is keyed by the `defects`
  field, which holds bug ids only.
- **System-qualified identity**: named systems form separate rows (`system:id`). A number in two named systems is a definite collision. An unqualified case joins only when the number belongs to one read defect identity; otherwise it remains listed for source clarification.
- **The join is computed once** by the projection (`matrix.ts`) and frozen in the item fields; the check applies the traced
  rule to the frozen fields and re-verifies every listed case against its raw defect ids. `matrix.ts` is tested against an
  independent double-loop join on a random corpus of 2,000 defects.
- **Case identity**: `data.node` (what the cases producer writes), else `data.case`, else the entry digest; the title is
  `data.title`, else the entry statement; the document is `data.document`, else null.
- **The two views must agree** on the product and on the knowledge root (alias build names of one root are fine). A
  mismatch refuses start_run (`view_mismatch`), because the matrix of two different roots says nothing.
- **The cases view is slim** (since 1.0.1): the workflow asks for `fields=document,node,title`, so the index view fits the
  byte budget at real-build scale (a full one did not). The cases' raw defect ids are not in the slim entries, so the check's
  join re-verification applies only where they are (full views, the samples); with slim entries the index's key mapping is
  the join's evidence.
- **No product binding** (since 1.0.1): the inputs' external ids already name product and build; binding a line made the
  engine lock an unrelated build (the newest released one of the line) into the run record. Like regression-scope, the
  workflow binds nothing (`product: { "catalogs": [] }`).
- **The two refutations exist** also because the publish check needs a negative sample per check (T02 R[0]); the matrix
  itself never fails on absence. `join_mismatch` cannot occur from the pack's own projection; it guards the frozen subject.
- The checks never receive the views again: everything they need is frozen in the item fields and the run's `groups` (the
  view facts). The grounds of the counts claim are the `src:` references of the two stored views.
- **No `api.ts`**: a pack is loaded by the engine from the registry and offers nothing to other packages (same as
  case-location; architecture section 10's file rule is met by this README and the declarations).

## How to test

```
node --test --test-concurrency=2 "packs/workflow/traceability/**/*.test.ts"
```

- `functions/ids.test.ts`, `matrix.test.ts`: the normalisation; hand-built views (one case, many, none, a case carrying two
  defects, a known defect, leading zeros, a story id equal to a bug id, dedupe under both spellings); metamorphic order
  independence; an independent double-loop join on 2,000 random defects; the spec's scale (5,000 defects, 60,000 cases)
  computes in well under a second.
- `functions/views.test.ts`, `project.test.ts`, `check.test.ts`, `counts.test.ts`: view reading, the projection (items,
  summaries, groups, refusals, budgets), the check outcomes, the run-level counts.
- `functions/sandbox.test.ts` (needs macOS `sandbox-exec`): every entry point gives the same output inside the Hub sandbox.
- `pack.test.ts`: the manifest and declarations; the publish check offline.
- `publish.test.ts` (temporary PostgreSQL): the real registry publishes the staged pack (6 samples pass, both polarities per
  check) and refuses a wrong or missing sample.
- `production.test.ts` (temporary PostgreSQL): a production run end to end with a fake knowledge reader — the items, the
  summaries, the per-item layers and claims, the run-level counts, the `statuses` parameter, and the pack kept from users it
  is not assigned to.

## Limits

- Budgets: at most 8,000 defect items and about 5 MiB of projection output per run (one sandbox call must carry the matrix).
  Beyond that the run is refused with a fix; the full matrix stays readable from the run's knowledge root with `get_nodes`.
- The pack reads only the listed part of a view: a truncated view is warned about and named in the counts, never silently
  completed.
- The end-to-end test on the REAL knowledge reader comes after the case index (the product pack's `cases` producer) lands;
  see below.

## Needs from other packages

- **hub/knowledge**: nothing new — `index-view@1` with `fields` as served.

## 发布状态的局部缺口（1.0.9）

缺 release-notes@2 原始 status 不再作为整个构建的 producer incomplete。结构身份可核对的缺陷保留原文引用，status:null、declaration_status:undeclared，并带 missing/next_action；缺身份另记 identity_declaration_status:undeclared，不能从正文数字、标题、标记或文件名猜编号和 fixed/known。HTML 仅从解析后的明确 tracker URL 结构取身份，不从锚文本猜状态。

命令树、手册等独立来源仍照常成根；未声明条目不被追溯状态过滤静默删掉，依赖“已修复”的判断保持未知并请求来源维护者补结构状态后重产。缺陷转用例单列 fixed_status 要求项，其他检查继续独立核对。历史根不改写，本版验证只使用合成 JSON/HTML、临时 PostgreSQL 和脚本化模型，不重跑真实同步。
