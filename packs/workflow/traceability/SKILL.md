# 追溯矩阵

Hub 直接算出一个构建的缺陷到用例的追溯矩阵：构建的 release notes 列出的每个缺陷，有没有已索引的用例携带它的编号。不需要你提交结果。

1. 开始运行：pack 写 traceability；inputs.defects 写 `{"external": "knowledge:index:<产品>:<构建>?kind=defect&key=bug"}`，inputs.cases 写 `{"external": "knowledge:index:<产品>:<构建>?kind=case&key=defects&fields=document,node,title"}`（瘦身的用例视图：条目只带文档、节点、标题），两个视图要指向同一个知识根（构建名写任一名称族的写法都可以）。这个任务包不绑定产品线：不要写 product、version、build——输入里的外部标识已经写明产品和构建，运行不会去锁定别的构建。可选参数 statuses 写 `["fixed"]` 或 `["known"]` 只看一种状态的缺陷，不写则两个都算。
2. 结果在开始运行时就算好了：每个条目是一个缺陷（条目编号是缺陷编号），摘要是“状态；用例数”，完整结论在 result.reference 指向的校验结果里。逐条结论用 get_nodes 读取：条目多时回答放不下所有条目，末尾的说明会写明略去了哪些、怎么接着读，照它读完再转述。
3. 原样转述每个条目的结论，不补全、不猜测：
   - “支持”：列出了追溯这个缺陷的已索引用例（编号、标题、文档），按用例编号排序。
   - “未知（缺输入）”：没有已索引的用例标出这个缺陷。这不等于没有用例——用例索引按构造不完整（只收录了能读到、能解析的文档），说明里会写出还有多少列出的来源没有读取、索引视图是否被截断。不要把“未知”说成“没有追溯用例”的结论。
   - “状态矛盾”：这个缺陷在来源里既列为已修复又列为已知，以缺陷系统为准；追溯到的用例照列。
4. 运行级的计数（要求项 counts）在结果的 cross_item 里：缺陷数、已追溯数、未追溯数、状态矛盾数，以及两个视图各自声明的总数、有没有截断、有没有列出的来源没有读取。视图被截断时计数只覆盖列出的部分，转述时照写。
5. submit_result 不是必需的；要补充看法时可以提交，看法记为模型转述的判断，不改变 Hub 算出的矩阵。
