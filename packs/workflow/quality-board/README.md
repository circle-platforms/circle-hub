# packs/workflow/quality-board

The quality board (capability 6b): a fact-only workflow pack, computed by the Hub at start_run (a production run, no model
submission needed). From the facet counts of the build's case index it shows, per (line, module) group: the case count, the
share without an expected result, the share with only vague expected results, and the negative-case share — plus the totals
of the whole view and the thresholds as advisory signals.

## The answer

- **Items** are the (line, module) groups of the view: id = `<line>/<module>` (`unplaced` for a null line or module),
  label = the pair, summary at most 200 characters (`用例 20 个；无期望结果 1 个（5.0%）；含糊期望 1 个（5.0%）；负面用例 1 个（5.0%）`).
- **board** (per item): always support, the metrics as claim data — counts and the ratios as exact fractions `{num, den}`,
  plus numbers rounded (4 decimal places) for display only. Nothing is rounded before the final ratio.
- **thresholds** (per item, advisory): a refutation with `quality-board.missing_expected`, `quality-board.vague_expected` or
  `quality-board.negative_share` when the group's share exceeds its maximum or falls below its minimum; equal to the
  threshold is not a violation. Defaults 0.05, 0.05, 0.02; the parameters move them.
- **totals** (run level): the totals over the whole view as a fact, and the note that the board describes the indexed
  cases, not the whole suite — every case of an indexed document has an entry (a case without command ownership is counted, whether or not it has a tree position), and only sources not read stay outside. When the view states skipped sources, the note names
  the count; when the view is truncated, the totals cover the listed part and say so.

## Decisions

- **The metric definitions are the ones of the owner's real-sample measurement**, quoted in the task page: a case without an
  expected result has `has_expected` false; a case with only vague expected results has `has_expected` true and
  `vague_expected` true; the negative share is `negative` true over all cases. No others are invented.
- **Unplaced cases (1.1.0)**: `placement` is mandatory and reads `by=commands`, on the same product and root as
  the count view. Only the `commands: null` row is counted, once; non-null command rows can repeat a case and are not
  summed. The count is disclosed in totals (`未归位（没有命令归属的用例） N 个`), without a threshold or a new requirement.
  An absent null row in a complete view means zero. If the view is truncated and has no null row, projection refuses:
  the missing fact is the unplaced count; the fix asks for a complete same-root view and identifies the current
  knowledge interface's inability to page/filter facets. It does not finish as an unknown result.
- **Test types (1.1.0)**: the optional second `facets` view is exactly `by=line,module,tags`; it must share product, root
  and total with the count view. Two count views or another combination refuse. Tags are kept out of the count view:
  list-valued fields repeat rows per value. `tag-table.ts` copies the six types and aliases declared by template-gap;
  `tag-table-consistency.test.ts` requires exact types, labels and aliases on both sides, and `coverage.test.ts` compares normalization with that pack on thousands of spellings. Per group the board states the
  types observed, the types with no observed tag and the exact empty-tag count, never a per-type case count. Unknown
  labels are tagged cases, not untagged ones. Several spellings on one case prove presence once.
  Truncation or skipped sources qualify absence as “在已读的来源里没看到” and “部分”; a missing null-tag row in a truncated
  view gives no invented zero. The claim names the follow-up action and SKILL requires the caller to perform it.
  The other 18 template categories need title/path/steps/expected text absent from this view; only template-gap reads them.
- **The violation codes live in the pack namespace.** The task page names `quality.missing_expected` etc.; the Hub requires a
  pack function's codes under `<pack>.` (hub/rules/check.ts), so they are `quality-board.missing_expected`,
  `quality-board.vague_expected`, `quality-board.negative_share`.
- **Integrity refutations**: the publish check needs a negative sample per check (T02 R[0]), and the checks guard the frozen
  subject rather than trust it: `counts_inconsistent` (a group's counts contradict the definitions, e.g. more missing than
  cases), `total_undercount` (an untruncated view's rows hold fewer cases than its stated total — a contradiction of the
  view), `multi_valued` (more — some entry carried a list in a by field and was counted twice). The pack's own projection
  never produces them; a view built by something else is checked the same way.
- **Null groups**: a null module is the group `unplaced`; a null line is too (`unplaced/SSL`, `unplaced/unplaced`). Two pairs
  whose ids collide (a `/` inside a value) refuse the run (`ambiguous_group`), never silently merge.
- **No product binding** (since 1.0.1): the input's external id already names product and build; binding a line made the
  engine lock an unrelated build (the newest released one of the line) into the run record. Like regression-scope, the
  workflow binds nothing (`product: { "catalogs": [] }`).
- The thresholds compare the exact fraction against the parameter as numbers; the boundary tests pin that equal is not a
  violation.
- **No `api.ts`**: a pack is loaded by the engine from the registry and offers nothing to other packages (same as
  case-location; architecture section 10's file rule is met by this README and the declarations).

## How to test

```
node --test --test-concurrency=1 "packs/workflow/quality-board/**/*.test.ts"
```

- `functions/board.test.ts`: hand-built facet views (known counts, a null module, a null line, rows that split a group by
  the other fields summed, the display rounding), and an independent plain-loop computation over a random corpus of 100,000
  synthetic cases compared with the pack's groups; order independence.
- `functions/thresholds.test.ts`: the boundaries (equal is not a violation, one case more is), several violations of one
  group, the parameters, the defaults.
- `functions/totals.test.ts`: the totals, the caveat text, skipped sources named, and both integrity refutations.
- `functions/views.test.ts`, `project.test.ts`: the view reading and the projection (items, groups, refusals, budgets).
- `functions/sandbox.test.ts` (needs macOS `sandbox-exec`): every entry point gives the same output inside the Hub sandbox.
- `pack.test.ts`: the manifest and declarations; the publish check offline.
- `publish.test.ts` (temporary PostgreSQL): the real registry publishes the staged pack (6 samples pass, both polarities per
  check) and refuses a wrong or missing sample.
- `production.test.ts` (temporary PostgreSQL): a production run end to end with a fake knowledge reader — the groups, the
  summaries, the advisory violations, the totals, the parameters, and the pack kept from users it is not assigned to.

## Limits

- The board reads the case index as it is: skipped sources and a truncated view bound what it can say, and the totals say
  so; nothing is extrapolated.
- Budgets: at most 8,000 groups and about 5 MiB of projection output per run (far beyond a real product's
  (line, module) count); beyond that the run is refused with a fix.
- The end-to-end test on the REAL knowledge reader comes after the case index (the product pack's `cases` producer) lands;
  see below.

## Open questions for the owner

- No unresolved product decision. The knowledge summary capability remains a cross-package dependency, recorded above.

Since 1.0.2, group summaries disclose the exact metric counts alongside percentages. Synthetic samples are regenerated from the same frozen counts.

1.1.0 validation: synthetic fixtures only, a 100,000-case independent comparison and order reversal, sandbox checks,
registry publication and a temporary PostgreSQL production run with a fake knowledge reader. These checks do not prove
results on real business inputs; the integrator runs the real scans and acceptance after publication.

Privacy update (integrator, 2026-10-23): acceptance group names use ordinals only. The scan prints build ordinals, never hashes of names. The board prints a digest of metric counts only, excluding line and module labels. Private `--out` files retain correspondence.

Gold closure A: --case-commands validates the consumed measurement fields, document coverage and per-document counts against
its case rows before counting paths. A listed document with zero case rows is an observed zero, not a missing export;
contradictory metadata and malformed paths are refused with a fixed rerun instruction. No Hub/pack runtime is imported.

Gold closure B: --placement only asks the scenario to bind placement and require the Hub count sentence; it omits
unplaced unless --case-commands provided an independent measurement. An observed zero remains a strict comparison,
while a count that was not measured is never invented as zero. Missing Hub output still fails the check.

Independent id policy: the gold extractors follow the FAMX README, preserving zero padding in output spellings and raw
source titles, using normalized nonzero keys only for classification/joins, and rejecting zero-only or out-of-bound digit
runs. Bare ids use the FAMX 4–7 written-digit range. Dates/versions are excluded before joining. This supersedes the old
location-gold exception that rejected every leading zero. The separate gold-location branch is aligned by its owner.

Gold closure C: board location independently follows the public FAMX module rule: labels are truncated to 1000 before
normalization, but a resulting module name is at most 40 characters and cannot contain four consecutive digits.
Version and activity labels, and marked identifiers, remain excluded. The 40/41 boundary, prefixed labels and numeric
control examples are covered without importing the product implementation into the gold.

## Count terminology (1.1.2)

The board keeps its `commands: null` business rule: “未归位（没有命令归属的用例）”
counts cases without command ownership. Knowledge root reports and view summaries instead use
“未挂到树上位置的条目” for content without a tree position. These are different properties
and need not be equal: a case mounted on a tree node can still have no command ownership.
Neither rule, thresholds nor null-group handling changes. Both labels come from the model's
`knowledge_count` axis through generated `functions/generated/vocabulary.ts`; the generator
registers this pack and `--check` locks that snapshot. For example, the same synthetic view
has five distinct case contents, two with a tree position and three without, while four lack
command ownership. The board still reports four.

标签按 resource-tags@1 的精确原文闭集读取，保留 resource 原值。闭集外是提示档结构违规“未声明的标签”；大小写、全半角与同义词不相等。非法声明不进入正反向比例分母。此版本替代旧关键词规则，历史结果不改写；应以新包重产新根与新运行。本次续接按所有者指令未运行验证。

R3：含糊期望不再由词表或生产器布尔决定。case-review 逐用例提交全部期望叶子的逐字引文及判断，由 Hub 核验身份、路径和引文；不可读原件保持未知并补读。quality-board 仅接 Hub 绑定的同根、同原件、已受理且有效的 case-review 记录；重复回执去重，同原件相互冲突的判断单计冲突并留在未判断中，不挑最后一句。含糊率分母仅为已判断数；零分母显示未判断并补评审，不能显示 0% 或判阈值通过。资源类型比例另按精确声明分母计算。旧结果不改写，新版本须重产新根和评审后再开看板。本次续接未运行验证。
