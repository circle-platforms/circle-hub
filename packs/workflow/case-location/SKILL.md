# 用例定位

Hub 按目录树直接算出每份测试脑图（或每个用例）在哪里：产品线、版本、版本线、发布火车、模块、目录和标题里写出的构建名，以及关联的需求和缺陷。不需要你提交结果。

1. 开始运行：pack 写 case-location；inputs.documents 写要定位的脑图，例如 `[{"external": "agile:mindmap:<文档编号>"}]`。产品线已由任务包绑定，start_run 不用写 product。要对照某个构建时，build 和 version 写在 start_run 顶层，与 pack、inputs 并列，不写进 parameters。一次最多约 40 份（按用例定位时一份）；回答放不下全部条目时，末尾的说明写明略去了哪些条目、用 get_nodes 怎么读（调用和翻页方式），照它读完再转述。
2. 结果在开始运行时就算好了：每个条目的摘要就是它的定位结论，完整结论在 result.reference 指向的校验结果里，用 get_nodes 读取。运行的“版本依据”是锁定的知识根，不是文档所在的版本。
3. 原样转述每个条目的结论和置信度，不补全、不猜测：版本的来源（目录、标题、参数）和置信度（高、低）照写；标“参考”的构建日期和 patch 只是参考；“目录版本层自相矛盾”是确定的冲突（提示档），保留每个版本和目录原文，转述整理目录或用 line 声明的下一步；优先报告版本层冲突，说明声明与哪些值一致。“不确定”的条目照说明转述缺的事实和下一步；“与声明矛盾”的条目以目录树给出的结论为准，并说明哪个声明与目录树矛盾。目录是敏捷平台读取时列出的，不是引用的片段。
4. 构建候选（要求项 build_candidates）：定位到的版本线在知识库里两个名称族的已知构建，按制作时间从新到旧（包括只有名字、还没有知识根的构建；制作时间相同的按名字，页上没有制作时间的排最后并写“制作时间未知”）；结论的文字逐个写出候选（构建名（名称族）、制作于 年-月-日 时:分，别名写“基于 <基础构建>”，发布状态另写“已发布 <日期>”或“未发布”），最多写前 12 个，更多的写“另有 N 个”。目录和标题里“写出的构建名”逐个核对过：是候选（或是候选别名的基础）记支持；属于另一条线记不通过（提示档，写明属于哪条线）；构建站没有列出的构建名记不通过（提示档 build_not_listed，写明“不认识不等于写错”，是确定的结论不是未知）——知识库只收录构建站列出的构建。定位没给出版本线、或这条线没有已知构建时，候选记未知（缺输入），不是出错，更不是没有构建的结论。目录版本层冲突时先说冲突，再分别列出每条线的候选。候选是运行开始那一刻知识库的状态。
5. 编号：“bug to case”及其既有错拼后的编号按缺陷号读，紧挨编号的类型词优先；PLM 仍未分类。按原文位数核对长度（带标记 2 到 9 位、不带标记 5 到 7 位），全零串不是编号；非零编号的身份去前导零，原文拼写保留，显示和引文用原文。需求、缺陷是标题或目录里有词标明类型的；“未分类编号”没有标明类型、声明的范围也分不出时，需求与缺陷两种都读，存在的那一个决定种类（结论的警告里写明）。可选参数 id_ranges 给出需求和缺陷的编号范围，按范围分出的类型是声明，结论里单独标“声明的范围”。关联编号在结论里按类别（需求、缺陷、未分类编号）分组**全部列出**，总数超过 20 个时只列前 20 个并写“另有 N 个”——原样转述，不要自己再截断。
6. 可选参数：line 和 product 是替调用方声明的版本线和产品，只补目录树没给的部分，结论标为声明；granularity 写 case 时每个用例一个条目（用例节点带标签或带用例优先级 2 的标记，决定 18）。
7. submit_result 不是必需的；要补充看法时可以提交，看法记为模型转述的判断，不改变 Hub 算出的结论。

第一步仅绑定 PLM 期望来源，不声称 PLM 里有或没有该编号；核验等待 hub-read-absence 后的第二步。

喂入层：这个包读到的用例、缺陷、构建、规格凡经 Hub 读的都由程序自动进喂入层（带锁定树苗和冻结序号），视图按"锁定树苗 + 冻结序号之前的喂入层"读；版本未声明和矛盾的对象单列计数，不进版本差。Circle 只经 knowledge-contribution 回注补程序填不了的语义（带逐字引文），运行中不问人；结构契约见该包 tables/knowledge-structure.json 或 get_nodes 根路径。
