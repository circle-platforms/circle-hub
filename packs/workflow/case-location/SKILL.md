# 用例定位

Hub 按目录树直接算出每份测试脑图（或每个用例）在哪里：产品线、版本、版本线、发布火车、模块、目录和标题里写出的构建名，以及关联的需求和缺陷。不需要你提交结果。

1. 开始运行：pack 写 case-location；inputs.documents 写要定位的脑图，例如 `[{"external": "agile:mindmap:<文档编号>"}]`。运行自动绑定这个任务包的产品线，不用写 product。一次最多约 40 份（按用例定位时一份）；回答放不下全部条目时，末尾的说明写明略去了哪些条目、用 get_nodes 怎么读（调用和翻页方式），照它读完再转述。
2. 结果在开始运行时就算好了：每个条目的摘要就是它的定位结论，完整结论在 result.reference 指向的校验结果里，用 get_nodes 读取。运行的“版本依据”是锁定的知识根，不是文档所在的版本。
3. 原样转述每个条目的结论和置信度，不补全、不猜测：版本的来源（目录、标题、参数）和置信度（高、低）照写；标“参考”的构建日期和 patch 只是参考；“不确定”的条目照说明转述缺什么（目录自相矛盾、版本只是目录名里提到的、只在标题里等）；“与声明矛盾”的条目以目录树给出的结论为准，并说明哪个声明与目录树矛盾。目录是敏捷平台读取时列出的，不是引用的片段。
4. 构建候选（要求项 build_candidates）这一版记“未核对”：Hub 还没有把知识库里版本线的构建交给检查。“写出的构建名”是目录和标题里原样写的名字，没有核对，也没有解析别名，不要当成构建候选或推出别的构建名。
5. 编号：需求、缺陷是标题或目录里有词标明类型的；“未分类编号”没有标明类型，不读取缺陷系统。可选参数 id_ranges 给出需求和缺陷的编号范围，按范围分出的类型是声明，结论里单独标“声明的范围”。
6. 可选参数：line 和 product 是替调用方声明的版本线和产品，只补目录树没给的部分，结论标为声明；granularity 写 case 时每个用例一个条目。
7. submit_result 不是必需的；要补充看法时可以提交，看法记为模型转述的判断，不改变 Hub 算出的结论。
