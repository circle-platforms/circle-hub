# 给自动化测试环境装构建

复现缺陷要在缺陷发现的构建上跑：在别的构建上没复现，不说明缺陷已经没有了。用例要在某个构建上跑、而自动化测试环境装的是别的构建时（例如缺陷发现于另一个构建），照测试框架的升级用例给整台环境装上那个构建，再复现；这是复现的一步，不用问用户要不要装，也不要让用户提供镜像名。每台负载均衡设备一个升级用例（用例号来自管理员发布的装构建档案）：设备已是目标构建就跳过；否则自动化测试环境的文件服务器上缺镜像时先从构建库下载，再更新设备、等它重启，最后用 show version 核对。装构建要整台独占，会让设备重启，只在需要的时候装。

1. 先用 test-bed 整台预订这个环境（action acquire，need.devices 按清单写全）。记下预订运行号，以及预订回答里“预订时在设备上看到的构建”：这是设备现在装的构建。
2. 定要装的构建（缺陷原件里 show version 写的那个），再到构建站上找它的镜像文件名：用 source-read 的 build_page 读入口页 `{"external":"buildsite:listing:index"}`，它列出各版本线的导航页；读这个构建所在版本线的导航页，它列出各平台的列表页；读列有这个构建的列表页（页面名照导航页上的链接写），在这个构建的条目里取镜像链接的文件名，形如 `<前缀>-<构建名>.<扩展名>`。镜像名按升级用例的读法（第一个 `-` 之后到最后一个 `.` 之前，`_` 读作 `.`）必须正是这个构建，扩展名必须是装构建档案里升级用例认的，否则 Hub 拒收并写明认哪些扩展名。
3. 在工作目录写 `install.json`：`{"schema":"bed-install@1","build":"<构建名>","image":"<镜像文件名>"}`，用 upload_file 上传。同一份请求（同样的字节）Hub 只派发一次：上一次装没成要再装时，请求里加 `"attempt": <第几次>`（从 2 起），另存一份上传，再开新运行。
4. start_run：pack 写本包，predecessor 写预订运行号，product 和 build 写设备现在装的构建（第 1 步看到的那个；派发前 Hub 在每台设备上再核对一次），parameters.bed 写环境名，inputs.inventory 写 `{"external":"doc:doc:bed-topology"}`，inputs.profile 写 `{"external":"doc:doc:bed-install-profile"}`，inputs.request 写上传得到的引用。条目是每台负载均衡设备的升级用例。Hub 说没有装构建档案或档案不完整时，把它的原话（缺什么、请管理员用哪条命令发布）转给用户，不要自己编升级用例号或扩展名。
5. submit_result：每个条目交 reason，data.build 写和 install.json 一样的构建，grounds 引用依据（缺陷原件里写的发现构建，或用户原话）。
6. 受理后 Hub 自己派发作业，不用再做别的。逐字原样重交同一份提交读进展；作业结束后读结果引用：每个升级用例的 pass/fail。没过的读它的日志和设备会话归因：日志或回显点名的步骤（放镜像、更新、重启、核对版本）、文件或报错照实写明；说明不了的推断（时序、等待）是判断，写明预测。说得出这次和上次哪里不同（请求改了，或要验证那条预测）才带 attempt 再装，不符就换假设；说不出就把失败连同证据交用户决定，不原样重装。装完以后，在新构建上编译和派发用例时，开运行写新构建。
7. 要装回原来的构建，照同样的步骤再装一次，build 和镜像写原来的构建，product 和 build 写设备现在装的构建。
8. 装构建是复现的一步：接着在同一个预订下编译和派发用例（case-compile 第 1 步沿用它，做完由它释放）。不接着跑用例时，作业都有终态后用 test-bed release 释放第 1 步的预订（booking 与 predecessor 写预订运行号）。

不证明构建库里有这个镜像，也不证明设备装得上：以作业结果为准。结论原样转述，保留“未排除本地操作”。
