# packs/workflow/case-compile

The compile half of test automation, phase A (task page `docs/hub-r4-tasks/case-compile.md`, design
`docs/hub-r4-compile-design.md`): the model compiles each reviewed case into an execution plan inside a restricted
structure (model W05 — bucket, blocks, operators and expected sources are finite sets), and the Hub re-runs every
check at the boundary: (object, method) against the contract, literal addresses against the bed, commands and
parameters against the build's command catalog, an explicit verbatim source on every expected result, and determinism
(the plan is re-generated from the submitted slots and compared byte for byte). Everything runs on a synthetic
contract and a synthetic bed; every conclusion says 按合成合约核对 (when the contract declares `synthetic: true`) and
不证明在真实设备上跑得通, never "可以运行".

## The restricted structure and the deterministic plan

Per case the model submits one `plan` claim with the slots only: `bucket` (a bed of the inventory), `blocks`
(`setup`/`teardown` only), `steps` of `(object, method, params)` — only what the contract declares, forbidden pairs
never, parameters by the contract's arity and types; contract parameters marked `command: true` carry command lines
(checked against the locked build's `commands@1` by the catalog@1 interpreter), parameters marked
`address: listen|backend|target|virtual` carry literal addresses (checked against the bed facts and the lineage
leases) — and `expects`, each with a verbatim `quote`. The execution plan itself is never written by the model
(P05): the pack's deterministic generator produces the canonical exec-plan@1 text from the slots
(`functions/plan.ts`), a second reader parses it back and compares it with the slots item by item, and only a
consistent re-read supports — the support names the plan's sha256 and carries the plan text in `data`. A generation
or re-read failure is unknown with reason `output_failed`, never charged to the model. A core-level generation step
and artifact storage for produced plans is the follow-up, not this pack's path (see Needs); the workbook format and
the execution entry stay owner-provided (design section 1), so only the JSON form exists for now.

## Decisions

1. **The contract shape is the pack's** (task page A.2): compile-contract@1 — objects and their methods with typed
   parameters (arity, ranges, enum values, keywords, address roles, command flags), forbidden (object, method) pairs,
   and the `synthetic` declaration. The sample contract in `examples/` is invented, names and values copied from no
   old system. When the owner's real contract does not fit this shape, the pack's validation function is what changes.
2. **Bed facts are this pack's own copy — with one intentional difference.** Pack functions may load only modules
   inside the pack, so the manifest parser and the bed-facts rules of `packs/workflow/test-bed` cannot be imported —
   `functions/manifest.ts` and `functions/bed.ts` re-implement the same shape and rules (the inventory document itself
   is shared, unchanged; the drift watch in `functions/bed.test.ts` pins the same listener/blind/backend outcomes as
   the test-bed fixtures). The one deliberate difference is the backend rule: bed-facts' backend candidates include the
   declared services, but the compile rule (design section 2: 后端地址必须是服务器设备的地址) accepts only the
   interface addresses of `type=server` devices — `isServerInterface` in `functions/bed.ts`, with a sample
   (`backend-not-server.json`) where a declared service on a client host is refused. A cross-pack facts library is a
   core gap, reported in Needs.
3. **Checks recompute from raw documents.** The projection freezes the raw contract and manifest into the run group;
   the checks re-parse them there (a parsed manifest holds bigints and could never serialize into samples).
4. **Conclusions are facts or unknowns, never "可以运行".** Every statement of this pack's function checks closes with
   the two markers: 按合成合约核对 when the contract is synthetic, and 不证明在真实设备上跑得通 always. An unreadable
   slot shape is unknown (the shape refute belongs to `contract_shape`), not a failure of another check. The catalog@1
   and quote@1 interpreter outcomes are generated by the core and cannot carry pack text; the two markers reach the
   answer through the projection's run note and every function claim, and the model relays both sentences per SKILL.md
   step 1. Marking the interpreter outcomes themselves would take a core change, which this pack may not touch.
5. **"分配到的地址" is the run's lineage leases**: an address with a live `bed/<bed>/ip/<address>` lease marked `mine`
   in the frozen lease view resolves as allocated (`workflow.json` declares `context: ["leases"]`); everything else
   that is not a device interface address is off the bed and refused.
6. **Delivered is not passed; a violating plan is unsatisfied, repaired, then incomplete (V05, V06).** This is a
   bookkeeping run: `delivered` only says an item reached a terminal state. Every model-fixable refute code (all of
   this pack's own codes, the `core.catalog.*` the catalog@1 interpreter actually gives, and the boundary's
   `QUOTE_MISMATCH`/`REFERENCE_UNRESOLVED`) carries a repair row in `requirements.json` (action repair, at most 2
   rounds per fact requirement): while rounds remain, the item stays in delivered with the requirement **unsatisfied**
   and the receipt's error list names the place (pointer) and the rounds left; a fixed resubmission turns it
   satisfied; with the rounds used up the item is recorded incomplete (`repair_exhausted`) and leaves delivered.
   Compliance is read from requirement satisfaction, never from the partition. Unknowns (`output_failed`, an
   unreadable contract or manifest, an unproven catalog) are not model faults and count no repair round. A gate run
   that hands an execution only plans whose required requirements are all satisfied is the follow-up (design section
   3, E5), not this pack.

## Pointers

Every refute and unknown of this pack's function checks carries a `pointer` at the judged content, in one shape:
`/data/bucket`, `/data/blocks/<i>`, `/data/steps/<i>`, `/data/steps/<i>/params/<name>`, `/data/expects/<i>`,
`/data/plan_json` (a plan written into the slots), and `/data` (shape problems keep their own pointer behind it, and
generation or re-read failures point at the whole slots). The core interpreters write their own (pinned by
`production.test.ts`): catalog@1 gives `/phrases/<k>` — k in step order, and per step in the contract's declaration
order of the command parameters, values trimmed non-empty, a missing value read from its `default`; quote@1 gives
`/quotes/<k>/text` — k in expects order, only entries whose reference and text are both non-empty.

## Limits

- At most 10 problems per item per check; shape problems of the slots are reported by `contract_shape` alone.
- The plan slot holds one claim per case; the plan itself (`exec-plan@1` text) is generated by the pack and travels in
  the deterministic check's `data.plan` with its sha256.
- Literal addresses are bed-checked only where the contract gives the parameter an `address` role. An address inside a
  command line is checked by the command catalog for its type only (the command tree has no per-parameter role such as
  target segment or mask), never against the bed — the gap against design section 2's 每个字面地址, recorded in Needs.
- Expected sources are verbatim quotes resolvable at the Hub boundary (src:/rec:/tree:). A defect fix note or a manual
  page that should ground expectations must be readable as a reference — publish it as a named document and cite its
  rec: reference; there is no extra input slot for evidence documents in phase A.
- The run's product line and build are locked at start_run among the lines declaring `commands@1`; the command check
  reads the locked catalog only.

## Needs from other packages

- **Core / pack infrastructure: cross-pack reuse of bed facts.** Today a pack function may not import another pack's
  modules, so the manifest parser and bed-facts rules are copied here from `packs/workflow/test-bed` with a drift
  watch in tests. A core-level shared facts library (or pack-versioned library imports) would remove the copy. Reported
  to the integrator with the task result.
- **Command-line addresses get no bed check.** Design section 2 says 每个字面地址 resolves against the bed; only the
  contract's address-role parameters are covered, because the command tree gives no per-parameter role (a target
  segment or a mask is not a bed address by shape). A catalog-entry@1 address role per parameter, or a contract side
  table mapping command parameters to address roles, is the follow-up — this pack is its first consumer.
- **Core: a generation step and artifact storage for produced plans.** P05's deterministic generator currently runs
  inside the pack's deterministic check (generate from slots, re-read, compare); the produced exec-plan@1 text travels
  only in the support claim's `data` with its sha256. A core generation step that stores produced artifacts as
  originals (every exact value resolvable to a reference) is the follow-up; this pack is its first consumer.
- **Owner: the real compile contract** (compile-contract@1 published via `circle-hub doc put`, e.g. as
  `doc:compile-contract`), the workbook format and the execution entry (design section 1). Until then every conclusion
  stays marked synthetic.
- **Owner: evidence binding for expected sources beyond the case document** — if a check should cite defect fix notes
  or manuals as first-class inputs, an `evidence` input slot (`doc:doc`, many) is the follow-up; phase A cites rec:
  references of named documents instead.

## How to test

```
node --test --test-concurrency=3 "packs/workflow/case-compile/**/*.test.ts"
npx tsc --noEmit
node packs/workflow/case-compile/pack-files.ts --check
```

The function tests cover the contract (positive and each negative), the address rules, the expected sources, the
deterministic generator (byte-identical twice), the extraction and the projection refusals. `publish.test.ts` publishes
through the real registry (temporary PostgreSQL; skipped where `sandbox-exec` is absent — a skip is not a pass).
`production.test.ts` runs start_run + submit_result against the real engine with fake externals.

## 2.0 migration decisions

The runner contract is read in its original format. Its complete original JSON participates in the sorted compact UTF-8 identity, except `contract_sha256` itself; defaults are never expanded into plans. Non-integer or unsafe JavaScript numbers and non-BMP keys refuse the whole input because their original identity cannot be proved here. Closed external-format values live in `tables/runtime-contract-format.json`. Only enabled, non-internal, non-candidate entries enter the callable set. The runtime version and identity must also match the published runtime profile. Synthetic contract tests establish parser behavior, not runner or device compatibility.

`runtime-profile@1` is defined by this pack: `runtime` carries the expected version and contract digest; `bed` selects one manifest bed; `workbook` carries nine headers, sheet/identity/range literals, a nine-cell closing row and an anchored autoid pattern. `seats` maps runner objects to manifest DUTs and nonnegative gateway ordinals; `hosts` maps enabled methods to test hosts. `allowed[].parameters` assigns roles from the profile format table. Unknown roles, unenabled combinations, credential parameters and unavailable seats refuse the whole profile with all pointers. Natural-language registry and three-argument checkpoint dispatches remain closed this round. `denied.device` and `denied.host` are deployment command rejection lists. The profile's `synthetic` declaration selects the conclusion marker; it does not change enforcement.

The compile workflow binds a required `profile` expected source and declares the `bed/` lease prefix. The frozen lease context can therefore include addresses held by its reservation predecessor. Manifest parsing retains its independent implementation and drift tests against test-bed: bed-name syntax, required services/reserved lists, numeric service address comparison, duplicate ownership and range containment. `autoid` is a required string parameter; the next projection migration selects exactly one case by the unchanged text.

Case items retain `autoid`, `auto` and `priority` as text, including long identifiers above JavaScript's safe integer range. The workflow selects exactly one authored autoid and refuses absent, malformed or duplicate selections with a repair action. Both the child-operation layout and a case body with one leaf expectation are preserved; the latter is one authored operation, not generated steps. Unsafe numeric identifiers are not reconstructed from rounded values: the author must supply the original textual identifier.

The 2.0 restricted structure has `steps: [{object, method, args, keywords}]`, `expects: [{text, quote, after}]` with one-based step numbers, `replacements: [{case, bed}]`, a manifest bed `bucket`, and empty `blocks`. Argument values are explicit text; no Python defaults or extra fields are inserted. `slots.schema.json` publishes the full nested shapes for engine repair messages. The integrator confirmed removal of the old Hub-side exec-plan generator and `plan_deterministic` requirement; task 2 owns client workbook generation and independent Hub rereading.

Plan slots contain final execution text (integrator-confirmed): replacements explain original-case addresses → bed addresses. Hub recomputes only the quoted-text transformation for verification, never rewrites steps. Every literal address in args, keywords and final expected text is examined, including invalid extra arguments. Device CLI values permit the mapped seat's own interfaces, lineage allocations and server interfaces; other device addresses are rejected. Each expectation judges a device CLI or host shell step, never a wait/assertion step. Original quotes remain unchanged for quote@1. The 1.x listen/backend parameter roles and default expansion are removed because the original runner contract carries neither.

The 2.0 samples replace the retired 1.x contract/plan samples and provide independent positive/negative inputs for every requested plan rule. Model-repairable rejection codes have repair rows with two rounds. `testing/samples.ts` deterministically rewrites only this package's synthetic author samples. The vocabulary scan currently reports eight existing matches in six files outside this package; there are no case-compile matches and no exception or baseline was added.
