# 收尾：返工、最后一次整卷上机与交付目录

第一次整卷上机有了逐条结论以后，照这里一直做到交付目录写好，中途不停下来让用户选方向。交付目录照 InfoTest 的规矩：通过卷要整卷上机、逐条通过才算交付；没通过的用例单独成卷；每条没交付的用例写清发生了什么、怎么判断的、怎么修或怎么取舍。

1. **返工。** 每次派发后把这次上机的设备返回原文下到工作目录（令牌照第 5 步的 here-doc 写法）：`node <技能目录>/tools/download-returns.ts --hub %HUB_URL% --run <核验运行> --out <新目录> --wait 3600`，作为后台命令启动。等待由它做：它每 20 秒读一次 Hub 的作业清单，作业结束才写文件、退出，最后一行打印各结论条数（verdicts），客户端在它退出时通知你；这期间不 sleep、不重交提交读进展，可以先做不依赖结果的事。到时限作业还没结束它什么都不写，用同一命令再等一次。作业已经结束时不写 --wait 也可以。它写出设备返回全文、每条用例的运行日志和没通过的用例的各设备会话，每份都核对过摘要，index.json 列出每条的结论和文件。运行器报通过、但它的运行日志里有合约声明的执行失败原话、而本条断言没读那一行的，工具照 InfoTest 当场改记无判定（verdict 是 no_verdict，runner_verdict 是 pass，pass_review 写出是哪一行）：这样的通过不算数，和没通过的用例一样返工、算一轮，让它的断言读到这一行，或换一种不会执行失败的观察。没通过的用例在 index.json 里还有 syntax_rejected：设备在回显下一行只回一个 `^` 的命令（command），`^` 指着的那个词（token）和下发时的提示符（prompt）。照 InfoTest，这是唯一由程序先判的失败原因：设备不认这条命令在那个提示符下的写法，命令没被接受，先修它，同一条用例后面的失败多半是它带出来的；它说的是命令的写法或下发方式，不说明环境缺什么。同一处还有 execution_refused：设备对一条命令回了运行器合约声明的执行失败原话的，列出这条命令（command；回显被终端折行的只有开头，echo_cut 为 true，整条在运行日志里）、下发时的提示符（prompt）和设备在这句之前给的原因行（reply）。照 InfoTest，上一轮有执行失败的行，问题在这条用例自己的命令序列，不在环境：按原因行改这条命令；原因行说取值或格式不对的，对照简报里手册对该参数的说明；原因行点名别的对象不存在的，先看建它的那条命令是不是也在这份清单里。运行日志或会话显示某台设备的会话中途断开（这台设备后面的命令都超时、运行器报会话已关闭）时，这台设备的清理没有发出：在说明的 batch 里写明是哪台设备、哪些清理没有发出；照 InfoTest 的床态体检，残留没核清之前不派发下一卷，向用户说明。按第 9 步的顺序读完这些文件再归因：先在该用例的运行日志和设备会话里逐字找出说明失败的那段设备原话，归因只以这段原话为依据，不凭推测补全；原话点名的命令或配置，先在锁定命令树和手册里读到再改计划。再次没通过的用例先确认上一轮的修改进了这一卷；进了而同一句失败原话又出现，那个方向就错了，换方向，不重复同一种改法（照 InfoTest）。返工保住作者的范围和每一项期望（照 InfoTest：修用例不缩小范围）：断言写不出来时换写法，不把这项检查去掉或改弱来换通过。只改没通过的用例（失败的和被改记无判定的），已通过用例的计划逐字不变；沿用预订，整卷重跑（新的计划运行、生成、核验、派发）。定下结论照 InfoTest 的规则：每条用例最多编写 3 轮（第一次上机算第 1 轮，同一份计划重跑不算新的一轮），3 轮都没通过的（通过被改记无判定的那一轮也算没通过），结论定为“模型未找到解决方案”。不到 3 轮不定结论：环境缺数据、缺拓扑、缺前置这类判断不是依据，照用例原样继续编写；“未定”就在被测命令前加只读观察再上机；只有核对得上的产品缺陷候选（第 3 步的 defect_candidate）可以提前定下结论。没上机的用例同样不凭说明定结论：它自己的计划交上去后 Hub 判缺原合约事实（记下数据缺口并点名补证请求）的，记为缺少 Hub 点名的事实；修正轮次用完仍没有受理的，照 InfoTest 记为模型未找到解决方案（要的是它交过编写出来的计划、修正轮数真的用完；把它声明成跳过的不算编写过，不论轮数剩不剩，照用例原样编写）；其余照用例原样编写、交卷，和其他用例一起整卷上机。工具照这些规则核对，不到 3 轮又没有缺陷候选的、没上机又没有这两种 Hub 记录的，都拒组交付。
2. **组通过卷并做最后一次整卷上机。** 所有最近一次上机通过的用例要放在同一卷里一起上机、逐条通过才交付，只重跑其中几条不算。最后一次整卷上机已经装着全部最近通过的用例并全部通过，那份工作簿就是通过卷，直接做第 3 步。否则开新的计划运行：parameters.exclude 写上没通过的和没编出来的用例，原样重交所有最近一次上机通过的用例的计划（用同一个计划目录交即可：submit-plans 会跳过本运行排除的条目并报出来，不用复制或改写文件），再生成、核验、派发；这一次上机就是最后一次整卷上机。它里面又有失败的，把它们也排除，再整卷上机一次；最多这样上机两次，还不过就停下，照实交付。最后一次上机一条都没通过时，没有通过卷。
3. **写说明文件（JSON）。** 每条没交付的用例写一项，交付的用例不写：
   `{"cases":{"<autoid>":{"judged":"…","remedy":"…","evidence":"…"}},"batch":"…"}`
   - evidence 上过机的用例必填：从第 1 步下载的、它最后一次上机的运行日志或设备会话文件里逐字复制说明失败的那一段，不改写、不拼接；工具逐字核对，对不上就拒组交付。
   - judged 写怎么判断的：以 evidence 那段原话为依据，加手册出处或缺的事实，分清计划、环境、产品还是未定。
   - remedy 写修复方案（陈述句，下一步改什么、谁来做），或者写取舍（继续加轮还是挂起，默认继续）。判产品缺陷要满足第 9 步的条件，说不清就写“未定”。设备拒绝执行的正是作者步骤原样要求的命令时，先读手册对那个参数的说明：说明支持作者的取值才是声明与设备行为冲突；说明不支持的，是作者步骤与手册冲突，judged 里逐字写出手册那一句和它的引用，不写 defect_candidate。
   - defect_candidate 只在判产品缺陷时写：`{"repro":"复现步骤","expected":"…","actual":"…"}`，expected 从这条用例的作者期望原文逐字复制，actual 从它最后一次上机的设备返回逐字复制；工具逐字核对，报告里写成“声明与设备行为冲突（待仲裁）”，只是待仲裁的候选。最后一次上机里有设备用 `^` 拒绝的命令（syntax_rejected 不空）的用例不能写：命令没被设备接受，作者的场景没有在设备上实现，够不上声明与设备行为冲突，工具会拒绝。
   - batch 写整批要披露的事：用户在第一条消息之后发来的每条消息（例如“继续”）都是人工介入，照实写出次数和起因；服务限流、改用的环境也写。没有核对过的事不写，不写“无人工介入”这类断言。
4. **组交付目录。** 令牌照第 5 步的 here-doc 写法：
   `node <技能目录>/tools/assemble-delivery.ts --hub %HUB_URL% --runs <核验运行>,<核验运行> --recompose <重组运行> --notes <说明.json> --out <新目录>`
   --runs 至少写最后一次整卷上机的核验运行；工具从 Hub 的运行血缘（预订下绑定同一份重组的计划运行及其核验运行）找全这份脑图的每一次上机，按开始时间排列，补上的在打印结果的 added_runs 里。同一份重组下的上机都算进同一批交付，另起一批要重新重组。通过卷是最后一次整卷全部通过、之后也没再失败的上机；之后补跑别的用例、或者重跑它们又都通过，不推翻它。最近一次上机通过的用例有一条不在这一卷里，工具就拒组交付，要先把它们一起整卷上机。工具还照 InfoTest 复核每条通过（和第 1 步下载时是同一条规则）：它的运行日志里有合约声明的执行失败原话、而本条断言没读那一行的，改记无判定，报告里写出是哪一行；这样的用例不到 3 轮也拒组交付。跳过了重组时省略 --recompose。工具从 Hub 读每次上机的逐条结论，核对通过卷就是最后一次整卷上机派发的那份字节；未通过卷由工具把每条用例最后一次上机的计划合成一卷（只生成，不上机），不用为它再上机，写出 `case.xlsx`、`unsuccessful_cases.xlsx`、`delivery_report.md`、`unsuccessful_cases.md`、`delivery.json`。工具拒绝时按提示补齐（通常是通过卷还没单独整卷上机一次），再跑一次；不手工拼工作簿或报告。
5. **最后的回复。** 回复就是工具打印的 reply 原文（交付目录、各状态条数、文件路径），不加表格、不逐条重述用例、不按主题分组，细节都在报告里。写完等用户说话。
