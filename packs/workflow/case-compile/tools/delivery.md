# 上机验证与失败分析

第一次上机验证后按这里完成失败分析、重新编写和交付目录，不在中途让使用者替模型选择常规写法。要交付的自动化用例必须放在同一份自动化用例 Excel 中上机验证，每条都正确。其他原始用例另写自动化用例 Excel，并逐条说明原因和下一步。

## 1. 上机验证

把设备输出整份下载到工作目录。带 `--wait 3600` 的等待命令**必须用 `background` 启动**（Circle 前台 `execute` 上限 600 秒会直接拒收），客户端在它退出后通知主会话；期间不 `sleep`、不重交自动化用例读进展，可以做不依赖结果的事。等到时限仍未完成时工具不写文件并退出 1，直接用同一命令重试继续等。

```sh
# 命令行与 <<'EOF' 写在同一行，切勿在 <<'EOF' 前换行
node '<技能目录>/tools/download-returns.ts' --hub %HUB_URL% --run '<脚本合并编号>' --out '<新目录>' --wait 3600 <<'EOF'
%HUB_TOKEN%
EOF
```

工具从标准输入取令牌，每 20 秒读取进展。设备输出、每条自动化用例的执行记录及设备会话都完整保存并核对摘要。已经完成时可不写等待参数。文件中的机器字段给模型读取，不逐字转述成使用者答复。

执行器说正确，但设备输出有执行器规则声明的执行失败原话、而本条期望没有核对到这一行时，交付复核仍是未知，保留执行器的原判与限定。核对这行观察或改用可执行的观察方法；内容份数按摘要合并，同一份内容不重复计数。未声明规则时披露缺规则，不能凭 Error、Failed 等字样自行判断。

## 2. 失败分析

先完整读设备输出。按主技能的顺序核对构建、配置是否生效、前置和多个原始用例的共同现象，再判断设备的问题。结论只依据逐字找到的设备输出，不用推测补齐。

- 设备用 `^` 指出命令中的词时，命令没有被接受。先修这条命令在当前提示符下的写法或下发方法；后面的错误可能由它引起，不能据此说测试环境缺什么。
- 设备输出包含执行器规则声明的执行失败原话时，只能说明该声明的执行失败条件命中，不单凭它判定原因属于模型或设备。核对原始返回后再改命令；取值或格式不对时读手册对该参数的说明；其他对象不存在时，先看创建它的命令是否也被拒绝。
- 某台设备会话中断后，后续清理没有发出。说明设备名字和哪些清理没做，残留没核清之前不上机验证下一份自动化用例 Excel，向使用者说明原因和下一步。
- 再次错误时，先确认上次修改已进本次自动化用例 Excel；已经改了而同一句设备输出又出现，就换解释，不重复同一种改法。设备输出点名的命令或配置，先在同一构建的手册和命令树里读到再改。

返工先读同构建手册对各参数的说明。参数取值：写进命令的每个值都要在手册对该参数的说明之内，包括长度、字符、范围和可选值。只有设备执行时才产生的值，要在同一条自动化用例里先取出再用；不写死设备生成的名字，不从上一次上机验证的设备输出抄值，也不沿用设备上已有的东西。设备上的配置和观察都用执行器规则为该设备声明的方法；要跑很久的设备命令，在那一步给足读取时间，秒数不超过测试环境上限。

重新编写要保住原始用例的范围和每一项期望。判断写不出来就换写法，不删掉或改弱来换“正确”。只改错误或未知的自动化用例，已有正确观察的与未改动部分通过 `tools/carry-plans.ts` 结转、不再重抄（未进入 `merge_run` 且 `scope`/`exclude`/`inputs` 未变、`rounds_left>0` 时，直接在原目录修改待改自动化用例并重交当前 `plan_run`）。沿用测试环境且 `rounds_left=0`、已进 `merge_run` 或 `scope`/`exclude`/`inputs` 变化时，先按 `SKILL.md` 第 2 节可照抄模板用 `start_run` 新开一次脚本编写运行（`predecessor` 填原 `test-bed` 预订号；禁止往已锁定的旧运行或脚本合并运行提交改动），下载新运行后再用下述命令结转未改自动化用例与保真核对结果（`.verdict.json`），再补写返工用例并重新做脚本合并和上机验证：

```sh
node '<技能目录>/tools/carry-plans.ts' --source '<上一轮脚本编写目录>' --target '<新脚本编写目录>' --plans '<自动化用例目录>'
```

结转可选参数：`--source-plans` 指上一轮计划目录；`--source-briefs` 与 `--briefs` 指上一轮和本轮核对目录；`--rework` 与 `--exclude` 为逗号分隔 autoid。路径和值用单引号。

原始用例要求不存在、无残留或不再包含时，不把这句话当设备输出去找，也不删掉这项检查；检查设备输出里没有对应记录；要求删除成功时，删除后再查询，检查这次查询的设备输出。按主技能的分块写法，不另立判定标准、不另请评审员再确认，不删掉这项检查。

每条原始用例最多对 3 份不同内容做本轮核验，同一份自动化用例重新验证不算新内容。未用尽预算且仍有可执行的编写工作时继续处理；次数用尽不自动证明原因在模型，也不证明所有可能的方案都失败。报告只陈述所记录的这些内容和结果，未归因就写还没查清。不能为凑次数重复提交，不自动开展第 4 份；只有补齐出口或按已有规则开新修订后才可重入。

未上机、声明跳过、候选引文未通过核对的用例仍进入逐条报告，不阻断其他用例。组交付读取 Hub 已记录的归因、全部独立缺口和具名请求的原受众/期限；资料不足保留未知，不用模型散文填充原因。模型声称无法编写、缺前置或规则未声明，均是未确认主张，不能直接充当已核验的不可编写凭据。具名出口缺失时明确披露，不自行发明受众或期限。

只有模型提出的缺陷候选或原始用例冲突所需原句均已逐字核对时，才记录相应未确认候选；核对不过则保留原主张并列明缺口。报告存在不意味着未知条目必须提前停止编写。设备只能经 Hub 的既有派发通道到达，不用本机终端工具或脚本直连。

## 3. 写每条结论

每条未交付的原始用例写 ID 加标题、结论、状态和判断。状态只用未确认、已确认、未知；模型的判断是未确认。判断只用正确或错误，未知不替它写判断。错误或未知才写原因和下一步。原因代码和显示文字来自生成词表；报告消费结构化归因，没有归因写还没查清。模型自报原因可在说明的 attribution 字段使用同一闭集，单列为未确认，不从 judged 散文提取。证据和决定者放最后；决定者只用程序、模型、使用者。

上过机的原始用例必须从最后一次设备输出逐字复制说明错误的那段，不改写、不拼接。结合手册说明怎么判断，下一步写清谁做什么；拿不准就写未知、还没查清。交付的原始用例不用另写说明。设备 pass/fail 按来源保留；当前目标自报和未排除本地操作的限定不能被程序解析提升成已确认。

怀疑设备的问题时，必须有忠实实现原始用例的步骤、原始期望原句和设备输出，并达到主技能的失败分析条件。原始用例要的取值被手册排除时，写原始用例的问题，不写设备的问题。设备用 `^` 拒绝了命令时，场景尚未实现，先修写法，不能以设备的问题或原始用例与手册不一致提前结束。

机器输入文件如下，字段和内部引用不给使用者展示。可选 attribution 使用生成词表的原始代码，模型声明与 Hub 原因分别保存。

```json
{"round":1,"cases":{"<autoid>":{"round":1,"judged":"结论、状态、判断；错误或未知时写原因","remedy":"接下来谁做什么","evidence":"最后一次设备输出原句"}},"batch":"这批原始用例需要说明的事"}
```

```text
defect_candidate 仅在怀疑设备的问题时填写:
{"repro":"复现步骤","expected":"原始用例期望原句","actual":"最后一次设备输出原句"}
expected/actual 逐字复制，由工具核对；模型判断未确认，由使用者决定
syntax_rejected 非空时不能写 defect_candidate 或 author_conflict
原始用例的否定结果: 常量用 OBSERVE_ASSERT/op=not_found，literal 写不应出现的记录；动态值在本条先 CAPTURE，再用 EXPECT_FROM/op=not_found，expected_from 指该捕获；执行器须声明寄存器的字面否定方法，不抄旧设备输出；quote 保留原始期望，这项检查不填 criterion，不为它写 criteria 或发起 criteria_review/criteria_review_run

author_conflict 仅在原始用例与手册不一致时填写:
{"author":"原始用例原句","manual":"手册原话","reference":"<下载文件中的手册引用>"}
author 从本条原始用例的标题、步骤或期望逐字复制
manual 从同构建手册或命令树逐字复制；reference 照抄对应“引用”行
工具向 Hub 重读并核原句，核原句存在不证明模型对两句话的理解正确
不论编写几轮、是否上机，均可等待作者或使用者决定，不再为它上机
不和 defect_candidate 同写；原始用例本来就测非法输入时不用这一项
parameters.exclude 排除尚未决定的原始用例
```

批量说明只写已核对的事。使用者第一条消息之后的每次发言都是人工介入，写明次数和起因；服务限流、换测试环境也写。不写未核对的“无人工介入”。设备清理未完成时在这里写设备名字和缺的清理。

## 4. 最后一次上机验证

交付卷必须是一份已整体上机且逐条正确、之后没有相关失败观察推翻的原工作簿。卷外最近一次正确的观察照记，但该条交付资格仍未知；它不阻断已满足条件的卷和其余条目的报告，也不能被拼入未经整体核验的交付卷。最近一次已有这样的卷就直接组交付目录；另需合卷的条目按既有规则继续验证。

否则先按 `SKILL.md` 第 2 节模板用 `start_run` 新开一次脚本编写运行（`predecessor` 填原 `test-bed` 预订号、`parameters.exclude` 填入本次排除的 `autoid` 列表；禁止往已锁定的上一轮运行提交变更），保留所有已有正确观察的自动化用例再重新做脚本编写。submit-plans 会跳过本次排除的原始用例，不用复制或改写文件；未改自动化用例与保真核对结果（`.verdict.json`）可用 `tools/carry-plans.ts` 带 `--exclude <逗号分隔autoid>` 结转。再做脚本合并和上机验证；其中又有错误的就再排除，一起上机验证。最多这样上机验证 2 次，仍有错误就停止并照实写结论。最后一次没有正确的自动化用例时，就没有可交付的自动化用例 Excel。

## 5. 组交付目录

```sh
# 命令行与 <<'EOF' 写在同一行，切勿在 <<'EOF' 前换行
node '<技能目录>/tools/assemble-delivery.ts' --hub %HUB_URL% --runs '<脚本合并编号>,<脚本合并编号>' --recompose '<用例重组编号>' --notes '<说明.json>' --out '<新目录>' <<'EOF'
%HUB_TOKEN%
EOF
```

令牌从标准输入给工具。工具从 Hub 找全同一份重组后的用例的每次上机验证，按时间排列；另起一批要重新做用例重组。至少提供最后一次上机验证对应的编号，确实跳过用例重组才省略相应参数。

若开运行时经 `parameters.scope` 冻结了本次范围，工具只从 Hub 运行记录读取并核对各次脚本编写与脚本合并运行的 `scope` 一致（不一致直接拒绝；中途改范围须用 `start_run` 重开运行），严禁传入本地 `--scope` 参数收窄范围；未纳入本次范围的原始用例将在 `delivery_report.md` 与 `delivery.json` 中单独披露，不阻塞其余用例结案，范围内用例仍严格按全量核对规则检查。

工具核对要交付的自动化用例都在同一份 Excel 中一起上机验证、每条都正确，且其后没有错误。后面单独重跑其他自动化用例不推翻它。卷外最近正确的观察进入逐条未知报告；需要把它交付时，再按既有规则整体核验，其他报告先行写出。设备输出的命令失败原话同样会重新核对；还未知的不能当正确。

工具核对交付的自动化用例 Excel 与上机验证的是同一份文件，另把每条未交付的自动化用例最后一次写法合成 Excel，只生成，不额外上机。工作簿仅在对应卷存在时写出，清单从实际写出的文件生成：

```text
case.xlsx                  # 有已验证交付卷时
unsuccessful_cases.xlsx    # 有最近一次已编写但未交付的用例时
delivery_report.md
unsuccessful_cases.md
delivery.json
```

工具指出缺什么就补齐后再试，不手工拼 Excel 或报告。最后回复原样采用工具给的回复，带交付目录、结论和文件路径，不另加表格或逐条重述；细节在报告中。所有上机验证及交付结束后不释放测试环境预订（预订跨运行保留），等使用者说话。
