# 上机验证与失败分析

第一次上机验证后按这里完成失败分析、重新编写和交付目录，不在中途让使用者替模型选择常规写法。要交付的自动化用例必须放在同一份自动化用例 Excel 中上机验证，每条都正确。其他原始用例另写自动化用例 Excel，并逐条说明原因和下一步。

## 1. 上机验证

把设备输出整份下载到工作目录。带 `--wait 3600` 的等待命令**必须用 `background` 启动、不给 `timeout`**（Circle 前台 `execute` 上限 600 秒会直接拒收；后台作业的 `timeout` 是它的最长寿命，到点就被结束，这条命令自己的时限是 `--wait`），客户端在它退出后通知主会话；期间不 `sleep`、不重交自动化用例读进展，可以做不依赖结果的事。等到时限仍未完成时工具不写文件并退出 1，直接用同一命令重试继续等。

```sh
# 命令行与 <<'EOF' 写在同一行，切勿在 <<'EOF' 前换行
node '<技能目录>/tools/download-returns.ts' --hub %HUB_URL% --run '<脚本合并编号>' --out '<新目录>' --wait 3600 <<'EOF'
%HUB_TOKEN%
EOF
```

工具从标准输入取令牌，每 20 秒读取进展。设备输出、每条自动化用例的执行记录及设备会话都完整保存并核对摘要。已经完成时可不写等待参数。结束后工具答复的 `message` 写着下一步：全部通过就按第 5 节组交付目录，有没通过的按第 2 节分析后跑 `pipeline.ts rework`。outcome=not_dispatched 表示没有发到设备，不是设备输出，也不算一轮上机验证；先读 missing_facts 和 next_action，按具名原因处理，不重交自动化用例来读取进展（每次重交可能再起一次尝试）。原因消除后用同一份计划重跑合并工具（open-merge.ts）。同一份自动化用例 Excel 里有几条用例时，运行器在一个测试里按顺序跑它们，某一步抛出异常就中止整本：排在后面的用例没有开始，Hub 对整份作业的每条都只答“没有判定”（报告里的条目看起来是从第一条起连续有日志、会话或结果，最后一条之后的条目什么也没有时，Hub 的 `report_check` 写明执行在哪一条处结束，下一步是读那一条的日志、处理后另开一次上机验证，不是“稍后 job resume”；其他不完整的报告仍写“稍后 job resume”，因为它可能还在来）。下载工具读各条日志的结构，前一条日志以运行器的异常结尾、其后各条没有日志也没有设备会话时，把后面的各条记为 `verdict: "not_run"` 并写 `not_executed`（`reason` 说明是排在前面的哪条在第几步出现异常，`next_action` 是下一步，`aborted_by` 给那一条的编号和步骤号；Hub 原来的 `report_check` 照留）；出现异常的那一条保留 Hub 给它的原判定；这份作业在 `index.json` 里另有一项 `aborted`：`by` 给那一条的编号和步骤号，`reason` 说明运行器在那一步中止了整本、其后几条没有执行、整份报告因此不完整，`next_action` 是修正那一条后重新上机，等待和 job resume 都补不出缺的报告（命令输出的 `aborted` 是有这一项的作业数；没有异常的结尾或后面有日志、会话时没有这一项）。步骤号是日志里异常前最后一行 `step<数字>:` 的数字，即工作簿 C 列的数字。文件中的机器字段给模型读取，不逐字转述成使用者答复。

执行器说正确，但设备输出有执行器规则声明的执行失败原话、而本条期望没有核对到这一行时，交付复核仍是未知，保留执行器的原判与限定。核对这行观察或改用可执行的观察方法；内容份数按摘要合并，同一份内容不重复计数。未声明规则时披露缺规则，不能凭 Error、Failed 等字样自行判断。

## 2. 失败分析

先完整读设备输出。按主技能的顺序核对构建、配置是否生效、前置和多个原始用例的共同现象，再判断设备的问题。结论只依据逐字找到的设备输出，不用推测补齐。

- 设备用 `^` 指出命令中的词时，命令没有被接受。先修这条命令在当前提示符下的写法或下发方法；后面的错误可能由它引起，不能据此说测试环境缺什么。
- 设备输出包含执行器规则声明的执行失败原话时，只能说明该声明的执行失败条件命中，不单凭它判定原因属于模型或设备。核对原始返回后再改命令；取值或格式不对时读手册对该参数的说明；其他对象不存在时，先看创建它的命令是否也被拒绝。
- 某台设备会话中断后，后续清理没有发出。说明设备名字和哪些清理没做，残留没核清之前不上机验证下一份自动化用例 Excel，向使用者说明原因和下一步。
- 再次错误时，先确认上次修改已进本次自动化用例 Excel；已经改了而同一句设备输出又出现，就换解释（上一轮假设已证伪，必须改换不同机制或命令形式，不重复同一种改法）。设备报错明确点出所缺对象、参数或条件，且同构建手册正文或配置示例支持尚未试过的可行假设时：尚有轮次就必须在下一轮先改写上机验证该假设，不得以“缺资料”或“剩一次机会”为由不试；轮次已用完时不开第 4 轮，把未试假设和试法写进下一步交使用者决定。只有在锁定手册正文、示例、命令树与环境声明均没有任何依据支持任何假设时，才归为“缺资料”。设备输出点名的命令或配置，先在同一构建的手册和命令树里读到再改。
- 主机上发起的访问没有任何应答（超时、连不上、没有服务器应答）时，回传和计划里可以核对的事实有：本条有没有执行这组功能的开关命令；所访问的地址有没有出现在本条的设备命令里（`check-plan.ts` 输出的 `advice` 列出这两项）；同一轮里拿到应答的用例访问的是哪个地址、从哪台主机发起。设备在每条用例开始前会被清理。
- 回传里的会话文件只有被测设备的；在客户端或其他主机上执行的命令，它的输出只有挂了检查点才写进 `log.txt`（检查点通过或不通过都会带出那段原文），只读观察块的输出读不到。下一轮要靠某条主机命令的输出来判别原因，就给它挂检查点。

返工先读同构建手册对各参数的说明。参数取值：写进命令的每个值都要在手册对该参数的说明之内，包括长度、字符、范围和可选值。只有设备执行时才产生的值，要在同一条自动化用例里先取出再用；不写死设备生成的名字，不从上一次上机验证的设备输出抄值，也不沿用设备上已有的东西。设备上的配置和观察都用执行器规则为该设备声明的方法；要跑很久的设备命令，在那一步给足读取时间，秒数不超过测试环境上限。

重新编写要保住原始用例的范围和每一项期望。判断写不出来就换写法，不删掉或改弱来换“正确”。返工由 `pipeline.ts rework`（`SKILL.md` 第 5 节）做：它用 `open-compile.ts` 新开一次脚本编写运行（沿用原 `test-bed` 预订和已受理的重组），用 `tools/carry-plans.ts` 把通过的自动化用例连同保真判断原样结转，只把错误的带着这一轮的计划、设备回传和失败分析重新派编写；不往已锁定的旧运行或脚本合并运行提交改动，不手工结转。

每条原始用例最多编写并上机 3 轮，第一次上机验证算第 1 轮，同一份自动化用例重跑不算新一轮。带 `not_executed` 的条目这次没有在设备上执行，不算它的一次上机，不写这次的 `round`，也不为它写失败原因（组交付时工具也不把它算进已上机次数）；先修 `aborted_by` 指的那一条，再把两条一起重新上机，它真正执行的那一次才是它的一轮。不到 3 轮继续编写；“缺资料”“缺拓扑”“缺前置”这种模型判断不能让它提前结束。只有在同构建锁定手册正文与配置示例对当前报错均无任何依据支持任何未试假设时，才按“缺资料”说明欠缺；只要尚有轮次且手册或示例支持未试假设，即使“剩一次机会”也必须继续修改重测。第 3 轮仍未写对即停止这一条的上机验证，仍跑一次 `pipeline.ts rework`：它把这一条留在交付卷外（第 4 节），之后照它的 `message` 办，严禁第 4 轮；没有结构化归因时原因写还没查清，说明已经做过什么及下一步。只有设备的问题有对应原句和设备输出，或原始用例与手册不一致，才可提前写结论。此外，设备只能经 Hub 上机验证或 `test-bed` 到达，严禁用终端工具（如 `terminal_connect`、`telnet`、`ssh`）或本机脚本直连设备。

原始用例要求不存在、无残留或不再包含时，不把这句话当设备输出去找，也不删掉这项检查；检查设备输出里没有对应记录；要求删除成功时，删除后再查询，检查这次查询的设备输出。按主技能的分块写法，不另立判定标准、不另请评审员再确认，不删掉这项检查。

每条原始用例最多对 3 份不同内容做本轮核验，同一份自动化用例重新验证不算新内容。未用尽预算且仍有可执行的编写工作时继续处理；次数用尽不自动证明原因在模型，也不证明所有可能的方案都失败。报告只陈述所记录的这些内容和结果，未归因就写还没查清。不能为凑次数重复提交，不自动开展第 4 份；只有补齐出口或按已有规则开新修订后才可重入。

未上机、声明跳过、候选引文未通过核对的用例仍进入逐条报告，不阻断其他用例。组交付读取 Hub 已记录的归因、全部独立缺口和具名请求的原受众/期限；资料不足保留未知，不用模型散文填充原因。模型声称无法编写、缺前置或规则未声明，均是未确认主张，不能直接充当已核验的不可编写凭据。具名出口缺失时明确披露，不自行发明受众或期限。

只有模型提出的缺陷候选或原始用例冲突所需原句均已逐字核对时，才记录相应未确认候选；核对不过则保留原主张并列明缺口。报告存在不意味着未知条目必须提前停止编写。设备只能经 Hub 的既有派发通道到达，不用本机终端工具或脚本直连。

## 3. 写每条结论

每条未交付的原始用例写 ID 加标题和结论。结论只用通过、未通过、无结论；模型自己的判断写明是模型的判断、未经确认，无结论不写成通过或未通过。未通过或无结论才写原因和下一步。原因代码和显示文字来自生成词表；报告消费结构化归因，没有归因写还没查清。模型自报原因可在说明的 attribution 字段使用同一闭集，单列为未经确认，不从 judged 散文提取。证据放最后。另写一句 `cause`：这条为什么没成功（设备怎么回的、差在哪），不换行、不超过 200 字；工具把它放进最后回复里这条用例的那一行，没写就取 judged 的开头。

上过机的原始用例必须从最近一次实际到过设备的输出中，选择一个文件里连续的一段原句作为 evidence。工具只接受单个字符串；可以选运行日志或一份设备会话，但不把文件名、jobs.json 说明或其他文件片段拼进去，不改写、不拼接。需要解释其他来源时在模型说明里用人能读的方式交代，不冒充连续的设备原句。结合手册说明怎么判断，下一步写清谁做什么；拿不准就写未知、还没查清。交付的原始用例不用另写说明。设备 pass/fail 按来源保留：它取自运行器的报告，运行期间也不能排除其他人同时操作设备，程序解析不把它提升成已确认；这一限定留在机器资料 `delivery.json` 里，最后回复和报告只写通过、未通过或无结论。原始用例没有给出具体取值、检查点由模型拟定（类型化判据，或 `model_judgment` 期望）的期望，报告在“需要复核的检查点”里逐项列出，写明检查点由模型拟定、未经独立复核；上机验证的结果只说明这个检查点是否命中，不说明作者的期望已被确认，也不写成已复核。这些检查点由工具从 Hub 的核对记录读出，写进报告，最后回复只给条数，不手写。

怀疑设备的问题时，必须有忠实实现原始用例的步骤、原始期望原句和设备输出，并达到主技能的失败分析条件。原始用例要的取值被手册排除时，写原始用例的问题，不写设备的问题。设备用 `^` 拒绝了命令时，场景尚未实现，先修写法，不能以设备的问题或原始用例与手册不一致提前结束。

机器输入文件如下，字段和内部引用不给使用者展示。可选 attribution 使用生成词表的原始代码，模型声明与 Hub 原因分别保存。

```json
{"cases":{"<已上机autoid>":{"round":1,"judged":"结论；未通过或无结论时写原因","cause":"一句话：设备怎么回的、差在哪","remedy":"接下来谁做什么","evidence":"同一个设备文件内连续的一段原句"},"<原始用例与手册冲突autoid>":{"judged":"模型判断原始用例与手册冲突，未经确认","remedy":"由作者或使用者裁定","author_conflict":{"author":"本条原始用例连续原句","manual":"同构建手册连续原句","reference":"下载文件中的锁定手册引用"}}},"batch":"这批原始用例需要说明的事"}
```

```text
defect_candidate 仅在怀疑设备的问题时填写:
{"repro":"复现步骤","expected":"原始用例期望原句","actual":"最后一次设备输出原句"}
expected/actual 逐字复制，由工具核对；模型判断未确认，由使用者决定
syntax_rejected 非空时不能写 defect_candidate 或 author_conflict
原始用例的否定结果: 常量用 OBSERVE_ASSERT/op=not_found，literal 写不应出现的记录；动态值在本条先 CAPTURE，再用 EXPECT_FROM/op=not_found，expected_from 指该捕获；执行器须声明寄存器的字面否定方法，不抄旧设备输出；quote 保留原始期望，这项检查不填 criterion，不为它写 criteria 或发起 criteria_review/criteria_review_run

author_conflict 仅在原始用例与手册不一致时填写:
{"author":"原始用例原句","manual":"手册原话","reference":"<下载文件中的手册引用>"}
author 从本条原始用例的标题、步骤或期望逐字复制
manual 从同构建手册或命令树逐字复制；reference 照抄对应“引用”行
工具向 Hub 重读并核原句，核原句存在不证明模型对两句话的理解正确
不论编写几轮、是否上机，均可等待作者或使用者决定，不再为它上机
不和 defect_candidate 同写；原始用例本来就测非法输入时不用这一项
parameters.exclude 排除尚未决定的原始用例
```

没有到过设备的条目不写 round、evidence，不用 null 或编造轮次代替。作者冲突必须按示例填写 author_conflict；缺资料先把本条计划交 Hub 取得具名事实和请求。没有可核验结论或具名出口时，工具退出非 0，stdout.hints 逐条点名缺什么、下一步和合法示例；按提示补齐后在新输出目录重跑，不把存在一份未知报告当作收尾已完成。

judged、remedy、batch 是给使用者看的说明，不写内部运行号、账号号、来源摘要、字段名或本机文件路径；机器引用和原始字段保留在 delivery.json 供模型核对。设备引文仅引用一个文件的连续原话。

批量说明只写已核对的事。使用者第一条消息之后的每次发言都是人工介入，写明次数和起因；服务限流、换测试环境也写。不写未核对的“无人工介入”。设备清理未完成时在这里写设备名字和缺的清理。

## 4. 最后一次上机验证

交付卷必须是一份已整体上机且逐条正确、之后没有相关失败观察推翻的原工作簿。卷外最近一次正确的观察照记，但该条交付资格仍未知；它不阻断已满足条件的卷和其余条目的报告，也不能被拼入未经整体核验的交付卷。最近一次已有这样的卷就直接组交付目录；另需合卷的条目按既有规则继续验证。

否则由 `pipeline.ts rework` 开交付卷（`SKILL.md` 第 5 节的命令，`--returns` 写最后一轮的回传目录）：它排除没通过的条目、新开一次脚本编写运行（禁止往已锁定的上一轮运行提交变更）、把通过的自动化用例连同已有的保真判断原样结转，照它的 `message` 收拢到新目录、做脚本合并和上机验证。这一卷上机后照 `download-returns.ts` 的 `message` 办：全部通过就组交付目录；又有没通过的跑 `pipeline.ts rework`，由它再排除、再开一卷。交付卷最多上机验证 2 次，仍有错误它会说上机到此为止，照实写结论。最后一次没有正确的自动化用例时，就没有可交付的自动化用例 Excel。

## 5. 组交付目录

```sh
# 命令行与 <<'EOF' 写在同一行，切勿在 <<'EOF' 前换行
node '<技能目录>/tools/assemble-delivery.ts' --hub %HUB_URL% --runs '<脚本合并编号>,<脚本合并编号>' --recompose '<用例重组编号>' --notes '<说明.json>' --out '<新目录>' <<'EOF'
%HUB_TOKEN%
EOF
```

令牌从标准输入给工具。工具从 Hub 找全同一份重组后的用例的每次上机验证，按时间排列；另起一批要重新做用例重组。至少提供最后一个脚本合并运行的编号；工具对显式传入和自动发现的未派发运行采用相同规则：不把它计为上机次数，在机器摘要和报告另列 Hub 记录的原因与下一步。确实跳过用例重组才省略相应参数。

若开运行时经 `parameters.scope` 冻结了本次范围，工具只从 Hub 运行记录读取并核对各次脚本编写与脚本合并运行的 `scope` 一致（不一致直接拒绝；中途改范围须重新开运行），工具没有 `--scope` 参数，不从本地文件收窄范围；未纳入本次范围的原始用例将在 `delivery_report.md` 与 `delivery.json` 中单独披露，不阻塞其余用例结案，范围内用例仍严格按全量核对规则检查。

工具核对要交付的自动化用例都在同一份 Excel 中一起上机验证、每条都正确，且其后没有错误。后面单独重跑其他自动化用例不推翻它。卷外最近正确的观察进入逐条未知报告；需要把它交付时，再按既有规则整体核验，其他报告先行写出。设备输出的命令失败原话同样会重新核对；还未知的不能当正确。

工具核对交付的自动化用例 Excel 与上机验证的是同一份文件，另把每条未交付的自动化用例最后一次写法合成 Excel，只生成，不额外上机。工作簿仅在对应卷存在时写出，清单从实际写出的文件生成：

```text
case.xlsx                  # 有已验证交付卷时
unsuccessful_cases.xlsx    # 有最近一次已编写但未交付的用例时
delivery_report.md
unsuccessful_cases.md
delivery.json
```

有模型拟定检查点的原始用例，工具生成的最后回复只给条数（几条用例、共几处），`delivery_report.md` 在“需要复核的检查点”里单列原句、检查点和模型的理由，写明是模型的判断、未经独立复核、上机验证的结果只说明检查点是否命中；机器资料 `delivery.json` 的 `model_checkpoints` 保留同样的内容。工具指出缺什么就补齐后再试，不手工拼 Excel 或报告。工具答复的 `message` 写着下一步：退出码为 0 且 hints 为空时，最后回复原样采用工具给的 `reply`（原始脑图共几条用例、生成成功几条、失败几条，自动化用例 Excel 的路径，每条失败用例一行：发生了什么、原因，再加报告的路径），不另加表格或逐条重述，细节在报告中；非零退出时先按逐条 hints 补齐并在新的输出目录重跑，已写出的未知报告保留事实，不代表收尾完成。所有上机验证及交付结束后不释放测试环境预订（预订跨运行保留），等使用者说话。
