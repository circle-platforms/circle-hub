# 场景保真审计（交卷前）

照 InfoTest 的场景保真：编写出来的计划还实现不实现作者写的场景，由一个新开的审计会话逐条判断，判断随计划交给 Hub。写计划的会话自己判，会顺着自己当初的理由判保住，所以审计要另开会话。

1. **算简报。** 每份计划写好或改过之后、交卷之前执行：
   `node <技能目录>/tools/fidelity-brief.ts --run <计划运行目录>/run.json --plans <计划目录> --out <新目录>`
   它先像 submit-plans 一样展开长度占位并写回计划文件，再给每条有作者动作原句的用例写一份 `<用例文件>.brief.json`，打印每份的 brief_sha256。没有作者动作原句的用例不用审计。计划再改，就重算简报、重新审计。
2. **审计。** 用 task 开一个新的子代理，任务说明里只放简报全文和下面的判断规则。一个子代理可以审几条用例，每条用例单独判。不要放你对计划的解释、设备返回或手册。
3. **写回。** 子代理交回 `{"steps":[…],"disclosure":"…"}`，原样写进这条用例计划的 `data.fidelity`，再加上 `"brief_sha256"`（简报里的值）。不改子代理的判断。
4. **交卷。** submit-plans 照常交。Hub 按同一规则重算简报、核对摘要，只核能机械核的：每条作者步骤恰好一行、结论在三种之内、判保住的写出实现它的计划步骤。判改了、没实现，或判保住却没写步骤的，退回编写：按审计理由改计划，再从第 1 步重来。

## 给审计子代理的判断规则（原样放进任务说明）

你是场景保真审计。只看简报：作者原文（author_steps 的 text；有适配的，作者原文在 author_text，text 是适配后的写法，adapted_commands 是适配给出的命令，basis 是适配依据）、期望原文（expectations）和计划步骤（blocks：index 是步骤号，host 是执行它的设备或主机，kind 是方法，cmds 是命令，asserts 是判断这一步输出的断言文字）。设备返回、手册和过去的用例都不在判断范围里；产品语义从简报给的文字自己推理。

对 author_steps 的每一条作者步骤判一次：

- preserved：计划里有步骤照作者写的实现了这一步。step_indices 写出这些步骤的 index，至少一个。
- changed：计划实现的是另一个场景，或改掉了作者写明的条件，包括丢掉作者写明的区别、把作者的前置换成别的前置。例如作者说重建的对象换了类型，计划重建的还是同一类型；作者说某个属性保持不变，计划却改了它；作者的前置被换成让期望更容易满足的前置。
- unrealized：计划里没有步骤实现这一步，step_indices 写 []。

有适配的步骤：计划实现的场景和作者原文写的等价时，适配算保住。准备用的取值、名字和观察工具的选择是编写方的自由，不算偏离。不判断言取值、期望值、判据类型和设备上通过与否（见 policy.not_judged）。mechanical.status 为 unavailable 表示没有做机械比对，每一步都由你判。

只交一个 JSON 对象，恰好两项：`steps`（每条作者步骤一行 `{"n","verdict","step_indices","rationale"}`：n 抄简报里的作者步骤号，verdict 是 preserved、changed、unrealized 之一，step_indices 只用简报 blocks 里的 index，rationale 写判断依据，只依据简报里的作者原文和计划步骤）和 `disclosure`（给用户看的一段中文：哪几步保住、哪几步改了或没实现、为什么）。不附加别的字段，JSON 后面不写说明。
