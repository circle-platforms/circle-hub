# 怎样写一份别人能看懂、能照着开发的设计

设计先说明用户遇到什么问题，以及完成后应该得到什么结果。接着解释平台准备怎样解决，再说明代码由哪些部分承担。函数名字和格式是核对资料，不应该占据整份说明。

## 每份设计都要回答的事情

说明用户是谁，当前发生了什么，为什么需要这项能力。给出一个正常使用的经过，也说明缺资料、权限不足、操作失败或结果不明时会怎样处理。

涉及产品时，写清楚型号、版本、环境和使用条件。涉及组合任务时，说明各步骤怎么连接，哪一步需要上一项结果，哪些步骤可以并行，什么时候需要用户回应。

涉及模块时，说明它负责保存什么、检查什么，谁会调用它，以及哪些事情交给其他部分处理。不要只画依赖图，却不解释每条依赖为什么存在。

涉及函数时，用自然语言讲它拿到什么输入、做什么、可能改变什么、返回什么，以及调用者遇到失败后该怎么办。需要查具体签名时，再附代码位置和格式说明。

## 说明哪些结论能确定，哪些需要 LLM

按[判断与披露原则](../design/truth-and-disclosure.md)，100% 置真内容交给脚本，其余内容由 LLM 判定。设计要说明脚本规则、适用条件、输入与可证明范围，也要说明 LLM 实际看到什么、怎样表达判断、冲突与缺项。不能用格式检查替代内容判断。

完整列出输入、原始输出、错误、重试、转换和实际作用如何保存及向有权限的用户展示。摘要要能追溯原件，遮蔽要注明范围。网络测试还须说明物理层到应用层中涉及的产品、拓扑、流量、故障位置和观察点。

## 要把出错后的行为写出来

耗时操作可能被重复提交，也可能执行完却没有收到回执。用户可能在执行途中改变输入，也可能接管后又交回。设计需要说明平台怎样知道实际发生了什么，哪些动作能重做，哪些必须先核对。

修复问题时，保留能复现原问题的样本。还要检查使用这个函数的其他入口和产品，防止只修好一条路径。

## 说明和证据分开

提出一种做法，表示它还需要讨论。写了代码，表示已有实现。跑过某次检查，只说明那次输入和环境下观察到的结果。交付还要检查必需结果是否齐全。

源码注释可以帮助理解，但不能替代实际检查。生成的函数清单也一样。它说明某个声明存在，不能证明权限、并发或设备效果已经正确。

## 使用模板时仍要把话说完整

[工作模板](../templates/README.md)提醒需要回答的问题。用完整的句子讲用途和经过，不要只填几个名词。没有决定或没有检查的地方直接写出来，之后再补对应依据。
