# 怎样检查结果，怎样说明支持范围

平台最终交付的是实际完成的工作。检查结果时，要先写清楚独立的预期，再记录实际观察。不能看到设备输出之后，反过来把预期改成一样。

## 每种检查能证明什么

格式检查能说明请求和结果符合约定，不能说明内容真实。方法测试能说明它在给定输入下怎样处理，不能直接证明真实产品也有相同行为。

组合任务需要实际经过相关部分，检查资料、操作、用户回应、结果保存和完成判断能否连起来。入口和显示也要单独检查，尤其是同一会话的实时画面和人工交接。

真实模型要用独立标注的材料测判断质量。真实设备和网站要记录型号、版本、环境、账号权限和实际作用。模拟环境通过不能替代现场检查。

## 多种产品和方法不能互相代替

同一种能力用在不同产品上，要检查资料和方法是否适用。升级产品版本或方法版本后，检查哪些原结果还能成立，哪些需要重跑。

选择有代表性的组合时，也要说明没有测过什么。不能从一个正常场景推出所有组合都能使用。通用能力需要检查同类问题的不同输入形式，产品方法需要检查该产品特有的条件。

## 交付要保留哪些东西

按[判断与披露原则](../design/truth-and-disclosure.md)，完整披露实际输入和输出，包括脚本和模型使用的输入、原始返回、错误与重试、转换过程和实际观察。脚本的可核验事实、LLM 判定和现场效果分别验收；不以模型置信度代替事实，也不以脚本格式检查代替语义判断。大内容可默认折叠，原件按权限可追溯，必要遮蔽须明确标记。

用户应该能取得产物、检查结果和必要的证据，并看见还没有完成或仍不确定的部分。每份结果要能找到生成它的资料、程序、目标和运行记录。

生成文件不等于已经发给用户。构建成功不等于发布成功。设备接受配置不等于业务恢复。平台应分别记录这些结果，再判断是否满足这项工作的交付要求。

版本发布和回滚要单独说明步骤、允许的作用和验证方式。当前真实环境和发布操作仍按原范围授权，本轮只整理设计和文档。
