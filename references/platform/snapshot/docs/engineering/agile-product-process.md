# 用短迭代把平台做成产品

2026-10-10。工作方式提案。采用产品目标、产品待办、Sprint 目标、可用增量与完成定义组织工作，按规划、每日检查、评审和回顾调整；参照官方 [Scrum Guide](https://scrumguides.org/scrum-guide.html)。两周节奏是本项目建议，不是 Scrum 强制要求，也不是已经开始的迭代。

## 谁负责什么

产品负责人决定价值、优先级和支持范围，处理需求取舍；当前由用户承担产品决策，后续团队需明确负责人。开发人员对实现、测试和完成定义负责，agent 可以协助设计、开发与核验，但不能自行签发需要用户或独立评审的结论。流程负责人帮助消除阻碍和改进协作，具体人员在团队建立时安排。

产品、网络、研发、测试和运维人员按任务协作。一个交付同时需要多种专业知识时，让它们在同一任务中形成结果，不按对象分成五个互不交付的小组。

## 从需求到下一次迭代

产品待办先按用户价值排序。大的目标作为 Epic，再拆成可以演示和独立验收的用户故事；实现任务、缺陷和限时研究关联到故事。架构、安全、文档和运维工作说明它支持哪项用户结果，不单独堆积完成数。

Sprint 规划先确定本次为什么值得做，再选择能满足完成定义的工作和实现办法。结合当前容量、依赖和实际历史，不凭空承诺故事点或工期。需求变化时保留原目标和影响，协商调整范围，不降低质量要求。

每天检查距离 Sprint 目标还有什么、哪些工作受阻、下一步怎么调整。产品评审演示真实经过和结果，核对用户要求并更新待办；回顾则讨论沟通、工具、测试和返工，选少量改进落实到下一次。评审不是产品发布的统一闸门，发布仍按环境和操作授权处理。

## 什么情况下可以开始开发

用户目标、适用产品/版本、输入和独立预期已说明；允许动作与权限已明确；关键依赖、故障/未知行为和验收方法已列出；任务大小能在迭代内完成。尚有不确定性时，先安排有具体问题、范围和退出条件的研究，不伪装成已就绪需求。

这份“开始条件”是本项目做法，不是 Scrum 新增的强制仪式。已有授权内的明确工作继续推进，不因为每个条目仍要细化就重复申请许可。

## 什么才算完成

代码、设计和相关说明一致；必要检查在当前提交通过；问题修复能复现原问题并检查相关使用者；身份、项目、环境和执行端权限拒绝场景被验证。实际输入输出、处理、重试、作用、产物和未验证范围可以追查；脚本事实、LLM 判定和实际业务效果分别呈现。资源、残留和恢复满足该故事要求。

用户故事还要达到它自己的验收条件。有人工签字或独立评审要求时，记录对应决定。截图、模拟模型、局部绿测、Issue 关闭或界面动画都不能替代实际交付。没有达到完成定义的工作回到待办，不计为已完成增量。

## GitHub 中怎样跟进

私有 [Projects 看板](https://github.com/users/qingshanfeihu/projects/1)关联此仓库。阶段用 Milestone，Epic/故事/任务用 Issue 和原生父子关系，代码改动关联 PR 与回执。看板状态为待整理、待规划、已就绪、进行中、评审中、阻塞、完成；状态反映工作过程，Issue/验收记录说明具体结果。

阶段、优先级和迭代安排分别登记。当前“首个 Sprint 候选”尚未成为 Sprint Backlog；规划后再固定目标、日期、选中工作及容量。远期只保留目标和重要依赖，不预先把未来所有 Sprint 填满。GitHub Projects 的关联与自定义字段参考 [GitHub 官方文档](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)。
