# GitHub 和文档怎样帮助我们把产品做下去

GitHub 用来把用户需求、讨论结果、代码修改和检查结果联系起来。文档用来解释做法；任务列表用来跟进还需要完成的工作。它们的作用应当让人一眼看懂。

## 一项工作从需求开始

先说明谁遇到了什么问题，希望平台交付什么，以及适用于哪些产品和环境。大的工作拆成几项可以分别讨论和完成的任务，再关联回总任务。

讨论方案时说明理由、影响和没有决定的地方。开始开发后，代码变更说明实际改了什么、影响哪些使用者，以及跑了什么检查。最后用证据说明结果，不用任务被关闭来代替验证。

## 迭代怎样推进

按[敏捷流程](agile-product-process.md)维护产品待办、Sprint 目标和完成定义。先交付一个产品上的完整任务，再扩展第二个产品和组合能力，见[实施路线](../implementation-roadmap.md)。看板状态、Issue 关闭和代码合并不替代用户结果及其证据。

## 当前工作怎样安排

已建立[平台总任务和子任务](github-work-items.md)。它们分别整理产品接入、能力组合、用户交互、函数说明、代码分工、验证和开发流程。

这些是设计和开发准备工作。已经确定的实施仍按原计划推进，新增任务不自动授权业务实施或真实设备操作。

## 文档放在哪里

项目首页介绍产品。[平台总说明](../product-framework.md)讲整体怎样工作，[项目内容说明](../project-explanation.md)讲现有代码。具体产品方法和模块设计继续放在对应设计文件中。

函数的源码位置和签名是核对资料。既有讨论和执行记录保留各自的日期、输入、环境和结果。需要追查时再展开阅读，不把所有历史记录堆在产品首页。

## 改动怎样检查和发布

修改公开函数或实际操作行为时，更新说明并检查所有使用者。修复问题要能复现原问题，文档中的通过结论必须有实际记录。

仓库提供需求、设计、验证和代码变更模板，还提供只检查文档链接和源码目录的自动检查。这个检查不安装平台依赖、不运行业务模块，也不启动设备或浏览器环境。

本轮没有修改分支保护或合并权限。现有工作树和并行改动继续保留，文档使用隔离工作树提交。产品资料、秘密和完整业务日志不放进 Git。
