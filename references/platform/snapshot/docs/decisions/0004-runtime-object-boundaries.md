# ADR 0004：运行对象与能力归属

日期：2026-10-10。

状态：按用户本轮“完整调研并重新划分不明确归属”的要求形成的职责基线。尚未实施 TS 重写、移动旧代码或部署。

## 依据

盘点 GitHub 名下 13 个仓库，固定默认分支提交并检查完整文件树。本地对应四个业务项目与设计仓库的 HEAD 对齐。扫描接口声明、工具表、skills、hooks、主要模块和研究程序，形成 403 条带来源的建议映射。

详见[调研](../research/project-capability-audit.md)、[CSV](../research/inventory/capability-catalog.csv)、[JSON](../research/inventory/capability-catalog.json)。统计是静态定义和模块记录，不代表同一 agent 已挂载全部能力。

## 决定

1. 原五类建设对象调整为五类运行职责：A 入口/Agent 运行；B 知识/证据/制品；C 任务/协作治理；D 操作/执行资源；E 能力包/业务规则。
2. 共享契约 F 和评测实验 G 单列为横切工程，不与运行服务混为一层。
3. 知识 B 与任务 C 明确分开；可先物理同进程。知识库 V1 的六类记录、PostgreSQL/原件存储和快照机制继续有效。
4. 工具/MCP/HTTP/skill/hook 是机制维度，不能决定业务归属；一个 facade 可组合多个对象，内部写入者和真实效果必须明确。
5. 编译器和领域验证归 E；编排、人工响应和任务收口归 C；实际设备/浏览器/进程归 D；产物、资料与证据归 B；通用交互和推理循环归 A。
6. 会话、任务、执行、知识/制品使用不同身份与状态空间；相互引用，不互相冒充完成。
7. 只读提示与效果描述、政策定义与最终执行检查、技术观测与业务事实分别表达。
8. 新 TS 系统按职责重新实现。旧仓库及候选工作树仅作经验和验收参考；不按旧项目整体归类或搬迁。

用户后续明确 A 可由 Circle/Pi/OpenCode 等替换，B/C/D/E 共用能力与状态；本轮只做计划。详见 [ADR 0005](0005-harness-neutral-planning.md)。该澄清不改变知识库六类数据记录和五类运行职责的区分。

## 范围说明

研究仓库归 G；归档 Circle-next 归 A 的行为参考；游戏、IOTA 业务和空 README 仓库不因用户持有就强行加入网络产品平台。

403 条中的主归属是本轮架构建议，104 条标记为需要拆职责或明确跨对象契约，不能解释成 104 个已经复现的代码缺陷或 104 个必须独立部署的新服务。

## 后续

先按 F 形成共用身份、操作、效果、回执和错误契约，再逐项设计 C/D 的任务和执行边界及 E 的专业能力。实现期间应继续验证具体消费者；语义分工仍遵守程序确定性工作与模型判断分别记录的原则。
