# ADR 0001：项目方向与重写边界

日期：2026-10-10

状态：已确认。仅本页“决定”中的事项作为已接受边界，其余设计文档继续讨论。

## 背景

最初从 Circle 与 Pi 的基础功能对齐谈起，随后以既有负载均衡工程实践讨论网络安全产品全生命周期的 agent 能力。用户进一步明确平台覆盖 InfoSec 全产品线，负载均衡是通用抽象的实践基础；Excel 编译和用例评审也只是例子，研究不能收窄为某一产品线或几个固定工作流，见 [ADR 0010](0010-product-line-scope.md)。

已有 InfoTest、compile skill/server/gateway 和知识主机提供了设计经验与数据基础。前期“逐步改造现有服务”的建议已被用户纠正。

## 决定

1. 项目名为 infosec-platform，GitHub 仓库位于 qingshanfeihu 账号下，保持私有。
2. Circle 保留；其余相关自研项目与代码用 TypeScript 全新实现。后续用户明确 Circle 为可替换通用 harness，Pi/OpenCode 等也可承担入口，见 [ADR 0005](0005-harness-neutral-planning.md)。
3. 旧项目用于研究需求、理解行为与故障、迁移数据、构造验收参考；不以改造旧项目或包装旧 Python 运行时作为新实现路线。
4. 产品目标覆盖用户答疑、需求与设计评审、开发、bug 定位修复、测试分析与单元测试、发布和版本维护、Web 操作与定位、产品 CLI 开发与定位。
5. Circle 基础能力以不逊于 Pi 的同等可用性为目标；重点强化长任务执行、外部环境操作、Web 能力和验证。
6. Skill 是承载部分专业方法的机制；具体 skill 数量、MCP/tool/hook 边界和协作方式需要继续研究。
7. 初始化仓库记录已进行的讨论和调查，随后逐项讨论实现，本轮不开始业务开发。
8. 本次提供的主机登录凭据只用于授权的只读查看，不进入 Git、文档或长期记忆。仓库使用部署别名记录调查。
9. 平台面向 InfoSec 全产品线，以负载均衡工程实践建立通用抽象；本页背景中原“尤其负载均衡”的定位已由 [ADR 0010](0010-product-line-scope.md) 澄清。

## 后果

- 新系统要重新实现服务、执行器、MCP、tools、验证器及 skill 配套可执行脚本；说明文档仍可使用 Markdown。
- 旧项目能复用的是知识、经验、数据和经确认的契约。实现边界需要重新设计。
- 历史缺陷不能因追求对拍一致而被复制为新系统要求。
- 私有仓库也不承载凭据、原始业务资料或完整对话日志。

## 尚未决定

- monorepo、进程与服务边界、技术依赖和部署拓扑。
- 知识对象与版本模型、任务模型、统一操作和证据契约。
- 第三方解析服务、基础设施和外部测试框架的接入范围。
- 产品 skills 的首批范围、任务角色配置和多 agent 默认策略。
- 最小完整场景、实施先后次序与量化验收标准。

## 被替代的提案

- 在原 InfoTest、compile server/gateway 仓库内逐步改造成最终平台：由第 2、3 条替代。
- 以 Excel、评审、Web 三个固定流程定义整个产品：由第 4、5 条替代。
- 初拟仓库名 circle-platform：用户最终指定 infosec-platform；可见性仍为私有。
