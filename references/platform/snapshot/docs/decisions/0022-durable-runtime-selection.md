# ADR 0022：持久运行选型

- 状态：**已定案**（2026-10-10，用户裁定：按 ADR 0022 采用 PG 任务表路线）
- 日期：2026-10-10
- 依据：ADR 0016（评估顺序与判据）、ADR 0017（PostgreSQL 基线）、`docs/p3-2-runtime-evaluation-record.md`（C-T03/C-T04 对比证据，两路线 9/9 场景通过）
- 编号说明：0021 已由 `0021-ssh-web-interaction-scope.md` 占用，本文件顺延为 0022

## 结论

**采用 PostgreSQL 任务表路线作为 C 的持久运行基线；Temporal 不作为当前基线采用。**

即：C 的 durable runner 在 P3-1 的事务受理之上继续以 PostgreSQL 任务表 + 自研 runner 推进（阶段推进与效果同事务、唤醒持久化、流程版本按行钉死）；Temporal 保留为已验证的备选，其评估工装与结论存档于 `packages/runtime-eval` 与 P3-2 记录。

## 理由（与证据对应）

1. **恰好一次的纪律两条路线相同，Temporal 没有减负**。C-T03a 实测：Temporal 活动是至少一次执行，被杀后重试使尝试计数为 2，效果恰好一次靠的是与 PG 路线同一个外部账本。PG 路线把效果放进阶段事务，原子性由数据库直接给出。
2. **版本钉死在 PG 路线是默认行为**。C-T04 实测：PG 路线流程行钉死版本，飞行中流程严格按创建版本完成；Temporal 的 `patched()` 只保护已记录步骤，未执行后缀会采用新代码，严格钉死需要入参纪律或部署版本化，二者都是持续负担。
3. **权威唯一**。受理、人工决定与交付门禁已在 C 的 PostgreSQL 事务中（P3-1）。PG 路线运行状态与业务记录同库同事务；Temporal 路线要在历史与业务记录之间长期维护 ADR 0016 的权威划分与对账。
4. **运维面与当前规模匹配**。PG 路线只新增一个自研 runner（评估实现 237 行含账本/唤醒）；Temporal 新增有状态服务器集群与 worker 进程群。本平台当前为单团队、隔离评估规模，其声明式长流程、计时器与重放调试的优势在本轮最小流程上没有转化为决定性差异。

## 再评估触发条件

出现下列任一情况时，按 P3-2 记录的同一组场景重跑对比，另行 ADR 再议，本决定不预先封死：

- 流程形态显著变化：大量长时（天级以上）等待、复杂计时/重试编排、跨服务编排成为常态；
- 流程数量或并发增长使自研 runner 的调度/认领成为可观测瓶颈；
- 需要现成的流程历史可视化与审计回放，且自研成本高于引入 Temporal 的运维成本。

## 定案后动作

- 将 P3 规划 P3-2 行标记完成，选型结论同步进 C/D/E 实施讨论的决策表；
- P3-3 起 D 控制面与 workers 的长任务运行一律构建在 PG 路线 runner 之上；
- `packages/runtime-eval` 保留为评估证据，不演化为生产代码。
