# ADR 0025：围绕完整产品任务建设和验收

日期：2026-10-10。状态：用户明确同意以下五项产品设计补充；具体阶段、Sprint 与实现细节继续按计划讨论。

1. 测试环境是一项正式能力，能够描述产品、版本、拓扑、配置、流量、故障和观察点，支持准备、检查、恢复与清理；物理、虚拟和模拟环境的证明范围分别说明。
2. 调查保留候选原因、支持与反驳证据，以及下一项检查能区分什么原因。LLM 判定可被新证据修正，历史输入和结果保留。
3. 完整披露需要可用的阅读方式：默认展示目标、当前动作、发现和下一步；展开查看实际输入、原始输出和处理过程，用户可以指出问题并发起重新核验。
4. 成功与失败经验均可沉淀为样本或方法候选；独立核验、明确版本和条件后，再晋级为可复用方法或脚本。一次成功或模型一致不能成为通用事实。
5. 以完整任务衡量平台：复现、验证原因、修复与回归、断线后继续、人工介入及实际交付分别评估。脚本正确性、LLM 质量、执行效果与交付不能互相替代。

优先在一个产品上贯通“查资料与代码 → 准备网络环境 → 复现采集 → 分析并验证原因 → 修复 → 回归 → 完整交付”，再用第二个产品检验公共能力是否通用。产品范围仍覆盖全部网安产品生命周期，不收窄为网络排障或单个负载均衡工具。

后续用户要求讨论标准敏捷流程，补充 B/C/D/E 的观察维护、人员权限与安全域，以及无需外部 harness 的原生 Web 入口，并要求可交互页面 demo。对应[阶段路线](../implementation-roadmap.md)、[敏捷流程](../engineering/agile-product-process.md)、[管理与入口设计](../design/web-workspace-and-operations.md)和[权限设计](../design/identity-and-security-boundaries.md)。这些细则标注各自状态，不由本 ADR 自动授权生产实施、真实环境操作或部署。
