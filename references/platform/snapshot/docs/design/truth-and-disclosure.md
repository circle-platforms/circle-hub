# 什么交给脚本，什么交给 LLM，用户应当看到什么

这是用户确认的全平台设计原则，见 [ADR 0024](../decisions/0024-truth-and-disclosure-principle.md)：**将 100% 置真内容交给脚本，其他非置真内容使用 LLM 判定，完整披露输入和输出结果。** 当前是设计要求，现有模块的符合程度需要分别核验。

## 能确定的事情由脚本负责

文件的原始字节与摘要、明确格式的解析、按已确认规则进行计算、实际采集值与固定预期的比较，可以在输入和适用条件明确时交给脚本。脚本输出应说明用了哪些输入、哪版规则、检查了什么，以及具体结果。

确定性必须有范围。例如，脚本能够证明一次采集中端口协商速率是某个值，不能由此证明链路永远正常；能够证明 TCP 握手完成，不能由此证明应用正常；能够证明配置回读一致，不能由此证明业务已恢复。脚本也可能有缺陷，规则、前置条件和结果本身仍需要验证。

缺输入、规则不适用或观察互相冲突时，脚本应返回具体缺项，保留原始结果。不能补造输入、根据现场输出改预期，或为了方便交付硬判。

## 需要理解和推断的事情由 LLM 判定

用户的目标是什么意思、资料是否支持某项要求、代码行为怎样影响产品、异常最可能发生在哪一段，以及下一步怎样调查，都可能需要 LLM。它应使用实际提供的产品资料、网络知识和现场证据，给出判断、依据、适用条件及仍不确定的地方。

“证据不足”也是一个可交付的判断，但不能用它代替已有依据的分析。平台可以列出候选原因、支持与反驳证据，并提出能区分候选原因的下一项检查。判断应允许后来被新证据修正，不能悄悄覆盖旧输入和结果。

LLM 可以提出脚本、断言或测试方案；在规则得到确认、程序经过检查并实际执行前，它们仍是提案。重复输出相同结论、命中动作缓存或通过 JSON 格式检查，都不会提高为确定事实。脚本事实与模型解释出现冲突时，应当显式呈现并调查。

## 完整披露实际输入与实际输出

用户应能展开查看本次实际使用的材料：资料与版本、代码或配置快照、采集目标与时间、脚本参数，以及实际发送给 LLM 的消息、上下文、附件引用和工具结果。不能只展示用户最初的一句话，却省略影响判断的后续输入。

输出包括脚本原始结果、模型实际返回内容、工具返回、标准输出与错误输出、产物和现场观察。还要保留解析、裁剪、摘要、转换、重试及失败记录，并说明最终报告怎样从这些结果得到。展示模型提供的解释和证据依据；不宣称能取得模型未返回的内部思考过程。

原件较大时可以默认显示摘要，但应有完整内容或受权限控制的原件引用。绑定内容摘要、来源、版本、任务、运行和相关时间，避免另一版输入的结果混进来。秘密通过受控途径管理；显示和发布时必要遮蔽，明确标注遮蔽范围，禁止把凭据写进 Git。

## 在网络排障里怎样使用

网络排障覆盖物理层到应用层，既需要产品知识，也需要网络知识。产品知识解释版本、内部模块、配置和已知行为；网络知识解释链路、交换、路由、回程、传输、加密和应用协议。两者共同用于搭建测试环境和判断现场现象。

| 调查范围 | 需要表达的环境与观察 |
|---|---|
| 物理链路 | 接线、介质、模块、速率、双工、链路与错误计数；软件模拟不能证明真实物理介质行为 |
| 二层网络 | VLAN、ARP/ND、MAC 学习、MTU、链路聚合及相关转发现象 |
| 三层网络 | 地址、路由、VRF、隧道、NAT、策略、正向和回程路径 |
| 传输与会话 | TCP/UDP、重传、超时、连接状态、会话保持及并发限制 |
| 加密与应用 | DNS、TLS/SNI、证书、HTTP、代理、认证和应用响应；按实际链路定位，不机械按层号归因 |
| 产品内部 | 虚拟服务、pool/member、健康检查、策略、内部进程与资源；按具体产品及版本选择 |

测试环境应说明客户端、设备、交换或路由节点、后端和观察点在哪里，预期路径是什么，各处使用哪版配置与方法。故障需要明确注入位置、持续时间和恢复方式。跨多个产品时，保留共同网络与各产品行为的关系，不能只创建一个管理页面就称为网络测试环境。

脚本采集可核验的状态、重放明确的流量、比较独立预期；LLM 根据跨层证据分析原因并选择下一项调查。测试环境中的确定事实与现实网络的推论分别报告。例如，前端超时与后端抓包没有请求，可以支持调查中间路径，尚不足以指定某条路由或某个产品模块有缺陷。

当前沙盒只覆盖已记录的回环协议和进程实验，见[本地研究](../research/local-sandbox-findings.md)。真实物理层、复杂路由与跨层诊断准确度仍需独立验证。这是产品范围与设计方法，不是新增实验的执行记录。
