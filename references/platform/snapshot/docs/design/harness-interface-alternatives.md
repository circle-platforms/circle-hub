# A 的界面怎样做：五个方案

2026-10-10。五个交互提案，尚未选择。用户明确否定上一版工作台：它把工作种类堆成菜单，把自然语言当作创建固定任务的表单，没有正确表达 A 是 harness，以及 B/C/D/E 的观察和管理。上一版不再作为界面基线；保留源代码用于追查这次纠正。

后续用户提出改为独立桌面客户端，参考 ZCode；见[桌面框架研究](../research/zcode-desktop-framework.md)。以下五种方式作为布局参考，不再默认依赖浏览器作为主入口，也未选定其中任何一个。

可操作的对比页面见[五方案 demo](../../demo/harness-concepts/README.md)。它展示信息组织和操作路径，没有接入真实模型或平台后端。

## 先把对象说对

A 是入口与 Agent 运行，包含会话、模型调用、上下文、技能/工具加载、工具调用与结果、用户中断和继续。Web 版应当能够承担类似 Codex 或 Claude Code 的 harness 交互。只加一个聊天框不构成它；Circle、Pi、OpenCode 可以作为其他 A 接入同一业务平台。

用户可以直接说“刚才又断了一次，你看看是不是昨天改的那块”。A 根据当前会话、工作区、资料和允许操作的范围理解并继续；必要时问具体缺项。无需先选择“故障定位”或写出正式任务描述。用户列举的答疑、开发、测试、设备操作和发布，是平台能完成的工作，不应直接变成固定首页流程。

A 的会话与 C 的长期工作不同。简单查询可以直接调用 B/E；需要长期运行、多人交接、人工决定或交付跟踪时，按共同契约进入 C。长期工作可以关联多个会话，后台执行也可以在 A 暂停后仍需 D 核对。

| 对象 | 自己保存和管理什么 | 用户或维护人员怎样观察、操作 |
|---|---|---|
| B 知识、证据与制品 | 来源、修订、关系、快照、证据和产物版本 | 查询与核对来源；查看原件和版本；导入、撤回、重建索引、备份恢复 |
| C 任务与协作治理 | 目标、依赖、持久运行、交接、授权、人工决定和完成准入 | 查看运行、等待和交接；调整目标；提出暂停/取消；处理人工决定和完成条件 |
| D 实际执行与资源 | 工作区、进程、SSH、浏览器、连接、租约、控制者和现场回执 | 查看同一现场；申请控制；停止与核对；排空 worker、清理残留和维护连接 |
| E 能力包与规则 | 工具/skill 的专业内容、方法、适用版本和验证记录 | 查看可用能力；加载到会话；检查、发布、停用或回滚方法版本 |

四个对象各有管理入口；A 还能在调用处直接打开相应记录。对象的管理界面不是四个新 agent，也不意味着每个对象必须独立部署。权限仍由 C 的规则及 B/D/E 的真实作用端共同执行，不能由 A 的按钮或模型输出授权。

## 方案 1：会话中心

左侧是会话与工作区，中间是 Agent 交互流和输入框，右侧按需打开上下文、模型输入、已加载能力及关联运行。顶部提供 A、B、C、D、E 的入口。工具调用能展开真实输入输出，并从原位置跳到知识、执行或方法记录。

适合把 A 作为日常工作入口，最接近用户熟悉的 harness。代价是复杂维护需要切换到对应对象页面。**这是我建议优先选择的 A 主界面。**

## 方案 2：双工作台

“Agent”与“平台管理”是两个区域。前者提供完整 harness 交互；后者明确分出 B/C/D/E。普通用户在 Agent 中工作，业务人员与维护人员按权限进入管理区；记录可以互相跳转。

适合团队化平台，人员职责和维护边界最清楚。代价是多一次区域切换。**如果维护与权限管理较重，建议在方案 1 的 Agent 界面外采用这种组织方式。** 两个建议分别是 A 的布局和整个平台的导航，并非将所有功能混在同一页。

## 方案 3：工程桌面

会话、代码、文件、差异、终端和浏览器在一个桌面中并排。B/C/D/E 可通过停靠面板打开，A 会话保持可见。用户可以一边阅读文件或查看设备页面，一边给 Agent 补充信息。

适合研发、测试和现场工程师。代价是窗口和上下文较多，小屏幕与非工程用户需要更简洁的模式。

## 方案 4：多会话控制台

多条 harness 会话并行显示状态，选中一条后进入详细交互。C 的长期运行与 A 的会话列表分开，避免把会话退出当作工作结束。每条会话有自己的工作区、上下文、能力与操作范围。

适合同时推进多项研发、测试或调查。代价是单会话的阅读空间较小，还需要清楚显示哪个会话正在等待人、哪个远端操作仍在运行。

## 方案 5：资源画布

主区域是工作区、文件、设备和浏览器等现场，A 会话停靠在旁边或下方。点击资源后，查看与之关联的资料 B、长期工作 C、实际执行 D、可用能力 E；完整管理仍有独立入口。

适合频繁切换代码、终端和浏览器的现场工作。代价是纯文字问答、需求分析和资料阅读不如方案 1 简洁，因此更适合作为专业模式。

## 五个方案共有的约束

自然语言不被强迫归类为预设工作。上下文可查看、补充和移除，能力加载可见；模型与工具实际输入输出可以展开。B 的版本查看不会悄悄改写 A 已使用的上下文，E 的会话加载不等于方法发布，暂停 A/C 不自动证明 D 已停止。

例子、截图和交互检查只能说明原型行为，不能证明完整 harness、后端鉴权或设备操作已实现。用户选择方案后，才据此修订界面实施范围；原产品目标、对象职责、安全要求及真值披露原则继续有效。
