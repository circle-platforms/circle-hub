# 关键函数需要把哪些事情做好

这份说明讲的是几个容易影响结果的地方，以及我们希望相关函数怎样工作。它保留当前代码的差距，不表示本轮已经修好或重新测试。具体签名和位置可以在[函数目录](../reference/README.md)中核对。

## 创建任务之后，要能继续找到它

创建一项长期任务时，平台需要把目标、重复提交的信息和待发送通知一起保存。保存成功后才能告诉用户已经受理。DurableTaskService.acceptTask 负责这件事，已有 PostgreSQL 实现和独立的[本地记录](../p3-1-persistence-record.md)。

读取和修改任务时还要检查用户是否能访问这项工作，以及正在修改的是不是当前版本。多人同时修改或旧输入迟到时，应当明确拒绝冲突，不能悄悄覆盖别人刚做的事情。

## 改进度不能绕过完成检查

TaskService.transition 和 DurableTaskService.transition 用来改变任务进度。进入“已经交付”必须检查结果是否齐全，不能只因为这一步状态转换被允许，就跳过去。

deliver 负责检查交付。需要的项目应当来自这项工作的完整要求，相关证据要真的能找到，用户的决定要对应当前材料，外部操作不能还处于结果不明的状态。

当前内存版本主要检查传入清单里的标记。PostgreSQL 版本增加了空清单、登记引用和角色检查，但仍需检查这些引用的内容，以及不同产品的完整交付要求。登记了一个引用，不能直接推出产品结果正确。

## 操作请求重复或断线时，不能重复修改设备

OperationService.submit 登记一次操作，并处理重复请求。要比较实际请求的目标和材料，避免同一个标识被用来执行另一项变更。已有内存实现还不能单独证明进程间和重启后的保证。

writeGuard 要在实际发送动作前检查许可是否仍有效。LeaseManager.acquire 负责取得资源使用权。过期的操作者不能继续发送，新的操作者也不能因为旧许可到期就假定远端已经停止。

## 请求停止之后，要知道实际停没停

confirmStopped 当前可以更新操作记录，但没有要求提交实际停止的观察。正式使用时，需要执行端检查进程、会话或远端操作，并记录仍然存在的影响。

reconcile 用来处理结果不明的操作。平台根据同一次操作的现场证据确认实际结果。连接断开、客户端超时或一段说明文字，都不能代替这个核对；核对之前不直接再发一次写命令。

## 资料读取必须对应正确的产品和版本

KnowledgeStore.getRevision 从指定项目范围取资料。createSnapshot 把一组资料修订固定下来，供同一次任务持续使用。资料被撤回、版本变化或权限不足时，应当根据实际情况处理。

现有代码是最小知识存储。完整的真实身份检查、检索和发布还要继续建设，不能从这几个函数存在就推出知识库已经完整。

## 生成报告或工作簿，不等于业务已经通过

compileMindmap 把当前支持的主题树或内容 JSON 转成工作簿。它需要保留节点来源和不能解释的内容。当前只处理结构，真实脑图版本和完整业务编译范围仍要另外确定。

ReviewService.review 按已声明的几项规则评审用例。问题要能定位到原文，修改以后按新版本再评审。它不能把没有发现规则内的问题，解释成所有业务逻辑都正确。

ScriptedAssessor.assess 用来跑通判断结果的传递。没有矛盾不等于证据真正支持结论，真实模型也要另外校准。方法只说明自己检查过的范围，并保留证据不足或不能判断的结果。

## 下一步怎样完善

对每个公开或会产生作用的函数，把用途、输入、实际行为、失败处理和使用者写清楚，再用独立的例子检查。优先保护完成判断、实际写入、停止和结果核对这些入口。对应工作已经放在[函数说明任务](https://github.com/qingshanfeihu/infosec-platform/issues/5)中。
