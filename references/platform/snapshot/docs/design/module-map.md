# 代码怎样分工，哪些部分相互依赖

当前仓库把相关代码放在一个项目中。后续是否拆成多个包或服务，要看谁使用它、怎样发布、是否需要隔离，以及连接和进程能否独立管理。这轮不搬动业务代码。

## 公共部分集中维护

各部分使用同样的任务、操作、错误和证据格式。格式检查、标识和基础工具应该集中维护，避免不同产品各写一套，最后对同一结果给出不同解释。

现有公共格式在 contracts 中。部分基础工具暂时放在 platform 中。完善代码结构时需要把公共工具与任务、执行服务区分清楚，避免知识库或产品方法为了取一个结果类型而依赖整个任务系统。

## 任务、资料和执行分别负责自己的数据

知识库保存产品资料、来源和报告。任务服务保存工作目标、进度、用户决定和交付要求。执行服务保存实际连接、进程、操作和资源占用。

它们可以在同一个程序里运行，但要通过明确的调用配合。执行服务报告现场发生了什么，任务服务决定这项工作接下来怎么走。其他部分不能直接改任务状态来宣布完成。

平台已有内存参考实现，随后加入了 PostgreSQL 任务实现。两者的用途和保证分别说明，不能用一份旧测试记录覆盖整个系统。

## 专业方法可以组合，也要说明适用范围

问答、评审和编译代码属于专业方法。具体产品的命令、页面和判定规则也放在相应方法中。公共任务系统负责安排工作，不把某一种产品的命令写成所有产品都要遵守的规则。

一种方法需要资料或实际操作时，通过知识库和执行服务取得。方法不能自带另一套设备租约、长期任务或凭据管理。

## 测试工具与正式执行分开

模拟设备、本地测试站、协议测试服务和校准程序用来检查平台。这些工具能把问题稳定复现，但不能成为正式产品操作的替代后端。

生产模块不能依赖某份样本里的预设答案来证明业务正确。接入真实产品后，要检查实际目标、实际作用和清理结果。
