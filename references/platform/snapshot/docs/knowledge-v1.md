# 产品知识库 V1 设计基线

日期：2026-10-10。

状态：按用户本轮“先定下来知识库设计方案”的要求形成的 V1 设计基线。用于接下来逐项实现；尚无运行中的新知识服务。本文件确定架构、数据职责、处理流程和验收边界，具体包、参数与部署配置在实现议题中确定。

范围依据：[ADR 0001](decisions/0001-project-direction.md)、[ADR 0002](decisions/0002-product-knowledge-scope.md)。本轮收敛记录见 [ADR 0003](decisions/0003-knowledge-v1-baseline.md)。

后续平台能力盘点明确本服务属于 B（产品知识、证据与制品），与 A 会话、C 任务、D 实际执行和 E 业务规则通过 F 共用契约协作，见[运行对象 V1](object-boundaries-v1.md)。本页六类知识记录与五类运行职责是不同维度，数据与发布基线保持有效。

## 1. 核心原则

程序承担在已绑定输入、规则和范围内可以确定、可复现的工作；Jev/LLM 承担语义理解和不确定判断。模型判断保留为带依据的判断，不因格式正确、置信度高或发布成功而自动变成产品事实。

三个例子：

- 原句是否存在于某份固定字节的资料中，程序可检查；原句是否足以支持某个产品结论，需要语义判断。
- 指定 XML 快照中是否存在某节点、参数结构是什么，程序可解析；该命令是否满足用户意图，需要结合资料与语义。
- 报价记录中明确的金额、币种和有效期可按已知格式读取；某客户是否满足条款，需要条件和依据，缺条件时保留未知。

结构化不是知识真实性证明。程序检查也必须说明检查对象与范围，不能把“引用存在”扩大为“结论正确”。

## 2. 产品级范围

覆盖产品、型号/SKU、功能与限制、架构、代码、测试、缺陷、商务/许可/报价、Web/CLI/API 操作、维护经验与友商资料。新领域可以注册新的对象和声明 schema。

保留原始资料目录与章节树、产品主题视图、命令能力树、代码结构、测试覆盖等独立视图。CLI/XML 和 footprint 是其中的来源和投影，不能作为全库唯一分类树。

## 3. 服务与存储结构

- 新建 TS 知识服务及后台处理 workers，Circle 和其他客户端通过共用契约接入。
- PostgreSQL 保存对象身份、声明、关系、版本、判断、发布记录与索引元数据。核心身份和引用使用关系表；领域扩展使用版本化 JSONB schema。
- 对象存储接口保存不可变原件、转换结果、图片、原始代码/XML 快照和证据产物。内容以 SHA-256 校验；JSONB 不承担原始字节保真存储。
- V1 在 PostgreSQL 中表达知识关系，不额外引入专门图数据库。
- 精确索引、全文索引、关系索引和可选语义索引均为可重建投影。正文召回需要支持中文、英文、产品名、型号和代码/命令词，分词器及查询参数用真实资料验收后固定。

语义召回是补充入口；查询执行者可以使用精确命中，或根据问题启用多路召回。索引技术可以演进，知识身份和证据契约保持稳定。

数据库、对象存储是外部基础设施；本项目的业务逻辑、处理器、工具、MCP 与验证脚本用 TS 全新实现。这里没有沿用旧 Python 自研运行链。

## 4. 六类核心记录

| 记录 | 职责 | 关键内容 |
|---|---|---|
| SourceRevision | 一份来源的固定修订 | 稳定 sourceId、revisionId、原件哈希、来源路径、发布/采集时间、权限、解析器版本 |
| Evidence | 可以核对的出处或观察 | SourceRevision、章节/页/行/字节范围、原文或产物引用、原始与转换位置映射、运行身份 |
| Entity | 产品相关对象的身份 | entityId、kind、名称、别名、所属产品/厂商、版本化属性和来源 |
| Claim | 属性、规则、行为或对象关系声明 | subject、predicate、value/objectRefs、条件、适用范围、Evidence、来源性质 |
| Assessment | 对候选或声明的判断记录 | 输入引用、问题/规则版本、模型或程序身份、结果、概率分布、检查范围、未决内容 |
| KnowledgeSnapshot | 一次可复现的发布 | 来源和记录修订集合、索引依赖、schema/处理器/模型版本、清单哈希、检查报告 |

关系作为 Claim 的一种形式存储。例如“组件实现功能”“型号支持功能”“测试覆盖行为”“缺陷影响版本”。关系有自己的出处与适用范围，不因连成图就成为已证实事实。

对象稳定身份与内容哈希分开。相同字节可共用 blob，但不同业务对象不因为文本相同而合并。修订不覆盖原件；别名对齐保留原对象和映射依据，错误关联可以撤销。

## 5. 范围和状态分别表示

适用范围按内容需要表达：厂商、产品、型号、软件版本、构建、硬件、许可、环境条件、时间、渠道、客户与币种等。明确的范围可机械过滤；需要语义解释的条件保存为条件声明，不能默认成立。

不要用一个 verified 字段覆盖不同层次：

| 维度 | 表达的事情 |
|---|---|
| 机械检查 | schema、哈希、引用、权限、解析等具体检查 passed/failed/not_run |
| 来源性质 | 文档声明、代码/配置结构、运行观察、人工确认、模型推断等 |
| 语义判断 | 选项和概率，以及支持/反驳/未涉及/证据不足等判读 |
| 外部验证 | 哪个测试或操作在什么环境下观察到何种结果 |
| 发布状态 | 草稿、候选、已发布快照或撤销/被替代 |

历史运行观察可以支持经验，但不能自动定义 expected。友商宣称、产品规格、现场测量和商务报价也要保留各自角色，不能混成无来源的事实。

## 6. 知识生成：程序骨架与语义步骤组合

```mermaid
flowchart LR
  A[采集固定来源修订] --> B[程序解析与结构索引]
  B --> C[模型理解与候选关联]
  C --> D[程序核对出处和结构]
  D --> E[语义复核与冲突记录]
  E --> F[候选快照检查]
  F --> G[原子发布 stable]
```

### 程序负责

- 采集、权限、原件保存、哈希和修订身份。
- 已知格式的 XML、JSON、表格、目录、代码符号和精确字段解析。
- 源片段存在性与位置核对、引用对象存在性、schema 与字段格式校验。
- 依据明确 ID、哈希和变更依赖去重、增量生成、失效标记。
- 来源与对象范围的精确过滤、索引构建、版本差异、发布清单和回滚。

### Jev/LLM 负责

- 原文涉及哪些产品主题、对象和行为。
- 别名是否同指一个对象、术语之间是什么关系、哪些内容应跨领域关联。
- 段落中的主张、条件、限制和潜在冲突。
- 用户意图、候选相关性、引用语义是否支持结论。
- 需要较长推理的架构、故障、测试或比较问题。

程序先提供来源、已知结构和候选对象。模型可提出新对象或关系，但需要保留引用，经结构核对后作为候选写入。不能因已有候选不覆盖新概念而强制归类；也不能用关键词规则代替语义裁决并丢弃知识。

## 7. 已有资产的接入

| 来源 | 程序可取得的结构 | 模型参与部分 |
|---|---|---|
| 手册与产品/架构资料 | 文件、章节、表格、原文位置、版本身份 | 主题、主张、条件、架构与功能关系 |
| XML 命令树 | 节点、参数、模式、函数标识和快照身份 | 与功能/操作意图的联系；跨版本语义差异 |
| 手册 catalog | 签名、取值、示例及其原文引用 | 规则含义、主题和支持程度 |
| footprint | 已有节点、字段、出处、观察和有效范围 | 重解释关联与条件，不能仅因旧字段写 verified 就升级可信度 |
| 代码 | AST/符号、路径、提交、静态引用 | 实现职责与产品行为的联系；静态图不能替代运行行为 |
| 测试与运行资料 | 用例、步骤、判据、结果、产物和运行身份 | 覆盖目标、结果充分性、问题与因果假设 |
| 商务/型号/报价 | 表格、明确字段、时效与授权信息 | 适用条件、客户需求匹配、产品比较 |
| Web 操作与友商资料 | 页面或文档修订、结构、流程记录 | 概念映射、动作意图、相似性与差异 |

原有来源统一有助于收集与追踪，不代表文档声明、能力结构、商业条件和运行事实具有同一验证方式。具体 XML 为资料树时按 SourceRevision/章节结构接入，为命令树时按能力结构接入。

## 8. Jev 的位置

Jev 处理可限定答案的语义小判断：实体对齐、候选分类、相关性排序和来源支持判断。独立问题可在同一份状态上批量评估；依赖前一步才能取得新证据的问题分步执行。

精确解析和命中不需要模型。开放抽取或长推理交给通用 LLM；程序再核对返回的引用和结构。模型接入使用适配器，保存具体模型、问题、候选与输入身份，不把 latest 别名当成可复现版本。

模型输出与 Assessment 分开存储，包含 Choice/Score/Noul 的真实返回语义。confidence 是分布统计，阈值必须用本产品样本校准；不会因为数值大就赋予事实权威或操作权限。

只有输入、问题、模型版本和范围未变的判断才可复用。证据更新会触发受影响的判断和投影重新检查，不以生成时间戳代替内容身份。

## 9. 索引与查询

1. 从用户问题和当前产品上下文形成查询；明确的对象 ID、版本、时间与权限由程序处理。
2. 通过精确字段、全文、多种结构视图和可选语义召回形成候选集合。
3. Jev 判断候选相关性、是否回答问题及是否支持某个声明；保留“不匹配/证据不足”。
4. 在同一快照和访问范围中扩展相关对象，补齐必要的章节、条件和反例。
5. 程序返回可消费的证据包；LLM 可在其上解释，用户或其他 agent 可继续核对。

没命中只表示当前查询和覆盖范围内没有命中。确定的缺失结论，需要完整闭集来源和相应检查，不能从语义搜索空结果推断。

中文正文、英文术语、型号、代码和命令的查询分别验收。格式或领域差异不应造成某类资料静默缺席。

## 10. 查询证据包与协作

候选共用契约：snapshotId、queryContext、entities、claims、evidenceRefs、assessments、conflicts、unknowns、coverage。

coverage 说明检索范围、采用的来源和尚未取得的依据；只表达当前用户可访问的范围。查询、排序、内容支持与实际验证分别呈现，避免程序拿相关性分数作为真假值。

用户、agent 和程序可以提交问题、纠正、候选关联或补充证据。它们形成新的 Claim/Assessment 修订，不直接改写原文或覆盖历史结论。多个 agent 对同一材料的同意不能充当多个独立来源。

TS 共用类型与运行时 schema 支持这些交接；原文和证据可以按 ID 展开，避免模型只能看到摘要或默认第一页。

## 11. 发布、消费与回滚

发布链按数据依赖运行：来源修订 → 解析/结构结果 → 模型候选 → 核验与判断记录 → 索引 → candidate → stable。

发布时程序检查：

- 来源、对象、证据、判断和索引引用闭合，哈希与 schema 正确。
- 需要的投影与其输入/处理器版本相匹配；失败步骤和缺席来源显式披露。
- 权限和适用范围能够执行，原件和展开证据可取得。
- 代表查询的已知行为通过回归；目标依赖改变时相关检查已刷新。
- 清单包含这次实际生成的内容和未决/冲突的状态，不能用模型自报完成替代。

发布快照是不可变的。stable 指针用事务与预期旧值进行原子切换；并发发布不能覆盖刚发生的回滚。同内容重复发布是空操作。回滚切换指针，不重写旧快照。

stable 说明包完整且通过发布契约，不说明全部语义判断或全部产品行为正确。未决知识可以带状态进入可检索快照；语义缺口不会被补造为事实。

任务消费时固定 snapshotId。新资料默认进入新快照，进行中的任务需显式选择刷新，并检查原结果是否仍有效。服务器、Circle、其他 agent 和程序按同一身份展开证据。

## 12. 对外能力

逻辑能力：search、getEntity、getEvidence、getRelations、compareSnapshots、submitAssessment、buildSnapshot、publishSnapshot。

读取、提交反馈、构建与发布是不同授权范围。HTTP/SDK/MCP 的具体名称与 wire schema 在实现阶段统一生成；客户端不各写一份业务逻辑。Circle 扩展或类似 mod 的事件处理器可组织查询和展示，发布与权限规则由知识服务执行。

## 13. 实现拆分

1. 共用 schema、来源修订、原件/Evidence、身份与 scope。
2. 目录/手册/XML/catalog/代码/表格等 TS 解析适配器，保留结构与映射。
3. Entity/Claim/Assessment 存储、Jev/LLM 适配与候选处理。
4. 精确/全文/关系检索和证据包；用跨领域问题检验覆盖。
5. 快照、依赖失效、candidate/stable 发布与回滚；再接 Circle 与协作入口。

每步使用隔离样本，不改现有项目和生产资料；迁移、部署与模型调用范围另行明确。

## 14. V1 验收

- 覆盖产品/型号、架构/代码、测试、商务/报价、操作与友商问题，不能只以 CLI 通过验收。
- 原句可展开、版本和权限过滤正确，裁剪和转换不破坏应保留的证据。
- 错误别名、跨版本冲突、过期报价、部分资料缺失、不同渠道概念相似等反例如实处理。
- 更新输入、处理器、问题或模型后，受影响索引/判断按依赖失效；其余结果可复用。
- 发布失败不切 stable；并发切换、回滚、重复发布和任务固定快照行为可复现。
- 分别记录召回遗漏、关联错误、语义判断错误、权限/版本错误、延迟和成本。真实产品资料上的模型阈值与质量目标在首批评测中确定，不能套用 cookbook 数值。

## 15. 依据与边界

- [Claude Code Mods](https://code.claude.com/docs/en/plugins/mods/overview)：JS/TS 事件处理可组合程序与模型能力；没有采用其完整插件 API 作为本项目标准。
- [TypeSafe 构建指南](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)：程序组织流程，模型做限定语义判断。
- [PostgreSQL JSON](https://www.postgresql.org/docs/18/datatype-json.html)：关系与 JSONB 共存；原始字节独立存储。
- [InfoTest 与发布过程调研](research/knowledge-design-basis.md)：沿用经验，全 TS 新实现。

设计固定的是数据职责、权威边界、流程、发布和验收，不是宣称已有生产能力。分词器、语义召回实现、模型阈值、SDK/framework 版本和部署规模在逐项实现中通过实验固定。
