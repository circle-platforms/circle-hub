# 五类对象的基础验证与全功能迁移计划

日期：2026-10-10。**状态：基础验证与迁移的计划基线。** 最初按用户要求只做计划；后续 P1/P2 已有有限范围执行记录，见 [P2 计划](p2-vertical-slice-plan.md)。计划条目不因已有代码而自动通过。本轮只检查文档与讨论 C/D/E，不实施或重跑业务测试；当前边界见 [C/D/E 讨论稿](cde-implementation-discussion-v1.md)。

配套：[运行对象](object-boundaries-v1.md)、[同类项目经验](research/comparable-platforms.md)、[harness 适配](harness-adaptation-plan.md)、[历史能力清单](research/inventory/capability-catalog.csv)。

产品范围覆盖 InfoSec 全产品线，负载均衡/APV 作为首批通用抽象与验证的实践基础，见 [ADR 0010](decisions/0010-product-line-scope.md)。下列 APV 样本保留；产品特有语义通过能力包与适配器扩展，某条产品链通过不能推及其他产品线。

## 1. 要回答的两个问题

1. 五类职责能否组成知识问答、APV 操作、Web 登录、用例评审、人工脑图编译为 Excel 的完整闭环，同时支撑长任务、恢复和 harness 替换？
2. 在不运行或复用旧项目代码的情况下，新 TS 实现能否逐项覆盖已决定保留的历史功能，并修正已确认的旧缺陷？

问题一是基础验证，问题二是完整迁移验收。五条 happy path 或 403 条静态分类不能回答问题二。

## 2. 新建与参考边界

2026-10-11：[ADR 0028](decisions/0028-circle-server-split.md)允许按版本复用 Circle 的 TS harness/界面基础组成 server，默认连接插件留在 Circle。这不取消下列针对旧 InfoTest、compile、Python 运行链的限制，也不宣布参考实现已迁移。两端兼容和同步验收见[工程计划](circle-server-plan.md)。

- Circle 作为已有通用 harness 使用，也可改用 Pi/OpenCode；平台 B/C/D/E 自研执行代码、适配器、验证器和 skill 脚本全部 TS 新写。
- 禁止复制旧函数、生成器或运行模块；禁止 vendor 旧引擎、启动旧 Python/server/gateway、由新工具转发旧生产实现，或要求旧 checkout 在运行时存在。
- 旧来源仅用于整理需求、公开/获准数据格式、行为契约、独立验收样本与已知故障。旧测试源码不整体搬入；新测试按独立行为要求编写。
- 可研究和使用成熟公共 TS 库及其公共 API；这是第三方依赖选择，与复用旧自研项目不同。版本、许可证和适用边界在对应实现议题确定。
- 验证新环境不挂载旧源码，不带旧项目 PYTHONPATH/venv/服务端点；记录依赖、镜像/构建、外部连接和子进程。检查实际运行链，不仅搜索 `import`。
- 原始业务资料按授权脱敏/固定版本，不进入设计仓库。固定样本身份是数据复用，不授权复用旧实现代码。

## 3. 五条最低功能链及归属

| 验证 ID | 场景与完整输出 | 五类对象协作 | 最低通过证据 |
|---|---|---|---|
| V01 | **产品知识问答**：针对产品/版本给出有据回答，冲突或缺失明确披露 | A 理解/呈现；B 来源/实体/声明/快照/检索；C 身份/任务；D 导入来源；E 检索与答题方法 | 每条事实性结论可回到固定 source revision/evidence；来源字节/范围、适用版本和引用正确；不跨租户；未命中不编造 |
| V02 | **APV 设备操作**：发现设备与版本，采集状态，执行获准变更/测试，核验并清理 | A 请求；B 规范/证据；C 准入/任务；D 租约/SSH/运行；E APV 规则与判据 | 目标身份、通道、实际收发和变更前后状态、操作/attempt/lease 与证据一致；执行成功与业务通过分别记录 |
| V03 | **Web 登录与操作**：实际登录，访问受保护页面/执行代表动作，可重放且能定位失败 | A 目标/视觉或接管；B 操作知识/证据；C 身份/任务/人工输入；D browser session；E 页面方法/TS 脚本/断言 | 独立 browser context、实际账户与权限、受保护业务结果、网络/截图/trace；错误密码失败；Cookie 串用被阻止 |
| V04 | **用例评审**：结构检查、规范与语义评审、问题定位、人工决定与再次评审 | A 交互；B SPEC/原件/Assessment；C 返工/人工响应；D 文件读取/worker；E 检查与评审方法 | 问题对应原用例节点/字段与固定规范，机械缺陷/语义建议/证据不足区分；未直接改原件；新修订重新核验 |
| V05 | **人工脑图 → Excel**：读原脑图，转结构化 case IR，经澄清/校验生成可读取的真实 `.xlsx` | A 澄清；B 原件/来源/制品；C 阶段/返工/收口；D 文件/worker；E 解析/重组/编译/工作簿规则 | 不漏/重复节点；节点→case→sheet/row 可追踪；命令/预期依据正确；新 reader 检查实际 workbook 与规范；Excel 生成不等于设备用例已通过 |

不是每条链都要新建五个进程或强行多 agent。对于简单问答，C 可只登记范围与结果；需要执行/等待/协作时进入完整任务生命周期。

## 4. 每条链的样本、边界与实验

### V01：知识问答

先用合成且人工核验的多版本产品资料，覆盖功能、CLI/Web 方法、架构/代码关系、测试、型号/商务/报价及友商资料，再用获准的脱敏真实样本。价格与商务资料要绑定时间/渠道/币种等范围，不硬塞进 CLI schema。

样本包括版本差异、同名不同产品、互相冲突的来源、来源更新/撤回、无答案、引用正文不支持结论、快照切换期间的长任务与越权检索。XML/catalog/footprint 只能按来源/转换规则形成知识，现场 actual 不能成为规范 expected。

程序核验身份、引用、哈希、范围与快照闭包；Jev/LLM 负责限定的语义对齐/支持性判断。脚本化判断只能验证协议与流程；语义准确率、错误确信和弃答行为需单独的人工标注集与真实模型实验。

### V02：APV 操作

先计划独立本地 SSH/HTTP fixture，验证真实协议收发与副作用；它不是把 executor 的结果写死成成功。随后才对指定专用 APV 设备做验收，记录型号、固件、拓扑、权限与指定通道。模拟协议通过不称 APV 真机通过。

样本包括身份/版本不符、只读采集、受控变更与清理、两任务抢占、过期 fencing、长输出/CRLF/分页/prompt、断连后已执行但回执丢失、取消后远端仍存活、重连核对。分别记录实际配置与需要时的独立业务流量结果。

SSH 与 Web 的维护能力逐步覆盖；用例要求验证某条通道时，不通过其他通道替代来宣称原通道通过。初始化、破坏性操作和升级等属于后续完整迁移/发布能力，不由一次 show 命令验收代表。

### V03：Web 登录、多模态与重复操作

计划创建全新本地测试站点和隔离 browser profile；先验证真实页面提交、账户与授权结果，再验证指定专用产品 Web。凭据只由可信执行环境注入，浏览器认证状态和敏感 trace 不入 Git。

三组对比：结构/DOM；结构+视觉；稳定参数化 TS 脚本。覆盖动态按钮、iframe/弹窗、页面刷新、会话过期、失败登录、下载和重复执行。安排视觉信息有意义的页面样本；只做普通表单不能证明多模态能力。图片理解使用合适的视觉模型，不能假定 Jev 可直接读图。

重复脚本用 TS Playwright Test 等候选原语，实现 pytest 所代表的参数化、隔离、断言、trace 与重复运行能力，不引入旧 Python 测试执行链。缓存/脚本复用绑定版本与前置条件；页面变化时保留失败，再探索修复，不能跳过断言变绿。MFA/验证码进入明确人工输入状态，不伪造成功。

### V04：用例评审

固定一个正确用例集和独立注入缺陷集：结构缺项、条件/步骤不一致、预期与 SPEC 冲突、版本不适用、来源缺失、含混或不可观测判据、覆盖遗漏及重复问题。单个 case 与批量、不同协议/算法/产品形态都要覆盖。

每个 finding 绑定输入修订、位置、规则或来源、影响和判断性质。机械检查应可复现；语义建议可保留概率与未知，由人工确认关键解释。修改产生新修订，原评审不能自动授权新版本；评审报告不是整个用例集正确性的绝对证明。

### V05：人工脑图编译

先确定获准样本的真实格式与版本，例如 XMind 原文件，并记录接受/拒绝范围；不将随意 JSON 提纲命名为“已支持人工脑图”。不同格式的解析器按 E 扩展；图片脑图另需 OCR/视觉及人工澄清。

验证树节点、笔记、关联、附件引用、重复 ID、多 sheet、中文与嵌套语义；支持范围外内容显式拒绝或报告未解释节点。人工表达中不确定的产品语义由模型建议/用户确认，确定的格式、节点身份、IR 与工作簿结构交程序。

从原节点到 IR 再到 Excel 保留映射，依据来源生成步骤/命令/预期。表头/工作表、单元格类型与旧约定以独立确认的输出契约为准；不能把新格式随意视作兼容。使用独立 reader/结构检查与人工抽验，覆盖截断、漏项、批次重复、返工后引用旧输入及重启后重复编译。

## 5. 长任务与更换 Harness 是共同验收

| ID | 实验 | 必须观察的结果 |
|---|---|---|
| R01 | A 退出、上下文压缩或进程重启 | C 的目标/阶段与 B 的输入/证据不丢失；D 现场存活可核对 |
| R02 | 设备/Web 操作执行后、回执写入前故障 | 恢复时按 operation 身份核对；不盲目重复副作用；无法确认保留 unknown |
| R03 | C/D worker 重启、重复/乱序通知 | 已完成阶段不重复推进；事件身份与租约有效；新实例不承接陈旧写入 |
| R04 | 用户请求取消/目标发生变化 | 区分请求、执行端收到、实际停止与残留影响；输入修订变化使旧完成/审批失效 |
| R05 | 等待人工澄清、其他用户或 agent 接管 | 可跨会话恢复 pending input；响应绑定请求/输入和授权；不强制共享私人聊天历史 |
| R06 | Circle → Pi → OpenCode | 同一任务、证据、资源与产物可继续；只更换 A 的薄适配，不重建 B/C/D/E |
| R07 | 原生 MCP/CLI 与增强 Tasks 路径 | 同样的操作与完成判据；没有扩展支持时显式走最低兼容路径 |
| R08 | 模型只说完成、伪造引用/回执或工具结果过期 | C 不凭 prose 收口；B/D 检查身份；缺证据保留未完成/未知 |

多 agent 是可选执行方式。后续比较单 agent、分工和独立复核，固定样本与预算，记录完成质量、耗时、成本和交接失败；没有测量结果不预设协作一定更好。

## 6. 验证层与未来回执

| 层 | 范围与不能越界的结论 |
|---|---|
| L0 静态设计/来源 | 当前已做分类与 source hash 校验；不证明新功能运行 |
| L1 契约/故障语义 | TS/runtime schemas、独立 scripted model 和协议客户端；不证明模型判断或实际 harness 可用 |
| L2 隔离端到端 | 真文件/新测试服务/本地协议/浏览器与重启恢复；不证明 APV 真机/产品 Web 兼容 |
| L3 真实 harness | 固定 Circle/Pi/OpenCode 版本与本地模型 gateway，验证实际调用/呈现/取消/接管；不能仅用通用 MCP client 代替 |
| L4 真实模型质量 | 固定模型/参数、人工标注集、预算和分布；机械通过与语义质量分别计量 |
| L5 专用产品环境 | 指定 APV/Web、版本/拓扑、实际业务效果；只对所测范围成立 |
| L6 全功能迁移 | 所有保留行为、消费者和缺陷回归均有有效证据；跨入口交付一致 |

每次回执计划包含 commit/build、依赖与模型版本、样本/输入/快照/规则身份、harness/transport、目标与 run/operation、观察/证据 hash、判据、pass/fail/unknown/skipped/not-run、清理与残留状态。耗时/token/成本另列，不能代替正确性。

不先编造一个统一准确率门槛：机械契约与身份检查有明确预期，语义质量按领域标注集设阈值；阈值在实验前冻结。跳过/未知不能计入通过。

## 7. 从基础链扩展到所有历史功能

[403 条清单](research/inventory/capability-catalog.json)是迁移入口，包含重复声明、镜像 skills、工程单元和范围外参考，不是 403 个独立业务功能。后续形成行为验收账本：

| 每条保留行为应补充的字段 | 用途 |
|---|---|
| source item IDs 与唯一行为 ID | 多个旧暴露位置可汇入一个行为；同一宏工具可拆成多个行为，不能因去重丢失消费者 |
| 保留/修正缺陷/替换机制/退出范围及理由 | 退出真正业务行为需用户确认；旧 bug 不作为新实现目标 |
| A–E 主责与协作、所有暴露/消费入口 | 确认只用五类职责能覆盖；F/G 归工程材料 |
| 输入样本、前后条件、可观察效果、边界与正确依据 | 固定独立验收，不只比较输出 prose 或旧 test 数 |
| 新 TS 实现与版本、harness 路径、证据/失败记录 | 逐条从 planned 到经验证状态，缺项不能计为完成 |

基础验证后继续覆盖：资料同步/发布与记忆共享、身份/登录/scope、拓扑/租约/初始化/设备批次、编译块语言与判据/返工/报告、文件和外部文档交付、Web 全流程、代码/Git/CI、需求与缺陷关联、产品构建/发布/升级/回退、观测与审计。Circle 的通用文件/代码/会话能力由候选 harness 提供并验收，不在四类后端重新造 harness。

“全部完成”需要：每个相关旧条目有处置，全部保留行为有当前证据，重复入口/权限/消费者闭包，获准真实样本与专用环境通过，已知差异及未实现项公开。归档/无关游戏等条目已有范围理由，不能借机把相关产品能力默默排除。

## 8. 后续逐项讨论顺序

| 阶段 | 要先确定的设计 | 未来实施与验收范围 |
|---|---|---|
| P0 当前 | 对象边界、同类经验、harness 适配和本计划 | 只提交文档/盘点资料；不安装依赖、不创建运行工程、不连真机 |
| P1 契约与样本 | 输入/身份/作用/回执、最低兼容面、五条原样本及输出契约 | 经讨论后才新建 TS schema/SDK 与独立样本检查 |
| P2 完整纵向链 | B 的知识 V1、C 的最小持久任务、D 资源/操作、E 首批方法 | 逐项实现 V01–V05 的 L1/L2；共同验证 R01–R08，不以 stub 代替关键对象 |
| P3 替换与语义 | 三 harness 固定版本、能力差异、真实模型与标注质量标准 | L3/L4；先有完整基础链，再评估额外协作与缓存收益 |
| P4 专用环境 | 设备/Web 目标、原样本授权、通道与清理要求 | L5；按明确授权执行，不使用知识主机冒充 APV/Web 测试环境 |
| P5 全部行为 | 迁移账本、产品研发/发布维护范围与交付准入 | L6；保留行为逐项完成后才能宣称全量替代 |

本计划没有工程排期或平台选型承诺。本轮文档/来源检查与未来功能验证分别记录；当前所有 V01–V05、R01–R08 和 L1–L6 均为未执行。
