# 项目里各部分做什么

这份说明用来读懂仓库。它介绍现有代码的用途，也说明这些代码与最终产品之间还缺什么。函数的原始签名和位置放在[核对目录](reference/README.md)，实际验证情况保存在对应执行记录中。

## 整体工作过程

用户给平台一个目标。入口理解并展示这个目标，任务服务把工作记下来，知识库提供资料，专业方法决定怎样操作和判断，执行服务连接设备或运行程序。得到结果后，平台检查结果是否满足要求，保存报告和证据，再向用户交付。

同一项工作可能要多次往返。查到新资料会影响计划；设备返回异常会触发调查；用户改变目标会让部分旧结果失效。各部分围绕同一个任务继续工作，而不是每调用一个工具就重新开始。

## 公共格式与基础规则

`contracts` 让各部分对同一件事使用一致的表达。它定义任务、操作、输入、结果、错误、证据引用和人工回答的格式，也规定哪些状态可以转到哪些状态。

其中的函数会检查引用有没有缺项、人工回答是否对应原问题、声明只读的操作是否真的没有声明写入，以及结果是否带着需要的证据引用。还有一些函数负责把状态转换成命令行退出码，或导出其他程序能使用的格式说明。

这些检查只解决格式和明确规则的问题。证据引用存在，不代表证据内容足以支持结论；格式通过，也不代表实际设备操作成功。

## 内存中的任务和操作

`platform` 是最早的公共参考实现。它把任务、实际操作、资源占用和证据登记放在一个包里，用来跑通流程。职责仍然分别由对应模块承担。

任务部分能创建任务、读取进度、等待用户回答、更新输入和检查完成清单。操作部分能登记一次操作、记录开始和结果、处理取消或结果不明。资源占用部分让操作取得、续期和释放使用权，并拒绝已经过时的写入。证据登记部分保存记录的身份、范围和内容摘要，方便其他步骤引用。

它还提供可控制的测试时钟、标识生成器和统一的成功/失败结果。这些帮助测试稳定复现。

这里的数据保存在内存中。它不能独自保证程序重启后仍能恢复，也不能仅凭内部状态证明远端进程已经停止。当前代码中的完成、停止和核对入口，还需要按正式使用要求补齐检查。

## 保存在数据库中的任务

`platform-pg` 开始把任务保存到 PostgreSQL。创建任务时，任务记录、重复请求记录和待发送通知一起提交；只有提交成功后才算正式受理。

它支持读取任务、改变进度、更新输入、提出问题和保存用户回答。多人同时修改同一项任务时，会检查是否仍在修改同一版内容。输入变化后，原完成清单失效。

交付前会检查清单、引用和签字人的角色。它还把需要通知其他部分的事情保存下来，再逐项发送，接收方处理重复通知。

这部分已有独立的本地验证记录，但还不能代表整个长期任务系统已经完成。真实身份接入、所有证据种类的检查、完整恢复和外部操作仍需要继续完善。

## 长期任务运行方式的比较

`runtime-eval` 是研究不同长期任务运行方式的实验包。它分别使用 PostgreSQL 任务记录与 Temporal，检查任务恢复、重复动作、运行中升级和操作结果等场景。两条路线使用各自的任务与 worker 脚本，便于观察实际重启和结果保存。

这部分用于选型比较，不是正式业务模块。已有记录描述本地场景结果；ADR 0022 已确认采用 PG 任务表路线；该实验包继续作为比较工装保留。本轮没有重跑这些场景，也没有把它们的历史通过数算成本轮沙盒结果。

## 实际进程与浏览器的执行管理

`execution` 开始把操作记录与真实子进程、浏览器连起来。控制部分登记操作、检查租约、处理取消和结果核对；进程监督部分启动 worker、记录运行信息并处理超时与停止。浏览器部分为任务创建独立上下文，操作本地登录站并读取页面的明确状态。

源码中已有本地测试和 P3-3 记录。这些是该模块的既有工作，本轮只检查源码并更新说明，没有运行它的测试。它尚不能由此证明真实设备兼容、复杂网络诊断、用户实时查看或所有远端停止方式已完成。独立沙盒里的网络与浏览器实验也没有替代本模块的验收。

## 真实模型评测的调用与判断

`llm-assessor` 为 P3-5 评测构造提示、调用模型并形成判断记录。预算跟踪器记录调用和用量，调用函数按现有策略处理传输错误与重试；判断适配器把输入和证据绑定到返回记录。无法解析或不在约定范围的结论转成弃答，预算超限向上报错。

当前调用通过外部桥接命令完成，不是已选定的 circle-server 生产模型接入。这里说明实际源码，未执行桥接、未读取密钥、未调用模型或重跑评测。语义准确率、预算策略与完整披露仍需各自验收；新增函数条目的归属只是待评审建议，静态登记不证明业务正确。

## 产品资料和知识快照

`knowledge` 保存一份资料的修订和内容摘要，记录它属于哪个项目、产品和版本，以及是否撤回。读取时按所属范围检查，避免把另一个项目的资料混进来。

它还把一组资料修订固定成快照。某次问答或测试可以使用指定快照，后来新资料加入时，原任务仍能知道自己用了哪一版资料。资料被撤回后，读取和答题时需要重新检查它的状态。

目前这是最小实现。完整知识库还要处理更多资料形式、对象关系、检索、发布和回滚。

## 怎样记录 AI 或程序的判断

`assessor` 为判断方法提供同一种结果形式。每次判断都要说明使用的方法、输入和证据，以及支持、反驳、冲突或证据不足等结果。

当前默认方法是按规则工作的程序。没有证据时不作支持判断，多份资料数值冲突时保留冲突。它用于检查流程能否正确传递判断结果，不能当作真实模型的质量证明。

以后接真实模型，可以沿用结果形式，但仍需记录模型版本并单独测量判断质量。

## 产品知识问答

`chain-v01` 把资料读取、产品和版本筛选、信息抽取、判断与答案登记连起来。它尽量给出可找到来源的答案，遇到冲突或没有依据时明确说明。

当前抽取方法只覆盖样本涉及的几类指标，例如连接数、会话超时和地址池。相关函数会识别问题中的指标或产品名，从资料中提取数值和原句，再交给判断方法。另有校准程序把结果与固定样本比较。

这条问答流程是一个小范围的参考，不能据此说任意产品问题都能回答。

## 用例评审

`chain-v04` 先把 Markdown 用例拆成可处理的条目，再按已声明的几项规则寻找问题，保存位置、严重程度和判断记录。

当前规则关注归属/权限检查、关键操作的异常分支、凭据明文和前后矛盾。评审报告还要经用户确认才能交付。修改了用例后，需要针对新版本再检查。

这里也有校准程序，用正确样本、缺陷样本和修订样本检查规则表现。规则没有发现问题，只能说明在它检查的范围内没有发现问题，不能证明整个用例完全正确。

## 脑图转 Excel

`chain-v05` 接收主题树或 XMind 的内容 JSON，先把它们转换成同一种树，再按约定把节点编成表格行，生成工作簿。

它记录哪些节点无法解释，无法全部处理时把遗漏写出来。生成后还能重新读工作簿，检查表名、表头、行和说明信息。标题整理、内容摘要和节点遍历等小函数帮助保持输出一致。

当前处理的是结构转换。真实 XMind 文件的版本范围、完整业务用例、命令和预期生成，还没有因此得到证明。

## 模拟设备与设备操作流程

`apv-fixture` 提供一台内存中的模拟设备。它能打开和关闭会话，读取、暂存、提交和回滚配置，还能模拟回执丢失、身份变化、版本冲突和延迟。

驱动部分把这些动作接到平台的操作记录上。它检查设备身份，发现身份变化就停止后续写入。提交结果不清楚时，先读取设备状态来核对，不直接再提交一次。场景程序检查正常变更、丢回执、版本冲突和身份变化，并检查会话和暂存内容有没有清理。

它帮助我们检查设备流程，未连接真实 APV，也未证明 SSH 的实际通道行为。真实 SSH 和产品现场要另外验证。

## 本地登录测试站

`test-site` 提供一个本地 HTTP 网站，用来检查登录、失败计数、锁定、验证码、退出和会话失效。

客户端负责发送 HTTP 请求和保存测试 cookie。登录驱动把账号和验证码的待输入请求接到任务中，再根据页面中的明确状态标记判断结果。场景程序检查错误密码、账号锁定、验证码过期和旧会话残留。

这部分的 HTTP 驱动直接发送请求；后续 `execution` 的浏览器 worker 已另外接入本地测试站。不同记录的验证范围分别保留，不能据此说用户实时查看、视觉理解或真实业务站点已经验证。

## 通信方式的测试服务

`server-stub` 是一个受脚本控制的测试服务。同一份输入可以通过 MCP、命令行或 HTTP 调用，检查三条入口是否返回同样的业务结果。

它可以模拟立即完成、慢任务、等待回答、目标失败和丢回执，也能保存和恢复测试状态。它的辅助函数负责整理请求、状态、错误和下一步提示。

这是协议试验台。正式产品不能把它当作拥有真实权限、持久任务和设备操作能力的服务。

## 外部入口的接入验证

`harness-adapters` 保存接入验证用的脚本化模型端点和驱动材料。模型端点按预先写好的计划发出工具调用，记录请求，用来检查固定版本客户端怎样传递工具、输入与结果。

P3-4 另有三入口的局部运行记录，其中 Circle 使用 loader 路径，平台任务由 stub 的状态文件承载。它不能证明全屏 UI、真实模型质量、PG 业务服务全链或用户实时查看已经完成。本轮只读取源码与记录，不重跑这些实验。

## 文档怎样读

项目首页介绍产品。平台总说明解释整体工作方式。这份文档说明代码。设计文档记录接入新产品、组合工作、模块和函数应该怎样完善。执行记录保存某次检查的输入、环境、结果和限制。

具体源码、签名和摘要放在核对资料中，需要追查时展开。它们帮助验证说明是否对应真实文件，不承担产品介绍的工作。

## GitHub 怎样安排工作

总任务把平台建设连起来，子任务分别完善产品接入、能力组合、用户交互、函数说明、代码分工、验证和开发流程。需求先讲用户问题，设计讲怎样解决，代码变更讲实际改了什么，验证讲怎样知道它有效。

现在的任务索引用来组织设计和开发准备。现有实现仍按原来的计划推进，不能因为新建了一项 Issue 就宣布功能已经完成。

## 前端工作台

前端通过 `Workbench` 注入宿主、数据与插件列表。注册器检查插件标识、页面、依赖与接口版本，按启用状态组合路由和会话组件。原来的集中管理页已拆成独立模块。停用插件保留记录，页面出错时显示局部错误，并保留其余界面的操作能力。当前插件只负责第一方界面组合，Circle 的真实连接、动态安装与第三方代码隔离仍需单独完成，见[插件设计与边界](design/pluggable-workbench.md)。

`workbench-ui` 是实际可构建的 React / TypeScript 前端。左侧切换会话，中间与 Agent 工作，侧栏查看上下文、文件、终端和浏览器。平台管理中分别查看知识、长期工作、执行资源和能力方法。自由输入不自动套成固定流程，A 的会话、C 的工作和 D 的执行各有状态。

页面通过 `WorkbenchGateway` 使用数据，通过 `PlatformBridge` 使用文件选择等宿主能力。当前只接本地预览适配器，保存草稿、消息、引用和请求记录；它没有运行真实 Agent，也没有后端鉴权或设备连接。B 的修订查看不会改写已有引用，E 的会话加载不会发布候选方法。

浏览器检查覆盖会话保存、跨对象边界和不同角色的界面操作，详情见[前端验证记录](validation/workbench-ui-20261010.md)。后续要独立完成服务接入、真实流事件、权限强制路径和桌面宿主。页面可运行不表示这些系统能力已经完成。
