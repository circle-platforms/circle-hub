## 长任务的生命周期

需要支持目标澄清、计划、执行、观察、验证、重新规划、等待、恢复、交付或带原因停止。聊天结束不等于业务任务完成。

重点研究：

- 上下文耗尽、模型切换、进程重启后，哪些状态可以继承，哪些必须重新核对。
- 用户中途改变目标后，如何调整剩余工作并处理已发生的影响。
- 等待构建、远程任务或人工反馈时，如何由事件唤醒，减少无意义轮询。
- 如何根据产物和环境变化判断有效进展，识别重复失败并改变策略。
- 如何限制预算和重试，同时区分“停止当前策略”和“整个任务没有可行方案”。

恢复时应检查外部操作是否已发生。操作超时且结果不确定时，需要核对或显式保留未知状态；不能一律重新提交。预算、基础设施错误、业务失败和因果归属分别记录。

## 循环的不同类型

| 类型 | 需要的机制 |
|---|---|
| 生成—验证—修复 | 输入和判据绑定、反馈、修复范围、收敛与停止条件 |
| 批量重复任务 | 单项身份、并发与资源控制、部分完成、失败子集恢复 |
| 定时或事件触发任务 | 外部触发、独立运行身份、唤醒、去重、权限与范围 |

以上都是能力方向。不能把所有工作强制编排成同一套固定业务流程。

## Web 操作

研究四种操作方式的组合：网站声明的工具或获授权 API、DOM/可访问性树、截图与坐标操作、生成的稳定脚本。

研究问题包括何时补充视觉观察、何时重新定位、何时将稳定动作批量执行，以及脚本适用条件变化时如何停止复用。需要覆盖多页面、frame、下载、登录状态、动态页面与人工接管。

重复 Web 脚本的自研部分使用 TS。先前提到的 pytest 是重复执行与验证模式的例子，不是保留 Python 新实现的决定。

## 设备与通道

区分两个契约：

- 维护操作：按目标和授权选择合适的 API、CLI 或 Web 路径。
- 通道测试：明确指定被测路径，并保留该路径的输入、输出与行为；不能绕过 Web 或 CLI 后宣布该通道正常。

设备、浏览器会话、工作区和流量发生器都需要所有权、占用、冲突处理、释放与恢复规则。共享依赖改变时，原验证结果是否失效必须重新判断。

以负载均衡产品为首批场景，应分别观察管理接口接受、配置变化、运行状态、实际业务流量，以及性能和兼容性结果。其他 InfoSec 产品线沿用操作与证据机制，具体业务观察和判据由各自产品能力包定义。

## 操作经验复用

候选循环：探索 → 操作 → 验证 → 提炼参数化程序 → 在新任务中复用 → 失效后重新探索。

可复用经验需要记录目的、前置条件、输入、权限、适用版本、后置验证、失败与失效条件。一次成功轨迹不足以证明泛化能力。复用的收益要和额外记录、检索、验证成本一起评估。

## 协作方式

建议先以一个任务负责人组织执行，按需增加研究、实现、验证等角色。以下是提案，不是固定团队配置：

| 协作 | 用途 |
|---|---|
| 人与 agent | 补充需求、处理关键分歧、调整方向、操作接管 |
| agent 与程序 | Agent 选择行动，确定性工具完成执行和检查 |
| agent 与 agent | 并行研究独立问题、隔离上下文、独立复核 |

协作交接依靠任务、产物、证据和明确范围。共享设备或工作区的写操作需要协调。多个模型意见一致不自动构成事实证明。是否增加角色，以相同预算下的效果和成本实验决定。
