## 讨论经过

1. **基础能力与研究方向。** 用户提出 Circle 的基本功能至少应与 Pi 对齐，并希望联网研究企业级 harness，重点加强循环任务、长任务和 Web 操作。Excel 编译、用例评审、多模态操作和可重复 Web 脚本被用作例子。
2. **纠正过窄的理解。** 用户强调要研究和探索能力方向，不希望 Circle 仅与其他 harness 大同小异，也不希望讨论只围绕几个固定业务列功能清单。
3. **明确产品领域。** 目标是网络安全产品、尤其负载均衡产品的操作、维护、开发、测试等完整敏捷研发流程，产品迭代与维护是 agent 的主要目标。
4. **明确完整范围。** 包括用户问题答疑、需求开发评审、bug 定位修复、测试分析与单元测试、开发发布与版本维护、Web 操作定位、产品 CLI 命令开发定位。
5. **讨论机制分工。** 用户认可部分内容适合写成 skills，但提出核心研究问题是 harness 平台如何划分类别，以及如何开发 MCP、tools 和 hooks。
6. **要求向已有工程取经。** 用户提出应研究 InfoTest、compile skill 和 server，从实际工作中学习。随后进行了本地源码与候选工作树的只读检查。
7. **讨论最终产品形态。** 用户询问最终应建设知识库、设备 server、一个或多个 skills、Circle，或其他协作方式。形成了多个逻辑组件配合、按需多 agent 的架构提案，尚未确定部署划分。
8. **明确全 TS 新建。** 用户纠正“沿现有项目修改”的建议，明确除了 Circle，其他项目和代码全部 TS 重写。旧工程定位改为需求、经验、数据和验证参考。
9. **检查知识雏形。** 用户授权 SSH 只读查看内部主机。观察到原始资料、转换结果、分类分发目录、三版本手册与结构化 catalog、文件管理服务。检查结束后退出 SSH，没有修改文件、配置或重启服务。

11. **开始知识库议题。** 用户提出 Jev 的结构化判断能力为用户/agent、agent/程序、agent/agent 的沟通与快速迭代提供新空间，并强调现有统一来源的产品资料、footprint 和 XML 等结构需要正确索引。

14. **全面盘点能力归属。** 用户要求完整调研名下项目，把 tools、MCP、skills、hooks 等映射到五类对象，对不清楚或无法覆盖的分类重新划分。固定 13 个 owner 仓库提交，检查接口声明与主要模块，形成 403 条建议映射并核对 211 个来源文件的 Git blob SHA。原五类调整为五类运行职责 A–E 加横切契约 F、评测 G，记录为 ADR 0004；没有运行旧业务、模型或设备，也没有搬迁旧实现。

## 已形成的研究判断

以下是提案或研究判断，不自动升格为已接受架构：

- 任务状态应独立于模型上下文和用户交互进程，支持跨会话持续执行。
- Web 应作为复杂操作环境研究，组合结构化、视觉与程序执行能力。
- 成功操作可逐步提炼成带前置条件、验证和失效条件的可复用经验。
- Circle 负责通用运行能力，领域知识与规则通过产品扩展提供。
- 知识资料、运行事实、模型判断与验证结论分开管理。
- 强制检查应在权威操作或交付路径上执行，普通事件回调不能替代。
- 维护操作与通道测试需要不同契约，测试指定通道时不能换路径绕过问题。
- 多 agent 需要明确任务归属和交接，并通过实验判断收益。

## 研究方式的纠正

- 先前建议保留 Python 侧执行能力不再适用于新系统实现；新自研代码遵守全 TS 方向。
- “借鉴已有工程”不等于“在旧仓库继续改造”。
- 不能因为已有框架或公开产品提供某能力，就宣称 Circle 或新平台已经具有该能力。
- 本地测试记录、离线对拍、真机验证和当前实现状态分别披露。
