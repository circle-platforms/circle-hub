# 这个平台要做什么，怎样工作

最新两端分工见[双产品计划](circle-server-plan.md)与 [ADR 0028](decisions/0028-circle-server-split.md)：用户在 Circle 默认插件库配置 server，B/C/D/E 与管理运维归 circle-server。共同代码、版本兼容和发布通过同一工作索引组织，下列产品目标继续有效。

infosec-platform 要成为一套通用的网安产品全自动化 AI 平台。用户把一项工作交给它，它能够查资料、理解代码、连接设备、修改配置或程序、运行检查，并交付有依据的结果。工作可以跨越研发、测试、发布和维护，也可以涉及多个产品。

这是产品的目标。仓库已有部分代码和隔离验证，完整产品还在建设。

## 用户交给平台的是一项工作

比如，用户说某个版本的连接有异常，希望平台找到原因并修好。平台先弄清楚产品、版本、出现问题的条件和允许操作的范围，再安排调查。它可能先看手册和代码，随后通过 SSH 采集设备状态，也可能打开管理页面确认配置。

找到一个可疑原因后，平台需要想办法验证。如果需要改代码，就在隔离工作区修改并运行回归。如果需要改配置，就先记录原配置，再执行获准的变更并读回结果。最后交付修复内容、检查结果和还没有解决的问题。

等待构建或设备响应时，工作可以停下来，条件满足后继续。用户换一个会话或入口，也应能看到原来的工作进度，而不必重新讲一遍事情经过。

## 平台怎样判断和披露

100% 置真的内容交给脚本，其余内容由 LLM 判定，完整披露输入和输出。脚本的确定结论只在明确规则、输入和适用条件内成立；需要理解和推断的内容由 LLM 给出依据、假设和证据缺口。用户能够展开实际输入、原始输出和处理过程，不能只看到最终总结。详见[判断与披露原则](design/truth-and-disclosure.md)。

网络排障覆盖物理层到应用层。平台既要理解产品版本和内部行为，也要熟悉链路、交换、路由、回程、传输与应用协议，才能建立有明确拓扑、流量、故障位置和观察点的测试环境。产品事实、网络观察和跨层推断分别保留。

## 平台中的五部分各做什么

**用户入口负责沟通。** 用户可以直接使用原生 Web 工作空间，也可以选择 Circle、OpenCode、Pi 等入口。它们理解用户的目标、展示进度、提出具体问题，并把用户的回答交给负责这项工作的服务。用户也在这里打开设备操作页面或 SSH 终端。

**知识库负责资料和依据。** 它保存产品手册、型号和版本信息、代码和测试资料，以及工作中产生的证据和报告。回答一个产品问题时，要能找到支持答案的原文。资料之间有冲突或没有答案时，也要把这件事说清楚。

**任务服务负责把工作做下去。** 它记住目标、当前步骤、正在等什么、谁可以操作，以及最后要交付什么。用户补充资料或改变目标后，它检查哪些旧结果还能用，哪些步骤需要重做。它也负责在宣布完成前检查结果是否齐全。

**执行服务负责实际操作。** 连接 SSH、打开浏览器、运行进程、读写工作区和收集现场结果，都在这里发生。它知道连接是否还在、命令是否已经发出、哪个操作者可以输入。如果操作途中断线，它需要核对实际发生了什么，不能为了给出确定回答而猜测成功或失败。

**专业方法负责知道怎么做。** 不同产品的命令、配置步骤、页面操作、测试规则和结果判断都放在这里。平台的公共部分负责组织工作，具体产品的方法告诉它如何进入配置模式、怎样保存配置、如何读回，以及什么结果才算符合要求。

这五部分可以是同一个程序里的模块，也可以在有必要时分开运行。它们共用格式和基础工具，也需要共同的测试。没有必要因为分成五类，就建立五个互相聊天的 agent 或五个独立服务器。

## 怎样支持多个产品

接入一种产品，需要把三件事准备好。

先整理该产品的资料，说明资料适用于哪些型号和版本。然后写清楚产品的操作方法，包括 SSH 命令、Web 页面、参数和配置步骤。最后准备能检查结果的样本和标准，说明在哪些环境中实际验证过。

换一个产品时，用户仍然通过同样的方式提出任务、查看进度和收到结果。产品资料与操作方法会变化，任务记录、权限检查、现场操作和结果留存的做法应当继续使用。

负载均衡工程是我们的起点。平台还要服务其他网安产品，所以公共代码不能默认所有设备都有负载均衡对象，也不能把某份测试样本的规则当作所有产品的规则。

当前设备操作范围是 SSH 和 Web。支持一种产品必须说明测过的型号、版本和环境，不能因为一种产品通过就宣布其他产品也支持。

## 一项任务怎样组合多个能力

知识问答、用例评审、脑图编译、设备采集、代码修改和测试，都可以成为一项工作的步骤。一次修复可能同时需要其中几种能力；同一种能力也可能被不同产品使用。

平台先选择适用于当前产品和版本的方法，再把步骤连起来。没有依赖关系、也不争用设备的步骤可以并行。需要同一台设备写入的操作要协调，避免两个步骤互相覆盖。

成熟的重复工作可以保存为一份工作步骤，下一次带入新的输入使用。遇到新问题时，agent 可以探索和调整计划。使用旧方法前仍要检查它的条件是否成立，不能把一次成功当作以后都能成功。

## 用户如何参与

用户可以直接聊天，提出目标、询问进展或补充信息。需要明确回应的事情会关联到具体任务和问题，例如确认一项配置变更，或处理评审中的分歧。用户说“同意”时，平台要知道同意的是哪件事、哪一版输入。

设备操作应当实时可见。SSH 展示正在使用的终端，Web 展示 agent 实际操作的页面。Otty 这类有浏览器的终端可以并排显示；普通终端可以打开 Chrome 查看同一个执行会话。

用户可以请求暂停、取消、接管或交回。暂停后停止派发下一动作；取消需要核对当前操作是否真的停止；接管时需要让自动执行和人工输入有明确的交接，避免双方同时改同一处。已经发生的变更也要记录下来。

产品目标是让已有授权内的常规工作自动推进。遇到目标不清、权限之外或证据不足的情况，再等待具体的信息或决定。

## 各部分怎样交换信息

各部分交换的是完成工作所需的信息。一次操作请求要说明是哪项任务、什么产品和版本、对哪个目标做什么，以及需要遵守哪些限制。结果要说明实际发生了什么，并能找到相关输出或证据。

查询资料或读取状态可以直接返回结果。耗时较长的工作先记录下来，让调用者拿到一个可查询的引用，再继续执行。需要人回应时，把问题保存到原任务中；取消和结果核对也分别处理。

实时输出和进度通知帮助用户看见过程。通知丢失后可以重新查询负责保存状态的服务。看到一条“完成”通知，不足以证明结果已经满足交付要求。

私人聊天记录留在入口，长期任务留在任务服务，实际连接和操作留在执行服务，产品资料和证据留在知识库。其他部分按需要读取引用，不把所有聊天和原始资料到处复制。

## 怎样组织代码和文档

代码按照实际职责组织。共享格式和基础工具集中维护；产品特有的方法放在相应产品或能力中；模拟设备、测试站点和校准程序作为验证工具保留。生产服务不能靠调用模拟设备来完成真实操作。

每个模块都要说明它解决什么问题、保存什么、谁会调用，以及出错后怎么办。每个公开或会产生实际作用的函数都要说明需要什么输入、会做什么、返回什么，以及怎样检查它的结果。内部帮助函数也要能在代码目录中找到，但不必把它们全部变成外部接口。

文档从用户需求开始，接着说明方案和代码分工，再记录测试与实际交付。源码签名和检查数据用于核对，不能替代对用途和行为的说明。

现有代码逐部分说明见[项目内容说明](project-explanation.md)。需要查具体函数时，再看[函数说明目录](reference/README.md)。

## GitHub 怎样配合开发

一项需求先说明用户遇到什么问题、希望得到什么结果，再拆成设计、实现和验证工作。讨论结果留在文档里，代码变更关联对应的工作项，最后用实际结果说明完成了什么。

当前已经建立一个[平台总任务](https://github.com/qingshanfeihu/infosec-platform/issues/1)和七个子任务。它们帮助我们逐项完善产品接入、能力组合、用户交互、函数说明、代码分工、验证和工程流程。它们目前是设计和准备工作，不意味着完整产品已经完成。

## 进一步确认的产品要求

测试环境要能够准备、检查、恢复和清理，明确拓扑、流量、故障与观察点。调查保留候选原因、支持和反驳证据；用户能展开输入输出并纠正判断。成功和失败经验经独立核验后成为方法候选，再按版本晋级。平台以完整任务的复现、原因验证、修复、回归、恢复和交付衡量，随后用第二个产品检验通用性。见 [ADR 0025](decisions/0025-complete-product-task-delivery.md)。

原生 Web 同时提供任务交互与平台维护，四个对象的观察和操作见[工作空间设计](design/web-workspace-and-operations.md)。人员、项目、环境、目标和动作共同限定权限，规则在数据读取和实际作用端强制检查，见[权限方案](design/identity-and-security-boundaries.md)。这些设计不因 demo 存在就成为已实现功能。

接下来按[产品阶段](implementation-roadmap.md)和[短迭代](engineering/agile-product-process.md)交付。既有 P0–P5 技术门禁与历史回执保留，不把产品阶段改名当作重新通过验收。

## 当前做到哪里

仓库已有共同格式、任务和操作的参考实现、最小知识查询、结构编译、规则评审，以及模拟设备和本地测试站。随后加入了使用 PostgreSQL 保存任务的实现，已有单独的执行记录。

真实入口接入、长期运行与恢复、实际浏览器操作显示、真实模型质量和产品现场验证，仍需按各自范围完成。既有执行记录保留原来的输入和环境；这轮工作只整理设计、文档和 GitHub，不运行新的设备或浏览器实验。
