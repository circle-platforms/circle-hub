## 0. 如何评审本文件

- 每条契约有稳定编号（如 `COM-01`、`BIND-03`）、责任对象、规范级别和验证方式。评审时按编号逐条给出：接受 / 修改后接受 / 拒绝 / 延后，并记录理由；未表态的条款保持“提案”状态，不得被实现阶段默默当作已冻结。
- 规范级别：**必须（MUST）** 表示不满足即不能宣称该链通过；**应当（SHOULD）** 表示默认必须做，偏离需在决策记录中写明理由与补偿；**可以（MAY）** 表示可选增强。
- 验证方式只写方法类别：程序核验（确定性检查）、协议对拍、故障注入、真实 harness smoke、人工标注评审、专用环境实测。某条款写了验证方法，不等于该验证已经执行；执行状态统一见[验证矩阵](validation-matrix-v1.md)，已有局部记录不能补判全部条款通过。
- 已确认方向（来自用户与 ADR 0001–0005）与本文件新提案严格分开：第 1 节复述已确认边界；第 2–15 节为本轮收口提案；第 16 节集中列出待定与未验证事项，不得在正文中把待定项写成结论。

## 1. 已确认边界（复述，不在本文件重新决定）

1. A 是可替换的入口与 Agent 运行职责：Circle 是当前候选实现，Pi、OpenCode 或其他满足最低接入条件的 harness 均可替换 A。平台不得以任一 harness 的专属生命周期、内部数据格式或本地状态定义 B/C/D/E 的业务语义。
2. B（产品知识、证据与制品）、C（任务与协作治理）、D（操作执行与资源）、E（能力包与业务规则）是四类可复用平台职责；F（共享契约与基础库）与 G（验证、评测与实验）是横切工程，不新增运行权威。五类是逻辑职责，不要求五个独立进程或五台服务器。
3. 除 Circle 本身外，新自研实现全部采用 TypeScript，包括服务、worker、MCP/CLI/HTTP 适配器、工具、验证器与 skill 配套可执行脚本。旧 InfoTest、compile 等项目仅作为需求、数据格式、行为与失败经验的参考：不复制其代码、不包装其运行时、不调用其服务、不要求旧 checkout 在新系统运行时存在。
4. 任务与执行状态不能依赖某个 harness：聊天结束、harness 进程退出、上下文压缩或 MCP 连接断开，都不等于任务完成、远端操作停止或租约失效。权威状态分别在 C（任务）与 D（执行）核对。
5. 程序负责能在已绑定材料、规则、身份与范围内确定的结构、核验与执行；语义理解与不确定判断交给 Jev/LLM，并保留依据、版本与未知。两者分别记录，不得合并为一个笼统的 success。
6. 本阶段边界：只做调研与计划文档。不实施业务代码、不连接设备、不部署、不对真实产品 Web 做实验。样本中的真实业务资料不入本仓库；凭据与内部连接信息不入 Git。

## 2. 身份体系：不同状态空间不得混用

下表是全平台的身份词典。任何契约、日志、证据与回执引用身份时必须使用本表语义；同名不同义（如各 harness 自己的 session）必须加来源前缀，不得直接当作平台身份使用。

| 身份 | 拥有者 | 语义与生命周期 | 关键规则 |
|---|---|---|---|
| `principalId` | C（身份来源为可信身份链） | 发起或负责行为的真实主体（人、服务账号） | 只能由可信认证结果产生；模型、提示词、请求体自报的用户名不产生 principal |
| `tenantId` / `scopeId` | C | 租户与授权范围（产品、项目、知识分区等） | 客户端只能在已授权范围内选择，不能自行扩权；跨 scope 引用默认拒绝 |
| `actorId` | C | 在一次任务中行动的角色实例（某用户、某 agent 运行、某审核人） | 与 principal 区分：同一人可有多个 actor；人工决定必须绑定具体 actor |
| `conversationId` | A | 某个 harness 内的一次会话/线程 | 仅 A 内部权威；可被 C 引用为来源，不能作为 task 身份或完成依据 |
| `taskId` | C | 一个可交付目标的长期身份 | 跨会话、跨 harness 稳定；聊天结束不终结 task |
| `runId` | C | task 的一次执行/阶段推进实例 | 一个 task 可有多个 run（返工、重试、接管后新 run）；run 结束不等于 task 交付 |
| `inputRevisionId` | C（内容身份由 B 支撑） | task 在某一时刻的完整输入修订（原件集合 + 参数 + 绑定版本） | 输入变化产生新修订；旧修订的审批、结论与完成自动对新修订失效 |
| `operationId` | D | 一次已受理的外部操作（设备命令、浏览器动作、文件处理等） | 受理后由 D 持久持有；A 断开不消失；重试产生新 attempt，不产生含糊的“同一个操作又跑了一次” |
| `attemptId` | D | operation 的一次实际尝试 | 每次尝试独立记录目标、租约、回执与结果；未知结果的 attempt 不得被静默覆盖 |
| `resourceId` | D | 设备、浏览器上下文、工作区、外部系统连接等资源 | 资源身份含类型与环境修订；同名设备在不同环境/固件下视为不同目标修订 |
| `leaseId` + `fencingToken` | D | 资源在一段时间内的独占/使用权与防陈旧令牌 | 令牌单调递增；过期或被接管的令牌的写入必须被执行端拒绝 |
| `sourceRevisionId` | B | 一份来源在某一版本的不可变修订 | 见知识库 V1；内容变化产生新修订，不原地改写 |
| `evidenceId` | B | 一份证据（原件字节或其可核验引用 + 定位） | 绑定来源、run/operation、目标与时间；摘要不能替代原件身份 |
| `artifactId` + `artifactRevision` | B | 制品（报告、Excel、评审结果等）及其不可变修订 | 发布指针（candidate/stable 等）与修订本身分开；指针移动需单独记录 |
| `snapshotId` | B | KnowledgeSnapshot 的不可变身份 | 任务开始时固定；运行中切换快照不影响已固定任务，除非产生新 inputRevision |
| `capabilityPackId` + `packVersion` | E | 能力包（规则、方法、模板、脚本集合）的版本 | 每次执行必须绑定确切版本；同名不同版本的结果不可直接比较 |
| `requestId` / `idempotencyKey` | F 定义格式，C/D 执行检查 | 一次调用的追踪与幂等身份 | 见第 8 节；由调用方生成、服务端校验，不得用时间戳临场拼凑冒充 |

- `HAND-` 条款中的“接管”只转移 task 的后续推进权与未决请求的响应权，不转移、不伪造历史 actor 的决定，也不自动转移 D 的 lease（见第 10 节）。
- 任何跨对象引用必须是显式字段（如 `taskId` 引用 `snapshotId`），禁止用标题、文件名、自然语言描述代替身份引用。

## 3. 通用信封与结构化输入输出（COM）

候选逻辑信封（非冻结 wire 格式）。MCP、CLI、HTTP 三条路径必须承载同一语义，差异只在传输编码，不在业务含义。

```text
RequestEnvelope
  requestId, idempotencyKey?
  principal / tenant / scope        # 由可信链注入或校验，不接受自报扩权
  taskId?, runId?, inputRevisionId?  # 适用时必填
  bindings: BindingSet               # 见第 4 节
  effectDeclaration: EffectDescriptor# 见第 6 节
  payload: <typed per operation>     # 按 F 的 schema 校验
ResponseEnvelope
  requestId, acceptedAt?
  status: ResponseStatus             # 见下
  result?: <typed per operation>
  verification: VerificationRecord[] # 程序核验，见第 11 节
  assessments: AssessmentRecord[]    # 语义判断，见第 11 节
  evidenceRefs: EvidenceRef[]
  artifactRefs: ArtifactRef[]
  pendingInputs: PendingInput[]      # 需要人工/外部输入时
  error?: StructuredError            # 见第 7 节
  nextActions: enum[]                # 可查询/可取消/需核对/需人工 等机器可读提示
```

- `COM-01`（必须，C/D/B/E 共同）：所有跨对象调用使用结构化 payload 并按版本化 schema 在服务端校验。自由文本只能作为 payload 的明确字段（如问题原文），不能作为完成信号、权限依据或状态推进依据。验证：协议对拍 + 非法 payload 注入。
- `COM-02`（必须，F/C）：`ResponseStatus` 至少区分：`accepted`（已持久受理，未执行完）、`running`、`succeeded`（执行完成，业务核验另列）、`failed`（已确认失败）、`unknown`（结果无法确认）、`partial`（部分完成，须列明完成/未完成部分）、`not-run`（未执行，如被准入拒绝）、`cancel-requested`（已收到取消请求，未确认停止）、`cancelled`（已确认因取消终止的最终状态；契约 v1.1 由 ADR 0009 增补，凡操作到达 stopped-observed 其最终响应状态为 cancelled）。禁止把上述状态压缩为单一 boolean success。验证：状态注入与对拍。
- `COM-03`（必须，C）：执行成功、业务核验通过、任务交付完成是三个独立结论，分别由 D/E/B 的记录与 C 的完成准入表达。任一层的 `succeeded` 不自动推出上层完成。验证：R08 实验（见验收文档）。
- `COM-04`（必须，A 适配）：harness 展示层可以渲染进度、卡片与 prose，但展示状态不是权威状态。A 收到 `accepted` 后只能表述为“已受理”，不得向用户表述为“已完成”。验证：真实 harness smoke。
- `COM-05`（必须，F）：每个 schema 有显式版本号与兼容策略。服务端遇到不支持的版本、未知必填字段或不支持的媒体类型时必须显式拒绝并给出结构化错误，不得静默忽略后继续执行有副作用的操作。验证：版本协商对拍。
- `COM-06`（应当，F）：CLI 路径的 stdout 只输出稳定 JSON 结果，进度与人类可读说明走 stderr 或独立事件通道；退出码与 `ResponseStatus` 的映射表必须成文并对拍一致。验证：CLI/MCP/HTTP 三路对拍。

## 4. 来源与版本绑定（BIND）

`BindingSet` 是每次任务运行与每次有副作用操作的强制附件。缺失必填绑定时，C 不得准入、D 不得执行。

| 绑定项 | 必填条件 | 说明 |
|---|---|---|
| 输入原件身份 + SHA-256 | 有文件/脑图/用例/资料输入时 | 绑定原件字节身份，不绑定“文件名相同”的另一份文件 |
| `sourceRevisionId` 集合 | 结论引用知识时 | 每条事实性结论可回溯到具体修订与定位（见知识库 V1 第 8 节） |
| `snapshotId` | 使用知识快照时 | 任务固定快照；快照切换的影响规则见知识库 V1 第 6 节 |
| 产品身份 + 版本/固件修订 | 涉及具体产品时 | 型号、版本、形态（物理/虚拟/云）分别绑定；同名不同产品必须可区分 |
| `capabilityPackId + packVersion` + 规则版本 | E 执行方法时 | 含编译规则、评审规则、页面方法、断言版本 |
| 目标身份 `resourceId` + 环境修订 | D 操作时 | 设备序列/别名解析结果、浏览器目标、租户环境；别名解析过程留痕 |
| 样本/数据集身份 | G 验证时 | 标注集版本、样本清单 hash；与生产运行绑定分开记录 |
| harness 与适配器版本 | 每次经 A 发起时 | 仅作审计与复现信息，**不**参与 B/C/D/E 业务状态判定；更换 harness 不改变绑定语义 |

- `BIND-01`（必须，C）：task 创建或产生新 run 时冻结一份 `inputRevision`，其内容为上述绑定项的闭包。运行中发现绑定项变化（原件被替换、快照发布新版、目标固件变化）时，必须产生新修订并使旧修订上的待审批/待完成结论失效，不得在旧修订上继续推进。验证：R04 实验。
- `BIND-02`（必须，B）：证据与制品生成时回写其完整 `BindingSet`。仅凭制品本身（脱离绑定）不得宣称其适用于另一产品版本、另一快照或另一目标。验证：伪造/错配引用注入（R08）。
- `BIND-03`（必须，E）：E 的每次执行在结果中回显实际使用的 pack/规则版本。调用方请求的版本与实际执行版本不一致时，必须显式报告，不得静默替换为最新版。验证：协议对拍。
- `BIND-04`（应当，B/C）：缓存与语义判断复用必须以绑定闭包为失效键：任一绑定项变化即失效。缓存命中不能跨 tenant/scope 复用。验证：缓存失效实验（P2 后）。

## 5. 权限与可信身份链（AUTH）

- `AUTH-01`（必须，C 为政策源、D/B 为执行端最终核对）：授权分两段：C 在任务准入时按 principal/tenant/scope/目标/效果做政策判断；D/B 在真正产生副作用或释放敏感内容前，基于同一政策与当前租约/修订再做一次最终核对。仅有 C 的准入、没有执行端核对，不构成完整授权链。普通事件回调、hook 观察、模型声明都不是授权边界。验证：无权接管与过期目标注入（第 10 节实验）。
- `AUTH-02`（必须，F/C）：principal 与 tenant 只能来自可信认证通道（连接器会话、企业身份、服务间凭据）。请求 payload、skill 文案、模型输出中出现的身份字段一律视为不可信数据，服务端必须忽略或拒绝，不得据此扩权。
- `AUTH-03`（必须，C）：人工决定、接管、取消、发布指针移动等敏感动作要求 actor 与动作时刻的授权快照一并记录。授权后来被撤销时，历史记录保留，但不得再以该授权推进新动作。
- `AUTH-04`（必须，D）：凭据只由可信执行环境注入 D 的执行上下文（如设备口令、Web 账号、MFA 种子引用）。凭据明文不得进入 A 的会话历史、B 的证据原件、任务 payload 或 Git；证据中涉及凭据的片段必须脱敏并标注脱敏规则版本。验证：证据抽检与仓库扫描（后续阶段）。
- `AUTH-05`（应当，C/D）：最小权限按 operation 声明的效果授予：只读采集不得附带变更权限；变更操作不得附带初始化、升级、破坏性权限，除非单独准入。效果分级见第 6 节。

## 6. 效果声明与真实副作用（EFF）

`EffectDescriptor` 取代单一 `readOnly` 布尔。每个 operation 在受理前必须声明、受理时由服务端核对：

| 维度 | 候选取值（示意，非冻结枚举） |
|---|---|
| 读取范围 | 无 / 本地文件 / 知识 / 设备状态 / Web 页面 / 外部系统 |
| 写入范围 | 无 / 本地工作区 / B 制品与证据 / 设备配置 / Web 数据 / 外部系统 |
| 资源占用 | 无 / lease 独占 / 共享会话 / 浏览器上下文 / 进程与端口 |
| 外部传输 | 无 / 向指定外部端点发送（须列端点类别） |
| 可逆性 | 可自动回滚 / 需人工回滚 / 不可逆（须单独准入） |
| 清理责任 | 执行方自动清理项 / 遗留项清单与责任人 |

- `EFF-01`（必须，D）：声明与实际不符时以实际为准并记为契约违规：例如声明只读却建立设备连接、占用 lease、写本地缓存或收据，必须在回执中如实记录连接、占用与写入。`readOnly` 字样不能单独作为授权或验收依据（承接对象边界 V1 第 5 节裁决）。
- `EFF-02`（必须，C/D）：不可逆或破坏性效果（初始化、升级、删除、覆盖发布指针等）必须单独准入、单独 attempt，并在验收中单独成链，不得由一次普通只读/普通变更的通过推及。
- `EFF-03`（必须，D）：每次 attempt 的回执列出实际发生的副作用与清理结果；存在遗留（未清理的配置、会话、临时文件、仍有效的 lease）时状态不得报为完全 `succeeded`，应报 `partial` 并附遗留清单。

## 7. 状态、失败与未知（STATE）

任务状态（C）与操作状态（D）分开建模，通过引用关联，禁止共用一套终态词表冒充彼此。

- C 候选任务阶段（示意）：`draft → admitted → running ⇄ waiting-input / waiting-resource → under-review → delivered | failed | cancelled | unknown`。`delivered` 只能由完成准入产生（见 `VER-03`）。
- D 候选操作状态（示意）：`submitted → accepted → running → succeeded | failed | unknown | partial`，另有 `cancel-requested → cancel-delivered → stopped-observed | still-running | unknown` 的取消子状态（见第 8 节）。
- `STATE-01`（必须，F/C/D）：结构化错误至少含：`code`（稳定枚举）、`category`（validation / permission / conflict-stale / lease / target / transient / semantic-insufficient / internal）、`retryable`（见第 8 节判定）、`bindingEcho`（出错时所依据的修订/目标/租约）、`evidenceRefs`、`userAction`（是否需要人工、需要什么）。自然语言 message 仅作说明，不能替代 code/category。
- `STATE-02`（必须，D/C）：`unknown` 是正式终态之一，不是异常边角。当回执丢失、连接中断、目标无响应且无法核对时，必须落 `unknown` 并保留核对入口；禁止为了给出确定结论而把 unknown 猜为 succeeded 或 failed。`unknown` 不计入通过率（承接基础验证计划第 6 节）。
- `STATE-03`（必须，C）：`partial` 必须附结构化清单：已完成部分、未完成部分、各自证据。只报百分比或 prose 摘要不算 partial 的合规表达。
- `STATE-04`（应当，C/D）：状态迁移只由拥有者写入：A 与 E 都不能直接写 C 的任务终态或 D 的操作终态；E 给出结果与判断，D 给出执行事实，C 依据准入规则推进任务状态。

## 8. 幂等、重试与取消（RC）

- `RC-01`（必须，C/D）：提交类调用必须携带 `idempotencyKey`。后续按 [ADR 0011](decisions/0011-idempotency-and-lease.md) 定案：键作用域为 principal + operation 类型 + key，同键同时比较请求规范哈希；同哈希在 24h 窗口内返回原 `operationId/taskId` 与当前状态，异哈希按契约 v1.2 的 `IDEMPOTENCY_MISMATCH` 拒绝。原“inputRevision 组成键/窗口待定”的提案由该决定替代；输入修订与其他执行绑定必须参与请求匹配，不能因键相同而执行新输入或混用目标。窗口内不得重复受理或重复副作用，超窗后风险按 ADR 明示。
- `RC-02`（必须，D）：重试只能发生在同时满足时：错误 `retryable=true`、该 operation 声明可重试、且上一次 attempt 的结果不是 `unknown`（unknown 必须先核对，见 `RC-03`）。每次重试是同一 operation 下的新 attempt，绑定新的 lease/fencing 检查结果；禁止换一个 operation 偷偷重跑来掩盖失败历史。
- `RC-03`（必须，D）：对 `unknown` 的唯一合规后续是 `reconcile`（按 operation 身份向执行端核对实际状态与已发生副作用）。核对出结果后才可决定重试、补偿或落终态。本地调用超时、客户端断开、进程重启都不构成“远端已停止”的证据（承接 AGENTS.md 证据规则）。
- `RC-04`（必须，C/D）：取消是四段可区分事实：`cancel-requested`（C 已受理请求）→ `cancel-delivered`（D 已送达执行端）→ `stopped-observed`（已观察到进程/会话/操作实际停止）→ 残留核对（遗留配置、会话、lease 的处理结果）。四段分别记录时间与证据；只完成第一段时对用户只能表述为“已请求取消，尚未确认停止”。
- `RC-05`（必须，D）：迟到的回执、重复通知、乱序事件按 `operationId + attemptId + fencingToken` 做陈旧判定。已被接管或已过期的 attempt 的回执不得推进当前状态，只能作为历史证据归档（承接 R03）。

## 9. 长任务、句柄与恢复（LONG）

- `LONG-01`（必须，C/D）：凡可能跨会话、跨进程或超过单次调用时限的工作，一律走持久任务模型：`submit` 返回句柄（taskId/operationId）后，`status`、`result`、`input`（提交人工响应）、`cancel`、`reconcile` 是五个独立调用。服务完成持久受理（状态已落 C/D 的权威存储）后才可返回 `accepted`；仅在内存或 harness 本地排队不算受理。
- `LONG-02`（必须，C）：task 的目标、阶段、绑定、待决请求与历史 run 在 A 退出、上下文压缩、进程重启后完整可查（R01）。恢复时以 C/D 的记录为准重建视图，禁止要求用户复述上下文来“恢复”任务。
- `LONG-03`（必须，C/D）：MCP Tasks 句柄、传输会话 ID 等易失句柄与平台 taskId/operationId 之间必须有显式映射与重新获取方式。易失句柄过期只能影响访问路径，不能删除或终结平台记录（承接适配计划第 6 节）。
- `LONG-04`（应当，D）：长操作应提供进度信号（阶段、已处理量、最后心跳），但进度只用于展示与超时判定，不作为完成或正确性证据。心跳停止触发核对流程，不直接判定 failed。
- `LONG-05`（必须，C）：等待状态必须显式：`waiting-input`（等谁、等什么、对应 requestId 与 inputRevision）、`waiting-resource`（等哪个资源/lease）、`waiting-review`（等哪个 actor 的决定）。无说明的“pending”不是合规状态。

## 10. 跨 Harness 薄适配与接管（HAND）

薄适配器（每个 harness 一份）只做四件事：协议/传输适配、身份通道透传、结果与媒体呈现、本地未决句柄的引用保存。它明确**不做**：不持有任务/执行权威状态、不缓存可当作事实的业务结论、不自行做完成判定、不保存凭据、不复制 B/C/D/E 逻辑。

- `HAND-01`（必须，A/F）：同一 B/C/D/E 语义必须可经 MCP、CLI、HTTP 任一路径访问且结果一致；适配器不得为某个 harness 维护私有分支语义。某 harness 缺少能力（如无视觉、无 Tasks 扩展）时走最低兼容路径并显式标注能力降级，不得假装具备（承接适配计划第 5 节三档兼容）。
- `HAND-02`（必须，C）：接管流程固定为：新 harness 以接管者身份重新认证 → C 校验其对该 task 的 scope 与接管授权 → 返回 task 当前阶段、当前 inputRevision、未决 PendingInput、关联 operation 及其 D 侧核对状态 → 接管以新 run 记录开始，旧 run 保留。接管不要求、不默认转移原会话的私人聊天历史（R05）。
- `HAND-03`（必须，D）：接管不自动转移 lease。D 必须先核对原 lease 状态：已释放则按新 attempt 重新获取；仍有效且归属原执行上下文时，新 harness 只能观察或按 `RC-04` 请求取消，待 fencing 推进后才可写入。禁止两个 harness 同时持有可写租约操作同一目标。
- `HAND-04`（必须，C/D）：接管时若存在 `unknown` operation，必须先 `reconcile` 才能继续推进任务。无法核对时任务保持 `unknown` 相关阶段并明确告知接管者，不得以“新会话新开始”为由清零。
- `HAND-05`（必须，F）：能力协商结果（harness、版本、支持的传输/媒体/Tasks/人工输入方式）随 run 记录，供复现与验收引用；协商失败或能力不足时，在产生副作用前拒绝对应能力并说明缺项。

## 11. 程序核验与语义判断双轨记录（VER）

两类记录使用不同结构、不同产生者、不同效力。UI 与报告可以同页展示，但存储与完成判定必须分开。

| 记录 | 产生者 | 内容（候选字段） | 效力 |
|---|---|---|---|
| `VerificationRecord`（程序核验） | B/C/D/E 中的确定性程序、F 的 schema 校验 | 检查 ID、规则/程序版本、输入绑定 hash、预期、实际、pass/fail、证据引用、执行时刻 | 在其声明的检查范围与绑定内可作确定结论；范围外不推出任何结论 |
| `AssessmentRecord`（语义判断） | Jev/LLM 方法（E 定义方法、C 记录归属） | 方法/prompt/模型版本、输入绑定、所依据的 evidence 引用、结论、置信或分级（如适用）、未知与弃答、理由摘要 | 是判断而非事实签发；可被人工推翻并保留推翻记录；不自动改变 Claim 的发布状态 |

- `VER-01`（必须，B/E）：事实性结论的发布与引用走知识库 V1 的 Claim/Assessment/来源性质分离：程序核验通过不等于语义正确，模型判断置信高不等于来源支持。两者任一缺失时，结论按其实际状态（未核验/未判断/证据不足）呈现（承接知识库 V1 第 3、7 节）。
- `VER-02`（必须，G/C）：验收计量分开：机械契约通过率与语义质量（标注集上的准确/弃答/错误确信）分别统计、分别设阈、分别报告。禁止用一个混合“总通过率”掩盖语义失败（承接基础验证计划第 6 节）。
- `VER-03`（必须，C）：任务完成准入是一份可核对的清单：必需的 VerificationRecord 集合齐备且通过、必需的 AssessmentRecord 存在且无未处置的阻断性未知、必需的人工决定已绑定当前 inputRevision、关联 operation 无未核对的 unknown、制品修订已登记。清单缺项时 C 不得落 `delivered`，只能停留在相应等待/未完成状态（R08）。
- `VER-04`（应当，E）：语义方法必须声明适用范围（产品、版本、问题类型）与弃答条件。范围外输入应弃答或转人工，不得硬答后由下游当作已判断。

## 12. 证据与制品（EVD）

- `EVD-01`（必须，B）：证据条目至少含：evidenceId、来源类别（来源原件/执行回执/现场观察/外部文档）、内容 hash 或原件引用、定位（页/行/节点/时间段/命令与输出段）、所属 BindingSet、采集 actor 与时刻、可信级别说明。原始字节在确切内容重要时保留；截图、trace、日志的裁剪版不能替代原件身份。
- `EVD-02`（必须，B/D）：执行类证据由 D 在执行现场产生并登记到 B，A 的转述、模型 prose、用户口述都不能补造执行证据。证据的事后补记必须标注为补记及其依据。
- `EVD-03`（必须，B）：制品（Excel、报告、评审结果）以不可变修订登记，含生成它的 run、BindingSet、生成程序/pack 版本与校验结果。对外交付（发送、上传、写外部文档）是 D 的独立 operation，制品已生成不等于已交付，交付状态单独记录（承接对象边界 V1 第 5 节）。
- `EVD-04`（应当，B）：证据与制品的保留、脱敏与可见范围按 tenant/scope 执行。含敏感内容的证据默认不跨 scope 可见；脱敏副本是新修订并保留与原件的派生关系。

## 13. 人工决定（HUM）

- `HUM-01`（必须，C）：每个需要人工的点都是一个 `PendingInput`：含 requestId、taskId、inputRevisionId、问题与所需决定类型、选项或格式约束、请求时刻、过期条件。口头/聊天中的模糊表态不直接构成决定，必须落为对具体 requestId 的结构化响应。
- `HUM-02`（必须，C）：人工响应只对绑定的 inputRevision 有效。修订已变化时，迟到响应必须被拒绝并提示重新确认，不得推进新修订（R04/R05）。
- `HUM-03`（必须，C）：重复提交同一决定按 idempotency 处理并返回原结果；相互冲突的决定（不同 actor 给出不同结论）进入冲突状态等待裁决，不得以“最后写入者胜”静默覆盖。裁决本身也是一条决定记录。
- `HUM-04`（应当，C/A）：MFA、验证码、凭据确认等敏感人工输入只经可信执行环境通道进入 D，不经模型上下文转述，不落会话历史与证据明文。此类等待同样用 PendingInput 表达，但 payload 通道与普通澄清分开。

## 14. 各对象契约面（候选能力，非冻结 API）

操作名为讨论用候选名。每个操作在实现议题中再冻结其 schema；在此之前不得按本表直接编码对外承诺。

### 14.1 B：知识、证据与制品

| 候选操作 | 输入要点 | 输出要点 | 本对象 invariants |
|---|---|---|---|
| 查询知识（按快照） | snapshotId、问题/结构化查询、scope | 证据包：Claim 引用、Evidence 定位、Assessment 状态、未命中声明 | 不跨 scope；未命中明确返回，不生成无来源结论 |
| 读取来源/证据原件 | sourceRevisionId/evidenceId、定位 | 原件字节或受控引用 + hash 核对结果 | 原件不可变；读取留审计 |
| 登记证据/制品 | BindingSet、内容、来源类别 | evidenceId/artifactRevision + 登记核验 | 未绑定不登记；重复登记按 hash 幂等提示 |
| 发布/移动发布指针 | snapshot/artifact 修订、目标指针、授权 | 指针移动记录 + 闭包核验结果 | 闭包不满足不得发布（知识库 V1 第 6 节）；移动可回滚且留痕 |

### 14.2 C：任务与协作治理

| 候选操作 | 输入要点 | 输出要点 | 本对象 invariants |
|---|---|---|---|
| 创建/准入任务 | 目标、BindingSet、EffectDescriptor、principal/scope | taskId、inputRevisionId、准入结论与缺项 | 未绑定/越权不准入；准入不等于完成承诺 |
| 查询任务 | taskId | 阶段、runs、未决请求、关联 operation 状态摘要、完成清单进度 | 只返回权威记录；摘要与 D/B 原记录不一致时以下游原记录为准并报错 |
| 提交人工响应 | requestId、决定、actor | 受理结果或过期/冲突拒绝 | 见 HUM-01–03 |
| 请求取消 | taskId/operationId、理由 | cancel-requested 记录 | 只表达请求段，不冒充已停止（RC-04） |
| 接管任务 | taskId、接管 actor、认证结果 | 接管 run + 当前状态包 | 见 HAND-02–04 |
| 完成准入检验 | taskId | 完成清单逐项结果 | 见 VER-03；检验本身留记录 |

### 14.3 D：操作执行与资源

| 候选操作 | 输入要点 | 输出要点 | 本对象 invariants |
|---|---|---|---|
| 发现目标/能力 | 资源类型、scope | 候选 resourceId、环境修订、可用通道 | 发现结果带时刻；过期发现用于执行前必须复核 |
| 获取/释放租约 | resourceId、用途、效果 | leaseId + fencingToken 或拒绝 | 同一资源可写租约唯一；释放留痕 |
| 提交操作 | operation 类型、目标、BindingSet、EffectDescriptor、idempotencyKey | operationId + accepted | 持久受理后才返回；未核对 lease/权限不得受理有副作用操作 |
| 查询/核对操作 | operationId | 状态、attempt 列表、实际副作用、回执证据 | unknown 只能经 reconcile 离开（RC-03） |
| 请求停止 | operationId | 取消子状态推进 | 见 RC-04 四段 |

### 14.4 E：能力包与业务规则

| 候选操作 | 输入要点 | 输出要点 | 本对象 invariants |
|---|---|---|---|
| 枚举/读取能力包 | 产品/scope、任务类型 | pack 清单、版本、适用范围、所需输入契约 | 适用范围外明确不可用，不降级冒充 |
| 解析/生成 IR | 原件引用、packVersion | 结构化 IR + 未解释节点清单 + 核验记录 | 未解释内容显式列出，不静默丢弃 |
| 评审/检查 | 输入修订、规则版本、知识绑定 | findings（绑定位置/规则/依据/性质）+ Assessment 记录 | 机械 finding 与语义 finding 分开标记（VER-01） |
| 编译/生成 | IR 修订、输出契约版本 | 制品内容（交 B 登记）+ 生成核验 | 输出契约版本绑定；生成成功不等于业务通过（如 Excel 生成 ≠ 用例在设备上通过） |

### 14.5 A：薄适配（每个 harness 一份）

| 必须具备 | 明确禁止 |
|---|---|
| 透传可信身份通道的结果；呈现结构化状态与证据引用；保存并出示 task/operation 引用以便接管；在能力不足时明确降级说明 | 以本地文件/内存保存任务权威状态；把模型 prose 当作 result 转交 C；自行合并或美化 ResponseStatus；保存凭据明文 |

## 15. 禁止事项（全平台）

1. 禁止以任一 harness 的本地状态、会话文件或 MCP 连接状态作为任务/执行完成的唯一依据。
2. 禁止复制、包装或运行时调用旧项目代码来满足上述任一契约（见第 1 节第 3 条）。
3. 禁止用单一 success、单一分数或单一 prose 报告替代第 3、7、11 节要求的多维状态与双轨记录。
4. 禁止在未核对时把 unknown 猜为确定状态，禁止对 unknown 副作用直接重试。
5. 禁止凭据、内部连接串、原始业务资料进入 Git 或证据明文（AUTH-04、EVD-04）。
6. 禁止在本阶段（计划阶段）以“验证需要”为由连接真实设备、登录真实产品 Web 或部署服务；验证一律先在后续阶段的隔离 fixture 与专用环境中按授权进行。
