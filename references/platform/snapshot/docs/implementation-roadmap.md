# 接下来怎样实施

2026-10-10。以下是产品交付路线提案，具体 Sprint 在规划时选定；没有承诺日历工期，也没有启动新的生产实施。已确认的产品原则见 [ADR 0025](decisions/0025-complete-product-task-delivery.md)。

先在一个产品上把一项工作做完整，再用第二个产品检查通用性。每次迭代都应让用户多完成一件事，基础设施和模块完善跟着这项工作推进。

## 现有工作的起点

P0/P1/P2 保留原收口记录。P3-1 有 PostgreSQL 任务记录，P3-2 有运行方式比较，ADR 0022 已确认采用 PG 任务表路线，P3-3 有进程与浏览器 worker 的局部记录。P3-4 后续已有[三入口的局部接入记录](p3-4-harness-record.md)：固定版本、脚本化模型、stub 状态与工具调用核对，Circle 使用 loader 路径，未覆盖全屏 UI。P3-5 的真实模型质量及 P3 整体收口仍按原计划检查。

D 控制面目前的记录明确说明它仍在内存中；不能因为 C 已使用数据库，就认为整个执行状态可恢复。实时观看、真实产品兼容、人员鉴权与跨层诊断也不能由当前局部测试推出。源码研究和本地沙盒回执是研究证据，不替代这些交付要求。本轮未重跑现有包测试。

## 四个产品阶段

| 阶段 | 用户能多完成什么 | 主要验收 |
|---|---|---|
| M1 首个可重复的完整任务 | 在桌面 harness 中直接对话，使用适用的产品上下文，准备合成环境，复现一个已知故障，查看输入输出并取得报告；任务能暂停和继续 | 可信登录与项目/环境权限；原生任务交互；资料、方法、环境和运行绑定；独立观察与原件；失败/未知与清理；同任务恢复；不宣称真实模型或真机诊断 |
| M2 诊断、修复与回归 | 给出异常，平台查资料与代码、复现、比较候选原因、验证修复并完成回归 | 冻结故障集；真实模型单独校准；脚本与模型结果分别披露；控制面恢复；任务、代码/配置、现场与报告闭合；实际作用和遗留分别核对 |
| M3 第二产品与组合任务 | 将相同公共流程用于另一产品，组合答疑、评审、开发、环境、测试或维护能力，并更换入口继续 | 产品规则与公共流程分离；版本差异、方法失效、跨产品组合；按既有 P3 门禁检查三 harness；不同人员/入口交接，不泄漏资料或权限 |
| M4 团队试用与发布维护 | 多人日常使用，维护环境和方法，处理平台故障，取得可追查的版本交付 | 组织身份接入；多人并发与安全回归；worker 与资源运维；备份恢复；升级/回退；运行指标与实际试用反馈；发布范围和支持清单 |

M1–M4 是产品价值的组织方式，不覆盖或撤销既有 P0–P5 技术验证门禁。一个阶段可能包含多个 Sprint；已完成的公共能力不需要重做，但必须确认它是否满足当前任务条件。真实产品环境仍按 P4/L5 的目标、版本、拓扑和允许动作授权，模拟通过不自动进入真实环境。

## 首个 Sprint 的候选目标

**让用户通过桌面入口完成一次合成产品故障的复现与证据交付。** 首批沿用负载均衡实践，使用明确标注的合成产品环境；候选故障为管理可达、业务转发失败、后端独立可达。先演示事实采集与任务闭环，真实 LLM 的原因判定另行评估。

候选工作包括冻结目标与预期、可信身份及越权拒绝、桌面会话提交和查看同一工作、准备与检查环境、采集独立结果、展开原始输入输出、检查清理和交付。所有工作围绕这一个场景，安全与观察从第一条链进入。

旧工作台已被用户否定，当前转向[参考 ZCode 的独立桌面框架](research/zcode-desktop-framework.md)。[五种 Harness 界面方案](design/harness-interface-alternatives.md)作为布局参考。最新实施顺序先完成 [Web 前端框架](../packages/workbench-ui/README.md)并评审交互，再验证独立桌面宿主、Host 与真实会话链，逐项接入四个对象；这些框架工作仍服务于同一产品目标。界面选择未定，不是这个 Sprint 的完成结果。缺少的后端、agent 运行、任务恢复和真实强制鉴权，仍需实现与验证。

开始规划时核对实际可用人力、现有实现缺口、样本、环境与允许动作，再选本次能完成的条目。建议两周为一个 Sprint，待规划时确定起止日期；暂不虚构容量、故事点或截止时间。

## 实施前仍需要落实

明确首个产品/版本与样本、可用身份来源、桌面 Host 与 Agent 会话运行方式、真实模型通道及评测范围。模型未就绪时仍可推进已授权的程序和管线检查，不能用模拟回答代替模型质量。真实设备、生产操作和部署不由路线图自动授权。
