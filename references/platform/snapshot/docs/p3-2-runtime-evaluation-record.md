- 日期：2026-10-10

- 依据：ADR 0016（DEC-P3-01：以 C-T03/C-T04 对比 Temporal TS 与 PostgreSQL 任务表路线，采用与否另行 ADR 定案）、ADR 0017（PostgreSQL 基线）、`docs/cde-implementation-discussion-v1.md` §7 的 C-T03/C-T04 样本定义

## 1. 对比方法

两条路线运行**同一个规范评估流程**，作用写入**同一个 PostgreSQL 恰好一次账本**（`eval_effects`，主键 `(flow_id, stage)`；`eval_attempts` 分开计执行尝试），使「重复作用」可直接计数，不靠日志推断：

```
效果 A → 等待人工决定 → 效果 B →（v2 语义新增）标记效果 C → 完成
```

- **PG 路线**：`PgFlowRunner`（`src/pgflow.ts`，237 行含账本与唤醒机制）。流程行钉死 `flow_version`；唤醒是持久行，可重复、可乱序（重复记 `noop`，早到的决定由流程行持有）；每个阶段的推进与其效果在**同一事务**内提交。
- **Temporal 路线**：`@temporalio/*` 1.24.0（TS SDK），本地评估服务器为 Temporal CLI 1.9.1 / Server 1.32.0（ephemeral dev server，内存持久化）；workflow v1/v2 两份代码（24/44 行），活动经同一账本落效果（43 行）。活动在执行前以自提交方式记尝试（`noteAttempt`），使被杀的尝试也可计数。

场景与 C-T03/C-T04 的对应：C-T03a 阶段执行中杀进程（真实 SIGKILL 子进程）；C-T03b 重复与乱序唤醒；C-T03c 等待人工时杀/停 runner 或 worker 后重启；C-T04 流程代码 v1→v2 升级时有飞行中流程。说明：C-T03 中「提交前/提交后杀受理进程」一半已在 P3-1 以事务受理口径验证（提交前 SIGKILL 无残留、提交后任务完好），本步补齐的是**运行期**杀进程。基础设施本身（PostgreSQL 服务器进程、Temporal 服务器进程）的崩溃不在本轮范围，两条路线对称处理。

## 2. 结果（2026-10-10 本地全量重跑，9/9 通过）

| 场景 | PG 路线 | Temporal 路线 |
|---|---|---|
| 规范流程 + 重复决定 | 通过：效果 A、B 各恰好一次 | 通过：重复 signal 由 handler 吸收（保留首个），效果各一次，尝试各 1 |
| C-T03a 阶段中 SIGKILL | 通过：阶段 A 事务被杀后回滚，作用 0 次、阶段未推进；新 runner 续跑后 A 恰好一次（尝试计数为已提交口径 1） | 通过：worker 在活动 A 执行中被 SIGKILL，服务器重新派发，活动共执行 2 次（尝试计数 2），效果恰好一次——恰好一次来自账本去重，不是活动本身 |
| C-T03b 重复/乱序唤醒 | 通过：决定早于 WAIT 到达被持有、重复决定记 noop，效果不重复 | 通过（同重复 signal 项） |
| C-T03c 等待人工时重启 | 通过：runner 被 SIGKILL 后状态与后续决定均完好，流程完成 | 通过：worker 停机后换新 worker，signal 照常推进并完成 |
| C-T04 升级（飞行中流程） | 通过且天然严格：流程行版本钉死，飞行中 v1 流程完成时无 C，新 v2 流程有 C | 有条件通过：见 §3 的关键发现——需要把语义版本放进 workflow 入参钉死，才达到与 PG 路线相同的严格程度 |

测试构成：`test/pgroute.test.ts` 5 项、`test/temporal.test.ts` 4 项，含真实子进程 SIGKILL 两侧各一。Temporal 侧单项耗时显著更长（worker 打包与活动超时回收，SIGKILL 项约 39 秒），PG 侧同类项约 1 秒——这是评估环境口径（dev server、轮询间隔），不作为选型性能结论。

## 3. 关键发现（C-T04 的 Temporal 语义）

第一版 v2 workflow 只用 `patched("marker-stage-c")` 把关新阶段 C，实测**飞行中的 v1 流程在 v2 worker 上跑出了 C**（效果序列 A、B、C，与预期 A、B 不符，测试失败并保留了该次运行结论）。原因：`patched()` 只保证**已记录步骤**的重放确定性；尚未执行的后缀会采用新代码。这不是缺陷，而是其版本语义与 PG 路线不同：

- PG 路线：版本是流程的**数据**（行字段），钉死是默认行为，代价是旧版 handler 必须在代码中保留到旧流程排空。
- Temporal 路线：版本是**代码**属性，严格钉死需要额外纪律——把语义版本放进 workflow 入参（入参记录在历史中、重放稳定；本评估最终采用此法并通过），或使用 worker 部署版本化并保活旧 worker 至旧流程排空。

## 4. 对比结论（供 ADR 0022 定案）

- **恢复正确性**：两条路线在 C-T03 全部场景下均无重复作用、无状态丢失。PG 靠「阶段推进与效果同事务」；Temporal 靠「服务器保存历史 + 活动至少一次 + 外部账本去重」——注意 Temporal 路线并没有免除恰好一次所需的账本纪律，只是把重试与调度交给了服务器。
- **升级成本**：PG 路线钉死语义是默认的，成本是旧 handler 保留；Temporal 路线声明式升级顺滑，但严格钉死要靠入参纪律或部署版本化，且 workflow 代码受确定性约束（重放、`patched`、活动边界）——是新的、持续的心智与评审负担。
- **运维开销**：PG 路线只增加一个自研 runner（237 行含账本/唤醒），复用 ADR 0017 的既有数据库；Temporal 路线新增一个有状态服务器集群（持久化、版本升级、监控）与 worker 进程群，且要在「历史（调度权威）」与「C 的事务记录（业务权威）」之间长期保持 ADR 0016 划定的权威划分一致。
- **权威划分契合**：本平台的受理、人工决定、交付门禁已经在 C 的 PostgreSQL 事务里（P3-1）。PG 路线中运行状态与业务记录同库同事务，权威唯一；Temporal 路线可维持划分，但多一个需要对账的系统。

## 5. 范围与未验证项（如实披露）

- 评估流程是刻意最小化的两阶段流程；未覆盖长时计时器精度、跨服务编排、大规模并发与历史增长下的表现——这些是 Temporal 的潜在优势面，本轮没有证据，结论不外推。
- Temporal 服务器为单机 dev server（内存持久化），其集群高可用、持久化调优不在本轮范围；PG 侧同样是本地隔离实例。
- 评估包 `packages/runtime-eval` 是评估工装，不是任一选型的生产实现；无论定案哪条路线，生产化都是后续步骤的工作。
- 评估中发现并修复的自有工装问题（与选型无关，仅记录）：PG runner 的待处理选择查询曾漏选「已持有决定的 WAIT 流程」（已修复并回归）；Temporal 慢活动的一次性标记文件曾跨运行残留（已改为按进程隔离）。
