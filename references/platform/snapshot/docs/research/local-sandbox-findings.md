# 从成熟平台学什么，以及我们还需要补什么

2026-10-10。本轮已经取得公开源码、安装独立研究依赖，并运行了本地合成实验。下面分别说明源码中看到的机制、实际观察到的结果和对本平台的建议。建议不自动成为产品选型。授权范围见 [ADR 0023](../decisions/0023-local-research-sandbox.md)。

我们最值得学习的是成熟平台怎样管理实际工作：操作由谁执行，连接断开后去哪里找结果，配置和预期怎样比较，以及用户怎样看到现场。我们的重点还要往前走一步：发生问题时，平台应能沿着真实网络路径调查，把产品代码、配置、日志和业务现象联系起来，并说明哪些原因已经证实、哪些还只是怀疑。

## 实际搭建了什么

研究目录独立于项目与已有开发环境。当前机器没有容器运行时，本轮采用独立进程、独立依赖目录和回环地址；这不是虚拟机，也不具有网络命名空间隔离。

本地网络包含两级 SSH 跳转、一个合成设备、独立的管理 HTTP 页面、业务转发入口和后端服务。SSH 使用真实协议，浏览器使用新建 Chromium 与研究专用配置目录。另行编译了上游 Receptor，启动控制、中继、执行三个节点。没有连接真实设备、真实业务站点或用户浏览器，没有改变主机路由、DNS、VPN，没有调用真实模型。

本轮没有部署完整 AWX、Nautobot 或 OpenHands 服务。OpenHands 运行的是选定的上游测试；Itential 的核心服务没有取得源码或商业镜像，研究其官方说明与公开适配器。逐个仓库的固定提交、文件哈希和本地依赖版本见[来源记录](sandbox-evidence/sources.json)，实验脚本见[沙盒说明](../../research/sandbox/README.md)。

## OpenHands：把会话、工具执行和中断各自说明白

OpenHands 的会话实现中，取消令牌供工具协作检查；异步任务取消与会话状态、未完成工具结果分别处理。它并没有因为会话显示暂停，就自然获得停止任意远端进程的能力。资源锁用于控制同时操作资源；WebSocket 订阅就绪的测试则关心首批事件能否完整到达。这些细节比简单的“多 agent 协作”更有用。

实际运行了会话中断、资源锁、远程事件订阅三个上游测试文件，结果为 **36 通过、1 条警告**。测试使用模拟模型；警告涉及 TypedDict 的 ReadOnly 标注不能保护字典不被修改。这个结果证明所选测试在本轮环境中的行为，不证明模型质量、整套服务或远端设备停止。记录见[测试回执](sandbox-evidence/openhands-tests.json)。源码见[会话实现](https://github.com/OpenHands/software-agent-sdk/blob/1cfba2117e92730b0fe1c32520a39aad8611bb8c/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py)。

我们的借鉴是：A 接收用户中断并呈现状态，C 记录停止意图，D 检查正在执行的进程和设备操作。若实际停止尚未得到确认，应明确显示这一点。B 保存事件原件与结果，不能只留下聊天中的总结。

## AWX / Receptor：任务要有落地的位置，断线之后还能查到

AWX 把工作交给执行节点；Receptor 负责节点通信、工作状态和输出保存。源码有远端任务标识、持续检查状态、同步输出和接管已有工作等路径。控制侧的监控记录与执行侧实际工作分别存在，不能假定两侧状态总是同步。本轮普通提交中两侧单元 ID 相同；这不改变分别检查两侧的必要性。源码见 [AWX 交接与接管](https://github.com/ansible/awx/blob/f8314ada72926580f2fe465c8eed7d41a726c363/awx/main/tasks/receptor.py)、[远端状态和输出监控](https://github.com/ansible/receptor/blob/8ae81214edb919208d4179ade87bab048c836a88/pkg/workceptor/remote_work.go)。

三节点实测中，traceroute 显示控制节点经过中继到达执行节点。提交任务后停止中继，执行节点仍完成任务并写出结果，此时控制侧保留了尚未更新的运行状态。恢复中继后，控制侧取得该任务完成状态和完整输出；输出中的执行 PID 与独立结果文件一致。所有本轮启动的 Receptor 节点都已停止。回执见[三节点实验](sandbox-evidence/receptor-lab-receipt.json)。此实验没有验证 TLS、签名、跨地域生产网络或真实设备兼容。

我们的借鉴是：D 的 worker 应放在能接近目标网络的位置，长期任务需要远端操作标识和查询途径。C 断连后先要求 D 查证，不能仅因超时就再次发送有副作用的命令。Receptor 值得借鉴其执行和通信机制；本轮没有决定把 Go 组件引入生产平台，也没有改变自身新代码使用 TypeScript 的要求。

## Nautobot Golden Config：先保留预期，再看现场，最后决定是否变更

Golden Config 将备份配置与预期配置分别读取，按设备平台和规则提取 CLI、JSON 或 XML 配置片段。缺文件、缺解析器、规则错误有明确失败路径；部署另有计划状态和执行结果处理。源码见[配置比较](https://github.com/nautobot/nautobot-app-golden-config/blob/597f3694103cf357bbf22cbacc02470a92665531/nautobot_golden_config/nornir_plays/config_compliance.py)、[部署计划](https://github.com/nautobot/nautobot-app-golden-config/blob/597f3694103cf357bbf22cbacc02470a92665531/nautobot_golden_config/nornir_plays/config_deployment.py)。本轮是源码检查，没有启动其应用或运行其测试。

我们的借鉴是：B 保存独立版本的产品规范、预期配置和现场快照，E 知道怎样按产品版本解释差异。这里还必须增加业务检查：负载均衡的 pool、monitor、TLS、会话保持等配置看似正确，也可能因后端、回程或运行状态而失败。配置一致只是一个检查结果。

## Stagehand / Browserbase：用户看的页面应当就是 agent 操作的页面

Stagehand 的公开代码把浏览器创建、连接、关闭和操作分开；初始化失败时还区分结果是否含糊，避免继续使用状态不明的浏览器。仓库固定提交的工作区声明为 4.0.0，本地安装包为 4.2.0，两者没有当作完全相同的版本。源码见[浏览器连接和生命周期](https://github.com/browserbase/stagehand/blob/1fc884992b68a0196ea5c6e96cc29924b0922ef4/packages/sdk-ts/src/browser/factories.ts)、[初始化与操作](https://github.com/browserbase/stagehand/blob/1fc884992b68a0196ea5c6e96cc29924b0922ef4/packages/sdk-ts/src/stagehand.ts)。

本地 4.2.0 SDK 启动真实浏览器，执行指定按钮点击，页面显示 Applied；独立 HTTP 记录确认发生一次操作，模型调用数为零。本轮没有验证自然语言找元素、动作缓存可靠性或托管浏览器。第一次用固定短等待检查时未及时看到 HTTP 结果，已改为有上限地等待独立观察；回执见[浏览器实验](sandbox-evidence/stagehand-lab-receipt.json)。

Browserbase 官方提供同会话的实时查看与交互显示；这是闭源服务文档所述能力，本轮没有实测其云服务。来源：[Session Live View](https://docs.browserbase.com/platform/browser/observability/session-live-view)。

我们的建议是：D 持有唯一浏览器会话，A 在 Otty 中并排显示或打开 Chrome 查看同一会话；C 管理接管与继续执行，B 保存必要的操作证据。新开一个登录页面不能代替查看执行会话。本轮已证明本地真实页面可见与操作，尚未完成跨入口实时显示、远程查看和人工接管。

## Itential：让 AI 使用已有自动化，而不是把每一步都交给模型

官方 FlowAI 文档将 agent 与确定的自动化工作流组合，工具执行由 Gateway 管理，会话追踪关联到实际任务。它提供不同角色的构建、运行和管理界面。来源：[FlowAI 概览](https://docs.itential.com/itential-platform/flowai/overview)、[执行引擎](https://docs.itential.com/itential-gateway/execution-engine)。

公开 ServiceNow 适配器把动作定义、输入输出格式和模拟数据组织起来，代码也检查返回中是否存在 response。核心能力部分位于依赖与商业平台，不能由适配器源码推断全平台实现。公开 dev-stack 要求镜像仓库访问，本輪只检查配置与启动说明，没有运行商业平台。来源：[公开适配器](https://gitlab.com/itentialopensource/adapters/adapter-servicenow)、[开发环境](https://github.com/itential/itential-dev-stack)。

我们的借鉴是：成熟的重复动作可以由程序执行，agent 负责选择方法、组合流程与分析新问题。E 保存按产品与版本验证的方法，D 执行；工具能返回 JSON 或通过 schema 检查，不等于操作成功，更不等于业务恢复。

## 本地网络实验已经说明了什么

九个场景全部通过，含真实两级 SSH、配置回读、完整终端字节、真实浏览器操作和进程生命周期检查。回执见[网络实验](sandbox-evidence/network-lab-receipt.json)。这里的“通过”是预先安排的本地场景得到观察，不是全平台通过验收。

| 观察 | 对产品设计的影响 |
|---|---|
| 管理接口 200，业务入口 502，直接访问后端 200；修正转发配置后业务入口恢复 200 | 调查要有独立观察点，能区分管理可达、前端转发与后端服务；本例只定位到合成转发配置，不泛化为所有 502 的原因 |
| 设备已执行配置，但回复连接断开；回读能找到操作记录，重复操作 ID 未增加变更次数 | 超时应先查证。本例去重是合成设备实现，真实产品必须另行核实，不能承诺通用 exactly-once |
| 本地 SSH 调用断开后，远端测试进程仍运行并产生结果 | 取消要检查真实执行状态；中断本地等待不能作为停止证明 |
| 同一 SSH 连接上的设备标识发生变化 | 连接存活不代表仍是原目标。本例验证了发现变化，没有实现阻止后续写入的强制边界 |
| 浏览器客户端关闭后浏览器进程仍存活，显式关闭 browser server 后停止 | 显示端、自动化连接与实际浏览器生命周期要分开管理 |

## 复杂网络 debug 应该成为怎样的产品能力

后续用户进一步明确：排障涵盖物理层到应用层，既要懂产品，也要熟悉网络，才能搭建网络环境测试。对应[判断与披露原则](../design/truth-and-disclosure.md)：100% 置真内容交给脚本，其余内容由 LLM 判定，完整披露输入输出。物理介质、交换、路由与回程、传输、加密和应用都要纳入环境设计；本轮回环实验没有验证这些层面的全部行为。

用户应当能提出“这条业务为什么不通”，平台首先明确哪一个产品、哪个版本、哪条业务、从哪里发起、什么结果才算正常。随后查现有拓扑和近期变更，确定调查的位置。SSH 能连上、管理 Web 能打开，都不能替代这一步。

调查时，D 从指定观察点采集 DNS 回答、TCP/TLS 连接、请求与响应、设备状态和相关日志；需要流量证据时，再在明确范围和时段内采集。B 将这些内容与目标、版本、时间和请求关联。E 根据产品方法解释，agent 比较解释是否能同时符合前端、设备和后端的观察。C 保存调查步骤、待证实原因和下一步，不因为模型表达得肯定就改成已证实。

例如 TLS 业务失败，平台不能只给出“证书问题”。应当核对请求使用的域名与 SNI、客户端看到的证书、设备选择的虚拟服务、设备到后端的 TLS 设置以及相关日志。若客户端握手已经失败，尚无证据说明后端也失败；若两段 TLS 都成功，则继续检查 HTTP 和应用行为。每个判断都应能打开对应原始记录。

多产品、多节点的复杂性，需要在同一任务里保留这些对象之间的关系：业务入口、虚拟服务、pool/member、健康检查、证书、网络路径、执行节点、配置版本和观察点。库存是查路的依据，实时观察用于确认现场；两者冲突时，应当呈现冲突并调查，不能自动用旧拓扑解释全部现象。

用户界面建议围绕三个问题组织：现在正在看什么现场；目前证明了什么；接下来为什么做这一步。A 显示当前终端、同会话浏览器、相关业务路径和证据，允许用户补充现象与接管；C 保留任务和决策；D 操作与观察；B 保存证据；E 提供产品方法。这些是现有对象需要具备的能力，本轮没有增加一个无明确职责的 debug 对象。

## 下一阶段需要补齐的证据

本轮已验证的是回环网络中的协议、进程、状态滞后与业务检查，尚未覆盖真实路由环境。后续应分批加入合成 DNS、TLS/SNI、代理、延迟与丢包、半开连接、会话失效、设备分页提示、多设备部分成功和网络路径变化。然后在真正隔离的网络中检验观测位置、流量关联和恢复行为。每一批都需要写清故障设置、独立观察和能排除的原因。

真实模型的诊断准确度需使用固定故障样本单独评估，不能由本轮指定动作和模拟模型测试推出。真实产品接入也需独立授权和兼容性验证。当前没有决定采用整套第三方平台；优先复用成熟的公开机制，把我们独有的产品知识、复杂网络调查和可核验交付补齐。
