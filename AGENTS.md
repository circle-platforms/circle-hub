# Instructions for agents

## Current scope

This is the public circle-hub repository. The Hub is being rebuilt as a standard MCP server (streamable HTTP, Bearer token) that verifies results and never generates them: six tools (`list_task_packs`, `upload_file`, `start_run`, `get_nodes`, `resolve_reference`, `submit_result`), task packs, a content-addressed knowledge tree per product line and version, append-only records and a web console whose pages are read-only and where administrators also manage users, tokens, packs, resources, secrets and knowledge sync, each action running the matching `circle-hub` command (decision 122). It serves HTTPS itself when configured (decision 121, `circle-hub tls`) and installs with one command on macOS and Linux (`install.sh`, release bundles, decision 123). The design authority is the generic model in `contracts/model.json`; read elements with `node tools/show-element.ts <ids>` and vocabulary axes with `node tools/show-element.ts --vocab <axis>`. The engineering brief for milestone 1 is `docs/hub-r4-architecture.md`: hard rules, package ownership, conventions, the case-review scenario, the structure of the real systems and the definition of done. Where the brief and the model disagree, the model wins; report the disagreement in your package README. The integrator records phase progress and the owner's decisions, each with its source, in `docs/hub-r4-progress.md`; a package agent records its own decisions, limits and needs in its package README (architecture section 10). The root README stays the public face. The maintained documentation set under `docs/` is declared in `.github/checks/doc-set.json` (`published`, `kept_internal`, `historical`, plus `docs/whitepaper.md` in `reserved`) and enforced with `.github/checks/exceptions.json` by `.github/checks/doc-set.ts`. User-facing text labels the Hub-wide shared knowledge space "公共空间" / "Public space" (distinct from created teams; its internal identifier `team` stays), while "团队" / "Team" refers to created teams used for workflow and business-system assignment (teams do not currently own separate per-team knowledge spaces).

Hub executables and configuration use only `circle-hub` and `CIRCLE_HUB_*`. The pre-rename environment names (`CIRCLE_SERVER_*`) were retired on 2026-10-16: they are not read or aliased, a hub process that still has one set refuses to start, and no fallback may be reintroduced. The Hub is not built on the Circle kernel. Circle and any other MCP client connect to it through an ordinary MCP server entry, and Circle shows no Hub-specific interface or label.

## Commands

Node >= 24, TypeScript run directly (type stripping; no build step).

```sh
npm ci
npm run typecheck                 # tsc --noEmit
npm run verify:contracts          # contracts/generated matches model.json, codes.json, contracts/src
npm run gen:contracts             # regenerate contracts/generated (never hand-edit it)
npm run test:unit                 # runs tools/run-unit-tests.ts (contracts, hub, packs, scripts)
npm run test:acceptance           # tests/acceptance, shared loopback PostgreSQL up to concurrency 8 (ACCEPTANCE_SHARD=i/n: concurrency 1)
npm run test:docs                 # .github/checks/*.test.ts
npm run verify:references && npm run test:references
npm test                          # contracts check + unit + docs + acceptance + references

node --test hub/runs/some.test.ts           # single test file
node --test --test-name-pattern="x" file.ts # single test by name
node --test "hub/server/**/*.test.ts"       # one package (a package agent's own check)

node tools/show-element.ts B01 W06          # print model elements
node tools/show-element.ts --vocab partition # print a vocabulary axis

bash install.sh --dry-run --version <x.y.z>  # the installer's plan, changing nothing
node tools/build-bundle.ts --platform darwin-arm64 --out <dir>   # build one release bundle
```

Tests start a temporary PostgreSQL from `embedded-postgres` (via `hub/testing/postgres.ts`). Backup/restore/deploy, `sandbox-exec` network denial and launchd tests need macOS and/or libpq (`pg_dump`/`pg_restore` of PG 18; `brew install libpq` or `CIRCLE_HUB_LIBPQ_BIN`) and skip elsewhere: a skip is not a pass; report skips explicitly. Never run `npm install` in a task worktree.

## Architecture

There are 15 packages under `hub/` with a strict dependency direction (cross-package calls go through each package's `api.ts` entrypoint, or `hub/config/index.ts` for `config`, with no cycles; enforced by `.github/checks/package-boundaries.ts` and `.github/checks/package-cycles.ts` from `.github/checks/package-edges.json`, plus temporary transition exceptions in `.github/checks/exceptions.json`). Leaf prefixes/packages: `config`, `platform`, and `contracts/`. Shared modules: `hub/ports.ts` (type-only shared interfaces) and `hub/listen.ts` (shared pure module). Narrow exceptions in `package-edges.json`: `hub/telemetry/usage.ts` (entrypoint exception importable only by `records`, `refs`, `rules`) and `hub/knowledge/directory-sources.ts -> packs/skill/adoc-format/api.ts` (pack exception).

Allowed direct dependencies (`package -> allowed_dependencies`):
- `config`, `platform`: `[]` (leaves)
- `records`: `config`
- `telemetry`: `config`, `records`
- `rules`: `telemetry`
- `refs`: `records`, `rules`, `telemetry`
- `connectors`: `records`, `refs`, `rules`, `telemetry`
- `health`, `jev`, `requests`: `records`
- `leases`: `config`, `records`
- `knowledge`: `connectors`, `jev`, `records`, `refs`, `rules`, `telemetry`
- `dispatch`: `connectors`, `leases`, `records`, `refs`, `telemetry`
- `runs`: `connectors`, `dispatch`, `knowledge`, `leases`, `records`, `refs`, `requests`, `rules`, `telemetry`
- `server`: `config`, `connectors`, `dispatch`, `health`, `knowledge`, `leases`, `platform`, `records`, `refs`, `requests`, `rules`, `runs`, `telemetry` (all other 13 `hub/` packages except `jev`)

Package responsibilities:
- `config`: Hub environment schema (`CIRCLE_HUB_*`), `retired.ts` (`CIRCLE_SERVER_*`, retired keychain vars) and runtime guards.
- `records`: append-only `records` table + content-addressed objects + the few mutable stores (users, teams, hashed tokens, root pointers with CAS, vault). Record digest = SHA-256 of RFC 8785 canonical JSON. `hub/records/migrations.ts` currently holds a single consolidated `baseline` migration (`version: 1`); applied migrations never change, and future schema changes append new checksummed migrations after it.
- `telemetry`: operational telemetry metrics/events and `usage.ts` helper.
- `rules`: interpreters and the sandbox that runs pack functions (child process, Node permission model plus macOS `sandbox-exec` or Linux bubblewrap/AppArmor network denial).
- `refs`: reference resolution, deterministic parsers, verbatim quote check.
- `connectors`: read-only access to business systems (GET / allow-listed read routes only).
- `knowledge`: tree, roots, producers, placement, personal spaces and the Hub-wide public space (`公共空间`, internal id `team`).
- `dispatch`: worker/task dispatch and scheduling.
- `runs`: pack loading, run engine, validation, per-(item, requirement, layer) terminal state and partitions. Unknown stays unknown, never failure or success.
- `health`, `jev`, `leases`, `requests`: database/system readiness checks (`health`), external evidence/JEV helpers for `knowledge` (`jev`), distributed leases (`leases`), and run/review request state (`requests`).
- `server`: MCP endpoint, web console, `circle-hub` CLI (`bin/circle-hub`). `platform`: key files (the vault master key and the operator token under `<data root>/keys`, on every platform; no macOS keychain), launchd/systemd, PG lifecycle, backup/restore/deploy/rehearsal.

`packs/` holds the product, workflow and system packs. `tests/fixtures` and `scripts/real/` (owner-run, read-only against real systems) are the only places where real-system structure appears.

## Authorizations and limits

Work on the hub-redesign branch. Since 2026-10-22 (decision 14 in `docs/hub-r4-progress.md`) every task has its own worktree and branch opened from hub-redesign, with its scope and allowed paths written in the pull request description rather than added under `docs/` (the maintained documentation set is fixed in `.github/checks/doc-set.json`); the agent doing the task commits only on that branch, and the integrator reviews it and merges it into hub-redesign with `git merge --no-ff --signoff`. Push, PR creation, GitHub settings or release-workflow changes, exposing the Hub beyond loopback, and any deployment other than the owner's persistent single-machine deployment require the owner's decision. The built-in HTTPS (decision 121 in `docs/hub-r4-progress.md`) is the owner's chosen way to reach a Hub on an internal address; enabling it on a deployment is still that deployment owner's decision. The release workflow (decision 123) only drafts a release on a version tag; pushing the tag and publishing the release remain the owner's decisions.

Circle's client lives in the separate Circle repository, and changing it requires the owner's explicit authorization. The scope planned for milestone 1 is the six generic MCP-client improvements of D06 R[1] and the removal of Circle's existing hub extension, which D06 R[1] ("no Hub-specific interface") requires; nothing Hub-specific is added, and the work stays on a separate Circle branch with local commits only and no push. The owner granted this scope, and more generally the whole Circle platform, on 2026-10-21 (decision 8 in `docs/hub-r4-progress.md`); only the integrator changes the Circle repository.

Tests, fixtures, CI and everything in Git use scripted models and synthetic fixtures only; fixtures mirror the structure of real systems, never their content. Real business systems are reached only by the deployed Hub and by the owner's scripts under `scripts/real/`, and only to read: GET and individually allow-listed read routes, no write route, no login retry after a failure.

The Hub calls no model and never generates content: it has no client for any model service, a typed-judgment service included (decision 15 of `docs/hub-r4-progress.md`; where knowledge placement needs a judgment, a bot proposes and the Hub verifies, which is not built yet). The reviewing models, the draft and its independent verification, run only on the Circle side (`classificationRules[8]` in the model): for the phase-5 real review, a Circle session of the owner's in a dedicated Circle home, connected to the deployed Hub, with model keys no agent ever sees. The owner granted the real review on 2026-10-21 and configures the endpoints (decision 7 of `docs/hub-r4-progress.md`; `resolvedConflicts[20]` of the model is rewritten accordingly). Tests, CI and package agents' development checks always use scripted models.

Circle Hub and its packs support macOS and Linux; Windows is not supported (owner's decision, 2026-10-30). The native Windows work on the `synthetic-platform/*` and `docs/windows-probe-*` branches is frozen: do not continue, rebase or merge it, and do not add Windows code paths or Windows CI without the owner's authorization. A pack may refuse to run on Windows instead.

Never open the owner's environment file or the owner's own credential stores yourself: only the scripts under `scripts/real/` read the environment file, at run time, take only the keys they name, and print key names, presence and lengths (never values); the owner or the integrator runs them. Tests use temporary data roots with their own key files and scratch vaults; the Hub's key files (the vault master key and the operator token under `<data root>/keys`; the Hub no longer uses the macOS keychain, decision 137) are handled only through its platform commands (`circle-hub key …`, `circle-hub operator-token …`), and secrets enter the Hub only through its vault commands. Real devices, writes to business systems and Python runtime dependencies are outside this authorization. SyntheticReference is a read-only behavioural reference: never run, import or copy its code, configuration values, credentials, hosts or business data. Never commit credentials, internal addresses, real business data or local absolute paths.

## Source and reference ownership

- The frozen public Circle baseline and its provenance remain in `foundation/circle` and `references/`. Keep the bytes and notices intact. Use these files for reference verification only.
- Every piece of content has one of the model's four homes (C01: knowledge, policy, method, resource) and one of its four ownership classes (C02): generic content goes into the Hub core, product content into a product pack, a system adapter into a system pack, workflow content into a workflow pack. Core code names no product, command or customer. Today `hub/` contains 15 packages (`config`, `records`, `telemetry`, `rules`, `refs`, `connectors`, `knowledge`, `dispatch`, `runs`, `server`, `health`, `jev`, `leases`, `requests`, `platform`), plus shared type-only interfaces in `hub/ports.ts` and shared pure module `hub/listen.ts`. Section 4 of `docs/hub-r4-architecture.md` lists package file ownership (and lags on `config`, `dispatch`, `jev`, `leases`, `requests`, and `rules -> telemetry`), while `.github/checks/package-edges.json` is the enforceable boundary authority (checked with cycle detection by `.github/checks/package-boundaries.ts` and `.github/checks/package-cycles.ts`, with temporary transition exceptions in `.github/checks/exceptions.json`): `config` (`hub/config/index.ts`), `platform`, and `contracts/` are leaves; `records -> config`; `telemetry -> config, records`; `rules -> telemetry`; `refs -> records, rules, telemetry`; `connectors -> records, refs, rules, telemetry`; `health -> records`; `jev -> records`; `leases -> config, records`; `requests -> records`; `knowledge -> connectors, jev, records, refs, rules, telemetry`; `dispatch -> connectors, leases, records, refs, telemetry`; `runs -> connectors, dispatch, knowledge, leases, records, refs, requests, rules, telemetry`; `server` may import all other 13 `hub/` packages except `jev`; `hub/telemetry/usage.ts` is an entrypoint exception importable only by `records`, `refs`, and `rules`; and `hub/knowledge/directory-sources.ts -> packs/skill/adoc-format/api.ts` is the sole core-to-pack exception. Edit only your own package's files, call other packages only through their declared entrypoints (`api.ts`, or `hub/config/index.ts` for `config`), and write what you need from another package in your README. Classification and code existence are not production availability.
- Records are append-only and derived state is recomputed from them; `hub/records/migrations.ts` currently holds a single consolidated `baseline` migration (`version: 1`). An applied database migration never changes; future schema changes append new checksummed migrations after the baseline. The earlier implementation is readable with `git show ca66002:<path>`: copy and adapt it, never import it, and do not import archived platform modules into runtime entry points.
- New code is TypeScript run directly by Node 24 (erasable syntax only: no `enum`, parameter properties or namespaces; imports ending in `.ts`; ESM) with exactly the dependencies in package.json. Enumerations, codes and their texts come only from `contracts/generated`: `vocabulary.ts` for the vocabulary axes, `protocol.ts` for record kinds, protocol and core violation codes, reference forms, pack file paths and the display order; vocabulary labels come only from `labelOf`. Never write an enumeration by hand and never coin a term. User-facing text is Chinese; tool and schema descriptions for models and code comments are English. Do not turn archived Python bridge or old SyntheticReference/compile runtimes into production dependencies.
- Errors are thrown as typed errors carrying a registered code (`PROTOCOL_CODES`, `CORE_VIOLATION_CODES`, `<pack>.<code>`); a new code is requested from the contracts owner, never invented. Pack functions are pure modules (`export default function (input: unknown): unknown`).

## Evidence and changes

Use scripts for conclusions established by explicit inputs and rules; use model judgments for other content and label them as judgments. Facts come only from versioned rules and integrity-checked observations re-run at the Hub boundary; every exact value resolves to a reference; unknown stays unknown and is never shown as a failure or a success. Disclose actual inputs, outputs, transformations and missing evidence to authorized users. Tool returns, model conclusions, produced artifacts, observed effects and verified outcomes remain distinct.

A failed read follows D05 R[3] in `contracts/model.json`: for public-space (internal id `team`), product and business-system content, absent is `SOURCE_ABSENT` and present but unreadable is `SOURCE_NOT_PERMITTED`; another member's personal-space content and credential or login failures stay neutral (`SOURCE_UNAVAILABLE`), with the real cause only in the admin call log.

Never use real Circle data, personal browser profiles or production devices for development checks; use scratch homes and synthetic resources. Local cancellation does not prove remote stopping.

## Git and commits

Inspect status and diffs and preserve other people's work; use isolated worktrees for parallel work. Stage explicit paths and never use `git add -A`, `git add .` or `git commit -a`. Commit messages are one capitalized imperative English sentence without a prefix or final full stop, and every commit is signed off (`git commit -s`, see CONTRIBUTING.md). Commit and push only within user authorization; pull before pushing, because maintainers push from more than one machine. Keep credentials, internal addresses and connection strings (samples use 192.0.2.0/24), raw business documents, logs, conversation dumps and local absolute paths out of Git. This section is identical in circle-hub and circle-packs; change it in both.

## Verification

A package agent runs `npx tsc --noEmit` and its own tests, `node --test "<own paths>/**/*.test.ts"`, and reports errors of other packages that are mid-edit instead of fixing them. The integrator checks by risk (the owner's decision of 2026-11-02): each merge runs the affected packages' tests and the cross-package acceptance the change touches, and the whole set runs once before every deployment: `npm run typecheck`, `npm run verify:contracts`, `npm run test:unit`, `npm run test:acceptance` (`npm test` runs the contracts check and the unit, docs and acceptance tests; the docs checks are `npm run test:docs`).

`contracts/generated` is generated from `contracts/model.json`, `contracts/codes.json` and the shapes in `contracts/src`, and is never edited by hand. A model change goes through the integrator, and a new code is requested from the contracts owner. A package that changes the `contracts/src` file it owns (`pack.ts`, `knowledge.ts`, `resources.ts`, `tables.ts`) runs `npm run gen:contracts` and hands the regenerated files in with its change; the contracts owner reviews that generated diff (`contracts/README.md`). Run checks before committing after changing provenance tooling or approved imports.

Acceptance uses a temporary loopback PostgreSQL through `hub/testing/postgres.ts`, synthetic fixtures and scripted models. SHA verification, static declarations and synthetic passes do not establish business correctness or a result on a real system. Say exactly which commands ran and what they returned; a skipped, unrun or weakened test is not a pass. A test may be deleted only when the subject it tests has been removed by decision, citing that decision in the commit or deletion record; otherwise a failing test must be fixed, and assertions must never be relaxed to make a check pass.

A test never asserts an absolute wall-clock limit (`elapsed < N` milliseconds): such a limit measures the runner as much as the code, and a correct change turns red on a slow or crowded runner. Super-linear work is checked with the growth ratio of `hub/testing/growth.ts` (the calling thread's CPU time between two input sizes), an ordering ("returns before the slow step finishes") against the slow step's own completion signal, a timeout by the outcome it reports under an injected limit, and scale by counts of queries, reads, batches or launches; a hang is caught by the test's own `{ timeout }` option or by a generous ceiling paired with a growth check (`CEILING_MS`, about ten times the slowest CI time). Lower bounds and polling loops with a deadline are not limits of this kind.

`docs/compatibility.md` and `docs/compatibility.en.md` are updated in the same pull request whenever a compatibility fact changes: a component's version or commit, a contract, schema or model version, the MCP SDK, how Circle connects, the release order, the supported platforms, or a configuration name that is added or retired. The change adds a dated line to the History section of both pages; the Chinese page is authoritative.

Root CI runs on Ubuntu: types, the contracts check, unit tests, acceptance, the pack sandbox under Linux isolation, the reference archive and the docs checks. A pull request runs only the fast checks (`Types`, `Generated contracts match the model`, `Docs and CI checks`, `Reference archive`); the merge queue, on the commit that becomes main, and every push to main run the full suite. On a pull request the shards are skipped and so are their aggregates, which a required check counts as passed; in the merge queue and on main each aggregate passes only when all its shards pass. Unit tests run as three shards of `regular` (`UNIT_SHARD`) plus `parser-bounds`, and acceptance as four slices (`ACCEPTANCE_SHARD`, balanced by the measured durations in `tools/run-acceptance-tests.ts`); `Unit tests` and `Acceptance on a temporary PostgreSQL` each pass only when all their shards pass. Each test job lists its counts and every skipped test in the job summary and fails when no test ran. The unit, acceptance and Linux isolation jobs also list their slowest test files there, from Node's junit report (`JUNIT_REPORT`, kept for 14 days), against which the measured durations that balance the shards can be checked. The `regular` unit shards install the PostgreSQL 18 client from the PostgreSQL apt repository, so backup, restore and deploy, which need `pg_dump` and `pg_restore` of the embedded server's major version, run on Ubuntu. These unit and acceptance jobs have no operating-system isolation, so the tests that guard on the pack sandbox skip there. They run in the `Linux isolation` jobs instead, in the merge queue and on every push to main: two unit and two acceptance slices (`GUARDED_SHARD`, balanced by the measured durations in `tools/run-guarded-tests.ts`) that install bubblewrap and AppArmor, load the Hub's AppArmor policy generated by `hub/rules/sandbox/linux.ts` for the job's own Node, fail unless `osIsolationAvailable()` is true, and run the unit and acceptance files that guard on the sandbox (selected from the sources by `tools/run-guarded-tests.ts linux`); `Linux isolation` passes only when all four pass. They leave `kernel.apparmor_restrict_unprivileged_userns` at the runner's default: the launcher profile's `userns` rule is enough. What needs macOS skips on Ubuntu: `sandbox-exec` itself, plutil and the launchd checks. The `macOS-only paths` workflow (`.github/workflows/macos.yml`, `macos-15`) runs the test files that guard on those or on the sandbox (selected by `tools/run-guarded-tests.ts macos`) on every push to main, nightly and on demand, never on pull requests, and is not a required check; the merge queue is therefore evidence for the pack sandbox under bubblewrap and AppArmor, but not for `sandbox-exec`, plutil or launchd, and a pull request's own checks are evidence for neither. A test file that imports a sandbox entry point uses `sandboxSkip()`, `osIsolationAvailable()` or `requireOsIsolation: false` (`.github/checks/sandbox-guards.ts`). Each deployment records the full local macOS run it was made from, with its skips, in `docs/hub-r4-progress.md`. Do not publish a release or enable deployment workflows without authorization.
