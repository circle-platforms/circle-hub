# Instructions for agents

## Current scope

This is the public circle-hub repository. The Hub is being rebuilt as a standard MCP server that verifies results and never generates them: six tools, task packs, a content-addressed knowledge tree per product line and version, append-only records and a web console where administrators also manage the Hub (decision 75). The design authority is the generic model in `contracts/model.json`; read elements with `node tools/show-element.ts <ids>` and vocabulary axes with `node tools/show-element.ts --vocab <axis>`. The engineering brief for milestone 1 is `docs/hub-r4-architecture.md`: hard rules, package ownership, conventions, the case-review scenario, the structure of the real systems and the definition of done. Where the brief and the model disagree, the model wins; report the disagreement in your package README. `docs/hub-r4-brief.md` states the milestone for people. The integrator records phase progress and the owner's decisions, each with its source, in `docs/hub-r4-progress.md`; a package agent records its own decisions, limits and needs in its package README (architecture section 10). The root README stays the public face. Pages under `docs/` marked historical or superseded describe the retired task-and-approval server; they are records, not instructions.

Hub executables and configuration use only `circle-hub` and `CIRCLE_HUB_*`. The pre-rename environment names were retired on 2026-10-16: they are not read or aliased, a hub process that still has one set refuses to start, and no fallback may be reintroduced. The Hub is not built on the Circle kernel. Circle and any other MCP client connect to it through an ordinary MCP server entry, and Circle shows no Hub-specific interface or label.

## Authorizations and limits

Work on the hub-redesign branch. Since 2026-10-22 (decision 14 in `docs/hub-r4-progress.md`) every task has its own worktree and branch opened from hub-redesign and a task page under `docs/hub-r4-tasks/` that lists the paths it may change; the agent doing the task commits only on that branch, and the integrator reviews it and merges it into hub-redesign with `git merge --no-ff --signoff`. Push, PR creation, GitHub settings or release-workflow changes, exposing the Hub beyond loopback, and any deployment other than the owner's persistent single-machine deployment require the owner's decision. The built-in HTTPS (decision 74 in `docs/hub-r4-progress.md`) is the owner's chosen way to reach a Hub on an internal address; enabling it on a deployment is still that deployment owner's decision. The release workflow (decision 76) only drafts a release on a version tag; pushing the tag and publishing the release remain the owner's decisions.

Circle's client lives in the separate Circle repository, and changing it requires the owner's explicit authorization. The scope planned for milestone 1 is the six generic MCP-client improvements of D06 R[1] and the removal of Circle's existing hub extension, which D06 R[1] ("no Hub-specific interface") requires; nothing Hub-specific is added, and the work stays on a separate Circle branch with local commits only and no push. The owner granted this scope, and more generally the whole Circle platform, on 2026-10-21 (decision 8 in `docs/hub-r4-progress.md`); only the integrator changes the Circle repository.

Tests, fixtures, CI and everything in Git use scripted models and synthetic fixtures only; fixtures mirror the structure of real systems, never their content. Real business systems are reached only by the deployed Hub and by the owner's scripts under `scripts/real/`, and only to read: GET and individually allow-listed read routes, no write route, no login retry after a failure.

The Hub calls no model and never generates content: it has no client for any model service, a typed-judgment service included (decision 15 of `docs/hub-r4-progress.md`; where knowledge placement needs a judgment, a bot proposes and the Hub verifies, which is not built yet). The reviewing models, the draft and its independent verification, run only on the Circle side (`classificationRules[8]` in the model): for the phase-5 real review, a Circle session of the owner's in a dedicated Circle home, connected to the deployed Hub, with model keys no agent ever sees. The owner granted the real review on 2026-10-21 and configures the endpoints (decision 7 of `docs/hub-r4-progress.md`; `resolvedConflicts[20]` of the model is rewritten accordingly). Tests, CI and package agents' development checks always use scripted models.

Circle Hub and its packs support macOS and Linux; Windows is not supported (owner's decision, 2026-10-30). The native Windows work on the `synthetic-platform/*` and `docs/windows-probe-*` branches is frozen: do not continue, rebase or merge it, and do not add Windows code paths or Windows CI without the owner's authorization. A pack may refuse to run on Windows instead.

Never open the owner's environment file or the owner's own credential stores yourself: only the scripts under `scripts/real/` read the environment file, at run time, take only the keys they name, and print key names, presence and lengths (never values); the owner or the integrator runs them. Tests use temporary keychain files and scratch vaults; the Hub's keychain item is handled only through its platform commands (`circle-hub key …`), and secrets enter the Hub only through its vault commands. Real devices, writes to business systems and Python runtime dependencies are outside this authorization. SyntheticReference is a read-only behavioural reference: never run, import or copy its code, configuration values, credentials, hosts or business data. Do not change foundation/circle or references bytes. Never commit credentials, internal addresses, real business data or local absolute paths.

## Source and reference ownership

- foundation/circle is the selected public TS source baseline. Keep its provenance and original license/notices. Do not run its client installers, updater or release scripts as server installation or deployment.
- The archive of the platform that preceded the hub was removed from this public repository on 2026-10-30 (owner's decision); `references/source-manifest.json` now records only foundation/circle. Do not add it back.
- Every piece of content has one of the model's four homes (C01: knowledge, policy, method, resource) and one of its four ownership classes (C02): generic content goes into the Hub core, product content into a product pack, a system adapter into a system pack, workflow content into a workflow pack. Core code names no product, command or customer. Section 4 of `docs/hub-r4-architecture.md` lists the work packages and the exact paths each one owns: edit only your own, call other packages only through their `api.ts`, and write what you need from another package in your README. Classification and code existence are not production availability.
- Records are append-only and derived state is recomputed from them; an applied database migration never changes, a new migration is added instead. The earlier implementation is readable with `git show ca66002:<path>`: copy and adapt it, never import it, and do not import archived platform modules into runtime entry points.
- New code is TypeScript run directly by Node 24 (erasable syntax only, imports ending in `.ts`, ESM) with exactly the dependencies in package.json. Enumerations, codes and their texts come only from `contracts/generated`: `vocabulary.ts` for the vocabulary axes, `protocol.ts` for record kinds, protocol and core violation codes, reference forms, pack file paths and the display order; vocabulary labels come only from `labelOf`. Never write an enumeration by hand and never coin a term. User-facing text is Chinese; tool and schema descriptions for models and code comments are English. Do not turn archived Python bridge or old SyntheticReference/compile runtimes into production dependencies.

## Evidence and changes

Use scripts for conclusions established by explicit inputs and rules; use model judgments for other content and label them as judgments. Facts come only from versioned rules and integrity-checked observations re-run at the Hub boundary; every exact value resolves to a reference; unknown stays unknown and is never shown as a failure or a success. Disclose actual inputs, outputs, transformations and missing evidence to authorized users. Tool returns, model conclusions, produced artifacts, observed effects and verified outcomes remain distinct.

Never use real Circle data, personal browser profiles or production devices for development checks; use scratch homes and synthetic resources. Local cancellation does not prove remote stopping.

Reference verification may read source bytes; it must never import or execute archived business modules.

## Git and commits

Inspect status and diffs and preserve other people's work; use isolated worktrees for parallel work. Stage explicit paths and never use `git add -A`, `git add .` or `git commit -a`. Commit messages are one capitalized imperative English sentence without a prefix or final full stop, and every commit is signed off (`git commit -s`, see CONTRIBUTING.md). Commit and push only within user authorization; pull before pushing, because maintainers push from more than one machine. Keep credentials, internal addresses and connection strings (samples use 192.0.2.0/24), raw business documents, logs, conversation dumps and local absolute paths out of Git. This section is identical in circle-hub and circle-packs; change it in both.

## Verification

A package agent runs `npx tsc --noEmit` and its own tests, `node --test "<own paths>/**/*.test.ts"`, and reports errors of other packages that are mid-edit instead of fixing them. The integrator runs the whole set: `npm run typecheck`, `npm run verify:contracts`, `npm run test:unit`, `npm run test:acceptance`, `npm run verify:references`, `npm run test:references` (`npm test` runs the contracts check and the unit, docs, acceptance and reference tests; the docs checks are `npm run test:docs`).

`contracts/generated` is generated from `contracts/model.json`, `contracts/codes.json` and the shapes in `contracts/src`, and is never edited by hand. A model change goes through the integrator, and a new code is requested from the contracts owner. A package that changes the `contracts/src` file it owns (`pack.ts`, `knowledge.ts`, `resources.ts`, `tables.ts`) runs `npm run gen:contracts` and hands the regenerated files in with its change; the contracts owner reviews that generated diff (`contracts/README.md`). Run npm run verify:references and npm run test:references after changing provenance tooling or approved imports.

Acceptance uses a temporary loopback PostgreSQL through `hub/testing/postgres.ts`, synthetic fixtures and scripted models. SHA verification, static declarations and synthetic passes do not establish business correctness or a result on a real system. Say exactly which commands ran and what they returned; a skipped, unrun or weakened test is not a pass, and a failing test is fixed or explained, never deleted.

Root CI runs on Ubuntu: types, the contracts check, unit tests, acceptance, the pack sandbox under Linux isolation, the reference archive check and the docs checks. Unit tests run as three shards of `regular` (`UNIT_SHARD`) plus `parser-bounds`, and acceptance as four slices (`ACCEPTANCE_SHARD`, balanced by the measured durations in `tools/run-acceptance-tests.ts`); `Unit tests` and `Acceptance on a temporary PostgreSQL` each pass only when all their shards pass. Each test job lists its counts and every skipped test in the job summary and fails when no test ran. The unit, acceptance and Linux isolation jobs also list their slowest test files there, from Node's junit report (`JUNIT_REPORT`, kept for 14 days), against which the measured durations that balance the shards can be checked. The `regular` unit shards install the PostgreSQL 18 client from the PostgreSQL apt repository, so backup, restore and deploy, which need `pg_dump` and `pg_restore` of the embedded server's major version, run on Ubuntu. These unit and acceptance jobs have no operating-system isolation, so the tests that guard on the pack sandbox skip there. They run in the `Linux isolation` jobs instead, on every pull request and push to main: two unit and two acceptance slices (`GUARDED_SHARD`, balanced by the measured durations in `tools/run-guarded-tests.ts`) that install bubblewrap and AppArmor, load the Hub's AppArmor policy generated by `hub/rules/sandbox/linux.ts` for the job's own Node, fail unless `osIsolationAvailable()` is true, and run the unit and acceptance files that guard on the sandbox (selected from the sources by `tools/run-guarded-tests.ts linux`); `Linux isolation` passes only when all four pass. They leave `kernel.apparmor_restrict_unprivileged_userns` at the runner's default: the launcher profile's `userns` rule is enough. What needs macOS skips on Ubuntu: `sandbox-exec` itself, the keychain, plutil and the launchd checks. The `macOS-only paths` workflow (`.github/workflows/macos.yml`, `macos-15`) runs the test files that guard on those or on the sandbox (selected by `tools/run-guarded-tests.ts macos`) on every push to main, nightly and on demand, never on pull requests, and is not a required check; a pull request is therefore evidence for the pack sandbox under bubblewrap and AppArmor, but not for `sandbox-exec`, the keychain, plutil or launchd. A test file that imports a sandbox entry point uses `sandboxSkip()`, `osIsolationAvailable()` or `requireOsIsolation: false` (`.github/checks/sandbox-guards.ts`). Each phase still records a full local macOS run, with its skips, in `docs/hub-r4-progress.md`. Inherited workflows remain inactive below foundation. Do not publish a release or enable deployment workflows without authorization.
