# 判定规则差分测试发现的引擎缺陷

参照实现在 `oracle.ts`，差分测试在 `differential.test.ts`。下面 7 条是参照按模型原文得出、引擎没有照做的地方。引擎代码没有改。每条测试都把引擎的现状钉住：引擎按建议改过之后，对应断言会失败，到那时再改断言。

严重程度只看对验收结论的影响。高：会把不该交付的结论交付出去，或者让“起草方不能签结论”失效。中：终态、归责或轮数是错的，但在当前钉住的场景里没有把独立判断签成满足。

按严重程度从高到低。

## 1. 同一份提交换会话重放，独立判断仍算满足

状态：已修。同一会话、同一声明模型的重放仍交回旧回执；会话或模型不同则按本次调用重算。

严重程度：高。

种子：`20261127`（`SEED + 105`）。前一份已被接受的提交是种子 `20261123`（`SEED + 101`）：前驱包 `oracle-draft`，作者会话 `sess-author`、模型 `alpha@1`；复核运行用 `oracle`，启动会话和提交会话都是 `sess-judge`，模型 `beta@2`，独立判断满足。种子 `20261127` 把同一份正文用作者会话 `sess-author`、模型 `beta@2` 再交给这同一个复核运行。

模型原文：A04 R[5]，作者未知时独立性记未知；作者与判断者同属一方时不是独立。要求项合约写明，独立判断只由另一个会话、另一个模型相对前驱运行来满足（`contracts/src/pack.ts` 里 `independent_of` 的说明，A04）。复核这条线的保证是起草方不能签结论（`hub/runs/engine/lineage.ts` 开头的说明）。

引擎实际：`hub/runs/engine/submit.ts` 的 `submitLocked` 用 `(run, 提交摘要)` 取已存结果（约第 135–136 行）。摘要只覆盖提交正文，不含本次调用观察到的会话。正文没变就直接 `answerOf` 交回旧回执，不再走同文件约第 353 行的 `origin`（运行启动会话加上本次 `sessionOf(call)`）和第 354 行的 `authorOriginOf`。

参照：这份提交的判断者会话就是作者会话，独立判断未满足，原因是独立性未知。

后果：独立复核被接受之后，起草方用自己的会话把同一份正文再交一次，回执仍写独立判断满足。起草方不能签结论这条保证在这条路上失效。正文改一个字节就会重新比较会话，这个洞只对原样重放成立，原样重放正是把复核回执再签一次的做法。

建议的修法：改 `hub/runs/engine/submit.ts` 的 `submitLocked`。同一摘要再次提交时，若本次观察到的会话或声明的模型与当初写入 `validate` 动作的 `detail.session`、`detail.model` 不同，不要交回旧回执，按本次调用重算独立性。不要改参照。

## 2. 声明跳过只盖住判断类要求项

状态：已修。声明跳过的条目，事实要求和判断要求都在已声明的层上记未完成（模型声明跳过）。

严重程度：高。

种子：`20261029`（`SEED + 7`），条目 `i1` 声明跳过，其余条目已处理，检查都返回支持。

模型原文：W07 R[2]，条目处理声明只是声明，终态由 Hub 计算；模型声明跳过的条目，各要求项在它声明的各层记未完成（模型声明跳过，附理由）。

引擎实际：`hub/runs/engine/terminals.ts` 的 `staticTerminal`（约第 117–123 行）只在生产者不是事实时看处理声明。事实要求项继续用检查结局。`hub/runs/engine/evaluate.ts` 约第 388 行也只把 `handling` 传给判断类要求项，事实要求项传入 `null`。种子上 `i1/fact` 因此是未核对、缺输入（脚本在没有槽位时返回这个未知）；`i1/judged` 才是未完成、模型声明跳过、不归责。

参照：`i1` 的每个要求项、每个已声明层都是未完成、模型声明跳过、不归责。

后果：在这个包里，`judged` 等必需要求项仍把条目留在未完成，跳过没有被收成已交付。若一个包的必需要求项都是事实，声明跳过不会制造未完成层，条目可以按 V05 R[3] 第 6 步进入已交付，跳过声明等于没生效。这不直接让起草方签独立结论，它让“跳过由 Hub 改写成未完成”这条保证对事实要求项失效。

建议的修法：在 `staticTerminal` 里先看处理声明，跳过和未覆盖对全部要求项生效，再谈检查结局。`evaluate.ts` 组 `staticTerminal` 参数时，事实要求项也传入同一个 `handling`。不要改参照。

## 3. 缺失条目只盖住判断类要求项，并报轮数已经用完

状态：终态已修。有条目判断槽的提交里，缺了的条目上每个要求项都记未完成（提交未覆盖）。只有事实、模型没有条目槽可交的包仍由 Hub 重算事实（生产运行上的评论不把事实擦成未覆盖）。errors 仍用 `core.coverage.shortfall`，剩余轮数仍按判断类要求项的最小值，这两处模型没有排定（选择 11），没有改。

严重程度：高。

种子：`20261030`（`SEED + 8`），条目 `i3` 没有处理声明，其余条目已处理且检查都支持。提交仍被受理。

模型原文：W07 R[3]，提交里缺某个条目时不因此整份不受理；该条目各要求项在它声明的各层记未完成（提交未覆盖），在 errors 里点名，计入修复轮数。模型没有给这个错误指定码，也没有说剩余轮数按 0 计。

引擎实际：与第 2 条同一处，`staticTerminal` 不把未覆盖用于事实要求项，所以 `i3/fact` 是未核对、缺输入。判断类要求项（如 `i3/judged`）才是未完成、提交未覆盖。`hub/runs/engine/evaluate.ts` 约第 463–475 行另发 `core.coverage.shortfall`，`rounds_left` 取判断类要求项剩余轮数的最小值（约第 360 行 `roundsLeftOf`）。这些要求项没有修复行，最小值是 0。

参照：`i3` 的每个要求项都是未完成、提交未覆盖、不归责。errors 只有一条不带码的点名，`rounds_left` 是运行最大修复轮数 3（一处还没消耗）。

后果：缺失条目的事实要求项仍像跑过检查。errors 里的 `rounds_left: 0` 把“计入修复轮数”写成已经没有轮数。只含事实要求项的包同样可能把缺失条目收成已交付。这不直接签独立结论。

建议的修法：与第 2 条一起改 `staticTerminal` 和 `evaluate.ts` 第 388 行附近，让未覆盖盖住全部要求项。第 463–475 行的点名按 W07 R[3] 计入尚未用完的修复轮数，不要在没有修复行时写成 0。模型没有规定码 `core.coverage.shortfall`，是否保留这个码要所有者定（见文末选择 11）。不要改参照。

## 4. 没声明的检查档被写成提示档

状态：已定/已修。所有者 2026-10-22 决定：每个检查必须声明档，发布时强制（缺 tier 则拒收 checks.tier_missing）。运行时起初保留旧版本缺省（有 basis 就阻断、否则提示）；2026-10-23 规矩核对后按决定移除回退：运行时再遇到没有档的包内函数检查，不运行、不猜档，按检查出错处理（未核对，原因“检查出错”，归责“生产者错误”，管理员日志写明缺档），在 hub/rules/check.ts 写明并用测试钉住。differential.test.ts 种子 20261223 钉住发布拒绝与运行时缺档出错，从随机生成空间中移除无 tier 检查，并遍历验证仓库内所有包均声明了 tier。

严重程度：中。

种子：`20261223`（`SEED + 201`），条目 `i1`、要求项 `loose`。`checks.json` 里 `c_loose` 没有 `tier`，也没有 `basis`。包内函数返回的反驳带 `tier: blocking`。

模型原文：检查条目的 `tier` 是声明档，有声明时替换该检查各结局的档（参照选择 9；`hub/rules/check.ts` 文件头对 `tier` 的说明也是“代替表里的档”）。没有声明时，合约没有说用提示档替换函数自己返回的档。W02 F[7]：进已拒收只用于待判定产物上的阻断检查码，档被改成提示之后这条拒收不会发生。

引擎实际：`hub/rules/check.ts` 的 `runCheck` 在约第 134 行把缺省档定成 `declaration.tier ?? (basis ? 'blocking' : 'advisory')`，约第 181 行 `withTier`（第 90–95 行）把这个缺省档写回每个结局。函数返回的 `blocking` 变成 `advisory`。

参照：检查没有声明档，保留函数返回的 `blocking`。

后果：包内函数给出的阻断反驳，只要检查条目省略了 `tier`，回执上就是提示档，不能按 W02 F[7] 把条目送进已拒收。独立判断的满足与否不因此改变。

建议的修法：改 `hub/rules/check.ts` 的 `withTier` 调用（约第 181 行）。只有 `declaration.tier` 有值时才替换结局的档；省略时保留函数返回的档。负例结局保持现在的例外。不要改参照。

## 5. 主体上的修复行不进入修复，轮数永远不消耗

状态：已定/已修。所有者 2026-10-22 决定：维持引擎读法。修复只用于待判定产物上的检查；评审主体上的反驳停在不通过，归作者输入，不进入修复，也不消耗修复轮数。改 oracle.ts 参照，引擎不改；contracts/model.json T03 R[4]、W02 F[7] 与 docs/hub-r4-architecture.md 第 6 节加原则说明。

严重程度：中。

种子：`20261222`（`SEED + 200`）。同一运行上连续两次提交，`i1/short` 都反驳 `oracle.hit`。该码的修复行最多 1 轮，检查 `c_short` 判断的是主体。

模型原文：W02 F[7]，码映射到修复（最多 n 轮）。W02 R[5]，修复轮数用完时，该要求项在它声明的各层记未完成（修复轮数用完），errors 带剩余轮数。T03 R[4]，归责和去向由错误处理表给出；只有陈述与它所引的源不一致时，才归生产者错误并进入修复。

引擎实际：`hub/runs/engine/terminals.ts` 的 `rowApplies`（约第 178–179 行）规定修复行只用于判断待判定产物的检查。主体上的反驳留在不通过，不进入 `detail.repair`。`hub/runs/engine/submit.ts` 的 `roundsUsedOf`（约第 61–72 行）只数先前校验动作里 `detail.repair` 列出的要求项。第二次提交因此仍是不通过、归作者输入，`rounds.used` 仍是 0。待判定产物上的修复行会进这个计数，引擎自己的提交测试里看得到；本条钉住的是主体这条路径。

参照：该行预算是 1，前一份提交已经用掉一轮，第二次在全部已声明层记未完成、修复轮数用完，归生产者错误，errors 里 `rounds_left` 为 0，`rounds.used` 为 1。归责仍按 T03 R[4]：主体不是“与所引的源不一致”，所以进入修复之前归作者输入；轮数用完之后的未完成归生产者错误。

后果：写在主体检查上的修复预算不会用完，同一条反驳可以一直以已交付的不通过交回来。这不让起草方签独立结论。错误表里的“修复”对主体是否生效，模型两句话可以读成两边，见文末选择 8；在所有者改口之前，参照保持“表给出的去向仍然是修复”。

建议的修法：若所有者维持参照的读法，改 `rowApplies`，让修复行也适用于主体上的反驳，并让该要求项进入 `roundsUsedOf` 所数的 `detail.repair`。归责不要改成生产者错误，除非轮数已经用完。若所有者采纳引擎现在的读法（修复只针对待判定产物），再改参照，不要先改引擎。不要在本文件之外动手。

## 6. “记未知”把反驳改写成完整性未证明

状态：已定/已修。所有者 2026-10-22 决定：照参照改引擎。动作 unknown 不改终态，反驳仍是不通过，码和档照记，归责留空（待归因，不走数据缺口），状态为未满足。已改 hub/runs/engine/terminals.ts 的 applyRouting。

严重程度：中。

种子：`20261222`（`SEED + 200`），条目 `i1`、要求项 `recorded`。错误表对该码的动作是 `unknown`（记未知）。检查返回反驳 `oracle.hit`、阻断档。

模型原文：V01 R[6]，反驳映射到不通过。W02 F[7] 的“记未知”是错误处理表里的去向，与修复、进已拒收、发请求并列。V04 F[5]，没有规则能判谁来回答时归待归因。V03 R[5] 的“完整性未证明”是动态层证明不了完整性时的无判定，不是静态反驳的原因。

引擎实际：`hub/runs/engine/terminals.ts` 的 `applyRouting` 约第 220 行把动作 `unknown` 写成未核对、原因 `integrity_unproven`。同文件 `BY_REASON` 约第 238 行把这个原因归成数据缺口。要求项状态是未决。

参照：终态保持不通过，码和档照记，不归责，状态是未满足（终态不符合期望）。记未知不修复、不拒收。

后果：一条已经返回的反驳在回执上变成“完整性没证明”的数据缺口，看起来像还没跑完，而不是不符合期望。条目不因此进入已拒收。独立判断是否满足不因此改变。

建议的修法：改 `applyRouting` 约第 220 行，动作 `unknown` 不要改终态、不要写 `integrity_unproven`。不通过上的归责按 V04 F[5] 留空（待归因），不要走 `BY_REASON` 的数据缺口。不要改参照。

## 7. 同一个任务包的前驱不算作者

状态：已修。前驱链没有离开本包时，这些运行就是作者。链上还有另一个包时，仍以那个包的草稿为作者，不把同包的上一稿算进去（复核修订仍对草稿负责，这条没有改）。

严重程度：中。

种子：`20261126`（`SEED + 104`）。作者运行和复核运行都用任务包 `oracle`。作者会话 `sess-author`、模型 `alpha@1`，复核会话 `sess-judge`、模型 `beta@2`，`start_run` 带了 `predecessor`。两个模型按引擎自己的分族也不在一族。

模型原文：要求项合约，独立判断只由另一个会话、另一个模型相对前驱运行来满足（A04）。A04 R[5] 只在作者未知时把独立性记为未知。模型没有说前驱必须是另一个任务包。

引擎实际：`hub/runs/engine/lineage.ts` 的 `judgedRunsOf`（约第 47–53 行）沿前驱链跳过与本运行同一包号的运行，链上只有本包时返回空。`authorOriginOf`（约第 77–81 行）因此看不到这位作者，独立性记为未知。独立判断的终态仍是判断，状态是未满足（独立性未知）。这是故意收紧：同包的后一次运行去判断另一包的草稿，而不是判断自己的上一稿（同文件开头）。相对模型原文，同包前驱被丢掉了。

参照：会话不同、模型不同、模板接受声明的独立性，独立判断满足。

后果：这条是收紧，不是放宽。起草方不能靠同包前驱把独立判断签成满足，起草方不能签结论在这里仍然成立。代价是同一任务包上换了会话和模型的正当复核也被记成独立性未知，交不了“已独立”的结论。换一个包号（种子 `20261123` 的 `oracle-draft` 再接到 `oracle`）时，两边都记满足。

建议的修法：改 `judgedRunsOf`，同一包的直接前驱也算作者来源（启动会话、提交会话、声明的模型），供 `authorOriginOf` 使用。同包更早的修订要不要继续排除，按文件头那条“不判断自己的上一稿”留给所有者；至少种子里的直接前驱应当算数。不要改参照。

## 模型没有排定的地方

种子 `20261032`，条目 `i1`、要求项 `both`：静态层是意外的不通过，动态层是未运行（这些场景没有完整性证明，V03 R[5]）。参照因静态层已经不符合期望，记未满足（终态不符合期望）。引擎因还有未决的层，记未决（`requirementStatus` 先看未决层）。V03 没有写“一层已经不符合期望、另一层未运行”时听谁的。随机生成不产生这个组合。所有者定夺之前，两边都保持现状，不把引擎改成参照，也不把参照改成引擎。
