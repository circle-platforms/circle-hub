# B6：原文的“声明”“未署名”旁写明含义（#228）

来源：所有者全量计划 #228/#199；基线 aded2ffd，`fix/source-labels`。做法同 #227：保留正式词，在旁边加说明，不改词表。

## 允许路径

- `hub/server/console/{knowledge-display.ts,source-archive.ts,source-labels.test.ts}`
- `tests/acceptance/51-source-archive.test.ts`
- 本任务页、`CHANGELOG.md`

## 决定

- 来源类型“声明”（词表 `provenance_type` 的 `declared`）：悬停提示“由上传方提供，Hub 没有独立的采集证明；不代表内容已被核实。”。观察、投影、候选等其他类型原样显示。
- 团队来源状态（词表 `source_attribution_status`）：未署名——“上传人尚未确认这份原文可作为团队来源；未署名的上传不会被团队知识接收。与上传人是谁无关。”；已署名为团队来源——“上传人已确认这份原文可作为团队来源，全体成员可读。署名不是数字签名，也不转让版权；署名人和时间见下。”。把“上传人”和“团队来源确认”分开说，不暗示作者缺失。
- 原文列表的来源类型列和原文详情都用同一组函数（`sourceTypeLabel`、`attributionBadge`），说明文字只在 `knowledge-display.ts` 一处。

文字所依据的事实：团队原文“上传原文须由上传人署名”“全体成员可读”（原文归档页和团队原文卡片的现有提示），分享到团队的检查“未署名上传拒收”（`contracts/model.json`）。

## 验收

- 单元：声明带说明且保留正式标签；其他来源类型不带；两种署名状态的说明各自出现并保留正式标签；整段过文案守卫。
- 验收（51）：上传的原文在列表行和详情里都显示“声明”的说明；改动前该断言失败（已实证）。

## 不做

署名动作本身的说明（谁在哪里点署名、允许什么用途）在上传与署名对话框里，需要对照当前行为，另做。
