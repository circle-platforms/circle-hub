# Synthetic Windows Job verification

Scope: a local public branch based on the existing synthetic platform matrix. Allowed paths are this task page, `.github/workflows/platform-matrix.yml`, `hub/rules/sandbox/windows.ts`, `hub/rules/sandbox/windows.test.ts`, `hub/rules/sandbox/isolation.ts` and `hub/rules/sandbox/sandbox.ts`.

The Job primitives and synthetic tests use the publication transform T on the source parent and new blobs, followed by `git merge-file` against the public files. The transform protects opaque hashes and dependency integrity values. Three adjacent Linux conflicts in isolation were resolved by retaining the public code and adding only the Windows import and fail-closed guards; sandbox merged without conflicts. No private task or progress history is imported. The subsequent KnownDLL and exact koffi 3.3.3 version checks and their synthetic counterexamples were merged through the same transform without conflicts; the loader does not consult environment paths.

The workflow runs exactly the Windows Job test file on the existing Windows x64 and ARM64 runners. Existing contracts and vault checks remain unchanged; the Windows release readiness verdict (not supported) is reported as a warning and in the job summary instead of failing the synthetic matrix. The LPAC probe starts with an allow-listed environment of system and profile locations only, because an empty block fails at process creation with ERROR_ENVVAR_NOT_FOUND (203). The LPAC probe's launch settings follow the native evidence in issue 73, where each of four settings alone made node.exe fail before running any code. It runs DETACHED_PROCESS with NUL standard handles instead of CREATE_NO_WINDOW, because the child-process restriction refuses the console host that CREATE_NO_WINDOW needs. It has no Win32k system-call lockdown, because node.exe imports USER32 and fails DLL initialisation under that mitigation; this is a loosening for the synthetic probe. Its LPAC token carries exactly one capability, registryRead, because zero-capability LPAC cannot read the Winsock catalog and Node aborts in WSAStartup; this is a loosening limited to registry reads that DACLs grant to the capability. Its write-restricted token uses the RESTRICTED SID (S-1-5-12) instead of the NULL SID, because the NULL SID together with any AppContainer fails DLL initialisation; writes are now allowed where a DACL grants RESTRICTED and the LPAC check also passes. The child-process restriction, the Job limits and every check on the suspended child remain, and the TCP, UDP, file and child-process denial fixtures must still pass. The child-process fixture spawns with ignored stdio, because LPAC denies the named pipes libuv creates for default stdio and libuv retries that without end, so the spawn never reached process creation. Job cleanup does not establish network or filesystem isolation; Windows pack execution remains unavailable even with synthetic OS opt-out.

The three loosenings are kept for the synthetic probe: the owner accepted them on 2026-10-29, after reading this trade-off. They are the least the native evidence in issue 73 allows: with any one of them restored, node.exe does not start. Chromium makes the same trade-offs for a comparable process, its network service in an LPAC sandbox, which runs without a restricted token and without Win32k lockdown and adds capabilities; this probe stays stricter by keeping the write-restricted token. Keeping them does not make Windows pack execution available, and the release readiness verdict stays "not supported". Before Windows is offered for release they are reviewed again; Win32k lockdown can return only with a host program that does not load USER32. Reverting the merge of PR 74 (e7ff305) restores the earlier launch settings, and the LPAC tests fail again.

No local native execution ran for these changes. This branch is for synthetic GitHub runner verification only; its workflow does not publish a release or deploy to a production system. Matrix run 40807264414 passed on all six targets; on the Windows x64 and ARM64 runners the LPAC start and the TCP, UDP, file and child-process denial tests ran and passed.
