# 设计与最小实现：写手按请求读设备的输出（device read）

状态：2026-11-19，分支 `wp/claude/t18-compile-flow`，本地实现，未发布、未部署。所有者的决定见进度页决定 181；通用模型第 85 版（D07 R[8]）。它是“写手问设备这个位置该写什么”（`device-help-read.md`）的姊妹：那边问的是一行里某个位置的说明，这边读的是一条只读命令的输出。网关在本仓库之外，这里不改它（第 7 节）。

## 1. 要办的事

写用例的人不知道设备对一条只读命令会打印什么：一张表怎么排，清过的设备上有什么。靠猜写出的检查点到上机才知道对不上，白费设备轮次。参考引擎给它的写手一个只读工具 `dev_probe`：在被测设备上执行一条只读的查看命令，把真实回显交回，一个写手会话至多五次，回显只作“语法和排版”的旁证，对期望值没有任何权威。

这里的目标一样：派发之前，写手可以让 Hub 在自己预订的设备上读一条只读命令的输出。Hub 只把设备的原话原样存下来、原样交回，不判断。

## 2. 先说结论

- **可行，不加错误码，不加 MCP 工具，不加前提认证。** 模型只在 D07 R[8] 末尾补一段（第 85 版），对照见第 4 节。
- **放在 test-bed 包的一个动作 `read`**，由预订谱系持有的租约之下发起（`start_run`，predecessor 写预订那次运行）。包的投影只声明“在哪台设备上读哪一行”，Hub 按部署数据去读，和问位置（`help`）、“预订后看一次版本”（决定 112）是同一类事。
- **复用执行器已有的逐台读**：调用是 `probes.call`（读版本、接口地址和残留的那一个），命令形状是 `probes.command_pattern`，设备文字的位置是 `probes.output`。执行器定义只多一处可选的 `probes.read`，表示“可以按请求读”和界限；不声明就读不了。
- **那一行发出前**只做结构核对（词法、没有控制字符、整行符合执行器声明的命令形状），再加两个前提：谱系持有这台设备的租约，设备上没有未结束的作业。核对里没有任何词表。
- **为什么不要新的前提或认证**：调用、工具和命令形状，就是每次预检已经发给同一批座位的那一个；这件事只是让预订的持有者在已声明的形状里选发哪一行。问位置要认证（`premises.read_only`），是因为它的工具往命令行里打字而不按回车，这是另一种工具、另一种保证；这里没有新工具，也没有新的发送方式。
- 一次请求只读一行，不成批；不解析设备的话；不缓存；没有任何写（第 14 节）。

## 4. 这个读放在哪里：对照设计

设计里写和读设备是分开的：Hub 只在预订时、派发前后，按执行器定义里固定的命令读设备；模型写的东西只经核验、派发的那条路到设备。按请求读和问位置一样，在两处扩展了它：读由写手的请求发起，不是 Hub 自己的时机；读带着写手选的一行文字去设备。和问位置不同的是，这一行**会被执行**。所以这里不引入任何新的发送手段：只用预检已经在用的那一个调用，那一行必须整行落在管理员为这个调用声明的命令形状里。

放法沿用问位置的结论（`device-help-read.md` 第 4 节）：不新增 MCP 工具（D06 的六个工具不动，决定 138），不放进 case-compile（编译运行的输入在开始时冻结），不做成管理员命令（写手用不了），放在 **test-bed 的一个动作里、在预订谱系的租约之下**。

对照模型，逐条看这个放法有没有越界：

- **D06 F[0]-F[5]、R[6]**：工具面不变，走 `start_run`。F[6] 的“现场观察”工具仍暂缓：这里没有新工具，只是 `start_run` 的一个包动作。
- **D07 R[8]**：只读核对和逐台探测“只在执行器定义里声明一次”，目标收的命令形状也写在定义里。按请求读用的正是这一份声明：同一个调用、同一个形状、同一个输出位置，没有第二份。不同之处有两点，模型第 85 版在 R[8] 末尾写明：发哪一行由预订的持有者在形状之内选；读发生在编写期，那时没有派发的网关租约，所以像问位置和“预订后看一次版本”一样，在一个临时网关租约里读，谱系的 Hub 租约不动。
- **D07 R[1]**：原始观察先存成源文件再解释：传输层的保存回调先存应答原样，再读指针。
- **D02 R[0]、R[1]、R[4]**：前提默认为假，置真要目标版本上的认证。这里没有新增任何前提：没有新工具，没有新的发送方式，发出的文字属于已声明的命令形状。预检发的版本、接口、残留命令靠同一份声明成立，按请求读不比它们多要什么，也不比它们少要什么。这个理由成立的条件写在第 6 节末尾和第 13 节：声明的形状只放行只读命令，是管理员的事。
- **D02 R[5]、D04 R[8]**：同期观察加“未排除本地操作”：每条观察主张都带。
- **D03 R[0]**：读失败有界重读：可重读的失败自动读三次（沿用 `read_retry_when`，和版本探测一样），明确拒绝立即停。
- **D05 R[1]、R[8]、A06**：没读成不是错误，是带缺什么和下一步的未知；下一步交给谁写明（缺声明是管理员的事，改写那一行是写手的事）。
- **D05 R[7]**：错误原因不以终端画面的关键词推：Hub 不看设备的话，设备拒绝这条命令时回的字也只是设备的话。
- **A01 R[0]、A05 R[3]**：观察 = Hub 在边界亲手读取并保存的内容，目标自己计算的部分加“目标自报”；只对那一刻成立：每条带采集时刻，不缓存。
- **A03 R[0]、R[6]、C07 R[8]**：判据只取期望来源；线索只用于排序和提示。设备的话不属于任何来源角色，不进运行的 `sources`，没有任何检查读它。
- **D07 R[12]**：派发安全不靠拒绝词表或删引号后的文字匹配：那一行靠声明的形状和词法，没有拒绝词表。

结论：不需要新的协议码（沿用 `LEASE_UNAVAILABLE`、`LEASE_PREFIX`、`LEASE_EXPIRED`；包自己的两个码 `test-bed.bad_read`、`test-bed.read_mismatch` 写在包的码表里），不需要新的词表取值，不需要新的前提。

## 5. Hub 怎么保持中立

Hub 说的话只有：在哪台设备上读了哪一行；设备输出了几行，或者没有输出文字；设备的原话和观察时刻；没读成时缺什么、下一步。

Hub 不做的：不判断这条命令对不对；不解释输出为什么是空的；不改写、不排序、不摘要设备的话；不拿设备的话和任何清单比；不按设备的话里的词把结果分成“成功”“被拒绝”；不让它成为任何检查或期望值的依据。

设备的话在运行里是主张的数据（`device_reads`），不是源：性质“事实”指“设备当时这样输出”，不指“这条命令这样写是对的”，也不指“设备以后还这样输出”；限定“目标自报”“未排除本地操作”；主张的前提写明它只说明输出的写法和排版，不是运行的来源，不能作为期望值的依据。回答里在设备输出之前有一句“设备输出仅供参考，不能作为原始用例的期望依据。”，问位置和读设备合用，只说一次。设备的话一行一行原样列出；终端控制字符只在回答里写成 `\xNN`，运行记录里仍是原样。预订编号保留在参数和机器可读字段中，不放在结论正文。

## 6. 那一行发出前怎么核对

都只看结构，没有一个词和词表比较（`hub/dispatch/read-line.ts` 的 `checkReadLine`）：

1. **一行完整的词**：共用词法 `commandTokens`——引号配对、闭合引号后不紧跟字符、至多 2000 个字符 320 个词。发出去的是各词用单个空格连起来的那一行。
2. **没有任何控制字符**（换行、回车、制表、转义都不行，引号里也不行）：一次请求就是一行。
3. **整行符合执行器声明的命令形状** `probes.command_pattern`（以 `^` 开头、`$` 结尾）：匹配要从第一个字符到最后一个字符。顶层“或”没有加括号的形状（`^a|b$`）在正则里并不锚定两头，这里按整行匹配，所以它也放不过半行。这是“允许什么”，不是“禁止什么”；形状里要不要放分号、管道符由部署定。
4. **租约**：包的投影只在冻结的租约视图里把这台设备标为“我的”才出 `read`；引擎再按租约表核一遍键（同一用户、谱系里的运行持有、没释放、没过期、在声明的前缀下）；执行器的资源里要有这些键；设备上没有未结束的作业。
5. **声明**：绑定同一份清单、座位指向这台设备的执行器声明了 `probes.read`。

这些核对保证的是：发给设备的只有一行，这一行属于管理员为逐台读声明的形状，发的人持有这台设备。它们不证明这个形状里的每一条命令都是只读的：那取决于管理员怎么写 `command_pattern`，以及网关的逐台探测工具自己放行什么。预检发的命令是 Hub 定义里固定的几条，形状写宽一些以前没有后果；加上 `probes.read` 以后，形状就是写手能发的全部。所以 `probes.read` 是要管理员明确加上的，不是缺省就有的。

**锁定命令树的前缀这次没有做**，原因同问位置（`device-help-read.md` 第 6 节）：test-bed 不绑产品线，运行里没有锁定的树。

## 7. 网关要加的工具

没有。按请求读用的是网关已有的逐台探测工具（预检读版本、接口地址和残留的那一个），参数也一样：本次网关租约的身份、座位序号、一条命令。网关不改、不部署。

管理员在真实环境上加 `probes.read` 之前要核对两件事，都在本仓库之外：网关的逐台探测工具自己只执行只读命令（它是独立的第二道）；部署里的 `probes.command_pattern` 只放行只读命令，而且顶层的“或”都加了括号。合成测试不证明这两件。

## 8. 一次读的过程

1. 写手已经预订了设备（test-bed `acquire`，得预订运行号 B）。
2. 写手 `start_run`：`pack` test-bed，`inputs.inventory` 同预订，`predecessor` 写 B，`parameters` 写 `{action: "read", booking: B, device: <设备名>, line: <一条只读命令>}`。不带 `mode`，带了就拒。
3. 包的投影在冻结的租约视图里核这台设备的键是“我的”，输出 `read`（一行）；检查按冻结内容重算一遍。
4. 引擎（`readClaims`）核键：在 `bed/` 前缀下、同一用户、谱系里的运行持有、没释放没过期；不合就拒（`LEASE_UNAVAILABLE`、`LEASE_PREFIX`、`LEASE_EXPIRED`），什么也不读。
5. `DispatchService.readDevices`：找到绑定同一份清单、座位指向这台设备、声明了 `probes.read` 的执行器 → 过第 6 节的发出前核对 → 同一执行器的读和问一个接一个排队（网关租约只有一个）→ 连接 → 取一个临时网关租约（心跳照常）→ 用 `probes.call` 在这个座位上发这一行，读一次 → 释放租约。
6. 应答先原样存（只许函数读），再按 `probes.output` 读设备文字；文字另存一份运行者和管理员能读的文本原件，凭据扫描扣住的不引用；日志里记读的那一行、有没有输出和两个引用。
7. 引擎把结果写成主张放进运行，回答里列出。

## 9. 声明：执行器定义多出来的一处

```json
{
  "probes": {
    "（逐台探测的声明不变：command_pattern、call、output、seats）": "…",
    "read": { "max_chars": 16000 }
  }
}
```

`probes.read` 只表示“可以按请求读”和界限：`max_chars`（一次最多给出设备文字的前多少个字符，1 到 64000，缺省 16000）；`max_reads`（一次请求读几行）固定为 1，可以不写，写别的值拒收。最短的写法是 `"read": {}`。它不带工具、命令形状和输出位置，写了拒收：这三样只有逐台探测声明的那一份。

登记时核的：`max_chars` 的范围；`max_reads` 只能是 1；没有别的字段。调用各绑定一次命令、座位序号和租约身份，工具在允许清单里、不是提交工具、不带工作内容字节，命令形状以 `^` 开头 `$` 结尾：这些是逐台探测原有的规则，按请求读用同一个调用，所以不另设交叉规则。已登记的旧定义不受影响。给已登记的执行器加 `probes.read` 是一次执行器更新：更新前开始的核验运行要按现有规则重新核验。

## 10. 记录、可见性、主张

- **应答原件**：网关调用的应答原样存，只许函数读（管理员能在控制台看）。
- **文本原件**：设备文字另存，运行者和管理员能读，模型可读；凭据扫描扣住的不引用。
- **日志**：一条 `device_read`（读的那一行、有没有输出、两个引用）；失败和不呈现的写管理员日志。
- **运行的 `device_reads`**（`RunSummary` 新增的可选字段）：每次请求一条主张，规则 `dispatch.device_read@1`。读到了是一条观察：设备原话在 `data.output`（最多留前 `max_chars` 个字符，`data.truncated` 标明截断，全文在文本原件），`data.line` 是发出去的那一行，`data.device` 是设备在清单里的位置，`data.has_output`、`data.withheld` 说明有没有输出、是不是被凭据扫描扣住；带限定“目标自报”“未排除本地操作”和采集时刻，根据是两个原件。没发出去、没读成或不呈现的是一条未知：`data.sent` 说明那一行有没有交给网关，`data.missing_fact`、`data.next_action` 写缺什么和下一步。
- 运行记录和回答只在运行者和管理员之间可读。设备的话不是运行的来源，也不是任何检查的输入。
- 应答原件或文本原件存不下来，设备的内容都不呈现；声明的位置上不是文字的应答同样不呈现。

## 11. 和参考引擎的差别，为什么

1. **只读靠什么**：参考引擎看首词是不是它写在代码里的两个只读命令词之一，再拒分号——这是词表匹配。这里由管理员在执行器定义里声明命令形状，整行匹配；Hub 的代码里没有任何命令词（C02、D07 R[12]）。
2. **次数**：参考引擎一个写手会话五次。Hub 没有“写手会话”这个对象，一次请求读一行，每次是一个有记录的运行；要不要给一轮编写定次数，是写手一侧规程的事（第 13 节）。
3. **假设**：参考引擎要写手写明这次读要分清什么，并拒绝重复的“命令加假设”。这里不收：那是模型自己的推理，Hub 不评判一次读值不值。
4. **缓存**：参考引擎在一次运行里对同一条命令只真读一次。这里不缓存：观察只对那一刻成立，写手改过设备以后同一条命令的输出可以不同。
5. **空输出**：参考引擎补一句“编写期设备是清过的，空不等于失败”。这里只说设备没有输出文字：为什么空是解释，不是观察。
6. **按词分类**：参考引擎按回显里的词把结果分成观察到、设备拒绝、探测出错。这里不分（D05 R[7]）：设备说的拒绝也只是设备的话，原样交回。
7. **留多少**：参考引擎留前 4000 个字符。这里留前 `max_chars` 个（缺省 16000），并存全文原件。
8. **通道和凭据**：参考引擎直接经跳转机登录设备，凭据在本机环境变量。这里只经执行器和网关，凭据在保险库，读在网关租约里。
9. **错误的处理**：可重读的失败自动读三次再停（D03 R[0]）；明确拒绝立即停。
10. **排队**：同一执行器的读和问一个接一个，因为网关租约只有一个。

## 14. 没做的

- 不解析、不匹配、不评判设备的话，也不按其中的词分类。
- 两次请求之间不缓存。
- 不成批：一次运行一行，一次请求一台设备。
- 没有任何写：不进配置级，不改设备上的任何东西；这一条靠声明的命令形状和网关工具成立（第 6、7 节）。
- 不冻结目标：读没有派发意图，读不成只答未知并写管理员日志。
- 跨运行的次数预算、锁定命令树前缀的核对、管理员命令、控制台上看读过什么：都没有做；读过什么现在从运行记录和调用日志看。

已知的限制：`start_run` 要等读完才返回，是一次网关调用加取放租约的时间；同一个执行器上的读和问是排队的。
