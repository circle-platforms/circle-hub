# 任务：知识库树苗（kb-seedling）

所有者 10-24 原话：**每个版本一个树苗，剩下的都是由 Circle 来喂给树的。** 即：每条产品线 × 版本线一棵树苗（不再每个构建一个根），由这个版本的 APP、CLI 两份 adoc 手册和该版本线已发布构建的命令树 XML 合成；用例、缺陷、规格、构建信息、自由文本都在 Circle 实际用到、引用到时带出处喂进来，由 Hub 核验后挂到这棵树上。

**修订：所有者 10-24**（修订 `docs/hub-r4-kb-direction.md` 第一节"资料分三类"，那一节已同步改）：只有 adoc 手册（APP、CLI）和命令树 XML 由 Hub 的生产器生成，合成初始树苗；其余资料——构建头、测试清单（用例）、缺陷导出、规格、工单纪要等自由文本——一律"Circle 用到了才放进 Hub"：实际工作里读到、引用到的原件和由此得到的结论，才经回注运行（带逐字引文、Hub 核验）进入 Hub 知识库，挂到树苗上或作为树苗外的独立对象；不再由生产器整批解析。

回归范围、巡检、追溯能看到多全，取决于 Circle 喂进来的有多全（和 InfoTest 一样是结构化数据问题），靠三条硬要求保证，方向 1、2 都受约束：

1. **必须回**：任务里用到的用例、缺陷、构建、规格必须作为本次运行提交的一部分交回 Hub，不是可选。
2. **必须按格式回**：每种资料一份固定格式，进 `contracts/model.json` 生成 schema；不合格式的整份拒收，给修正说明。
3. **树的结构先定死**：本页先把树苗的节点布局，以及用例、缺陷、构建、规格各自挂在哪个路径、按什么键逐项写死（下表），再实现。

## 粒度

- 一条产品线 × 一条版本线一棵树苗。
- 命令树：这条版本线当前已发布构建的命令树 XML（哪个构建当前发布由产品包的构建清单机械决定，不猜）。
- 手册：这个版本的 CLI、APP 两份 adoc，按 SVN 固定修订号整批读（kb-svn 只读包），修订号进组成记录。
- 同输入同字节：身份只含内容摘要（自下而上），时间戳不进身份。

## 合并规则（只认结构）

不许关键词、词典、同义词、前缀表或自由文本正则。

1. 命令树 XML 是命令部分的骨架：路径（menu/item 词序列）、参数、命令树里声明的类型。
2. CLI 手册里记载命令的章节，只当章节的命令签名锚与命令树路径**完全相等**时挂到该命令节点上；对不上的按章节路径留在 CLI 手册子树里，不猜。
3. APP 手册按章节路径成一棵子树。

## 树苗节点布局（逐项写死）

| 路径 | 内容 | 键 |
| --- | --- | --- |
| `/commands/<词…>` | 命令树骨架：签名、参数、树里声明的类型；CLI 手册匹配上的章节也挂这里 | 命令树 menu/item 词序列 |
| `/manual/cli/<章节路径>` | CLI 手册没匹配上的章节，按章节路径 | 章节路径（adoc `=` 层级） |
| `/manual/app/<章节路径>` | APP 手册整棵 | 同上 |
| `/cases/<用例号>` | Circle 喂回的用例 | 用例号 |
| `/defects/<缺陷号>` | Circle 喂回的缺陷 | 缺陷号 |
| `/builds/<构建名>` | Circle 喂回的构建信息 | 构建名 |
| `/specs/<规格号>` | Circle 喂回的规格 | 规格号 |

- 路径段按 hub/refs 的 TreePath 规则编码。
- 材料↔命令、材料↔章节的关联不搬节点：记在条目上，仅当材料自身结构里逐字声明（如用例步骤里的命令串与命令路径完全相等）才建立，Hub 核验。
- 后四个命名空间方向 1 只把路径和键定死；条目由方向 2 的回注运行填。

## 存在 Hub 上的形状

- 节点、条目照现有 `tree_node@1`、`knowledge-entry@1` 记录；新增 `seedling@1` 组成记录：产品线、版本线、根摘要、三样来源（command-tree / cli-manual / app-manual，各带原件 SHA 和 adoc 修订号）、父树苗（方向 2 的血缘）。
- 每条产品线 × 版本线一个"当前树苗"指针（`seedling-pointer@1`），比较并交换地移动。
- 读法：`get_nodes` 按路径取子树。
- 不引入归位/未归位、组成分片、分面这类机制，越简单越好。

## 和现有知识库的关系

树苗是新的生产路径；现有的每构建知识根先不删，这次只是不再往上加东西。

## 方向 2（等集成者通知再做）

客户端数据流能更新树苗：模型在 Circle 里读手册和用例，提出对树苗的更新（新增节点、手册章节和命令的关联、适用条件、更正），带逐字引文；Hub 核验后按血缘只追加地产出树苗的新版本，走现有的回注运行（knowledge-contribution 包）。三条硬要求在这条数据流上执行；四类材料的固定格式 schema 随这一步进 `contracts/model.json`。

## 方向 1 的实现（本页经所有者看过、集成者通知后开始）

- 复用：adoc 生产器（kb-adoc，沙箱里的 asciidoctor）、命令树生产器（command-tree.ts）、章节挂树（kb-sections）、SVN 只读包（kb-svn）。
- 分支和工作树：`kb-seedling`，目录 `circle-hub-kb-seedling`（依赖已装好）。
- 可以改的路径：`hub/knowledge/seedling*.ts` 和测试、`contracts/src/knowledge.ts`（新 schema，重跑 gen:contracts）、`hub/knowledge/README.md`、`packs/product/apv/**`（生产器侧如需）、本页。

- 验证：`npx tsc --noEmit`；`node --test --test-concurrency=1` 对 `hub/knowledge/**`、`packs/product/**`；`node tools/gen-contracts.ts --check`。
- 真实的 SVN 读取和部署由集成者做。
