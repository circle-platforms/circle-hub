# B1：任务详情页读一个提交窗口，不读整段历史（#200）

来源：所有者全量计划 #200/#195/#199（“长历史、分页”）；基线 aded2ffd，`fix/run-history-page`。

## 允许路径

- `hub/ports.ts`
- `hub/runs/engine/{queries.ts,service.ts,run-history-page.test.ts,README.md}`
- `hub/server/{fakes.ts,console-run-history.test.ts}`、`hub/server/console/{pages.ts,README.md}`
- 本任务页、`CHANGELOG.md`

## 决定

详情页 `getRun` 读取任务的全部提交，为每条结果读正文并逐条做可读性核对，历史越长越慢（#200）。不能直接截断 `getRun`：`hub/server/readers.ts` 用 `detail.submissions` 做“某条提交记录能否读”的授权判断，导出、JSON 任务视图和结果页也要完整列表。所以窗口只作为显式选项，只由控制台详情页使用，不带选项的读取与原来完全相同。

- 选项 `{history:{limit, before?}}`：最近 `limit`（1–200）条提交，页内由早到晚；`history.next` 是读更早一页的不透明游标（到头为 null）；当前结果对应的提交若比窗口更老，置顶在最新一页的第一行（`history.pinned`），页面不会出现没有对应提交的结果。
- 只为列出的行读结果：每行按自己的索引项取“最新且可读”的结果，与完整读取的取舍一致；生产结果按自己的索引项取。
- 撤回提示按本页显示的结果判断（列出的行、当前结果、生产结果），页面写明；完整读取仍按全部结果。
- 无法使用的游标得到空窗口，不使页面失败。页面忽略长于 512 个字符的 `older` 参数。
- 页面每页 50 条（`RUN_HISTORY_LIMIT`），表头上方写明列出几条、每页最多几条、第一行是否为当前结果对应的提交，并给“查看更早的提交”和“回到最近的提交”入口。

## 验收

- 引擎（真实记录与临时 PostgreSQL）：12 条提交、每页 5 条：不带选项的读取不变且不含 `history`；窗口含置顶的第 2 条和最新 5 条；每一行与完整读取中同一提交的行逐项相等；当前结果、生产结果、任务头与完整读取相等；沿游标取完的页合起来恰好是全部提交各一次、由早到晚（3 页）。
- 增长：当前结果在最新提交时，110 条与 220 条提交的窗口读取都加载 118 条结果正文，完整读取分别是 211 与 321（增量不少于新增的 110 条）。
- 权限：未分享的成员读到中性的 null；分享后与完整读取逐行一致；撤销分享立即失效；坏游标为空窗口且不创造记录；limit 小于 1 抬为 1。
- 页面（脚本化假服务）：页面按窗口读取并带 `before`；有 `history` 时显示说明、更早的入口、置顶说明，最旧一页没有“更早”入口、最新一页没有“回到最近”入口；过长的游标不传给服务；整页过文案守卫。

## 没有解决的

`latestAccepted` 为找到当前结果从历史末尾向前扫描，成本是当前结果到末尾的距离；当前结果很老时窗口读取仍随之增长（测试里把已受理结果放在最新一条以隔离列表的开销）。完整运行正文、摘要的持久化投影、全局并发上限、堆容量和两周观测仍在 #200/#195。#273 的任务头读取与此互不重叠。
