## 要做到的（验收标准）

1. **提交共享（知识）**：
   - 本人可以对一条“已核验”的个人条目发起提交共享，经 Circle 或控制台都可以。
   - Hub 依次检查：依据都能解析；引文逐字一致；来源可以共享（个人凭据读取的来源拒收；上传文件在第五阶段的署名完成前一律拒收）；与团队空间不重复（只与团队比对，不跨个人空间）；凭据扫描（决定 60 R8）。
   - 全部通过即合并为团队空间的一个新版本，记录提交人、时间与来源条目，不审核（R8）；个人原条目保留。
   - 未通过时条目留在个人空间，给出注册过的拒收码与中文原因。
2. **撤回**：
   - 管理员可撤回任何团队条目；提交人可撤回自己提交到团队的条目。
   - 撤回后读取方看到“已撤回”，以它为依据的条目与结果随之标出（沿用 `grounds_withdrawn`）。
3. **依据可见范围**：提交结果时，结果的每个依据都必须对结果的全部读者可读，即团队条目，或已授权给这些读者的个人条目；不满足时拒收，拒收说明里写明该怎么做（先提交共享或补授权）。
4. **个人工作流与通用技能（Hub 侧）**：
   - 成员可以把工作流或通用技能发布到自己的个人空间，沿用现有发布校验（结构、沙箱运行、引用）与凭据扫描。
   - 个人空间先开放这两个种类；产品知识来源与业务系统接入只在团队空间。
   - 本人可以把个人工作流或技能授权给指定成员或全体管理员使用，并可收回。
   - 用个人工作流跑出的结果，只对发起人和被授权使用该工作流的人可见。
5. **发布到团队**：
   - 个人工作流与通用技能可以发布到团队，沿用现有的“发布权”（权限，不是逐次审核）。
   - 发布到团队后按使用范围分配，结果按使用范围共享。
6. **控制台**：
   - 个人条目上加“提交共享”。
   - 新增“我的提交共享”列表：状态为已合并或已拒收，附原因与拒收码。
   - 团队条目上显示提交人和来源。
   - 工作流页的“工作流”“通用技能”两栏各分个人与团队。
   - 个人工作流详情里有授权管理和“发布到团队”。
7. **测试**：
   - 覆盖提交共享的每一项检查（含凭据命中与重复）、合并后的版本历史、撤回的传播、依据可见范围的拒收。
   - 覆盖个人工作流的授权与结果可见范围，以及没有发布权时发布到团队被拒。

## 实施方案

1. **合约与兼容**：按决定 84、87 将模型升为 19，复用已有个人／团队空间、授权对象与授权动作词表，增加“已合并／已拒收”的共享结果轴、共享申请／个人包发布与授权追加记录和拒收码。新字段为可选字段，旧团队包、运行、结果和旧引用保持可读；不改已应用迁移。生成合约与必需的四个技能协议镜像及补丁发布清单，技能业务代码不变，测试从 `repositorySkillVersion` 取版本。
2. **知识共享**：知识服务新增本人共享、共享历史与团队条目归属读取 API。只受理本人当前已核验条目；按依据解析、逐字引文、来源资格、团队去重、凭据扫描的顺序重查，不信任旧的核验标记。个人凭据来源和上传文件均拒收；依据链递归检查并保留可追溯来源，不把个人读权隐式扩大给团队。通过后在团队空间锁与事务中追加团队条目、原文归属、版本及共享回执，保留个人原条目；拒收只写安全的元数据、注册代码和原因，不写来源原文或凭据，不比较其他个人空间。
3. **撤回与结果依据**：团队管理员可撤回任意团队条目，提交人可撤回自己的团队提交；撤回追加记录，不改旧条目与旧结果。知识树读取、条目详情和结果读取派生 `grounds_withdrawn`，递归发现撤回依据并限制循环／深度。结果受理前按其实际读者集合检查每个依据的读取权和底层来源；团队可见结果的个人依据须有覆盖全部读者的授权，否则给出先共享或补授权的拒收说明。读取时仍重查授权，结果记录本身保持原字节。
4. **个人包与授权**：注册表增加个人空间命名空间，清单内包 ID、版本和内容摘要保留原格式，查询、发布占用、权限记录和历史锁按空间限定；相同 ID 可在不同人的空间和团队空间独立存在。个人仅可发布工作流或通用技能，复用现有结构、引用、样例／沙箱和凭据检查；不要求团队发布权。授权由本人追加给指定成员／全体管理员并可收回，管理员没有个人包的默认使用权。个人运行冻结包的空间与摘要，只有发起人和当前获授权使用该工作流的人可读；个人技能和依赖解析同样限定调用者及冻结的空间，避免通过全局安装或裸摘要扩大权限。
5. **发布到团队与接口**：发布到团队重新检查现有发布权和既有发布校验，生成团队发布记录并沿用团队分配规则，不把原个人运行改为团队运行。仍为六个 MCP 工具，在现有工具增加个人知识共享／撤回及必要的包空间参数，不新增第七个工具；接口与中文文本同步说明结果、拒收和读取出口。个人包在控制台上传／校验／发布，所有动作按本人或团队权限执行；具体返回形状在实现时与生成合约同步。
6. **控制台与登录规则**：个人条目增加提交共享，新增“我的提交共享”及代码／原因；团队条目显示提交人与原条目引用。工作流、通用技能各分个人／团队，个人详情管理使用授权和发布到团队。所有写入沿用同源、CSRF、密码会话及首次改密限制；新增测试通过 `testConsoleCredentials` 登录。用户名加密码唯一登录规则随上游审查修正变基纳入，不重做或恢复令牌登录。
7. **提交与验证**：按合约／知识共享、个人包／运行权限、控制台／跨包验收、文档收尾分步签署本机提交。每步跑类型与受影响测试，合约变化跑 `verify:contracts`，文档变化跑 `test:docs`；权限、运行、技能锁、旧记录回放及 MCP 变化跑相应验收，补充本阶段合成端到端场景。重套件逐个运行，跳过与未运行分别记录；不增加任意 SHA 校验或全量回归，不推送、不建 PR。第二阶段审查修正到达后按要求变基并只复查受影响路径。
