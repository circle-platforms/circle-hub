## 为什么

#319 之后，总览和任务列表的时间几乎都花在一件事上：每个任务读出一整份结果（合成数据约 0.93 MB，现场约 8 MB），只为算出“通过／待处理／被拦下”几个数，并判断读者能不能读它。126 个任务的合成数据上，总览一次请求校验 178 MB，其中结果 139 MB；它随任务数和结果大小线性增长。这件事不能靠缓存绕过去（统计要读到经过校验的记录），所以需要一条小的、自己经过校验的记录来代替整份结果。

## 决定

- **写**：存下一条校验结果时，在同一个事务里另追加一条 `result_summary` 记录（`result-summary@1`，来源类型为投影）。内容全部由这条结果算出：所属运行、结果的摘要、它的提交摘要、回执、是否带系统交付输入、它作为运行当前结果时的统计数（结果类别、待处理数、各层终态计数、未交付原因计数）、它引用的根据、有效条件绑定的摘要、对提交者不可用的引用。结果记录本身不变，只多一个索引标记表示“它是连同摘要一起存的”。
- **读**：任务列表和总览用的统计（`getRunStatistics`）按原来的步骤选出“当前结果”和“生产结果”，但每条结果只按摘要记录了解，不读结果正文：先从结果的索引里取摘要（不取正文），再读这条结果的摘要记录。待回应的请求对读者是否可见，也改用“下发它的那条结果”的摘要来判断。
- **读者能不能读一条结果，规则不变。** 仍然对同一批根据、按同样的顺序逐条判断；这批根据原来从结果正文里取，现在从摘要里取（摘要按结果存下时的成员顺序记录它们）。读取权限不缓存。
- **摘要是记录，照常校验。** 每次读都按它自己的摘要校验，被改动就拒绝。一条结果最早的那条摘要才算数，之后追加的同名摘要不会顶替它；摘要里写的结果或运行对不上时不用它，改读结果。
- **结果仍是权威。** 读结果正文的地方（任务详情、导出、引用解析、`getRunSummary`）照旧读结果并校验。W08 R[0]“计数不存进结果记录”仍成立。
- **没有摘要的结果答案相同。** 这条规则之前存下的结果照旧读整条结果、现算同样的内容。维护流程在后台按存入顺序给它们补写摘要（每次读四条），补到第一条“连同摘要一起存的”结果为止，做完标记，之后启动不再扫。
- **原有的一条要求因此改变。** 以前统计每次都读出并校验结果正文，结果被改动时列表上的这一行就拒绝。现在结果有摘要时，列表只校验它读到的摘要；结果被改动要到读它的地方才被拒绝。没有摘要的结果仍和以前一样。`hub/runs/engine/statistics.test.ts` 里那条测试没有改，它覆盖的正是“没有摘要的结果”；新的行为由 `result-summary.test.ts` 覆盖。

## 结果

本机，合成数据，126 个任务，一个进程，回环数据库。“校验的字节”是临时计数（没有提交）数出的一次请求读到并校验的记录正文总量。

| 总览 | 2.77 秒 | 1.18 秒 | 0.52 秒 | 178 MB → 41 MB |
| 任务列表 | 0.68 秒 | 0.30 秒 | 0.14 秒 | 43 MB → 10 MB |
| 等待回应中的请求 | 0.68 秒 | 0.30 秒 | 0.14 秒 | |

| 56 次提交的任务，默认页签 | 1.41 秒 | 59 毫秒 | 62 毫秒 | 不变 |

总览和任务列表不再读任何一份结果（126 个任务的总览读 149 条摘要，共 1.9 MB）。只把结果换成摘要时总览是 0.92 秒：采样看到剩下的时间花在重复计算上，一并改了三处。

- 同一条结果的摘要，每条等待中的请求都重新核对一遍形状（上百条根据逐条按引用文法检查）。现在摘要记录的形状按它的摘要只核对一次；记录本身仍然每次读、每次校验。
- 一条请求对读者是否可见，只取决于它的运行和下发它的那次提交；一条结果一次下发几十条请求。现在同一次读取里每个“运行 + 提交”只判断一次。
- 运行的来源引用了哪些根据，每次判断读者能不能看这个运行都重新提取。现在按运行记录的摘要保留（和 #317 对结果的做法一样），能不能读仍然每次判断。

## 还剩什么

- 总览现在的 0.52 秒里，最大的一块是运行记录：每个任务的运行记录（合成数据约 132 KB，现场约 1.7 MB）读两遍，一遍是列出任务，一遍是算这个任务的统计。第二遍是因为统计在自己的读取范围里做、用完就释放，这是 `statistics.test.ts` 固定的做法（原意是不把一百多份结果留在内存里）。统计改读摘要之后，这个隔离只对“没有摘要的结果”还有意义；要不要放开，没有在这里决定。
- 总览列出本期全部等待中的请求（这里 5,530 条），逐条读出。
- “过程”页签一页列 50 次提交、各读一份结果（0.69 秒），没有变。
- 个人知识页显示容量时把空间的每个历史版本都读一遍（400 条知识时 0.7 到 0.9 秒），没有变；它现在是走查里最慢的一组页面。
- 现场已有的结果没有摘要，升级后由后台补写；补完之前这些任务仍按原来的方式读整份结果。

## 验收

- `contracts/src/result-summary.test.ts`：模型版本、记录种类、W08 R[6] 的要点；摘要的形状是封闭的，各字段取值不合法时拒绝。
- `hub/runs/statistics.test.ts`：对已有的每一种运行状态，`statisticsFor(是否放弃, resultStatistics(计数结果))` 与 `runStatistics` 逐字段相同。
- `hub/records/find-digests.test.ts`：`findDigests` 与 `find` 逐页给出相同的摘要、相同的游标，查询里不带正文。
- `hub/runs/engine/result-summary.test.ts`：
  - 结果连同摘要一起存；摘要内容等于按存下的结果算出的内容；摘要里的根据加上运行绑定的来源，与从结果取的根据相同、顺序相同；未受理的结果也有摘要。
  - 同一个场景分别带摘要和不带摘要各跑一遍（私有根据、分享、撤销分享、后来的未受理结果、停用账户）：发起人、被分享的读者、管理员得到的统计都与 `runStatistics(getRunSummary)` 相同；带摘要时一份结果正文都不读。
  - 摘要被改动时统计拒绝；结果被改动而摘要完好时，统计照答，`getRunSummary` 和 `getRun` 拒绝；后来追加的同名摘要不被采用；写错结果或运行的摘要不被采用。
  - 补写：被中断时不做标记；补写的摘要与“连同结果一起存”写出的逐字节相同；做完后再跑什么都不做；补写前后统计相同，补写后不再读结果。
  - 请求：下发请求的结果依赖读者读不到的根据时，无论这条结果有没有摘要，这位读者都看不到这条请求。
- 完整单元测试和完整验收测试。
