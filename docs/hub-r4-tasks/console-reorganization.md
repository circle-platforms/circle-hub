# 控制台按设计稿重排（决定 151）

来源：所有者 2026-11-10（决定 151）。合入的 40 个控制台改动各修一处，页面之间没有共同的结构，所有者看后认为整体仍然乱。本页写各页的目标和实施顺序；每一步有自己的分支和拉取请求。设计稿是本机的可交互静态页面，不进仓库，目标以本页的文字为准。

## 原则

1. 每页只回答一个问题：标题行（标题、一行事实、主要操作），至多四个数字，一个主列表。
2. 次要内容进页签；单个对象的详情在右侧打开，列表仍然可见；右侧不再放和主区重复的概况。
3. 解释“怎么读这一页”的句子放进标题旁的提示，页面上只留事实：时段、数量、状态、时间。
4. 哈希、标识、会话、追踪只在“技术信息”里出现；列表和详情用名称和“打开原文”。
5. 内容相同的行归并成一行并写数量（请求列表）。
6. 页签、筛选、右侧详情都对应地址，由服务端渲染，不加前端框架。

## 第 1 步：导航和技能入口

### 允许路径

- `hub/server/console/{html.ts,style.ts,packs.ts,pack-display.ts,space-layout.ts,index.ts,search.ts,packs.test.ts,shell.test.ts}`
- `hub/server/{console-places.test.ts,console-section-navigation.test.ts}`
- `docs/design/console-navigation.md`、`docs/design/circle-design-system/components/Sidebar/README.md`
- `docs/hub-r4-progress.md`、`CHANGELOG.md`、本任务页

### 决定

- 导航顺序和分组：总览｜任务、知识库、工作流、技能｜连接、团队、记录｜设置、运行状况。组之间是一条分隔线（`ch-nav-sep`），不写组名。团队移到记录之前。
- 技能入口 `/console/skills` 只列通用技能，`/console/packs` 只列工作流。两页各自的范围计数、右侧概况和“最近发布”都只算本页的种类；原来两种合计。
- 入口叫“技能”，种类名称仍取词表的“通用技能”。
- 种类的用途说明（#219）改为所在页面标题的提示：一页一种，不再需要在列表里并列两段说明。
- 技能详情链接到 `/console/skills/<标识>`；`/console/packs/<标识>` 对任何种类照旧可读，页面按该包自己的种类显示所在区域。技能的面包屑是“技能 › 名称”，不再重复种类名（与 #206 一致）。
- 搜索结果里的技能链接到技能页。发布入口沿用原地址，按钮写明种类。

### 验收

- `hub/server/console/packs.test.ts`：技能的面包屑；两页互不列出对方的种类，链接各在自己的入口下；范围计数各算各的，详情页的计数与所在列表一致。
- `hub/server/console/shell.test.ts`：成员九项、管理员十项的顺序，三条分隔线各在任务、连接、设置之前，工作流和技能用同一种区域色。
- `hub/server/console-places.test.ts`：`/console/packs` 没有技能分组，`/console/skills` 有且链接正确；两页各自高亮自己的导航项；技能详情在两个地址下都可读、都高亮技能、面包屑不重复种类；成员看不到未获分配的技能。
- `hub/server/console-section-navigation.test.ts`：两种用途说明各在自己的页面上。
- `node --test "hub/server/**/*.test.ts"` 全包。

### 不做

- 页面布局、列表样式、字号在后面的步骤里做。
- 个人发布后的跳转仍回 `/console/packs/<标识>`（该地址对技能可读并显示技能区域）。

## 第 2 步：总览

### 允许路径

- `hub/server/console/{overview.ts,ui.ts,style.ts}`
- `hub/server/{console-overview-priority.test.ts,console-overview-bound.test.ts}`
- `CHANGELOG.md`、本任务页

### 决定

- 页面回答一个问题：现在有什么需要处理。顺序是四个数字、左边“需要处理”的任务、右边的统计和状态；时间范围移到标题行右侧。
- 四个数字：任务（写出其中等待提交中的个数，链接到任务列表）、已通过（个数和已有结果的个数，不再写百分比）、未决项、等待回应中的请求（写出内容相同的归并后有几类）。
- “需要处理”最多 8 个：先列有等待回应中的请求或未决项的任务，再列尚未完成的，最后是其余的；每组内新的在前。每行写执行人、开始时间、结果，以及还欠什么（几项未决、几条请求等待回应中）。说明在标题提示里。
- 右边：检查项结果、每日任务（两张表仍可展开）、主要阻塞原因（有才显示）、业务系统读取和 Hub 状态（管理员）或知识库概况（成员）。
- 去掉：四个折叠区、“规划中的功能”、按调用跨度画的“期间任务”图。后者每次打开总览都要读 500 条调用记录，任务的先后在“需要处理”和任务列表里已经有了。
- 新的页面积木 `box`（带边框的块，头、体、尾）和 `tile`（一个数字）在 `ui.ts`，样式是 `ch-card`、`ch-tiles`、`ch-board`、`ch-stack`；后面的步骤沿用。窄屏下数字两列、主列和侧列上下排。

### 验收

- `hub/server/console-overview-priority.test.ts`：数字在前、任务在中、统计在侧；四个数字块；列表 8 行且不含已无事可做的任务；没有折叠区和规划中的内容；侧列有检查项结果、每日任务、业务系统读取、Hub 状态；空团队看到“所选时段没有任务”和“查看工作流”。
- `hub/server/console-overview-bound.test.ts`：有等待回应中的请求的任务排在第一行并写出条数，别的行不写；请求数字写出归并后的类数；原有的读取次数上限和业务系统行的结构不变。
- 本机真实控制台（验收台架、合成数据）在 1440 和 390 宽度、浅色和深色下截图核对，没有横向溢出。
