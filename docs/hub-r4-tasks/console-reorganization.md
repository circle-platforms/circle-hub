# 控制台按设计稿重排（决定 151）

来源：所有者 2026-11-10（决定 151）。合入的 40 个控制台改动各修一处，页面之间没有共同的结构，所有者看后认为整体仍然乱。本页写各页的目标和实施顺序；每一步有自己的分支和拉取请求。设计稿是本机的可交互静态页面，不进仓库，目标以本页的文字为准。

## 原则

1. 每页只回答一个问题：标题行（标题、一行事实、主要操作），至多四个数字，一个主列表。
2. 次要内容进页签；单个对象的详情在右侧打开，列表仍然可见；右侧不再放和主区重复的概况。
3. 解释“怎么读这一页”的句子放进标题旁的提示，页面上只留事实：时段、数量、状态、时间。
4. 哈希、标识、会话、追踪只在“技术信息”里出现；列表和详情用名称和“打开原文”。
5. 内容相同的行归并成一行并写数量（请求列表）。
6. 页签、筛选、右侧详情都对应地址，由服务端渲染，不加前端框架。

## 第 1 步：导航和技能入口

### 允许路径

- `hub/server/console/{html.ts,style.ts,packs.ts,pack-display.ts,space-layout.ts,index.ts,search.ts,packs.test.ts,shell.test.ts}`

- `docs/hub-r4-progress.md`、`CHANGELOG.md`、本任务页

### 决定

- 导航顺序和分组：总览｜任务、知识库、工作流、技能｜连接、团队、记录｜设置、运行状况。组之间是一条分隔线（`ch-nav-sep`），不写组名。团队移到记录之前。
- 技能入口 `/console/skills` 只列通用技能，`/console/packs` 只列工作流。两页各自的范围计数、右侧概况和“最近发布”都只算本页的种类；原来两种合计。
- 入口叫“技能”，种类名称仍取词表的“通用技能”。
- 种类的用途说明（#219）改为所在页面标题的提示：一页一种，不再需要在列表里并列两段说明。
- 技能详情链接到 `/console/skills/<标识>`；`/console/packs/<标识>` 对任何种类照旧可读，页面按该包自己的种类显示所在区域。技能的面包屑是“技能 › 名称”，不再重复种类名（与 #206 一致）。
- 搜索结果里的技能链接到技能页。发布入口沿用原地址，按钮写明种类。

### 验收

- `hub/server/console/packs.test.ts`：技能的面包屑；两页互不列出对方的种类，链接各在自己的入口下；范围计数各算各的，详情页的计数与所在列表一致。
- `hub/server/console/shell.test.ts`：成员九项、管理员十项的顺序，三条分隔线各在任务、连接、设置之前，工作流和技能用同一种区域色。
- `hub/server/console-places.test.ts`：`/console/packs` 没有技能分组，`/console/skills` 有且链接正确；两页各自高亮自己的导航项；技能详情在两个地址下都可读、都高亮技能、面包屑不重复种类；成员看不到未获分配的技能。
- `hub/server/console-section-navigation.test.ts`：两种用途说明各在自己的页面上。
- `node --test "hub/server/**/*.test.ts"` 全包。

### 不做

- 页面布局、列表样式、字号在后面的步骤里做。
- 个人发布后的跳转仍回 `/console/packs/<标识>`（该地址对技能可读并显示技能区域）。

## 第 3 步：任务列表和请求归并

### 允许路径

- `hub/server/console/{pages.ts,requests.ts,style.ts}`
- `hub/server/{console-pagination.test.ts,console-places.test.ts}`
- `CHANGELOG.md`、本任务页

### 决定

- 任务页分两个页签，各是一个列表：“任务”和“等待回应中的请求”（`?view=requests`），页签上写各自的数量。原来请求表接在任务表下面。
- 任务表留六列：任务、产品 / 版本 / 构建、执行人、开始时间、条目、结果。去掉“工作流版本”（和任务名重复）、“会话”和每行的技术标识（在任务详情的技术信息里）。结果一格写出该任务有几条请求等待回应中。
- 按工作流筛选改为下拉框，列出本页任务用到的工作流的名称；原来是一个要填包标识的输入框。本页只有一种工作流且没有筛选时不显示。
- 去掉右侧概况栏（本页任务数、筛选后数量、各结果的数量）：这些数字就在筛选条上。
- 等待回应中的请求按“类型、待补充内容、后续处理”归并，一类一行：数量、所属任务（一个任务时给链接，多个时写个数）、接收人（最多写三个名字）、最早期限，有逾期的写出几条已逾期。有逾期的类排在前面，其次按最早期限。标题旁写总条数和类数。任务详情页的请求表用同一种归并。
- 一页最多画 100 类，超出时写明“显示 100 / 共 N 类”。原来按条画，上限 100 条。
- 没有任何任务时只显示“尚无任务”，不出现页签、筛选和为零的数量。

### 验收

- `hub/server/console-pagination.test.ts`：请求在自己的页签里，逾期的一类在前并写出条数，只有它带逾期标记；接收人显示名字，不出现记录摘要和账户标识；任务页签不带请求表，但每个任务写出等待回应中的条数，页签上有总数，没有概况栏；内容相同的 150 条请求是一行“150 条”；150 类不同的请求只画 100 类并写明；空页面不出现请求和为零的数量；有筛选时仍显示下拉框和“本页 0 个任务，筛选后 0 个”。
- `hub/server/console-places.test.ts`：总览和任务页没有概况栏，其余页面暂时保留。
- 本机真实控制台截图核对：提交过 4 次的任务在列表里写“70 条请求等待回应中”（作废规则生效前是 280 条），请求页签把 142 条归并为 5 类。

### 允许路径

- `CHANGELOG.md`、本任务页

### 决定

- 标题是任务的名称，上面是回到任务列表的链接，下面一行写产品 / 版本 / 构建、执行人和开始时间。
- 页面最上面是一块，左边是任务结果（结果、未决数、回执一句），右边是“还需处理”：等待回应中的请求按内容归并后数量最多的三类，以及去“请求”页签的链接。没有请求时写明没有。
- 其余内容分六个页签，地址是 `?tab=`：验收要求（默认）、条目、请求、过程、来源、技术信息。页签上写数量。
  - 验收要求：每个要求项的名称、各条目的结果（按条目汇总的状态和个数）、说明、检查方式、交付规则、接受的生产者、修复轮数。原来的“键”一列是标识，不再显示。
  - 条目：结果分类下各条目的检查结果、跨条目主张、错误与修正，以及纯事实工作流的模型评论。
  - 请求：归并后的请求表和判据变更声明。
  - 过程：执行过程图、提交与回执、调用日志；翻页链接留在这个页签里。
  - 来源：各来源的可读块和版本来源。
  - 技术信息：运行标识、哈希、会话等事实，当前分享，来源和条目的技术表，投影字符串字段。旧地址 `?view=record` 打开这个页签。
- 分享提示、判据撤回提示和管理处置放在结果块下面，任何页签都看得到。
- 去掉右侧详情栏：它的标题、来源和任务信息分别进了标题行、来源页签和技术信息页签。
- 每个页签只计算自己显示的内容：调用日志、每次提交的原文、来源块、逐条结果只在各自的页签里读取。原来打开任务页要读全部这些（issue #200）。

### 验收

- `hub/server/console.test.ts`、`console-results.test.ts`、`console-sharing.test.ts`、`console-criterion.test.ts`、`console-projection-fields.test.ts`：原来对整页的检查改为读相应页签或用 `testing-task-tabs.ts` 读全部页签，检查的内容不变（分区与各层终态的写法、转义、逐次提交原文、模型评论与生产结果分开、分享与撤回、判据变更、投影字段）。
- `console-run-history.test.ts`、`console-environments.test.ts`：提交历史的窗口和翻页、派发步骤的运行环境都在过程页签里读。

- `packs/workflow/case-review/packs.test.ts`（词表检查）和 `npm run test:docs` 在分支顶端通过。

### 决定

- 连接页原来是一长页：页内目录、业务系统接入表、四个数字、连接关系图、客户端表、业务系统表、运行环境表、两张“规划中”的卡片。现在是四个页签，一个页签一张表，由地址上的 `tab` 决定：业务系统（默认）、业务系统接入、客户端、运行环境。页签上写数量。
- 选中一个业务系统、客户端或运行环境时，页面停在它所属的页签，详情照旧在右侧打开。
- 成员只看到自己的客户端，没有页签；下面一行写明业务系统和运行环境的配置仅管理员可见。
- 去掉：页内目录（内容已不在同一页上）、连接关系图（只是把客户端和业务系统两张表各取前五行再画一遍）、“多终端协同”“消息通知”两张规划中的卡片、四个数字。数字里的事实移到各页签表格上方的一行：业务系统写“已启用几个，共几个”和统计时段，客户端写“24 小时内使用过几个”，运行环境写“可用几个，共几个”和其他状态的数量。“业务系统写操作未开放”移到标题的提示里。
