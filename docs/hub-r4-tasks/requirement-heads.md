# B6：要求项表的“交付规则”“接受的生产者”旁写明含义（#229 的一部分）

来源：所有者全量计划 #229/#199；基线 aded2ffd，`fix/requirement-heads`。做法同 #227、#228：保留正式词，在旁边加说明，不改词表、不改合约。

## 允许路径

- `hub/server/console/{pack-display.ts,packs.ts,pages.ts,requirement-heads.test.ts}`
- `hub/server/{console.test.ts,console-places.test.ts}`
- 本任务页、`CHANGELOG.md`

## 决定

工作流页的“验收要求”表和任务页的“要求项”表都有两列用了抽象词：交付规则（记账型／门禁型）和接受的生产者（事实／判断／独立判断）。表头改为带悬停提示（也进 `aria-description`），文字取自模型的定义：

- 交付规则（V06）：“记账型：每个条目都有终态、证据齐全、效果已知或已处置，就算交付；结果只显示已交付和各分区的数量，不显示“通过”。门禁型：要求同一运行、同一产物，全部必需的要求项都满足才算交付。”
- 接受的生产者（W02 F[4]）：“这一要求项的结果接受谁产生的：事实由 Hub 按规则算出；判断由模型给出；独立判断要求给出判断的不是起草者自己，是否独立按任务包的规定核对。”

两张表用同一对函数（`doneRuleHead`、`acceptedProducerHead`），说明只写一处。每一行的值（记账型、事实等）原样显示。

## 验收

- 单元：两个表头保留正式名称，提示和 `aria-description` 带说明，说明含上面各要点，整段过文案守卫。
- 页面：工作流页和任务页都含这两句说明；去掉表头改动时这两处断言失败（已实证）。

## 不做

#229 里其余的词：“性质与依据等级”“观察上的规则”“出口未写”“边界政策”“缺失事实未写”。它们出现在声明与要求项详情的别的位置，需要逐个对照当前页面和词表，“出口”还要与词表维护方确认如何用“下一步处理安排”表述，不另造枚举。
