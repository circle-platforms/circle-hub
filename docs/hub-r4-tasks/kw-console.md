## 要做到的（验收标准）

### 一、两页共用的空间栏

1. 知识库页和工作流页的内容区左侧加一列空间栏（约 240 像素），自上而下为“全部”“个人”“共享给我的”“团队”，取值沿用生成的搜索范围轴。当前范围写在网址参数里，便于收藏和返回。全局导航保持 8 项不变。
2. 知识库中，“个人”“团队”展开为目录树，用原生折叠元素，不需要脚本。产品知识来源作为团队下的“产品 › 产品线 › 版本线”目录出现，取代现在单列的“按产品线浏览”区块。
3. “共享给我的”按授权人分组，例如“李四 › 排障记录”。没有任何授权时，整组不显示。
4. 工作流页使用同一空间栏，每项下注明“工作流 N · 通用技能 M”；右侧保留“工作流”“通用技能”两栏，只列所选范围内的内容。
5. 窄屏时空间栏收为页首标签行，沿用现有标签样式。
6. 撤掉知识库页的“知识入库流程”卡片。“个人默认私有”由空间栏的分组表达，“提交共享经 Hub 检查”由预检页表达，其余说明放进标题的悬停提示。
7. 目录在界面上**不显示斜线**：只写名称（接口规范），层级用“ › ”连接（接口规范 › 认证；团队 › 产品 › 产品 A › 2.x）。内部路径与接口参数不变。

8. 每行在标题之后显示范围，用受众措辞，由服务器按实际受众计算，包括继承自上级目录的授权和全体管理员的当前人数。知识列名为“可见范围”，工作流列名为“使用范围”：

   - 本人及 N 名成员

   - 来自 某成员（他人授权给本账户的内容；被授权者只看到这一句，不显示授权细节）
   - 全体成员（团队）
   - 该产品线的读者（团队的产品目录）
9. 目录授权覆盖下级，条目详情注明“继承自 接口规范 的授权”。
10. 状态另列，不混入范围列。知识条目用：已核验、未核验、已撤回、被取代；工作流用：已发布、已退役。
11. 条目的“种类”列取模型的条目种类：定义、行为、用例、缺陷、观察、步骤、教训；列标题的悬停提示列出全部种类。原文不是条目：目录页的条目表下方另设“原文”区块，列出文件名、大小和“被 N 条条目引用”。

### 三、知识库各视图

### 四、工作流页

### 五、授权对话框（知识与工作流共用）

19. 入口在个人目录标题处、个人空间根目录（显示为“整个个人空间”），以及个人工作流、个人通用技能的卡片和详情页。沿用控制台现有的无脚本对话框做法。
20. 对话框内容：
    - 当前范围；
    - 授权给：二选一，“指定成员”（精确输入用户名，不提供成员目录浏览）或“全体管理员”（只显示当前人数；悬停提示写明以后新增的管理员同样可读，停用或降为成员后不再可读）；
    - 授权内容：知识为“目录（含全部下级目录）· 只读”，工作流为“包号与版本 · 仅可使用”；
    - 授权前检查及结果：知识为凭据扫描、引用个人凭据来源的条目、仅本机内容；工作流为凭据扫描、所依赖的个人条目或技能对被授权者是否可读；
    - 现有授权表：对象、授权内容、授权时间，以及“收回授权”按钮；
    - 后果说明：收回后对方不能继续读取，已读或已引用的内容无法追回。工作流另写明：被授权者的运行结果对发起人和全部被授权者可见。
21. 不设“全体成员”，也不设权限级别、链接分享或公开发布。多个授权按并集生效（悬停提示写明）。不能授权时按钮置灰，悬停提示写明原因与处理办法。授权和收回都写入记录。

### 六、提交共享与发布到团队（两步）

22. 两者用同一个两步流程：预检页 → 结果页。
    - **知识的提交共享**：本人的已核验条目才能发起。
    - **工作流的发布到团队**：本人的个人工作流或通用技能，且持有发布权。
23. 预检页依次显示：
    - **范围变化**：个人一侧注明“保留不变”及其范围，团队一侧注明“新写入一条”及“全体成员”；
    - **写入位置**：可选择团队目录，默认与个人目录同名（决定 88 第 7 项，见 `kw-share.md`）；
    - **自动检查**：逐项显示，状态用检查轴现有用语（通过、未通过、未检查、检查未完成）。知识依次为依据可解析、引文逐字一致、来源可共享、与团队条目不重复、凭据扫描；工作流依次为发布权、结构校验、沙箱运行（正反样例）、引用可解析、凭据扫描；
    - **提交之后会怎样**：个人原条目及其授权不变；团队条目由本人署名，本人和管理员可撤回；撤回不能追回已读内容；结果记入“我的提交共享”。
24. 预检规则：
    - 第一项未通过即停止，其后各项显示“未检查”，不显示为通过；
    - 因来源暂时不可读等原因未能完成的检查显示“检查未完成”；
    - 未通过的一行写明拒收码、原因与处理办法；
    - 凭据扫描只指出命中的位置，不回显疑似凭据；
    - 与团队条目重复时，链接到已有的团队条目。
25. “确认提交共享”“确认发布到团队”只在全部检查通过时可用。确认时服务器重新执行全部检查，以确认时的结果为准。结果页显示“已合并”并链接到团队条目和团队版本，或显示“已拒收”及原因。
26. 知识服务提供只检查、不写入的预检模式，供预检页显示真实的检查结果。工作流沿用已有的暂存加预检流程。
27. 不称“移动”：个人原件保留。不设“申请”或“请求审核”：没有审核环节。

### 七、管理员可见性

28. 团队页的成员详情只显示个人空间的元数据：已用容量与上限（可调整）、授权给全体管理员的目录或工作流数量，第四阶段再加同步方式。不显示条目标题、条目数量或个人版本历史。

### 八、记忆（Hub 端）

31. 记忆是 Circle 会话自动加载的说明，内容是偏好与约定。记忆不要求出处，不经核验，不能作为运行输入或依据，结果不能引用记忆。
32. 存储：个人空间和团队空间都能保存记忆文档，格式为 Markdown 文本，有版本，可被取代。
    - 单篇上限默认 24,000 字节，与 Circle 读取说明文件的上限一致；每个空间的记忆总量另设上限。两者都可以在 Hub 的限额配置里调整。
    - 写入时做凭据扫描，命中即拒收，并按规则留下拒收记录。
33. 个人记忆：
    - 默认仅本人可用。可以像知识一样授权给指定成员或全体管理员，但只能在控制台和读取接口中查看，**不会**自动加载到被授权者的会话；
    - 随本人的各个 Circle 同步，同步本身属于第四阶段。
34. 团队记忆：
    - 由管理员维护（新建、修改、停用）；
    - 成员可把个人记忆提交共享到团队记忆，不审核，只做凭据扫描和大小检查，预检页同第六部分；
    - 全体成员的 Circle 加载团队记忆，加载本身属于第四阶段。
35. 控制台：知识库页首加“知识 / 记忆”切换，共用空间栏，全局导航仍为 8 项。记忆列表的列为标题、可见范围、大小、更新时间；编辑用纯文本框；个人记忆可提交共享。
36. MCP：仍是六个工具。先在本页“实施方案”写出读取与写入记忆的协议，例如在现有工具上加参数，经 Claude 审查后再实现。协议须让第四阶段的 Circle 能：
    - 读取团队记忆；

    - 分辨各条记忆的范围与版本。

### 一、记忆对象与模型边界（协议草案）

- 记忆是声明的客户端会话说明：偏好与约定，不是运行的知识条目、要求项或核验结论。标题和 Markdown 均由账户提交，Hub 不起草、不调用模型。
- **模型归类建议，待审**：内容归 C01 政策类的会话偏好声明，效力限客户端上下文，不增加第五个家；不交给 Hub 的运行政策或方法解释器，也不成为依据。在 C01 明确该用途限定，现有运行政策的样例及生效规则保持。该归类与记忆记录一并交模型审查，避免仅靠界面区分。
- 文档的稳定 ID 取首次 `memory_document@1` 记录摘要；每次修改产生 `memory_version@1`，该记录摘要为版本。文档改名或换目录不换文档 ID。创建记录只存空间、创建人、时间和幂等键的安全身份，不含正文；正文检查通过后在同一事务建立首版本。
- `space` 实际值仍是 `team` 或账户 ID；请求中的 `personal` 只映射到当前账户。记忆有独立目录投影，不出现在 `tree:` 知识树、来源 `src:` 或包文件中。
- 通用 `rec:`／`get_nodes.reference`／`resolve_reference`、记录输入与依据解析统一拒绝全部记忆记录，管理员也不能借通用记录读取绕过专用权限。记忆专用模式与 `run` 互斥。文档 ID 和版本字段是管理标识，不返回可作依据的 `reference`。
- 独立上传仍按自身的声明来源处理；不按正文相同就禁止正常原件，也不新增按字节全局拒读规则。直接记忆对象和它的读取回执不会被 Hub 接受为运行输入或依据。

### 二、读取：`get_nodes.memory`

仍用 `get_nodes`，新增可选对象 `memory`，与现有 `root`、`reference`、`search`、`pack`、`run` 等读取模式互斥。不是第七个工具。

| 字段 | 约束与含义 |
| --- | --- |
| `scope` | 列表时使用已有 `all`／`personal`／`shared`／`team`；默认为 `all` |
| `document` | 省略时列元数据；给出时只读这一篇，先按当前权限检查 |
| `version` | 只随 `document` 给出；浏览时可省略取当前版本，会话加载时须从列表复制 |
| `for_session` | 默认 false；true 是第四阶段客户端的会话读取模式，只允许团队或本人的启用记忆 |
| `cursor` | 列表或正文的有界续读；绑定账户、模式、可读版本集合及参数 |

列出会话可加载的团队记忆：

```json
{"memory":{"scope":"team","for_session":true}}
```

列出本人的个人记忆，或手动浏览获授权记忆：

```json
{"memory":{"scope":"personal","for_session":true}}
{"memory":{"scope":"shared"}}
```

读取列表中锁定的版本：

{"memory":{"document":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","version":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","for_session":true}}

返回形状建议：

- 列表为 `memory_page: {scope, snapshot, items, next}`；每项含 `document`、`version`、实际 `space`、`title`、`path`、`state`、正文 `bytes`、`updated_at`、`updated_by`、`auto_load_allowed` 及当前可见范围。被授权者不收到授权对象名单或人数。
- 正文为 `memory_document: {document, version, current_version, space, title, path, state, bytes, markdown, offset, next, auto_load_allowed}`。单次正文默认最多 16,000 个 UTF-8 字节，在字符边界截取，游标固定版本；不把部分正文称为完整。
- `snapshot`／游标复用现有授权与版本绑定方式，只覆盖当前有权的文档集合。集合变化时要求从第一页重读；每次续读重查权限。不给被授权者返回未授权文档的总数、更新时间或历史活动。
- `for_session=true` 的列表只接受 `personal` 或 `team`，不接受 `shared`／`all`。正文也独立核对“团队或本人”及当前启用状态；只有查看权的非本人个人文档不能通过会话模式返回。浏览模式可查看当前获授权文档，但 `auto_load_allowed=false`。
- 本人可浏览个人历史，管理员可浏览团队历史；被授权者只浏览当前个人版本。普通成员读取团队当前启用版本。停用／取代期间会话续读要求重新列出当前版本，不能借旧版本继续加载。
- 第四阶段的 Circle 分别列出团队与本人记忆，按文档 ID 稳定排序，逐篇收齐所列版本再加载；两组分开返回，Hub 不判断偏好冲突或替客户端拼接优先级。本阶段只验证接口与资格，不把接口返回等同于会话已经加载。

### 三、写入：`upload_file.memory`

`upload_file` 新增 `memory` 载荷，与文件、个人知识、知识共享／撤回等载荷互斥。每次请求提供 `client_key`，用既有幂等机制按账户、空间和操作限定；相同键、相同载荷返回原回执而不重复写版本，载荷不同使用已有 `IDEMPOTENCY_MISMATCH`。返回缓存前仍检查当前账户与写权限。

创建本人记忆：

```json
{"memory":{"space":"personal","expected_version":null,"title":"合成会话约定","path":"/preferences","markdown":"先列出已知事实与缺失信息。","client_key":"synthetic-create-01"}}
```

修改记忆：

```json
{"memory":{"space":"personal","document":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","expected_version":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","markdown":"先列出事实、缺失信息和下一步。","client_key":"synthetic-edit-02"}}
```

- 创建时不带 `document` 且 `expected_version=null`；更新必须带 `document` 和当前 `expected_version`。冲突返回当前版本的安全元数据，不覆写正文；客户端保留本机修改。第四阶段的分支同步另行实施。
- `title`、`path`、`markdown`、`enabled` 是可修改字段。更新未给出的字段保留；仅改启用状态也追加版本。本人只能写本人的个人文档，团队新建／编辑／停用限管理员；获授权者只读。
- Markdown 保留提交的文本，不裁剪或做宽窄字等价变换；要求合法 Unicode 文本，以 UTF-8 字节计限额。原样读取不经过模型或 Markdown 执行器，界面按文本转义。
- 新正文和可能公开的标题／目录做完整凭据扫描；拒收只记录安全摘要、码和命中位置，不回显可疑值。停用和收回授权等管理动作不因正文额度已满而被阻止；重新启用须重新检查正文与当前额度。
- 返回 `memory_write: {document, version, previous_version, space, state, bytes, updated_at, unchanged}`，另带现有工具回执。显示为保存结果，不显示“已核验”。
- 正文写入与文档头、额度累计值、幂等回执在同一事务提交；拒收动作在回滚后独立保留恰好一条，沿用 B05 的 `validate`，不新增动作种类。

### 四、授权与共享

1. **授权隔离建议，待审**：记忆授权使用独立的 `memory_grant`，复用目录前缀、`member`／`administrators` 及 `grant`／`revoke` 词表；旧知识目录授权不自动开放新记忆。本人可授权整个个人记忆空间或目录，仅查看。共享给指定成员或管理员不使记忆可自动加载。

7. 团队副本有独立正文，个人停用或之后的个人修改不改团队副本。团队文档由管理员维护；本阶段不实现删除、跨设备同步或 Circle 会话加载。
