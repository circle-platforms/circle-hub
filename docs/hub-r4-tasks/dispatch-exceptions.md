# 派发出的问题随触发它的那次调用返回（决定 155，issue #142）

来源：所有者 2026-10-31 的方向（issue #142）；2026-11-11 对两个待定项的回答：“应该看客户端 circle 的状态，如果是 auto 就不需要，如果是手动就需要，跟着客户端走，自动触发派发”。基线 `origin/main` 812c52b2，分支 `fix/dispatch-exceptions`。

## 开工前核对到的现状

issue 写的时候（2026-10-31）派发只有管理员命令。之后决定 105 的实现在 2026-11-04 进了主线：任务包声明 hub_template 效果行时，受理的 `submit_result` 由 Hub 自己派发，作业进展写在答复的 `dispatch` 里。所以两个待定项里：

- **自动触发**已经在主线，这次不用再做。
- **要不要确认**不需要 Hub 做任何事。`submit_result` 在调用者会触发派发时，工具注解照实是“对外写、破坏性”。Circle 的文档写明：标了破坏性的工具每次都问，没有“本次会话都允许”；在 `auto` 模式下不问，和那个模式下的所有调用一样。这正好是所有者要的“跟着客户端走”。不改 Circle。

真正缺的是 issue 里约定的三种返回。

## 三种返回

| 情况 | 以前的答复 | 现在的答复 | 原样重交 |
|---|---|---|---|
| 未发出：目标没给租约、连不上或应答不完整、预检条件不满足 | “未发出”，没有原因；“这个核验运行不会再派发” | “未发出”和原因；“原因消除后原样重交，Hub 会再试一次” | 再试一次 |
| 未发出：在效果边界被拒，什么都没碰目标 | 有原因，重交再试 | 不变 | 再试一次 |
| 目标拒绝（有认证的拒绝阶段）、已证明未执行 | 只有结局名 | 写出目标在哪个阶段拒绝；“修正后原样重交，Hub 会再试一次” | 再派发一次 |
| 派发结果未确认：已发出，没有可信应答 | “结果未知，等管理员对账” | “派发结果未确认”，请求号，“不要重交，也不要另开运行重发，目标可能已经执行过一次”，处置的管理员和期限 | 只读进展，不到目标 |
| 最终边界的拒绝（到过目标之后，原因在运行本身） | “不会再派发”，开新的核验运行 | 不变 | 只读 |

重试的那次答复先列出此前各作业的结局（注明“这次重交 Hub 已再试”），再列新作业。否则模型只会看到“已派发”，不知道上一次为什么结束。

## 做法

- `hub/dispatch/service.ts`：提交之前失败时，按错误的种类写一条给运行者看的原因（`notSentReason`），只用 Hub 自己的固定说法；目标的原文、地址和错误细节照旧只进管理员的 `reason`。为此给“没取得目标租约”和“目标应答不完整”各一个错误类型（`TargetLeaseError`、`IncompleteReplyError`）。作业状态多三个字段：`not_sent`（在调用提交前结束）、`request_id`（提交意图的请求号）、`rejection_stage`（认证拒绝的阶段词，只有是短的普通词才给出）。
- `hub/dispatch/accepted.ts`：`retriable` 决定重交时能不能再派发；`runnerNote`、`nextStep` 按上表写文字。
- 派发本身的守卫没有动：每次仍然核对全部前提、同一血缘此前的尝试、字节与预算。已发出、已生效、未知的尝试照旧不能再发同一份内容。
- “查不清才交给管理员”原来就有：执行器登记了查询调用时，未知结局先按请求号向目标查询（`reconcileRequest`，运行维护的 `job resume`），仍未知才产生处置请求；没有登记查询调用的执行器直接产生处置请求。这次只是把请求号、管理员和期限写进答复。

## 没有做的

- 没有给 `dispatch` 条目加结构化字段（结局、请求号、能否重试）。那要改 `submit_result` 的输出格式和合约；现在文字里都有。需要的话另开一项。
- 没有限制重试次数。每次重试都要模型自己再调用一次，答复里有上一次的原因。

## 验证

`node --test hub/dispatch/accepted.test.ts`：13 项通过。新增五项：未发出（目标不给租约、预检不满足、目标连不上各一）、有认证阶段的目标拒绝（重交后第二次提交）、已发出无应答（重交不再发、不到目标）。原有“最终边界拒绝后不再试”和“效果边界拒绝后重交再试”两项仍然通过。只用回环 MCP 桩和合成字节，不能据此认证真实目标。
