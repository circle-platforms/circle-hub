# 设计与最小实现：同一被判对象此前在目标上的核验（run history）

状态：2026-11-20，分支 `wp/claude/t18-compile-flow`，本地实现，未发布、未部署。所有者的决定见进度页决定 182；通用模型第 86 版（W06 R[8]）。Hub 一侧只加一条只读的导出路由；谁来读、读了怎么用，是客户端工具和工作流包的事（第 8 节）。

## 1 要办的事

同一份文档一轮一轮地从头写：每一轮第一次上机，总有那几条要靠设备才学得到的改动（一张表每个键打印两行、两种记录不能并存、一次同步要几分钟），而每条用例的上机轮次有限，常常不够重新发现一遍。此前每一轮的上机结果都在 Hub 的记录里，新开的运行却看不到：运行导出只按运行给作业（`/run-export/<运行>/jobs`），没有“这个被判对象以前上过哪些机”的入口。

这里补上这个入口：给一个运行，列出同一被判对象此前在目标上的核验。只列已经记录的事实，Hub 不比较、不归纳、不评判，不调用模型。

## 2 先说结论

- **一条只读路由** `GET /run-export/<运行>/history`，与其余运行导出路由同一套认证（Bearer 访问令牌，控制台会话令牌拒绝）和同一条读取规则。不加 MCP 工具、协议码、词表取值、记录种类和迁移。
- **读取规则不新增**：被问的运行和每一个列出的运行，都按运行导出的既有规则判断：运行对读者可见（`runReadableBy`，就是 `getRun` 答不答的那条），且读者是它的运行者或管理员（`mayExport`，`hub/runs/engine/run-history.ts`；其余四个导出改用同一个函数，规则没有变）。读不到的运行不出现，也不计数。
- **被判对象的身份**取运行里角色为被判对象（`subject`）的来源：外部对象取 `external` 去掉 `@修订号`（同一对象的另一个修订仍是同一被判对象），直接绑定字节的取它的引用（同样的字节才算同一个）。运行没有这种来源时身份为空，答空列表。
- **只列已结束且已生效的作业**：作业日志有终结记录（`ended` 为 `done`）且效果结局为“已生效”（`effective`）。没发出的、目标拒绝的、证明未执行的、未知的、还在跑的都不列。
- **行里只有条目和动态层终态**，取自作业导出所用的同一份经核对的结果投影，按读者自己的层级读；读不到时 `rows` 为 `null`，不补判定。日志、会话等原件的引用不在这里给，仍由 `/run-export/<该运行>/jobs` 和 `/sources/<sha256>` 给。
- **有界**：缺省列最新的 8 个运行，`?limit=<1-8>` 只能调低；查找至多看最近派发的 512 个运行，没看全且没列满时 `complete` 为 `false`。

## 3 请求与回答

```
GET /run-export/<运行>/history[?limit=<1-8>]
Authorization: Bearer <访问令牌>
```

| 情形 | 状态 | 说明 |
|---|---|---|
| 运行可导出 | 200 | `application/json`，`run-history@1`，带 `content-digest`；没有此前的核验时 `runs` 为空 |
| 运行不存在或不可导出 | 404 | 与其余路由同一句话，不区分 |
| 查询不是单独一个 `limit=<1-8>` | 400 | “这个地址只接受查询参数 limit，取 1 到 8 的整数” |
| 没有令牌或令牌不可用 | 401 | |
| 控制台会话令牌 | 403 | |
| 不是 GET / HEAD | 405 | |
| 没有这条路由的旧 Hub | 404 | 客户端据此知道读不到，不当作“没有历史” |

回答的形状是 `contracts/src/run.ts` 的 `RunHistoryExport`：

```json
{
  "schema": "run-history@1",
  "run": "run_…",
  "subjects": ["<系统>:<类型>:<编号>"],
  "limit": 8,
  "complete": true,
  "runs": [
    {
      "run": "run_…",
      "started_at": "2026-11-19T02:00:00.000Z",
      "build": "<锁定的构建>",
      "jobs": [
        {
          "job": "<64 位十六进制>",
          "plan_run": "run_…",
          "ended_at": "2026-11-19T03:00:00.000Z",
          "outcome": "effective",
          "rows": [{ "item": "<条目>", "dynamic_terminal": "pass" }]
        }
      ]
    }
  ]
}
```

- `runs[].run` 是作业所属的运行（核验运行）；`jobs[].plan_run` 是这份作业核验的计划运行，作业没有记时为 `null`。
- `build` 是该运行开始时锁定的构建，没有锁定时为 `null`。
- `ended_at` 是作业日志里第一条终结记录的时刻（`RunJob.ended_at`，本次在 `hub/dispatch/read-runs.ts` 加的字段），那条记录不带时刻时为 `null`。
- `outcome` 用词表 `effect_outcome`，这里总是 `effective`；`dynamic_terminal` 用词表 `dynamic_terminal`。
- 顺序：按各运行最晚一个作业的结束时刻，晚的在前；一个运行里的作业按日志顺序。
- 被问的运行自己不在列表里。核验它的运行（`plan_run` 等于它）只要满足条件照样列出，由 `plan_run` 可以认出。

## 4 怎么找：有界的顺查，不加索引

运行记录没有按被判对象身份的索引，记录只追加。这里不加迁移、不回填索引，改为从派发日志出发顺查：

1. 读一次全部预订记录（`runReservations`，作业导出本来就要读的同一份；每 500 条一次查询），得到“哪些运行被预订过作业”，按日志首次出现的顺序，最新的先看。
2. 按 32 个一批读这些运行的记录（每批一次查询），先看记录里现成的两件事：读者能不能导出它、它的被判对象身份对不对得上；都满足再按可见规则复核。
3. 对得上的运行才读它的作业（每个作业读一次状态、一次日志，再按读者层级读一次结果投影）。
4. 列满 `limit` 个就停；至多看 512 个运行。

在临时 PostgreSQL 上量过（`hub/runs/engine/run-history.test.ts`，运行记录垫到约 60 KB，接近冻结了十七条用例和规程的运行）：

| 派发过的运行 | 情形 | 查询 | 行 | 读入 | 用时 |
|---|---|---|---|---|---|
| 100 | 命中 8 个，且都是最旧的（要看完全部） | 32 | 261 | 6.3 MB | 约 55 毫秒 |
| 300 | 同上 | 38 | 661 | 18.7 MB | 约 120 毫秒 |
| 300 | 没有命中 | 13 | 602 | 18.7 MB | |

多看 200 个运行只多出它们的记录（7 批），每命中一个运行约 3 次查询，不随历史增长。测试按查询次数断言这两点，不断言时钟。命中的运行在最近派发的那些里时，第一批读完就停。

读入量主要是运行记录本身。真有一天派发过的运行多到这个顺查显得贵，再加索引（新的迁移，回填旧运行）；现在不值。

## 5 对照设计

- **Hub 只核验、不生成**：这里没有新判断。行里的终态是派发服务自己写的结果投影里已有的值，经作业导出同一套核对（生成者是 `dispatch@1`、绑定这份作业和产物摘要、逐条覆盖）才给；不满足就是 `null`。
- **未知保持未知**：投影读不到、作业没有终结记录、效果未知，都不折算成通过或失败，直接不列或留空。
- **读取规则**（D05 R[3]）：不可导出的运行答 404，与不存在的不区分；别人的运行不出现在列表里，也不透露数量。
- **记录只追加**：不写任何记录，不加索引项。每次请求照旧写一行调用日志（工具名 run-export），管理员备注里是列出的运行数。
- **核心不认产品**：身份只看来源的角色和外部标识的形状，条目只是字符串；代码里没有任何产品、命令或客户的名字。
- **不是来源**：这些记录不绑定到被问的运行上，不进它的锁定版本，不能作期望值的依据。模型 W06 R[8] 写明了这一点。

## 6 顺带修的一处

`/run-export/<运行>/jobs` 自 2026-11-15 的提交 718d5acf7 起，对不是管理员的运行者，只要运行有作业就答 500：`exportedJobs` 把读者本人交给派发服务读作业状态，而派发服务只答管理员（`ExecutorRegistry.admin`），调用抛错。本次改为由具名管理员读日志（`applyDispatchResults` 一直这样做），结果投影仍按读者自己的层级读，缺失原因仍给成员可读的那一版。没有这一处，成员既读不到自己运行的作业，也读不到这里的历史。验收 63 用真实的派发服务核对了成员读两条路由。

## 8 不做的事

- 不按条目过滤、不合并多轮、不挑“最好的一次”：这些是读的人的事。
- 不给日志、会话和设备原话：它们按原有的作业导出和原件路由读，读取层级照旧。
- 不缓存、不存储、不建索引。
- 不改六个 MCP 工具，不改任何工作流包的合约。
