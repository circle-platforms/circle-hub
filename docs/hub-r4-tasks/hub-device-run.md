1. 转换脚本（集成者在本机对只读副本跑；只打印计数和摘要；输出写到参数给的暂存目录，从不写进仓库）：check-runtime-contract.ts <合约文件> --expect <摘要>，用 case-compile 的合约解析器核形状和身份，不改字节；bed-topology.ts <网关拓扑回答> --services <文件> --reserved <文件>，机械转换成 test-bed-manifest@1，目标类型从 test-bed 包的 manifest 模块导入，源标签表只在脚本里写一处，撞名、不认识的标签、没前缀或掩码是假定的地址拒绝（或按显式参数列出后丢弃），两个包的清单解析都要通过，打印源回答的摘要；runtime-profile.ts 从环境核对的回答、转换后的清单和合约起草配置，所有者要确认的部分留成显式的待填项，用包的配置解析器校验。
2. 合成全链路验收（tests/acceptance 新文件）：真 Hub 装配、临时 PostgreSQL、回环网关桩、脚本化模型；合约、配置、清单都是编的，地址只用 192.0.2.0/24。发布三份文档、登记执行器、job precheck、预订、计划运行（脚本化模型交槽位，驳回一次再修好）、生成脚本出工作簿、上传、核验运行、job dispatch、结果、释放。另走三条：上传的工作簿改一个字节，核验不支持，派发被拒；网关丢回执，冻结，对账后继续；只有计划运行（缺工作簿）不能派发。
3. 真机运行脚本 scripts/real/accept/device-run.ts（集成者在所有者答复以后才跑）：按设计第 1 节的次序调用已部署 Hub 的命令，每一步先打印要做什么，派发前要求输入确认；只打印阶段、码、摘要和逐用例结论；不进 CI。

- 全仓检查：词表扫描零命中、不加例外；仓库卫生检查（没有真实地址、凭据、绝对路径）通过。

4. **第 4 问：合约启用的（对象，方法）全开，拒绝表照旧。**
   - `runtime-profile.ts` 起草 `allowed` 时取合约里每个启用的（对象，方法），不再只取四类。每个参数要落到 case-compile 格式表里的一种角色（设备命令行、主机 shell、字面断言、等待）；合约里看不出的，草稿留成显式的待填项，由集成者填，`--check` 再用 case-compile 的配置解析器核。
   - 有参数落不到这四种角色的组合不开：核验对这个参数什么都查不了，开了就绕过拒绝表，碰底线（不重启设备）。草稿把它们单列成“未开”，每项写缺的事实（哪个参数、为什么落不进）和下一步（case-compile 为它加角色和检查，另写一页）。
   - 拒绝表照旧：设备上拒绝重启、清配置、升级、HA 这类整机命令，主机上拒绝重启、关机、格式化这类命令，写在配置的 `denied.device`、`denied.host` 里；命令文字是部署数据。
   - `--check` 另核：`allowed` 是启用组合的子集；每个启用的组合要么在 `allowed` 里，要么在“未开”里，不重不漏。
   - 测试：合成合约 6 个启用组合（四类各一、一个参数能定角色的别的方法、一个有落不进角色的参数）加一个禁用对象：开 5 个、未开 1 个，禁用的两边都没有；待填项没填时 `--check` 不过；漏列、多列都不过。

5. **第 5 问：地址。**
   - 设备命令行里可以出现本台架其他设备的地址；台架外的地址照旧只能经替换表换进来。这一件改 case-compile 的 `checkAddresses`（`packs/workflow/case-compile/functions/checks.ts`，现在别的设备的接口地址报 `address_wrong_device`），不在这条分支上：hub-case-workbook 正在改同一个文件，排在它合并以后，由集成者交给下一条改 case-compile 的分支，包升次版本、重签。
