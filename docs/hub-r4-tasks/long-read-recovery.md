# Recover a disconnected read response

`long-call-status` can identify a long `get_nodes` call but did not retain its answer. Keep a bounded, short-lived in-memory copy of successful read responses, keyed by the authenticated user, exact original argument digest and original trace. Do not store it in a log, database or file. A status query with an unambiguous trace and a completed matching log may recover the original answer after rechecking the current reader, source tiers and the visibility/validity of any included contributions and feeding records. Label it as a historical snapshot, not the current latest data.

Never return cached source text when current access or credential status cannot be established. For a source reference, use the existing current source reader. For a tree page, recheck the root, currently readable and clean source captures, and each included dynamic record; bound the number of rechecks and do not expand the command tree. Unsupported reference forms, excessive source counts, expired/evicted results, changed permissions or incomplete checks stay unknown with a re-read/repair exit. Old responses lost before this feature and responses lost on a process restart cannot be reconstructed. No original call is reissued by the status query.

This is a platform mechanism: no new tool, contract, record or package format. Scope: server in-memory cache, reauthorization, MCP capture and read rendering; a knowledge-owned read-only source check using the existing synchronizer identity; synthetic tests; this page, the previous task's follow-up note, server README and simplification inventory. Use the affected-tests workflow with adaptive concurrency; independently review only actual credential-leak/real-write risks. No real data, credentials, devices, services or deployment.
