# 任务：运行器自己清理的配置命令不要求逆命令

依据：决定 112（所有者，2026-11-01，"2检查跳转机的clear py函数"，随后选"按 clear 规则算，规则外仍要逆命令"）；InfoTest 的 `lib/apv/clear.py` 和 runner；CES 的框架清理类 C1（`gen_command_teardown_atlas.py`、`tau_coverage.py`）。

此前 case-compile 要求每条到用例结束还生效的配置命令都在清理段里有一条声明过的逆命令。InfoTest 的 runner 自己会清理：第一个用例之后，每个用例开始前，runner 对每个设备对象调用 `clear()`；整本结束时，夹具收尾也调用一次。`clear_config` 拿这个对象连接以来发过的全部命令行，按 `get_clear_list` 里 `CMD_RULES` 的源码顺序逐条比前缀，第一条命中就用那条规则的清理命令；没有规则命中的命令不清理。CES 把命中的命令归为 C1（框架每例清理），只对其余命令要求对象级逆操作；它的规则表只给前缀和源码行，故意不给具体清理命令，因为很多是模块级的 `clear … all`。

## 做了什么

1. **契约里的清理声明**：runtime-contract@2 加一项封闭的补充声明 `cleanup`：`source`（runner 里的路径）、`sha256`（文件字节摘要）、`objects`（runner 会清理的 1–16 个合约对象）、`rules`（1–512 条，每条 1–16 个单行前缀，可带源码行号）。不声明清理命令。和其他补充声明一样，恢复原合约身份时去掉它；`sha256` 和原合约 `source_hashes` 里同一路径记的摘要不同就拒绝整份合约。
2. **清理义务**：清单对象上的一条还生效的配置命令，命令行以某条规则的前缀开头，就不要求逆命令；其余的照旧要在清理段按逆序写声明过的逆命令。给被覆盖的命令写了逆命令也照样接受。
3. **披露**：合约检查的支持结论写出有几条配置命令由运行器自己的清理收尾、各由哪条规则和前缀覆盖，以及原合约的源文件摘要表是否记了同一摘要（没记时写明摘要只是 Hub 侧声明、跳转机上的字节未核对）。
4. **说明**：README 加 3.9.8 一节，SKILL 的清理段一句话说明。
