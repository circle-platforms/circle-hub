## 复核（`b3b97cce`）

原有五项与四个疑点已修正；运行角色仍可按设计清除、恢复或收集任一成员的个人内容，授权检查在应用层，已在记录中写明。复核发现：

1. **严重：迁移 15 的 `hub_collect_personal_sync` 可被运行角色借临时对象提权。**
   - 原因：它以所有者身份执行（SECURITY DEFINER），`search_path` 写成 `pg_catalog,public`，没有把 `pg_temp` 放在最后；PostgreSQL 会先在 `pg_temp` 里找类型名，而函数声明了 `removed text[]`。
   - 复现：运行角色在自己的会话里建 `pg_temp` 下的同名域类型，域检查以表所有者身份执行，可以关掉 `records` 的只追加触发器、改写正文。
   - 影响面：平台自建的数据库已收回 PUBLIC 的临时对象权限，挡住了这条路；测试环境和外部管理的数据库没有挡住。
   - 修正：所有以所有者身份执行的函数，`search_path` 一律以 `pg_temp` 结尾；类型写全名（`pg_catalog.text[]`）；把这个复现做成回归测试；授权运行角色或启动自检时，发现它有临时对象权限就拒绝。
2. **策略：被运行引用的个人上传。** 旧数据中被运行来源或其他非空间记录引用的个人上传在清除时保留，新数据中被运行引用的会被清除，前后不一致。
   - Claude 的决定：个人上传一旦被绑定为运行的依据，就已向那次运行的读者声明过，与团队副本一样属于独立持有者。清除时保留文件，只断开与个人空间的关联；新旧数据一致处理，并写入文档。
3. **说明：** 迁移 14 的 SQL 在 `e2d6c98c` 之后改过。只有应用过旧版本的数据库会拒绝启动；迁移 14 没有部署过，按审查结论允许修改。

## 第三轮复核（`0ab652a8`）

- 临时对象提权已关闭：全部 12 个以所有者身份执行的函数，`search_path` 都以 `pg_temp` 结尾；授权和启动时都拒绝带临时对象权限的运行角色。用 11 种类型名做冒充探针，没有一次以所有者身份执行。
- 运行引用的个人上传按决定保留，新旧数据一致。另一成员的运行经分享引用了本人的上传时，清除后字节同样保留，只有本人可读。这一点交所有者确认。
- 第 4 步（`a266c5e9`）逐项检查无误：提交不会部分生效；过期的期望状态不能覆盖新头；冲突不会被悄悄解决；服务器总会重新核验；控制台、MCP 与同步写入都受代次与“仅保存在本机”守卫；缺失与无权相同。

需要修正：

1. **严重（可用性）：迁移 17 让每次记录读取都扫全表。**
   - 原因：`hub_read_records()` 加了 `SET search_path` 子句，PostgreSQL 不再内联带 SET 子句的 SQL 函数。
   - 影响：`get`、`getById`、`getMany`、`find`、`list` 等每次读取都构造整张表再过滤。5 万条记录时，单次读取从 0.49 毫秒（走 `records_digest_key` 索引）变成 22 毫秒（全表扫描并溢出到临时文件），并随记录数线性增长。
   - 修正：去掉这个 SET 子句。这个函数不以所有者身份执行，内部名称都已写全模式名。再加一个执行计划回归测试，要求按摘要读取时走索引扫描。
2. **说明：** 迁移 14、15 又被就地修改过；只在它们从未部署的前提下可以接受，合并前冻结。
