依据：`docs/hub-r4-kb-direction.md` 第二、四节，K03、K04 R[6]、W07 R[4]、B02、B03（`node tools/show-element.ts K03 K04 W07 B02 B03`）。

- Circle 和 Jev **按文档**的产出（分类、归位提议、声明、关系）存到候选层；**按任务**的产出（排序、取舍、分数）只进运行记录。

- 归位提议由 Hub 按确定性规则核验：引文逐字出自源文件、路径可解析、不越过声明。
- 候选层要不要团队可见待所有者决定。在那之前照模型：按人挂，只本人可见（管理员也看不到候选的根据）。

## 要做的

1. 写法：工作流包怎样声明“这一项的产出进候选层”（分类、归位提议、声明、关系四种），提交怎样带上它们。
   - 照 W07 R[4]：候选内容不进提交记录和运行记录，两者只存条数和摘要。
   - 每条候选都带引文和引用。来源和依据等级由 Hub 按来源定，不收模型自报的等级。
2. 核验，全是确定性规则，不调用任何模型：
   - 引文逐字出自所引源文件（和边界同一个比对规则）；
   - 提议的节点路径在所依据的根里能解析；
   - 不越过声明：提议只说放在哪，不改片段的来源类型，不给片段加它原文没有的适用条件；
   - 关系提议（例如两个片段说的是同一件事，或者互相矛盾）只记关系和双方引用，不改任何一方。
   
   核验不过的不入层，回执里给出修正说明。
3. 入层：写成 `knowledge-candidate@1`，绑节点路径、被引片段摘要和所依据的根；读者锁定的根里同一路径的片段变了，就显示“被引片段已变（根 X → Y）”（K03 已写的规则）。只本人可见。
4. 按任务的产出（排序、取舍、分数）只进运行记录，测试钉住它们不出现在候选层。
5. 测试：合成包和合成源文件，四种按文档产出各有正例和反例；引文不逐字、路径解析不出、越过声明、他人读不到、根变了显示已变，都要覆盖。

完成后在终端里回报：提交号、测试数量、没做完或拿不准的地方。另一家族的终端会复核这一件。
