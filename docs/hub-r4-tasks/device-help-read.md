# 设计与最小实现：写手问设备“这个位置该写什么”（device help）

状态：2026-11-12，分支 `it-device-help`（从 `f5849a42f3` 开出）完成本地收口，等待集成。七件事里的第 4 件。网关在本仓库之外，这里不改它，只写它要加什么（第 7 节）。

## 1. 要办的事

真实运行里，写手猜了设备不认的参数写法，到上机才被拒：设备只在出错的词下面回一个插入符，没有字。参考引擎给它的写手一个只读工具 `dev_help`：取设备能解析的最长前缀，后面加一个问号，**不按回车**，读设备自己对这个位置的说明，把输入行清掉，什么也不执行。

这里的目标一样：派发之前，写手可以只读地问设备“这一行写到这里，设备下一处要什么”。Hub 只把设备的原话原样存下来、原样交回，不判断。

## 2. 先说结论

- **可行，不改模型，不加错误码，不加 MCP 工具。** 对照见第 4 节。
- **放在 test-bed 包的一个动作 `help`**，由预订谱系持有的租约之下发起（`start_run`，predecessor 写预订那次运行）。包的投影只声明“问哪台设备的哪一行”，Hub 按部署数据去问，和决定 112 里“预订后看一次版本”是同一类事。
- **问的那一行发出前**要过四道结构核对（词法、没有控制字符、执行器声明的形状、只发整词的前缀），再加两个前提：谱系持有这台设备的租约，目标这一版的“只读”已有认证。核对里没有任何词表。
- **网关还没有这个工具**，所以眼下真实环境问不了：没有认证，Hub 一个字也不会往设备发（第 7 节写明网关要加的工具和它必须守的安全）。合成测试证明的是 Hub 这一半。
- 不要的部分：参考引擎在上机失败后自动附一份设备说明给归因，这次不做（第 14 节）。

## 4. 这个读放在哪里：对照设计

设计里写和读设备是分开的：Hub 只在预订时、派发前后，按执行器定义里固定的命令读设备；模型写的东西只经核验、派发的那条路到设备。问位置在两处扩展了它：读由写手的请求发起，不是 Hub 自己的时机；读带着写手选的一行文字去设备。第二处是风险所在，所以第 6 节的核对和 `premises.read_only` 是这件事的核心，不是点缀。

先排除的放法：

| 放法 | 判断 |
|---|---|
| 新增 MCP 工具 | 不行。D06 的六个工具不动；F[6] 里“现场观察”的工具和名字所有者仍暂缓；决定 138：不增加模型读取通道 |
| case-compile 的动作 | 不行。编译运行的输入在开始时冻结，它也不声明租约上下文，读设备混进计划运行会让“冻结”含义含糊 |
| 管理员命令 | 写手问不了。留给集成者在真实网关上只读核验时用（第 14 节） |
| **test-bed 的一个动作，在预订谱系的租约之下** | **采用。** 租约按血缘持有（D04 R[0]），只有持有者碰得到这台设备；test-bed 已经是 Hub 看设备的地方（预订后看一次版本）；动作由包声明、Hub 按部署数据执行，核心里没有产品词（C02）；结果是运行里的观察主张（B01） |

对照模型，逐条看这个放法有没有越界：

- **D06 F[0]-F[5]、R[6]**：工具面不变，走 `start_run`。F[6] 的“现场观察”不是在这里被决定：这里没有新工具，只是 `start_run` 的一个包动作，和 `observe` 同类。
- **D07 R[8]**：只读核对和逐台探测“只在执行器定义里声明一次”，在派发所用的同一租约里发。这里在**同一个**执行器定义里再声明一种读（`probes.help`），用逐台版本探测的同一个座位。不同之处：问发生在编写期，那时还没有派发的网关租约，所以像“预订后看一次版本”一样，在一个短网关租约里读，期间谱系的 Hub 租约不动。
- **D07 R[1]**：原始观察先存成源文件再解释：传输层的保存回调先存应答原样，再读指针。
- **D02 R[0]、R[1]、R[4]、D03 R[6]**：“只读由传输层强制”默认为假，置真要目标 + 目标版本上的认证；未认证的读外部系统按写处理。问位置把一行写手的字打进真终端，只有目标自己保证不按回车才是读。所以新增 `premises.read_only`（证据的格式同其他前提），**没有认证就不连租约、不发一个字**——不走“按写处理”那条路，因为按写处理要过效果边界的九款，而这里根本不该写。
- **D02 R[5]、D04 R[8]**：同期观察加“未排除本地操作”：每条观察主张都带。
- **D03 R[0]**：读失败有界重读：可重读的失败自动读三次（沿用 `read_retry_when`），明确拒绝立即停。
- **D05 R[1]、R[8]、A06**：没问成不是错误，是带缺什么和下一步的未知；下一步交给谁写明（缺认证是管理员的事，改写那一行是写手的事）。
- **D05 R[7]**：错误原因不以终端画面的关键词推：Hub 不看画面，网关回结构字段。
- **A01 R[0]、A05 R[3]**：观察 = Hub 在边界亲手读取并保存的内容，目标自己计算的部分加“目标自报”；只对那一刻成立：每条带采集时刻。
- **A03 R[0]、R[6]、C07 R[8]**：判据只取期望来源；线索只用于排序和提示；不读帮助散文推类型。设备的话不属于任何来源角色，不进运行的 `sources`，没有任何检查读它。
- **D07 R[12]**：派发安全不靠拒绝词表或删引号后的文字匹配：问的那一行靠声明的形状和词法，没有拒绝词表。

结论：不需要改模型，不需要新的协议码（沿用 `LEASE_UNAVAILABLE`、`LEASE_PREFIX`、`LEASE_EXPIRED`；包自己的两个码 `test-bed.bad_help`、`test-bed.help_mismatch` 写在包的码表里）。可选的模型补句见第 13 节。

## 5. Hub 怎么保持中立

Hub 说的话只有：问的是哪台设备哪一行的哪些前缀；设备在哪个前缀回了说明，那个前缀后面的词是什么；设备的原话和观察时刻；没问成时缺什么、下一步。

Hub 不做的：不判断这条命令对不对；不说“这个词为什么不对”（参考引擎那句评判不移植）；不改写、不排序、不摘要设备的话；不拿设备的话和任何清单比；不用它做类型推断；不让它成为任何检查或期望值的依据。

设备的话在运行里是主张的数据（`device_help`），不是源：性质“事实”指“设备当时这样回答”，不指“命令这样合法”；限定“目标自报”“未排除本地操作”；回答里的块标题和技能文字都写明它不是命令树、不是手册、不能当期望值的依据。设备输出只作参考，不能作为原始用例的期望依据。设备的话一行一行原样列出；终端控制字符只在答案里写成 `\xNN`，运行记录里仍是原样。预订编号保留在参数和机器可读字段中，不放在问设备的结论正文。

## 6. 问的那一行发出前怎么核对

都只看结构，没有一个词和词表比较（`hub/dispatch/help.ts` 的 `checkLine`）：

1. **一行完整的词**：共用词法 `commandTokens`——引号配对、闭合引号后不紧跟字符、没有回车换行和空字符、至多 2000 个字符 320 个词。
2. **没有任何控制字符**（制表、转义也不行）。参考引擎没有这一道：引号里的换行会被当成回车发出去。
3. **执行器声明的形状** `line_pattern`（以 `^` 开头、`$` 结尾）：发给设备的**每一段文字**，整行和每个前缀，都要符合。这是“允许什么”，不是“禁止什么”。形状里要不要放问号、分号由部署定。
4. **只发整词的前缀，Hub 自己一个字也不加**：问号由目标补，Hub 发的文字里不会有问号。
5. **级别**：执行器声明了级别集合（`modes`）就必须从里面选，没声明就不能带。
6. **租约**：包的投影只在冻结的租约视图里把这台设备标为“我的”才出 `ask`；引擎再按租约表核一遍键（同一用户、谱系里的运行持有、没释放、没过期、在声明的前缀下）；执行器的资源里要有这些键；设备上没有未结束的作业。
7. **认证**：`premises.read_only` 对目标这一版有效（版本相符、证据能读且摘要对）。

**锁定命令树的前缀这次没有做。** 原因：test-bed 不绑产品线，运行里没有锁定的树；设备说明恰恰是树答不了的地方（参数取值范围、因级别而异的写法）；命令是否存在以命令树为准（参考引擎 2026-08-03 的裁定就是这样），写手一侧的 case-compile 已经按锁定树解析每条命令。以后若有产品绑定的宿主，可以加一道“这一行以锁定树的一条路径开头”，并用该路径的访问级别定 `mode`（第 14 节）。

## 7. 网关要加的工具

网关在本仓库之外，不改、不部署。建议并列于 `probe_show` 加 `probe_help`（工具的真名由部署的定义决定；本仓库的合成测试里叫 `ask_position`）。

- **参数**：本次网关租约的身份（同 `probe_show`）；座位序号（同 `probe_show`）；`line`（必填，要问的文字，不含问号）；`mode`（可选，工具的参数模式里列出它认的级别，缺省不换级别）。
- **应答**（结构化内容）：`line`（原样回显）；`help`（设备对这个位置的说明，去掉回显的那一行和提示符行；设备什么也没说是空串）；`caret_only`（设备是否只在行下回了一个插入符）；`entered`（必须是 `false`）；`cleared`（必须是 `true`）；`raw`（等待期间收到的全部字节，不加工，给原件存档）。拒绝走工具错误，同其他碰设备的工具带阶段和 `reached_device`。
- **安全，也就是要认证的东西**：
  1. 碰设备以前先核 `line`：一行，没有回车、换行、空字符和任何控制字符，不含帮助键，不超长；`mode` 在网关自己的列表里；租约确实是调用者的。
  2. 进入 `mode`、回到原来的级别，用网关自己固定的命令，**绝不取自 `line`**。
  3. 先清一次输入行，再打“`line` + 空格 + 帮助键”，**整个发送路径里没有任何行结束符的写入**——靠构造保证，不靠检查。
  4. 设备静默一小段时间或到上限就停止读。
  5. **无论成败、超时或异常**（`finally`），都发整行删除键，并核对输入行已空（提示符重绘、没有残留），再回到原来的级别。
  6. `entered=false` 只在确实没有写过行结束符时给；`cleared=true` 只在清行发了、输入行也空时给；否则工具报错，并把这个座位标出来等管理员看。
  7. 权限同 `probe_show`：运行权限的密钥能调；审计记调用者、座位、级别和 `line` 的摘要。
  8. 升一个次版本号（`serverInfo.version`）：Hub 的认证按这个版本。
- **集成者认证它时要有的证据**（登记成 `premises.read_only` 的 `src:`）：网关这一版的代码审读和测试——假终端断言在 `line` 的第一个字节之后到整行删除键之前没有 0x0A、0x0D 被写出；在真实环境上一次只读取样，前后床面基线逐字节相同。真实环境的动作由集成者做。

## 8. 一次问的过程

1. 写手已经预订了设备（test-bed `acquire`，得预订运行号 B）。
2. 写手 `start_run`：`pack` test-bed，`inputs.inventory` 同预订，`predecessor` 写 B，`parameters` 写 `{action: "help", booking: B, device: <设备名>, line: <要问的一行>}`，设备分级时加 `mode`。
3. 包的投影在冻结的租约视图里核这台设备的键是“我的”，输出 `ask`；检查按冻结内容重算一遍。
4. 引擎（`askClaims`）核键：在 `bed/` 前缀下、同一用户、谱系里的运行持有、没释放没过期；不合就拒（`LEASE_UNAVAILABLE`、`LEASE_PREFIX`、`LEASE_EXPIRED`），什么也不问。
5. `DispatchService.askDevices`：找到绑定同一份清单、座位指向这台设备、声明了 `probes.help` 的执行器 → 过第 6 节的发出前核对 → 同一执行器的问一个接一个排队（同一谱系的几个写手同时问，网关租约只有一个）→ 连接、核认证 → 取一个短网关租约（心跳照常）→ 从整行起逐个前缀问，设备回了说明的最长前缀就停 → 释放租约。
6. 每个应答先原样存（只许函数读），再读指针；说明另存一份运行者和管理员能读的文本原件，凭据扫描扣住的不引用；日志里记问的前缀和两个引用。
7. 引擎把结果写成主张放进运行，回答里列出。

## 9. 声明：执行器定义多出来的两处

```json
{
  "probes": {
    "（逐台版本探测的声明不变）": "…",
    "help": {
      "line_pattern": "^[A-Za-z0-9 ._:/\"'-]{1,500}$",
      "modes": ["level-a", "level-b"],
      "call": {
        "tool": "ask_position",
        "arguments": {
          "seat": {"$value": "seat_index"},
          "line": {"$value": "line"},
          "level": {"$value": "mode"},
          "ticket": {"$value": "lease_id"}
        }
      },
      "text": "/help", "caret_only": "/caret", "entered": "/entered", "cleared": "/cleared",
      "max_positions": 12
    }
  },
  "premises": { "read_only": { "version": "<目标 initialize 回答里的版本>", "evidence": ["src:<证据摘要>"] } }
}
```

登记时核的：`line_pattern` 以 `^` 开头 `$` 结尾；调用各绑定一次 `line`、`seat_index`、`lease_id`；只有声明了 `modes` 才绑定 `mode`，且恰好一次；工具必须在允许清单里，不能是逐台版本探测的工具或提交工具，不能带工作内容字节；`entered`、`cleared`、`text` 必填。已登记的旧定义不受影响。给已登记的执行器加 `probes.help` 是一次执行器更新：更新前开始的核验运行要按现有规则重新核验。

## 10. 记录、可见性、主张

- **应答原件**：每次网关调用的应答原样存，只许函数读（管理员能在控制台看）。
- **文本原件**：设备说明另存，运行者和管理员能读，模型可读；凭据扫描扣住的不引用。
- **日志**：每个位置一条 `device_help`（问的前缀、是否有说明、是否只有插入符、两个引用）；失败和不确认安全的写管理员日志。
- **运行的 `device_help`**（`RunSummary` 新增的可选字段）：每行一条概述；每个被问位置一条观察（设备原话在 `data.help`，最多留前 16000 个字符并标明截断，全文在文本原件）；没问成或中途停下的是带缺什么和下一步的未知。观察都带限定“目标自报”“未排除本地操作”和采集时刻，前提写“目标这一版的问位置工具只读（已认证）”。
- 运行记录和回答只在运行者和管理员之间可读。设备的话不是运行的来源，也不是任何检查的输入。

## 11. 和参考引擎的差别，为什么

1. **级别**：参考引擎按首词是不是一串只读命令词决定要不要进配置级——这是词表匹配。这里由写手从执行器声明的封闭集里选，进出级别是网关的事。
2. **说明的抽取**：参考引擎在客户端用正则读终端画面。这里目标回结构字段，Hub 按指针读（D05 R[7]）。
3. **评判句**：参考引擎写“你写的词不满足这个期望”。这里不写：那是判断，Hub 只核验。
4. **次数**：参考引擎的 `dev_help` 没有次数预算（`dev_probe` 有 5 次）。这里一次最多问 `max_positions` 个位置，问几次不限，每次是一个运行。
5. **安全**：参考引擎直接登录设备，凭据在本机环境变量，也不检查引号里的换行。这里只经执行器和网关，凭据在保险库，控制字符一律拒，只读先要认证。
6. **应答不确认安全**：参考引擎发清行键就算数。这里要求应答自己说“没按回车、行已清”，否则不呈现内容、不再往下问。
7. **收据**：参考引擎的 `dev_help` 不留收据。这里每个应答存原件，存不下来就不呈现。
8. **错误的处理**：可重读的失败自动读三次再停（D03 R[0]），参考引擎一次失败就返回“查询失败”。
9. **排队**：同一执行器的问一个接一个，参考引擎各开各的会话。网关租约只有一个，并发的写手会撞上。
