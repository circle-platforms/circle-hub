# 已存结果的根据清单按摘要保留（issue #200）

来源：issue #200（登录后总览及任务详情超时）；所有者 2026-11-10“按照这个思路处理所有issue和PR”和 2026-11-11 的目标“用合成数据确认功能和性能都能正常流程使用”；基线 `origin/main` 42b192b7，分支 `perf/result-grounds-memo`。

## 允许路径

- `hub/records/{store.ts,api.ts}`
- `hub/runs/engine/{grounds.ts,grounds-memo.test.ts}`
- `CHANGELOG.md`、本任务页、`docs/hub-r4-tasks/backlog-status.md`

## 现象和原因

控制台重排之后，用合成数据把数据量加到 #200 记录的生产规模附近（126 个任务、13 个账户、约 410 条知识）再量：

- 总览 2.9 秒，任务列表 0.72 秒；和重排之前的代码（`43868676`）在同样数据上的 2.8 秒、0.68 秒基本一样。也就是说重排没有让这两页变慢，也没有让它们变快。任务详情是变快了的：普通任务 134 毫秒降到 48 毫秒，56 次提交的任务 1.4 秒、8.8 MB 降到 0.38 秒、13 KB。
- 对总览做 CPU 采样：45% 的时间在引擎的 `groundsReadableBy` 里。读者不是任务的发起人时，引擎要判断他能不能读结果里引用的每一条根据；为了知道结果引用了哪些根据，每次都把整份结果用模式完整解析一遍，再深度遍历两遍。126 个任务就是每次打开总览做 126 遍。
- “结果引用了哪些根据”只取决于结果的内容。结果是不可变的记录，存储层每次读出时都校验过正文和摘要一致（不一致就抛完整性错误），所以摘要就代表这份内容。

## 决定

- 存储层在记录通过校验的地方记下“这个正文对象对应哪个摘要”（弱引用表，随对象回收），并提供 `verifiedBodyDigest(body)`。只有存储层读出并校验过的那个对象查得到；它的拷贝、调用方自己拼的对象、`put` 时交进来的对象都查不到。
- 引擎把“一份已存结果的根据清单”按摘要保留（最多 2,048 份，最久没用的先丢）：`groundsOf` 对单个已校验正文按摘要保留；`resultGrounds` 还取决于运行绑定的来源，按“摘要 + 运行编号”保留。保留的只是这份清单。
- **读者能不能读每一条根据，仍然每次调用都重新判断。** 分享、撤回、成员停用之后的下一次读取结果照旧立刻变化。
- 传入的是一组值（数组）时不保留，按原来的算法整体遍历，返回的顺序和原来一样。
- 查不到摘要的值按原来的算法现算。所以行为只在“同一条已存记录第二次被问到”时不同，而那时的答案和第一次现算的一样。

## 结果（本机，合成数据，一个进程）

| 页面（126 个任务） | 重排之前 | main | 加上这项 |
| --- | --- | --- | --- |
| 总览 | 2.77 秒 | 2.89 秒 | 1.60 秒 |
| 任务列表 | 0.68 秒 | 0.72 秒 | 0.38 秒 |
| 等待回应中的请求 | 0.68 秒 | 0.69 秒 | 0.37 秒 |

加上这项之后再采样，总览剩下的时间里最大的一块是记录层逐条校验读到的记录（约四成）。那是“读到的每条记录都校验”的设计；要再降，需要给每个任务存一份小的摘要记录，列表和总览不再读整份结果。这是 #200 里记着的“摘要的持久化投影”，要新增记录种类，属于模型改动，这里没有做。

## 验收

- `hub/runs/engine/grounds-memo.test.ts`（新）：
  - 存储层读出的正文查得到它的摘要；拷贝、展开出来的新对象、`put` 时交进来的对象、非对象的值都查不到。
  - 同一条记录读两次得到两个对象：第一次解析一遍，第二次不再解析；得到的清单和对拷贝现算的清单内容、顺序都相同；调用方改动拿到的清单不影响下一次；另一条记录另算；一组值照旧整体遍历、不保留；清空之后重新解析。
  - 读者能不能读根据每次都问：同一份结果连问两次，第二次不解析，但照样去问知识空间；把空间的回答改成不可读，结果立刻变成不可读；换一个运行编号时只重算和运行绑定的那一步。
- `hub/runs/engine/grounds.test.ts`、`grounds-boundary.test.ts` 和引擎里读取权限相关的测试照旧通过。
- 完整单元测试和完整验收测试。

## 不做

- 不缓存任何“能不能读”的结论，不缓存记录的校验结果。
- 不改请求的读取方式：总览和任务列表每次仍要读出全部请求及其了结记录才知道哪些还在等待，这部分耗时随历史增长。
