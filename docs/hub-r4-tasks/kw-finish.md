## 要做到的（验收标准）

1. **上传文件署名**（改写决定 62 中“上传不作团队根据”）：
   - 上传的文件进个人空间，按本人授权可见。
   - 引用它的知识分享到团队时，由上传人署名，来源类型记为“声明”，团队知识上显示署名人。
   - 没有署名的仍拒收（第三阶段的拒收码改为提示“需上传人署名”）。
2. **原文归档**：
   - 控制台上标着“规划中”的原文归档改为可用：原文（网页快照、文件、业务系统读取结果、会话摘录）按内容哈希存档，按空间与授权可见。
   - 条目详情能打开所引原文，定位到引文。
3. **成员停用与删除**：
   - 停用：个人空间冻结，授权暂停；恢复后照常。
   - 删除：清除 Hub 上该成员个人空间的内容，记录只留内容哈希。复用第四阶段的可清除存储与清除流程，与切回“仅保存在本机”走同一条路径，不另写一套。
   - 分享到团队的知识与记忆属于团队，保留不动；分享人显示为“已删除的成员”。其中依赖已清除个人来源的部分变为待验证，管理员可见。
   - 删除前在控制台提示影响范围，并由管理员确认（沿用决定 75 的命令与记录）。
4. **容量**：
   - 每个成员在 Hub 上的个人空间默认 1 GiB，管理员可在团队页调整。
   - 超出时拒收新的写入与同步，提示还剩多少、该怎么做。
   - 第二阶段已做的部分只补管理员的调整入口与提示。
5. **界面与文档**：控制台各处的“规划中”标记与实际一致；`docs/design/knowledge-workflows.md` 末尾补“实施状态”一节，逐项写明完成情况与对应决定。
6. **测试**：
   - 署名与拒收、原文打开与定位、停用与恢复、删除后的清除与团队条目保留、容量超限与调整。
   - 改动波及的验收场景。

### 3. 上传署名：团队声明与运行内声明分开

- 保留原件内容寻址与私有归属：导入进入上传者的空间，默认仅本人，读取随文件夹分享权限重查；同内容的另一份采集不会因摘要相同而取得署名、名称或权限。
- 拟增加上传者明确确认的团队来源声明：在原文 Inspector 提供“署名为团队来源…”及确认 Dialog，确认者必须是该精确采集由 Hub 观察到的上传账号。记录绑定采集、原文字节摘要、署名人、时间及团队使用范围；不采信文件作者字段、客户端自报姓名或别人的同字节上传。署名是对指定来源供团队使用的声明，不是内容已被观察证实。
- 分享预检缺署名时保留 `SHARE_UPLOAD_UNSIGNED` 的拒收语义，把下一步改为“需上传人署名”，给可读原文入口。确认分享重新检查上传者、精确采集、声明、当前权限、引文、凭据、读取档位及全部既有团队规则，预检本身不署名、不写团队内容。非本人上传不得由分享人或管理员代签。
- 团队副本记录可核对的署名关联，来源类型通过生成词表显示“声明”，团队条目上显示署名人。只为明确获准的原件建立团队来源关联/持有，不全局放宽私人原件 ACL；署名与分享到团队是两个可审计事实。事务失败不留下半份团队条目或来源关联。
- 不开放个人凭据来源、不可读取来源、被扫描阻止的原文或私人解析器绕行；引文仍按原字节/既有解析结果逐字验证，不把署名当作扫描或验证的豁免。旧源记录、旧回执及运行冻结绑定不改写。
- 第三阶段的 `SourceBinding.upload_declaration` 仍只表示“上传者将本人普通上传的精确采集绑定为这一次运行的输入”，只借给该运行的实际读者，不改变全局 ACL，也不自动取得团队来源署名。管理员以本人普通上传作团队导入的现有声明保留。两者在记录和 UI 中区分；新增团队声明不能借运行内声明跨场景升级。

验证：本人署名、无署名拒收、他人/管理员代签拒绝、同字节不同采集不串权、旧原件不变；团队预检不写入、确认重查、失败回滚和重复提交；个人凭据/凭据命中/读取档位/引文不符仍拒收；运行内声明的权限范围保持原样。

### 4. 原文归档：复用采集与权限，不另建抓取器

- 复用 records 的内容寻址原件与 knowledge 的空间来源登记，补齐按全部/我的/与我共享/团队及文件夹浏览的原文入口、分页与选择详情；不按全库摘要列举，不泄露不可读名称、计数、会话或署名。
- 拟使用知识区的原文列表/详情路由，参数只选择已授权来源。名称、来源类型、采集/上传人、时间、大小留在列表或 Inspector；技术摘要、采集记录和引用放在明确的“查看”入口。行不放按钮，打开、署名等动作放在选中来源的详情底部。
- 文件、网页快照、业务系统读取结果、会话摘录均以实际采集的原字节及来源元数据归档，不因归档重新获取网络内容、执行 HTML/脚本或生成摘要。复用现有上传/连接器读取/会话摘录边界，不增加任意 URL 抓取或业务写入。只对本阶段确实可走通的入口解除“规划中”，不把容器或声明存在当成已归档。
- 条目 SourceBlock 的“打开原文”带上精确采集和引文定位信息；服务器重查读权、完整性和逐字匹配后定位，长文用有界分页/片段，二进制沿用解析能力和只读下载。原文转义显示，不把 HTML 快照直接当可执行页面。无法解析或无法定位时据实说明，不猜位置，不抬高验证状态。
- 相同字节可复用物理对象，但空间/采集关联、读权和署名分开。普通上传纳入原文空间的兼容处理不得改旧引用或把运行内上传擅自公开；其归属和容量在写前核对，防止同时保留两条可绕过边界的入口。

验证：四类合成来源、完整性、同字节隔离、本人/获分享成员/团队/无权者、旧版本与收回权限；从条目打开并定位引文、错误定位、长文/二进制、脚本内容转义与 CSP；归档不调用模型、不进行外部写入。

### 5. 停用与恢复：冻结而非清除

- 复用现有管理员 `user disable/enable` 命令、账号历史与最后一名启用管理员保护，控制台仍按决定 75 在成员 Inspector 展示 danger 按钮及原有命令确认 Dialog，不新增网页直接执行停用的管理动作。
- 检查知识、原文、记忆、个人工作流/技能和各自分享：停用者不能写入，其他人也不能继续借其私人分享读取或启动新的个人工作流。每次读取/写入重新检查当前账号与所有者；已持有的旧 Principal、旧会话、分页/下载链接不得绕过。并发停用与写入在提交边界重查，返回实际接受或拒绝结果。
- 停用只暂停私人空间和分享，不删除原件、版本或永久撤销原有分享。恢复后按仍有效的记录恢复；恢复不得重新启用已经明确收回的分享。团队已经独立取得的知识、记忆与原件保持团队归属，不因停用上传者而一并隐藏；署名显示原账户状态，不冒充“已删除”。
- 同步 HTTP 的停用/恢复覆盖等其合入后补，不改只读分支，也不通过自建同步接口提前验证。冻结不声称已经停止远程 Circle 或清除了本机数据。

验证：持有旧会话/令牌/主体的读写、本人和被分享方的知识/原文/记忆/个人包入口、停用中写入、恢复和已撤销分享、团队副本保留、管理员边界及最后一名管理员保护。

### 6. 容量：补现有入口与真实剩余量

- 复用默认每人 1 GiB、`spaces.capacity/setCapacity` 及团队成员 Inspector 的管理员表单；不另建配额存储。展示上限、已用、剩余量及实际计费说明；普通成员不能调整他人配额，管理员只能看批准的元数据，不借计量读取私人标题/正文。
- 写前预查与事务提交使用同一口径：保留现有条目、原文、空间版本和记忆历史的计费约束，单次上传上限、索引上限和记忆启用额度各自保留。超限整次拒收，不截断、不留下可读半份原件；提高上限后可按原规则重试。
- 降到已用以下或设为 0 不删除既有数据，显示已超额度/剩余 0，拒收新增占用；旧数据仍按权限可读。提示给出实际已用、上限、剩余和本次所需，不能错误建议“撤回就释放历史容量”。可操作的下一步是联系管理员调整上限；需清除 Hub 副本的入口等同步落地后才接入。
- 与同步合入后的统一空间计量对接，复核暂存、冲突头、知识/记忆/包清单和重复批次的计量与回滚，不另外维护一个同步计数器。本块不擅自重定义个人工作流可执行文件与同步清单的容量口径；若现有合约未覆盖，先列出差异交 Claude 确认，再改模型/计费，不静默排除或重复计量。
- 第二块的回归已发现并修复首次在根目录保存原文被误当作空空间初始化的问题；本块另查旧版本 `used_bytes` 可能因此少计的历史状态与重建办法，不改写旧记录。

验证：默认额度、管理员调整、非管理员拒绝、负数/溢出、0 和低于已用、刚好达到/超过、并发写入与调整、失败回滚、重复提交及提示不泄露他人数据；同步到位后补同步写入同口径和失败不残留。

### 7. 同步合入后才做成员删除

- 等 Claude 确认同步合入并安排本分支变基，先复查其最终公开端口、合约、迁移和安全回归，重新生成合约；不手工拼接生成物或复制未完成的清除实现。
- 通过同一可清除存储及 purge 流程清理该成员在 Hub 的私人知识、文件夹、引文、原件、记忆与相关派生索引/暂存；范围与同步的“仅保存在本机”清除一致。个人包的正文/安装产物若不在同步 purge 范围内，先交 Claude 明确归属和接口，不能漏清或另写清除器。
- Claude 批准第一块合约时明确：`knowledge_source_attribution` 属于上传者个人空间；变基到同步后，把它纳入同一个个人空间 purge 范围。第一块只追加声明，不提前实现清除；团队持有副本的保留及缺失私人来源的状态在本块统一核对。
- 删除保留身份墓碑及必要的摘要审计，旧主体、令牌、会话和客户端不能复活旧代次；已删除账户不能恢复为普通停用账户。新成员即使同名也不能继承旧空间。禁止删除最后一名有效管理员，防止自删在途操作绕过权限检查。
- 团队知识、团队记忆和团队独立持有的原件保留；显示“已删除的成员”。仍依赖被清除私人来源的部分，复用同步的来源失效投影显示待验证及管理员可读的缺口，不改原始团队回执、默默通过或冒充验证失败。同字节的其他合法持有者不受损坏。
- 先只读预检影响范围，再由管理员在成员详情的确认 Dialog 核对，以决定 75 的管理员命令及追加记录执行；确认时重查权限、范围和代次。清除失败/中断须返回真实进度，可安全重试/恢复，不能先报删除完成。并发上传、同步、分享及署名须受同一账户/代次边界约束。

#### A. 记录与最小形状

1. 在模型的 `formatProposals.recordKinds` 注册 `knowledge_source_attribution`，注册 `knowledge-source-attribution@1` 的严格 Schema。正文拟为：

   ```ts
   {
     space: UserId,       // The uploader's personal space
     source: Sha256,      // Exact knowledge_space_source record
     artifact: Sha256,    // Exact source_artifact capture, not just equal bytes
     sha256: Sha256,      // Original immutable bytes
     by: UserId,          // Observed authenticated uploader
     at: IsoTime,
     audience: 'team'
   }
   ```

   记录 provenance 为现有的 `declared`。结构要求 `space === by`；服务端另外核对来源登记、采集、摘要、观察到的上传人、当前身份、当前读权和扫描/读取档位。浏览器不能指定署名人、时间或以文件作者替代上传人。已有同范围精确署名重复确认时返回原记录，不追加不同时间的重复声明；预检不写记录。索引只用于定位候选，不替代上述正文验证。
2. `SpaceSourceBody` 增加可选 `attribution: Sha256`：只由服务器在团队来源关联中填写，指向本次所依据的署名。原有团队读取来源及旧记录可不带该字段。新团队上传来源必须有可验证的关联；不能把上传记录本身当作署名。
3. `SpaceEntryBody` 增加可选 `source_attributions: Sha256[]`（去重、有界，至多 100 项）：团队分享成功时记录实际使用的署名集合，用于来源与署名人显示及回溯，不由个人条目输入传入。每项必须能对应本次核对过的精确上传采集与团队来源关联；超限整体拒绝，不截断成功。旧记录缺字段视为“未记录团队署名”，不能反推已署名。
4. 声明记录不保存原文、文件夹路径、引文或客户端自报作者。私人原件与旧记录不改写。仅成功分享到团队的原文才建立可供团队读取的明确来源关联，作为团队声明来源提供；原件仍在本人空间，未使用该来源的其他私人记录保持原读权。同字节原件、另一上传者或后来的新采集不继承此声明。实现将复用既有原件/来源关联端口；本块不新增可清除存储或预设删除时的个人工作流归属。

`share_entry`、个人条目写入的公开入参和六个 MCP 工具的数量不变，不增加 MCP 署名模式。署名确认先通过控制台的本人动作进入 knowledge 服务；现有 `upload_file.share_entry` 在确认分享时同样重查声明，不能绕过。新的 record Schema 及其分类/读取限制进入合约注册；私人署名记录只经本人端口读取，团队页面只展示已随成功分享公开的署名事实，不开放原私人来源登记或任意 `rec:` 旁路。
