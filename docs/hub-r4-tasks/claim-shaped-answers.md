# 任务：Hub 自己的回答也按主张给出

依据：决定 111（所有者，2026-11-01，"按照这个思路修改 重复我的对话回放，并检查结果"）；通用模型 B01、D05、A05 R[1]、A05 R[3]、A06、V08；ADR 0024 和《判断与披露原则》；设计文档理论分页的三条定律。

10-31 所有者亲测时，模型被 Hub 自己的回答带偏了，原因有三：

- 候选清单丢了限定：构建候选只列了前 20 个，全是同一条旧版本线的，没有说一共多少个、其余在哪里。模型据此断定新版本线没有知识根，其实新版本线有带自己知识根的构建，只是没列进前 20 个。
- 下一步没有根据："先升级""或把某台升级到该构建"，可平台不能升级。
- 原因没定时只给了一个原因：缺陷没有修复说明，就说"请集成者配置字段"，可缺陷的状态是 active，还没修复。

不另立原则，只把错误和修正放进 B01 的结构里。

  - `hub/server/text.ts`、`hub/server/claims.ts` 里印错误的部分；
  - `hub/runs/engine/target.ts`、`hub/runs/engine/projection.ts`、`hub/runs/engine/start.ts`，`hub/leases/service.ts` 的占用拒绝；
  - `hub/knowledge/views.ts` 里"同步这条产品线"那句的执行者；
  - `packs/workflow/test-bed/**`（升 1.2.12）、`packs/workflow/defect-to-case/**`（升 1.6.24）；

## 要做的

1. **错误也是主张**：ProtocolError 和 PackError 可以带根据（引用）、规则@版本、限定（声明、观察或投影，采集时刻，所查范围和覆盖），回答按固定格式印成文字。
2. **候选清单带覆盖**：写明共几个、列出几个、其余在哪里；源头不再静默截断，文字里也不再丢掉总数。构建候选按版本线从新到旧，先列有自己知识根的构建。
3. **下一步要有根据**：修正写明由谁、用哪项现有能力去做；没有能做的，不写这一步，改写缺的事实。test-bed 去掉"升级"两处；"同步这条产品线"写明由管理员做；占用拒绝写出持有运行和取得时刻，是调用者自己的运行时说明。
4. **原因没定时给假设集**：错误可以带几个假设，每个带支持和反驳，固定再留一个"其他"。假设状态按 V08 R[0] 算：只有规则给出的预测被观察反驳，才记已排除。defect-to-case 的"没有修复说明"按这个改：一个假设是缺陷还没修复（看状态和解决字段），一个是修复说明在没配置读取的字段里。
5. **不在这一件里做**：case-compile（执行器授权还在 @3.9.5）；在装构建的观察值进 test-bed 的搜索（要从派发记录取观察，另开一件）；按命令找用例、按经办人列缺陷两种读法。

## 第二轮（重放之后）

第一轮上线后在 Circle 里重放所有者的四句话，模型走了别的路，碰到三处同一类的问题，分支 `claim-shaped-answers-2`：

1. **视图截断的拒绝**：只说"请按视图说明处理来源或凭据"，说明却没带上；修正一律是"用 only= 收窄"，可只因条目取值未知而截断时，收窄去不掉它们（模型照做了五次）。改成写明是哪种截断，带上视图页引用、覆盖和视图自己的说明（作为缺的事实），修正按原因给；体积超限才建议收窄，分页和结构问题写明要管理员修，续读变化写重新绑定。可以改：`hub/knowledge/complete-view.ts`、`hub/ports.ts` 的读取错误类型、`hub/runs/engine/inputs.ts` 把这些字段带进回答。
2. **锁定的根和默认选构建**：运行写某个构建，锁的却可能是版本线的树苗根，或别的构建产出的根，回答没说；默认规则只在已发布的构建里选，回答也没说候选范围。改成在构建那条依据里写明锁的是树苗根还是同步根、根产自哪个构建、这个构建另有的同步根，以及从多少个可以锁定的构建里选、其中已发布的多少个、未发布的不参加。可以改：`hub/runs/engine/target.ts`。
3. **test-bed 1.2.13**：清单声明的在装构建和要的构建不同时，原来说"在装构建不是该版本线"，可它们常在同一条版本线上；改成"清单声明的在装构建是别的构建"。
