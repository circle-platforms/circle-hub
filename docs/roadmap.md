# 平台方向与路线图

本页说明 Circle 平台（[circle](https://github.com/circle-platforms/circle)、circle-hub、[circle-packs](https://github.com/circle-platforms/circle-packs)）要解决什么问题、现在做到哪一步、接下来按什么顺序做。"现在"一栏以代码、[README](../README.zh-CN.md) 和[更新日志](../CHANGELOG.md)为准；"计划"一栏是方向和顺序，不是带日期的承诺。具体工作在三个仓库的 Issues 里跟踪。

## 要解决的问题

每家公司都有自己的系统：缺陷管理、代码库、知识库、OA、测试环境和设备。把 agent 接到这些系统上并不难，MCP 和各类连接器已经很多。难的是接上之后：

- 同一时间有很多人、很多 agent、很多共享资源，谁能动什么？
- 一个动作在执行之前，由谁批准？批准的究竟是哪一份内容？
- 动作执行之后留下了什么，别人能不能核对？
- 结果不确定时，系统会不会假装成功？

在这种环境里，任何一步出错都可能造成严重后果：配置下到了错误的设备，测试床被两个任务同时占用，代码推到了错误的分支，缺陷状态和事实对不上。Circle 平台要做的，是让 agent 在一家公司已有的系统之上协同工作，并且每一步都可以被定义、被批准、被核对。

## 三条原则

1. **确定的事交给程序，不确定的事交给模型。** 意图理解、取舍和撰写由模型完成；凡是有唯一正确答案的检查，由脚本对照有版本的权威来源完成。例如设备命令对照绑定版本的命令树，引文逐字对照原文，字段由脚本抽取。
2. **审批发生在变更时，并且绑定内容。** 审批请求绑定输入修订、目标身份和动作摘要，内容一变，原来的批准就不再适用。申请人不能批准自己的变更，平台本身也不是审批人。运行时不再审批，而是走执行链：权限、绑定、核验、租约、审计。
3. **证据归 hub，未知就说未知。** 工具返回原样保存并给出 evidence id，agent 只拿到指针；脚本事实和模型判断分开标记。结果无法确认时记为未知，不重试写操作来"碰运气"。

## 从哪里来

Circle 平台起源于一个网络设备测试团队的内部自动化系统 InfoTest。团队发现，设备命令、测试用例脚本这类必须逐字符正确的任务，靠一个 skill 解决不了，于是把用例生成做成了"编译"：测试人员写脑图，模型负责重组意图和撰写，程序负责结构和对照命令树的核对。这套做法后来被抽成可以被任何 harness 调用的程序化 skill。再往后，团队把它需要的知识、任务、审批、执行资源和技能分发拆成独立的对象，形成了现在的三个仓库：Circle 是通用 agent，circle-hub 是团队 hub，circle-packs 是领域包。旧平台的设计与调研归档在 [references](../references/README.md)，运行时从不导入。

## 黄金路径：一句话走完一条研发链

平台的目标场景是，一位研发工程师说：

> 我今天分配了哪些 bug 需要复现修复，你来自己搞。

agent 在一个持久任务里依次做完下面九步，每个碰到共享资源或写入记录系统的动作，都先递给人一张绑定了具体内容的审批单。人不再对"能不能用这个工具"点头，而是对"这台设备、这段配置差异、这个分支"点头。

| 步骤 | 涉及的系统 | 平台用什么防错 | 现在 |
|---|---|---|---|
| 1 找出今天分给我的 bug | 缺陷管理系统 | 按身份计算的工具目录；证据 | 缺陷系统镜像的只读连接器，可按产品、状态、日期检索和读详情 |
| 2 连接并搭建测试环境 | 测试床、环境清单 | 资源租约、防过期令牌 | 环境视图只读；执行流已有租约 |
| 3 下发配置 | 被测设备 | 对照绑定版本核对每条命令；变更集审批；投递前复核 | 已批准的产品模块通过 `module-execute` 执行；投递前由 hub 重核每条设备命令 |
| 4 模拟流量 | 测试仪或流量发生器 | 资源租约；动作摘要审批 | 无 |
| 5 复现与分析 | 代码库、日志、抓包 | 证据；脚本事实与模型判断分开 | Circle 的通用能力（读代码、搜索、LSP、执行命令、子任务） |
| 6 修复 | 代码库 | Circle 的权限模式与审批 | 已有 |
| 7 验证 | Web 管理界面 | 浏览器会话隔离；`%NAME%` 变量与密钥不进提示词 | Circle 的浏览器工具，含录制与回放 |
| 8 提交合并请求 | 代码托管平台 | 变更集审批；修复与 bug、验证的关联 | 只能在 shell 里用 git，推送走 Circle 的审批 |
| 9 回写 bug、记录工时 | 缺陷系统、OA | 审批绑定内容；与同一任务的证据关联 | 无 |

横向能力已经在 hub 里：PostgreSQL 持久任务（输入修订、事件流、游标续读）、资产生命周期、只写凭据保险箱、绑定内容的独立审批、证据、带试跑记录并由他人批准的技能包，以及供任何 harness 接入的 MCP 端点；按范围的角色与变更集正在完成。这些全部在合成来源和临时 PostgreSQL 上验收。登录目前只有开发登录，所以 hub 还不能用于真实系统的写操作。

## 路线图

按"补上之后整条路径能否第一次走通"排序。前一阶段没完成，后一阶段的写操作不在真实系统上开启。

### 阶段 1：让写操作可以安全地碰真实系统

- 真实身份登录（接入企业已有的身份提供方），取代开发登录。
- 完成[第二阶段简报 r3](server-s2-brief-r3.md)：按范围的角色与两人规则、作为唯一审批概念的变更集、带固定错误码的执行链、通知流与工作队列、执行资源的静态密钥凭据模式。
- 打通网关对真实设备的投递。

### 阶段 2：打通黄金路径

- **缺陷系统**：支持"指派给我"的查询；写操作（评论、解决、转派）作为受审批的动作，绑定内容和证据。
- **测试环境**：测试床从只读视图扩展为可预约、可初始化的执行资源，复用现有租约。
- **配置下发**：除了编译好的工作簿，单条或一组配置也走同样的命令核对、审批和投递前复核。
- **代码托管**：合并请求连接器（如 GitLab、Gitea），并在 hub 里登记"这次修复对应哪个 bug、哪次验证"。
- **流量**：软件流量工具作为受租约管理的执行资源；测试仪厂商提供的 MCP 接口挂在网关后面，平台不自己做测试仪。
- **工时**：OA 工时作为最后一条写入，绑定到同一任务的证据上。
- **复现修复包**：把以上步骤写成一个领域包，写明哪些是模型判断、哪些由脚本核对，和现有的脑图编译包一样走试跑和独立批准。

### 阶段 3：让任何团队都能接自己的系统

- **适配器 SDK**：连接器和技能一样是资产，有版本和 SHA，经试跑、独立批准后才能运行。接入一个新系统，就是装一个包。
- **治理任何 harness**：hub 通过 MCP 向其他 agent 提供"核对、审批、证据"环节。`packages/harness-adapters` 已能把 Claude Code、Codex CLI、OpenCode、Gemini CLI、Cursor 的技能、命令、agent、hook 和 MCP 配置导入中立清单，并再导出。
- **由 D 持有的浏览器**：人和 agent 看同一个获准的浏览器会话，需要时接管（[融合提案](bcde-integration-plan.md) S3）。

### 阶段 4：运维与扩展

- 备份恢复、排空 worker、升级时保留在途工作、新旧版本组合的兼容清单（融合提案 S5）。
- 沿业务路径定位网络问题的方法，按故障逐批扩展（融合提案 S4）。
- 扩展到其他"输出必须逐字正确、动作要碰共享物理资源"的研发场景。

## 不做什么

- 不做通用聊天入口，也不和协同办公套件争员工的入口。
- 不比连接器数量。长尾系统由使用它的团队通过适配器 SDK 自己接入。
- 不做自己的模型；模型可以替换，领域包要在不同模型上都能通过核对。
- 不做测试仪或流量发生器，只把它们作为受治理的资源接入。
- 在真实身份和两人规则上线之前，不在真实系统上开启写操作。
