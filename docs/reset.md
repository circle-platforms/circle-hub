# 重置和重建

> **初稿说明**：本页基于当前设计契约、部署定义模块与控制台界面编写。`circle-hub reset` 命令行参数、具体归档目录命名与真实执行过程输出，将在 Codex 重置实现并入 `hub-final` 后逐条实测校正。

Circle Hub 用**重置和重建**处理不兼容版本更新、配置混乱或需要清空某类数据重来的场景，**不再走旧的在线升级迁移路线**。核心原则是：先校验与归档留底、按选定范围重新建库建基线、**独立保存的 `keys/` 与 `vault/` 不随重置删除**。

---

## 什么时候用

出现以下三类情况时，使用重置和重建：

1. **版本更新后进入「需要重建」状态（`needsRebuild`）**：新版 Hub 启动时检查数据库结构与基线版本，发现与当前运行版本不兼容，会进入受限的「需要重建」状态，要求通过重建进入新基线，而不再在旧库上做就地结构迁移。
   - 区分提示：如果只是数据库连接失败或权限不足，属于不可达状态（`unavailable`），服务不会将其判为「需要重建」，也不会允许执行破坏性重置。
2. **局部数据写乱或需要单独清理**：例如只想清掉合成测试运行历史，或单独清空知识库/已发布包/业务配置，同时保留其余部分。
3. **从头初始化整个数据目录**：需要把运行历史、知识、包和配置全部清回初始空白状态（例如切换部署规划、彻底重装一套干净环境）。

---

## 每个范围清掉什么、留下什么

契约（`contracts/src/reset.ts`）将重置范围定义为四个独立作用域和一个全选选择器，对应关系如下：

| 契约标识 | 中文名称 | 清掉什么 | 留下什么 |
|---|---|---|---|
| `history` | 运行历史 | 任务运行记录、执行历史与仅依附运行历史存在的数据 | 知识、包、配置、`keys/` 与 `vault/` |
| `knowledge` | 知识 | 知识树与知识索引等相关数据 | 运行历史、包、配置、`keys/` 与 `vault/` |
| `packs` | 包 | 已发布/安装的包记录及包清单数据 | 运行历史、知识、配置、`keys/` 与 `vault/` |
| `config` | 配置 | 账号、团队、工作流分配、业务系统资源登记、资源分配、执行器配置、普通变量及会话/令牌等配置定义 | 运行历史、知识、包、`keys/` 与 `vault/` |
| `all` | 全部初始化 | 同时重置以上四类（运行历史、知识、包、配置） | **`keys/` 与 `vault/` 仍完整保留** |

关于范围选择，有三点约束需要提前了解：

- **引用保护**：如果未选中的保留范围中仍有记录正式引用了即将被清掉的对象（例如保留的配置中仍指向待清理的包），预检会直接阻止此次重置（`blocked`），而**不会**悄悄扩大清理范围。
- **密钥与根凭据独立留存**：无论选择单个范围还是 `all`（全部初始化），数据目录下的 `keys/`（主密钥与操作员令牌）与 `vault/`（按大写密钥名存放的加密密钥密文与元数据）都**不会被删除**。
- **当前代码基线衔接说明（待随后续合并对齐）**：
  - 控制台已有两个相关入口：受限状态下访问 `/console/rebuild`（「需要重建」页面），正常运维状态下访问 `/console/settings?tab=hub#reset-rebuild`（Hub 设置页中的重置与重建区域）；两处操作均要求输入确认词 **`重建`**。
  - 在当前代码基线中，契约层（`contracts/src/reset.ts`）定义运行历史的值为 `history` 且支持多范围组合，但控制台界面（`hub/server/console/reset.ts`）选项值目前仍写为 `runs` 且表单为单选，同时命令注册表与平台命令行入口尚未接入 `reset` 子命令；这些接口将在 Codex 重置实现并入 `hub-final` 时统一对齐。

## 「保留配置重建」怎么回事

当你希望清理运行历史、知识或包（或重建当前兼容基线下的数据库结构），同时尽量保留现有账号、团队、包登记、资源与执行器配置时，可以使用保留配置模式（设计参数为 `--keep-config`，控制台界面对应「保留配置重建」选项）。

### 适用前提

- **仅限结构兼容时可用**：只有在当前数据库与基线处于兼容状态时，才允许保留配置重建。
- **「需要重建」状态不可用**：一旦服务因版本不兼容进入 `needsRebuild`，`--keep-config`（保留配置重建）会被拒绝，因为旧库记录结构已无法跨不兼容基线直接原样重放；此时需改用声明式部署定义文件（见下文与[十分钟上手](quickstart.md#用部署定义文件一次配好)）或在全量重置后重新配置。
- **互斥约束**：不能同时请求 `--keep-config` 与外部部署定义文件重放。

### 受保护配置快照（`protected-deployment@1`）

启用保留配置重建时，重置流程不会把配置明文留在普通位置，而是通过专门的受保护快照机制流转：

1. **落盘位置与权限**：流程在停服后、归档旧库前导出受保护配置快照（`protected-deployment@1`），写入数据目录下的 `private-config-snapshots/<UUID>.json`。目录权限校验为 `0700`，快照文件权限校验为 `0600`（阻止符号链接访问），并同时校验整个文件与规范载荷 `payloadSha256` 的 SHA-256 摘要。
2. **包含什么**：保留重建配置所需的完整结构与受保护身份元数据（账号、密码散列 `password_hash`、令牌散列 `tokens`、团队、包、资源定义、执行器、分配关系、OAuth 客户端、普通变量等）。
3. **不包含什么**：快照**不包含** `vault/` 中的真实密钥值、明文令牌、明文密码或密钥库内容本身——这些真实凭据始终留在独立的 `vault/` 与 `keys/` 中，按名称在重建后重新对接。

### 与 `deployment@1`（`export` / `apply`）的配合

- 如果你即将跨不兼容版本重建（触发 `needsRebuild`），建议平时就用声明式部署定义（`deployment@1`）管理账号、团队、包、资源与分配关系。
- 对比而言，`export` 导出的是面向人工与版本库维护的 `deployment@1` 清单（同样**不导出任何密钥值**，也不导出内部令牌散列），适合跨环境复用或在 `needsRebuild` 全量初始化后用 `apply` 重新装配；而 `protected-deployment@1` 是 `--keep-config` 在同基线兼容重建时使用的内部一次一密级恢复快照。

## 归档在哪、留下什么

> 最终 `circle-hub reset` 命令参数写法、旧库归档目录的具体命名格式与实跑过程，将在 Codex 重置实现并入 `hub-final` 后以实际运行输出为准补全到本节。

### 归档原理与状态追踪路径

重置过程遵循「先验后停、先导出归档、再建新库、最后恢复重启」的顺序，不在未留底的情况下直接覆盖旧数据库：

1. **停服后改名归档**：在校验可用备份（如有）并停止 Hub 服务后，旧数据库与受影响数据会整体留档，而不是原地直接销毁，随后再初始化新库、应用基线结构、保留未选中的数据并按需重放配置。
2. **独立一次性工作进程**：从控制台发起重建时，Hub 会通过系统托管的一次性任务在独立进程中执行（Linux 使用 `systemd-run --user`，macOS 使用一次性 `launchctl bootstrap`），避免 Hub 在停服重启自己的过程中断执行流。
3. **状态与请求目录**：执行期间的请求、确认与状态文件计划存放在 `<数据目录>/run/reset/` 下（私有权限：目录 `0700`、文件 `0600`），按操作 `<UUID>` 区分请求（`<UUID>.request.json`）、确认标记（`<UUID>.ack`）与实时状态（`<UUID>.status.json`）（具体文件名待重置实现并入后实测确认）。
4. **进度查看**：按当前接口约定，控制台在发起后会轮询 `/console/reset/status/<UUID>`（同一已认证会话下，接口尚在接线，当前基线不可用）；如果选择 `all` 或 `config` 清掉了管理员会话，后续亦可在命令行通过对应只读状态查询参数跟踪执行结果（具体参数待并入后确认）。

### 重置后 `keys/` 与 `vault/` 留下什么

- **`keys/` 完整保留**：包含密钥库主密钥与操作员令牌等根凭据文件（由 `circle-hub key` 与 `circle-hub operator-token` 管理），重建后无需重新初始化主密钥。
- **`vault/` 完整保留**：已写入的所有密钥密文与其元数据文件（`vault/metadata/secret.<密钥名小写>.sealed`）按**大写密钥名**独立留在 `vault/` 中。
- **重建后如何接回资源与执行器**：
  - 只要重建或重新 `apply` 后的资源定义、执行器配置里继续引用原来的密钥名（例如资源凭据里的 `SYNTH_PLM_PASS` 或执行器里的 `${secret:SYNTH_PLM_PASS}`），Hub 会按名字直接读取原有密文，无需重新索取密钥值。
  - 如果新配置引用了 `vault/` 里尚未写入或缺失 `vault/metadata/secret.<密钥名小写>.sealed` 元数据的密钥名，系统会在运行前与状态提示中明确报出缺少哪个密钥名及缺少哪些元数据字段，并引导下一步处理，**不会**陷入无限重启循环，也不会静默丢弃已有密钥。此时只需用 `circle-hub secret set --name <NAME> ...` 补齐缺失密钥或元数据，或把不再使用的资源引用从配置中移除即可。

## 失败会怎样

重置过程把失败明确分为两个边界：

### 1. 停服前失败：原状不动

以下检查均在停止服务与改动数据库之前完成，任一步不通过都会立即中止，**原有数据、运行中服务与配置完全保持原状**：

- 当前仅处于连接/权限异常（`unavailable`）而非真正的结构不兼容；
- 在「需要重建」状态下尝试保留配置重建（`--keep-config`），或同时给出了相互冲突的重放来源；
- 要清理的范围与未清理范围之间存在正式引用依赖（`blocked`）；
- 待保留范围的数据结构无法被当前版本安全识别；
- 数据目录、归档父目录、`private-config-snapshots/` 或 `run/reset/` 的权限与磁盘预检未通过；
- 先行校验备份或导出受保护配置快照失败。

### 2. 停服后失败：立即中止并尝试退回归档

一旦进入停服之后（包括旧库归档、新建数据库与基线、保留数据写入、恢复配置快照/应用定义、启动前预检与重新拉起服务）：

- 任一步失败都会立即终止后续动作，并自动执行**退回（rollback）**：把已归档的旧数据库与原始状态还原回原位、清理新建残余，并尝试重新拉起原服务，尽量恢复到发起重置前的可用状态，避免出现“删到一半既起不来又找不到旧数据”的中间残局。
- 执行结果与失败阶段（以及是否退回成功）都会记录在 `<数据目录>/run/reset/<UUID>.status.json` 中；极少数情况下若自动退回本身也因磁盘、权限或外部数据库异常受阻，状态报告会标出卡住的阶段与遗留归档位置，管理员排查修复目录权限、磁盘空间或数据库状态后即可再次检查并重试。
