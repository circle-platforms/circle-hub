# 重置和重建

> **运维与基线说明**：本页基于已合入 `hub-final` 的重置与部署实现（`hub/server/reset/`、`hub/platform/reset/`、`hub/server/cli-apply.ts`、`hub/server/console/reset.ts`）编写，并同步记录当前控制台与恢复链路上尚未对齐的已知限制（详见[兼容矩阵](compatibility.md)与 [CHANGELOG](https://github.com/circle-platforms/circle-hub/blob/main/CHANGELOG.md)）。

Circle Hub 用**重置和重建**处理不兼容版本更新、配置混乱或需要清空某类数据重来的场景，**不再走旧的在线升级迁移路线**。核心原则是：先校验与归档留底、按选定范围重新建库建基线、**独立保存的 `keys/` 与 `vault/` 不随重置删除**。

---

## 什么时候用

出现以下三类情况时，使用重置和重建：

1. **版本更新后进入「需要重建」状态（`needsRebuild`）**：新版 Hub 启动时检查数据库结构与基线版本，发现与当前运行版本不兼容，会进入受限的「需要重建」状态，要求通过重建进入新基线，而不再在旧库上做就地结构迁移。
   - 区分提示：如果只是数据库连接失败或权限不足，属于不可达状态（`unavailable`），服务不会将其判为「需要重建」，也不会允许执行破坏性重置。
2. **局部数据写乱或需要单独清理**：例如只想清掉合成测试运行历史，或单独清空知识库/已发布包/业务配置，同时保留其余部分。
3. **从头初始化整个数据目录**：需要把运行历史、知识、包和配置全部清回初始空白状态（例如切换部署规划、彻底重装一套干净环境）。

---

## 每个范围清掉什么、留下什么

契约（`contracts/src/reset.ts`）将重置范围定义为四个独立作用域和一个全选选择器，对应关系如下：

| 契约标识 | 中文名称 | 清掉什么 | 留下什么 |
|---|---|---|---|
| `history` | 运行历史 | 任务运行记录、执行历史与仅依附运行历史存在的数据 | 知识、包、配置、`keys/` 与 `vault/` |
| `knowledge` | 知识 | 知识树与知识索引等相关数据 | 运行历史、包、配置、`keys/` 与 `vault/` |
| `packs` | 包 | 已发布/安装的包记录及包清单数据 | 运行历史、知识、配置、`keys/` 与 `vault/` |
| `config` | 配置 | 账号、团队、工作流分配、业务系统资源登记、资源分配、执行器配置、普通变量及会话/令牌等配置定义 | 运行历史、知识、包、`keys/` 与 `vault/` |
| `all` | 全部初始化 | 同时重置以上四类（运行历史、知识、包、配置） | **`keys/` 与 `vault/` 仍完整保留** |

关于范围选择，有几点约束与当前基线现状需要提前了解：

- **引用保护**：如果未选中的保留范围中仍有记录正式引用了即将被清掉的对象（例如保留的配置中仍指向待清理的包），预检会直接阻止此次重置（`blocked`），而**不会**悄悄扩大清理范围。
- **密钥与根凭据独立留存**：无论选择单个范围还是 `all`（全部初始化），数据目录下的 `keys/`（主密钥与操作员令牌）与 `vault/`（按大写密钥名存放的加密密钥密文与元数据）都**不会被删除**。
- **CLI 与控制台接口现状**：
  - 控制台已有两个入口：受限状态下访问 `/console/rebuild`（「需要重建」页面），正常运维状态下访问 `/console/settings?tab=hub#reset-rebuild`（Hub 设置页中的重置与重建区域）；两处确认词均为 **`重建`**。
  - `contracts/src/reset.ts` 与控制台界面（`hub/server/console/reset.ts`）均已对齐 `history`、`knowledge`、`packs`、`config`、`all` 五个范围值（控制台单次表单为单选，CLI `--scope` 可多次传入）；`reset`、`apply`、`export` 也已接入 `circle-hub` 主命令。
  - **当前基线已知限制**（待后续补齐修复）：① 选择性范围（如 `--scope history|knowledge`，或被保留配置引用的 `--scope packs`）在预检受阻时目前会以退出码 1 返回通用前置失败提示而未展开 `ResetBlocked.problems` 明细；② `/console/rebuild` 授权提示仍写 `circle-hub setup-code --rebuild`，实际应运行不带 `--rebuild` 的 `circle-hub setup-code`；③ `export` 导出与 `apply` 差异提示的跨库已知缺陷见[兼容矩阵](compatibility.md#历史)。

## 「保留配置重建」怎么回事

当你希望清理运行历史、知识或包（或重建当前兼容基线下的数据库结构），同时尽量保留现有账号、团队、包登记、资源与执行器配置时，可以使用保留配置模式（设计参数为 `--keep-config`，控制台界面对应「保留配置重建」选项）。

### 适用前提

- **仅限结构兼容时可用**：只有在当前数据库与基线处于兼容状态时，才允许保留配置重建。
- **「需要重建」状态不可用**：一旦服务因版本不兼容进入 `needsRebuild`，`--keep-config`（保留配置重建）会被拒绝，因为旧库记录结构已无法跨不兼容基线直接原样重放；此时需按下方三步恢复路径完成重建（或参考[十分钟上手](quickstart.md#用部署定义文件一次配好)）。
- **与首次设置的区分**：选择 `--keep-config` 会在重置流程内部自动导出受保护快照并还原账号、令牌散列与配置，**重建后不需要再执行首次设置与 `init-admin`**；反之，任何不带 `--keep-config` 且包含 `config` 或 `all` 的清零重置都会清空管理员账号。
- **清空账户时禁止同时传 `--definition`**：任何会清空账户的重置组合（包含 `config` 或未带 `--keep-config` 的 `all`）如果同时指定 `--definition`（或与 `--keep-config` 冲突混用），会在触碰数据库、备份或停服之前于预览阶段直接拒绝；提示信息会明确要求改走三步恢复路径。

### 正式三步恢复路径（清空账户与不兼容重建）

当处于 `needsRebuild` 不兼容状态、或执行会清空账户的 `reset --scope all` / `--scope config` 后准备用 `deployment@1` 声明文件恢复时，请严格按以下三步执行：

1. **全量归档并建空库**：
   ```bash
   circle-hub reset --scope all
   ```
   停止服务、校验并试恢复一份标准 `circle-hub-backup@3` 备份，将原库改名归档，再按照唯一 `baseline` 重建空库（此时库内尚无任何管理员账号）。
2. **首次设置首位管理员**：
   ```bash
   circle-hub init-admin <账户名> --password-stdin
   ```
   （从标准输入读取 12–256 位非空密码；或在网页端访问 `/console/setup` 使用本机维护码完成初始化。）`init-admin` **只检查当前数据库里是否已经有管理员账号**，不以本地旧令牌文件作数；如果 `<数据目录>/keys/` 下仍留有上一个库写入的旧 `operator-token` 文件，会以原子方式直接替换，无需人工删除旧令牌文件。
3. **应用声明式部署定义**：
   ```bash
   circle-hub apply <部署定义.json>
   ```
   恢复账号、团队、包与分配、业务系统资源、执行器、普通变量、命名文档当前版、租约前缀与知识同步目标（密钥仍按名字从已保留或新写入的 `vault/` 接回）。如果跳过第 2 步、在还没有管理员的空库上直接执行 `circle-hub apply`，命令会拒绝改动任何配置，并提示先运行 `circle-hub init-admin`。

重置结束后，若需恢复运行依赖的基线、历史文档版本、认证证据、租约预订或知识构建身份，请继续核对文末[重建之后要补登记的东西](#重建之后要补登记的东西)。

### 受保护配置快照（`protected-deployment@1`）

启用保留配置重建时，重置流程不会把配置明文留在普通位置，而是通过专门的受保护快照机制流转：

1. **落盘位置与权限**：流程在停服后、归档旧库前导出受保护配置快照（`protected-deployment@1`），写入数据目录下的 `private-config-snapshots/<UUID>.json`。目录权限校验为 `0700`，快照文件权限校验为 `0600`（阻止符号链接访问），并同时校验整个文件与规范载荷 `payloadSha256` 的 SHA-256 摘要。
2. **包含什么**：保留重建配置所需的完整结构与受保护身份元数据（账号、密码散列 `password_hash`、令牌散列 `tokens`、团队、包、资源定义、执行器、分配关系、OAuth 客户端、普通变量等）。
3. **不包含什么**：快照**不包含** `vault/` 中的真实密钥值、明文令牌、明文密码或密钥库内容本身——这些真实凭据始终留在独立的 `vault/` 与 `keys/` 中，按名称在重建后重新对接。

### 与 `deployment@1`（`export` / `apply`）的配合

- 如果你即将跨不兼容版本重建（触发 `needsRebuild`），建议平时就用声明式部署定义（`deployment@1`）管理账号、团队、包、资源与分配关系。
- 对比而言，`export` 导出的是面向人工与版本库维护的 `deployment@1` 清单（同样**不导出任何密钥值**，也不导出内部令牌散列），适合跨环境复用或在 `needsRebuild` 全量初始化后用 `apply` 重新装配；而 `protected-deployment@1` 是 `--keep-config` 在同基线兼容重建时使用的内部一次一密级恢复快照。

## 归档在哪、留下什么

> 命令用法：`circle-hub reset --scope <history|knowledge|packs|config|all> [--scope <范围> ...] [--keep-config] [--definition <本机文件或src引用>]`。执行前会先检查应用角色权限并在 `<数据目录>/backups/reset-<UUID>/` 写入且试恢复校验 `circle-hub-backup@3` 标准备份，再将原数据库改名归档为 `<数据库名前20字符>_archive_<32位UUID>`（结果报告另记于 `<数据目录>/logs/reset-<UUID>.json`，过程断点记于 `<数据目录>/run/reset-operation.json`）。

### 归档原理与状态追踪路径

重置过程遵循「先验后停、先导出归档、再建新库、最后恢复重启」的顺序，不在未留底的情况下直接覆盖旧数据库：

1. **停服后改名归档**：在校验可用备份（如有）并停止 Hub 服务后，旧数据库与受影响数据会整体留档，而不是原地直接销毁，随后再初始化新库、应用基线结构、保留未选中的数据并按需重放配置。
2. **独立一次性工作进程**：从控制台发起重建时，Hub 会通过系统托管的一次性任务在独立进程中执行（Linux 使用 `systemd-run --user`，macOS 使用一次性 `launchctl bootstrap`），避免 Hub 在停服重启自己的过程中断执行流。
3. **状态与请求目录**：网页端异步重建的请求、确认与状态文件存放在 `<数据目录>/run/reset/` 下（私有权限：目录 `0700`、文件 `0600`），按操作 `<UUID>` 区分 `<UUID>.request.json`、`<UUID>.ack`、`<UUID>.claim` 与 `<UUID>.status.json`（及挂起标记 `pending`）。
4. **进度查看**：控制台在发起异步重建后会轮询 `/console/reset/status/<UUID>`（或 `/console/rebuild?operation=<UUID>`，同一已认证会话下）；在命令行执行 `circle-hub reset` 时，命令会同步等待重置（及必要时的自恢复）完成后直接打印原数据库归档名、已核对备份路径与归档表行数统计。

### 重置后 `keys/` 与 `vault/` 留下什么

- **`keys/` 完整保留**：包含密钥库主密钥与操作员令牌等根凭据文件（由 `circle-hub key` 与 `circle-hub operator-token` 管理），重建后无需重新初始化主密钥。
- **`vault/` 完整保留**：已写入的所有密钥密文与其元数据文件（`vault/metadata/secret.<密钥名小写>.sealed`）按**大写密钥名**独立留在 `vault/` 中。
- **重建后如何接回资源与执行器**：
  - 只要重建或重新 `apply` 后的资源定义、执行器配置里继续引用原来的密钥名（例如资源凭据里的 `SYNTH_PLM_PASS` 或执行器里的 `${secret:SYNTH_PLM_PASS}`），Hub 会按名字直接读取原有密文，无需重新索取密钥值。
  - 如果新配置引用了 `vault/` 里尚未写入或缺失 `vault/metadata/secret.<密钥名小写>.sealed` 元数据的密钥名，系统会在运行前与状态提示中明确报出缺少哪个密钥名及缺少哪些元数据字段，并引导下一步处理，**不会**陷入无限重启循环，也不会静默丢弃已有密钥。此时只需用 `circle-hub secret set --name <NAME> ...` 补齐缺失密钥或元数据，或把不再使用的资源引用从配置中移除即可。

## 失败会怎样

重置过程把失败明确分为两个边界：

### 1. 停服前失败：原状不动

以下检查均在停止服务与改动数据库之前完成，任一步不通过都会立即中止，**原有数据、运行中服务与配置完全保持原状**：

- 当前仅处于连接/权限异常（`unavailable`）而非真正的结构不兼容；
- 在「需要重建」状态下尝试保留配置重建（`--keep-config`），或同时给出了相互冲突的重放来源；
- 要清理的范围与未清理范围之间存在正式引用依赖（`blocked`）；
- 待保留范围的数据结构无法被当前版本安全识别；
- 数据目录、归档父目录、`private-config-snapshots/` 或 `run/reset/` 的权限与磁盘预检未通过；
- 先行校验备份或导出受保护配置快照失败。

### 2. 停服后失败：立即中止并尝试退回归档

一旦进入停服之后（包括旧库归档、新建数据库与基线、保留数据写入、恢复配置快照/应用定义、启动前预检与重新拉起服务）：

- 任一步失败都会立即终止后续动作，并自动执行**退回（rollback）**：把已归档的旧数据库与原始状态还原回原位、清理新建残余，并尝试重新拉起原服务，尽量恢复到发起重置前的可用状态，避免出现“删到一半既起不来又找不到旧数据”的中间残局。
- 执行结果与失败阶段（以及是否退回成功）都会记录在 `<数据目录>/run/reset/<UUID>.status.json` 中；极少数情况下若自动退回本身也因磁盘、权限或外部数据库异常受阻，状态报告会标出卡住的阶段与遗留归档位置，管理员排查修复目录权限、磁盘空间或数据库状态后即可再次检查并重试。

## 重建之后要补登记的东西

声明式部署定义（`deployment@1`，由 `circle-hub export` / `circle-hub apply` 读写）只携带结构化的账号、团队、包与分配、业务系统资源、执行器、当前普通变量、命名文档**当前修订版**、租约前缀与知识同步目标。做完 `reset`、重连新库或切换测试环境后，仍有一批保存在数据库表、对象存储或现场测试环境里的运行时事实不会完整随定义文件迁移。如果不按顺序核对并补登记，上机验证会在放行核对阶段以 `未派发` 拒绝，或因缺少前提认证证据在动态核验阶段判为 `no_verdict`（无判定）。

下面按 **F1–F13** 逐项列出需补齐或核对的事实、缺失后果与恢复方法（如涉及未入选 `documents` 的旧版原件或证据字节，须在切库或清零前通过 `circle-hub original export` 导出备份）：

### 1. 执行器、凭据、变量与认证证据（F1–F4）

- **F1. 执行器登记与普通变量**
  - **缺失后果**：变量未设值导致发布检查整批不能通过（`circle-hub executor list` 会显示缺失变量）；跨库重新 `apply` 会为执行器分配新的 `exe_…` 内部编号（同时重置 F6 占用与 F11 序号起点）。
  - **恢复方法**：通过 `apply` 自动恢复，或运行 `circle-hub executor add <定义文件> --name=<管理员明确指定的执行器名字>` / `executor update <执行器> <定义文件>`、以及 `circle-hub var set <变量名> (--file <文件> | --text) --not-secret --reason <理由>`。若普通变量里存放了清单摘要（如 `manifest_sha256` 等），须核对其值与新库目标文档摘要一致（见 F3）。
- **F2. 执行器与业务系统凭据（`vault/`）**
  - **缺失后果**：所有对执行器或业务系统的发送在发出前直接拦下，状态记为 `未发请求`（提示对应密钥没有可用设置）。`export` 与 `apply` 从不写入或导出任何密钥明文。
  - **恢复方法**：同机 `reset` 会保留 `<数据目录>/vault/`，重建后按大写密钥名自动接回；跨机迁移新库或需补录/轮换时，在写入任何依赖连通性的基线之前运行 `circle-hub secret set --name <密钥名> --reason <理由>`（从标准输入传入密钥值）。
- **F3. 命名文档内容与清单变量指向版本**
  - **缺失后果**：读取或编译阶段报文档不存在、或绑定清单字节不可读；如果变量里保存的摘要与当前版本或实机探针清单对不上，上机验证会以「没有绑定同一份清单」拒绝。
  - **恢复方法**：`export`/`apply` 只携带每个命名文档的**当前修订版**。如果线上执行器固定引用过旧版本文档，须在切换前用 `circle-hub original export <sha256> --out <文件>` 导出各版本原文，切换到新库后用 `circle-hub doc put <文档名> <文件>` **严格按从旧到新顺序依次写入**（最后写入当前最新版），再经 `circle-hub doc list` 确认摘要并与 `circle-hub var set` 绑定一致。
- **F4. 前提认证证据文件（`premises.*.evidence` 的 `src:` 引用）**
  - **缺失后果**：执行器可以下发，但动态核验阶段会因 `result_ownership`（或对账前提）未认证通过，将所有轮次判为 `no_verdict`（无判定）而非通过或失败。
  - **恢复方法**：`export` 不会导出未登记为当前命名文档的裸 `src:` 对象字节。切换前先按执行器 `premises.*.evidence` 列出的 `src:<sha256>` 用 `circle-hub original export <sha256> --out <文件>` 备份原件，恢复后用 `circle-hub doc put <证据文档名> <文件>` 写回对象存储，保证相同 SHA-256 的原件字节在新库可读（并核对对应目标版本声明与实际结果一致）。

### 2. 测试环境基线、残留占用与租约（F5–F7）

- **F5. 测试环境基线（干净状态快照）**
  - **缺失后果**：`export`/`apply` 不迁移基线。由于基线按 `<新执行器编号>:<探针id>` 登记，新库只要有探针未配置全量解析器、或该测试环境需要基线对比判断残留，上机验证会在放行核对时直接拒绝（`not_dispatched`：「未登记基线，无法判残留」）。
  - **恢复方法**：运行 `circle-hub bed baseline record <新exe_…> --probe <探针id> --reason <说明>`。
  - **前置条件**：必须在 **F2 凭据与网关连通性就绪、且物理测试环境已人工确认清理到干净基准态**之后再录制基线；切忌在设备仍有遗留测试配置时直接录为基线。
- **F6. 测试环境残留占用状态（`bed_hold`）**
  - **缺失后果**：不随定义文件迁移。旧库如果存在未清的测试环境占用标记，新库不会自动继承这份拦截，可能导致误把带有残留的现场当成空闲环境甚至误录进 F5 基线。
  - **恢复方法与前置条件**：停用旧库或切库前，先核查控制台状态及任务包状态，清理测试环境并在旧库执行 `circle-hub bed hold clear <执行器> --reason <理由>`（或确认对应残留占用已解除）再开始录制新库 F5 基线。
- **F7. 租约前缀登记与有效预订运行**
  - **缺失后果**：`export`/`apply` 会恢复租约**前缀登记**（`leaseRegistrations`），但**不恢复**已获批的生效租约（`leases`）和预订运行血缘。缺席时放行核对直接拒绝（「缺少覆盖派发窗口的同血缘资源租约」）。
  - **恢复方法与前置条件**：用 `circle-hub lease list` 核对前缀（必要时补跑 `circle-hub lease register <前缀> --owner <用户> --reason <理由>`），待 F9（包与分配）和 F10（发起人账号/令牌）就绪后，由发起人重新执行一次覆盖该测试环境的整套预订工作流运行，拿到新的同血缘租约根。

### 3. 知识构建、任务包身份与账号令牌（F8–F10）

- **F8. 知识库构建身份（Product Build）与同步结果**
  - **缺失后果**：`export`/`apply` 只携带 `knowledgeSources`（启用的产品包 ID）与可选 `knowledgeSync` 目标配置，**不携带**已同步/导出的知识树快照与构建身份记录。缺席时依赖指定产品构建的工作流会提示缺少构建身份记录或解析构建未知。
  - **恢复方法**：根据来源类型运行 `circle-hub knowledge sync --product <产品> --line <版本线>`，或通过离线基准来源运行 `circle-hub knowledge seed --product <产品> --line <版本线> --build <构建> --basis <一句理由>`，直至目标产品线版本树就绪。
- **F9. 包发布、启用、分配与核验函数身份（`proof.warrant_id`）**
  - **缺失后果**：若依赖技能或任务包未完整发布/安装/启用/分配，运行或知识读取会报包不可用；若包升级后与执行器声明不一致，放行检查会在「核验函数身份等于执行器指定身份」条目上拒绝派发。
  - **恢复方法**：确认 `apply` 已发布全部包（若遇到未发布包缺 `directory` 的跨库限制，手工补跑 `circle-hub pack install <通用技能@版本>`、`circle-hub pack publish <包目录>`、`pack activate <产品知识来源>` 与 `pack assign`），再核对执行器 `proof.warrant_id`，必要时通过 `circle-hub executor update <执行器> <定义文件>` 对齐最新版本身份。
- **F10. 在职管理员与发起人账号及客户端令牌**
  - **缺失后果**：没有在职管理员会导致 `apply` 与派发入口直接拒绝（「没有在职管理员负责作业未知结果的处置」）；即使 `apply` 恢复了账号行，旧库的 OAuth 令牌、控制台会话密码散列与用户授权关系也不会迁过来。
  - **恢复方法**：按三步恢复路径先完成 `circle-hub init-admin <管理员> --password-stdin`，再为使用人签发一次性邀请或令牌（`circle-hub user invite <用户>` / `circle-hub token issue <用户>`），并让各客户端 Circle 重新完成 MCP 登录授权。

### 4. 运行态流水与冻结边界（F11–F13）

- **F11. 派发日志、至多一次状态与未了结作业**
  - **操作原则**：派发日志（`action`）、作业序号与未结束作业状态不随定义文件迁移。切换前务必在旧库先用 `circle-hub job list --executor <执行器>` 和 `circle-hub job dispose …` 处置完进行中、冻结或 `unknown` 的作业，确认现场无在跑作业；在新库中**不要手工伪造或复用旧的内部 `exe_…` 编号**，让至多一次计数在新执行器身份上干净起步。
- **F12. 设备版本探针观察（`device_observation`）**
  - **操作原则**：探针观察结果属于自动生成的派生记录，**无需人工登记**；只要 F1/F3 中的清单摘要（`manifest_sha256`）与 F5 基线和当前实机一致，新库会在首次预订与上机检查时自动重建观察记录。
- **F13. 运行开始时冻结的执行器与放行边界快照**
  - **操作原则**：`start_run`（脚本编写/合并）在运行开始瞬间就会冻结当时读到的执行器定义、普通变量与放行边界策略。事后再修改执行器（F1/F9）或清单变量（F3），**之前已经发起过的旧 `run_…` 在派发时仍会被拦截**。
  - **前置顺序硬约束**：必须先完成上述 **F1–F10** 全部补登与基线录制之后，再让发起人重新发起脚本编写/合并与预订运行。

### 推荐恢复与补登顺序

1. **停服与切库前（旧库）**：处置并结束所有未了结作业（F11），清理或核销残留测试环境占用（F6），并对不在 `documents` 当前版里的历史清单或 `src:` 证据文件执行 `circle-hub original export`（F3、F4）。
2. **三步恢复重建（新库）**：`circle-hub reset --scope all` → `circle-hub init-admin <管理员> --password-stdin` → `circle-hub apply <部署定义.json>`（F1、F7 前缀、F9/F10 结构）。
3. **补齐密钥与包差距**：按名字补写 `vault/` 密钥（F2），必要时手工补发布/安装/启用缺源码目录的任务包并核对执行器 `proof.warrant_id`（F9）。
4. **按顺序回写原文、变量与知识**：从旧到新用 `circle-hub doc put` 回写历史文档和证据原件，核对 `var set` 清单摘要与执行器一致性（F3、F4），再执行 `knowledge sync` / `seed` 建立知识构建身份（F8）。
5. **现场清理后录基线**：确认测试环境与网关就绪且现场干净后，录制各新执行器的干净基线（F5）。
6. **重发客户端授权与新运行**：为用户重发邀请或令牌（F10），由发起人重新发起覆盖派发窗口的预订（F7）及新的脚本编写/合并运行（F13；探针观察 F12 将随之自动生成）。
