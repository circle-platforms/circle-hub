# 核心直接导入产品目录代码：拆分设计

## 结论和范围

建议以**方案二**为目标：目录读取、权限、固定修订和来源记录由 Hub 与系统包承担；可复用的目录遍历放入按需安装、按摘要锁定的通用技能包；版本线目录写法、书的角色、主文件和文件选择由产品包显式声明。Hub 用有界、无 I/O 的沙箱协议编排，不再直接导入产品代码。方案一可作为较小的过渡，但不能把产品包中的一份遍历逻辑复制到核心，或把旧包默默解释成新技能。

本说明只做设计，不表示新增能力已实现或已验证。核查基线为本分支建树时的 `fb04374d`。在 `hub/**` 的非测试、非测试辅助代码中，直接导入 `packs/product` 的位置是 `hub/knowledge/directory-sources.ts:4`；这不是说核心已经没有其他产品或系统布局假设。特别是 `hub/knowledge/seed.ts:290-305` 从生产器参数取 `root`、`main`、`app_main`，并把字符串根视为 SVN 目录；消除 import 而保留这套隐式约定，只消除依赖的一部分。

## 现状与符号清点

`hub/knowledge/directory-sources.ts:8-25` 的 `declaredDirectory` 从 `Producer.inputs` 识别单个元数据槽和至多一个 `many` 槽；多个列表返回 `several`。`bindDirectorySources`（:36-117）展开目录，按待取清单分轮读取，记录读取修订，核对根、子目录和每个文件的修订一致；文件组使用生产器声明的解析器读取，去重并保序，最后返回 `{ok:true,sources:角色→外部号或外部号数组}`；读取或预算不足返回 `{ok:false,slot,detail,next}`，不把不完整组当作成功。无目录声明或多个列表时绑定器本身返回空绑定；多个列表由 `seed.ts:295` 另行报告缺口。

`tree.ts` 的遍历处理的是目录与书的来源组，不解析正文的 include 次序。include 展开和原文映射另在 `packs/product/apv/functions/adoc/includes.ts:8-51`；把目录遍历迁移后，不能声称已经迁移或统一了 adoc 引擎。

核心调用链是 `hub/knowledge/seed.ts:290-303,359-367`：树苗读声明和变量后调用绑定器，得到 overlay；试运行 `:375-380` 和正式树苗 `:392-393` 都把它交给生产。`hub/knowledge/produce.ts:478-484` 将 overlay 合入构建来源。与此同时，产品包的 `packs/product/apv/functions/adoc/deployment.ts:12-35` 在同步计划中直接用同一 `tree.ts`；`:40-65,72-95` 的手册生产再次用它核完整组并生产条目。同步的产品计划通过 `hub/knowledge/sync.ts:181-204,598-607` 沙箱运行；其整轮协议见 `contracts/src/product.ts:115-156`。只改 seed 而让同步与生产各保留一套可漂移算法，不满足单一实现目标。

系统包 `packs/system/svn/system.json:102-137` 声明目录、固定修订目录和文件读取；`packs/system/svn/functions/webdav.ts:115-147` 投影目录身份与成员。产品声明的两类文件组及 `text@1` 解析器见 `packs/product/apv/product.json:128-170,187-229`。`packs/product/apv/functions/adoc/deployment.test.ts` 和 `hub/knowledge/seed.test.ts` 依赖这条语义；测试与测试辅助工具也通过 Hub API 建夹具。反向方向中，`packs/product/apv/functions/types.ts:4` 和 `functions/adoc/k1-model.ts:14` 是对 Hub 类型的 `import type`，不是沙箱中的运行时反向导入；`packs/workflow/knowledge-contribution/pack-files.ts:11-12` 是包维护工具对 Hub 代码的实际导入，另有工作流 `test-hub.ts` 测试辅助依赖。它们不是本条目录绑定调用链，但不能据此声称整个 `packs/**` 没有对核心的引用。

## 分类依据及模型差异

用 `node tools/show-element.ts C01 C02 D01 T01 K01 W06` 核对：C01 将内容按知识 B、政策 C、方法 E、资源 D 分类，R[2] 明确发布包与四家正交；C02 R[0] 要求按子组件、合同与实现分别归类，R[1] 不以多个工作流使用就认作通用。D01 R[0,1,2,7,8,12] 分别约束系统适配、来源清单、有界读取、产品方言和部署变量；T01 F[0,8]、R[0,2] 要求包文件摘要、确定性实现与版本记录。K01 R[1,6,7] 和 W06 F[3-5]、R[0] 区分内容寻址的根、组成记录及运行冻结。

**模型文字与现行分层有差异**：C02 原文仍写通用内容进 Hub 核心、系统与工作流分开；T01 定义仍列产品、工作流、系统包。所有者决定 72（`docs/hub-r4-progress.md:606-610`）则把工件格式解释放入不随 Hub 发布的通用技能包，核心只保留机制；决定 75（:624-626）将开放文本格式留在核心。本文据此采用核心、通用技能包、产品包、系统/工作流包四层，**没有把通用技能包冒充已写入 C02/T01 的原文**；模型文字如何同步需要决定。

## 方案一：产品包声明目录规划函数

- 布局：Hub 的 `directory-sources.ts` 保留通用读取编排和身份核验，不再 import 产品路径；`packs/product/apv/functions/adoc/tree.ts` 留在产品包，同包新增一个公开、版本化的纯规划入口，`product.json` 声明其函数。同步计划和手册生产继续共享包内同一实现。
- 接口：以纯 JSON 传入 `{line,root,mains,已读目录及固定修订}`，输出 `{pending,groups,unread,revision}` 或结构化失败；Hub 按 `pending` 在授权与上限内读取、验证并回传。当前 `booksOf` 的同步回调和 `Map` 不能直接跨沙箱，需定义数组及分轮数据协议。不得把未经核验的包输出直接当来源事实。
- 影响：新产品包升版本、重签；现有树节点和条目在相同输入下应不变，但新生产的组成记录会记录新包身份与时间。旧包没有新声明；读旧根不需要新规划器，用旧包重产需单独证明已有 `sync.plan` 可适配 seed，或明确未知及补迁移出口。现有 `sync.plan` 输入包含全轮 `known/options/read` 与所有构建（`contracts/src/product.ts:123-149`），不能直接假定与单构建 seed 等价。
- 工作量粗估 2–4 个提交：规划协议与校验、产品声明与重签、迁移差分和历史兼容。风险是通用目录遍历暂留产品包；若将其永久当产品专用，可能不符合决定 72，须明确后续迁移计划。

## 方案二：通用技能加产品布局声明（推荐）

- 布局：新建如 `packs/skill/directory-format/` 的通用技能，承担清单的有界遍历、显式主文件分组与有序投影；产品包保留名称族、版本目录语法、主文件角色、文件选择和预算声明；系统包提供固定修订目录、文件身份与读取投影。Hub 保留协议校验、授权读取、沙箱、记录和组成冻结，不执行产品路径代码。
- 接口：产品声明提供 `{root, mains:[{role,path}],文件选择声明,limits}`；Hub 将已核对的 `{id,revision,model}` 按需送入技能，技能返回 `{revision,groups:[…],pending:[…],unread:[…]}` 或结构化缺失与下一步。Hub 对返回的外部号、固定修订、来源权限、数量和完整性逐项核验。输入/输出均是有界 JSON，不传回调、`Map`、凭据或文件路径访问能力；需对轮次、累计输入输出、时限和失败后重试设上限。
- 现有能力不能直接复用为此接口：`contracts/src/pack.ts:73-83` 的 `skill@1` 目前只声明解析器和可选 locate，`hub/refs/skills.ts` 按 parser 加载；需要新的技能能力声明、发布校验和生成契约。产品沙箱不能静态导入另一包（`hub/runs/packs/imports.ts:315,376`），因此由 Hub 把同一锁定技能的结果作为产品计划/生产器输入，或另行设计可验证调用机制；不得复制第二套实现冒充共享。
- 新技能需发布签署、由管理员安装；新产品包需升版重签，声明所需技能版本。知识生产和树苗还须明确冻结产品包及技能的精确摘要并记入新的生产/组成记录；普通运行的技能锁不能自动证明历史生产时曾使用该技能。若技能缺失、摘要不匹配、目录不全或修订不一致，停止生产并给缺失事实和安装、修复或重读出口。
- 工作量粗估 4–6 个提交：能力契约/生成、技能与测试、Hub 编排及生产摘要冻结、产品声明/重签、跨版本兼容与端到端差分。主要风险是协议与来源顺序漂移、包间沙箱边界、旧包兼容和目录组预算；价值是分层符合决定 72，避免将该产品的双书与命名规则固化为所有产品的核心行为。

## 兼容与证明

1. **历史读取**：保留已发布产品包字节与摘要、原源记录、旧条目、节点、根和组成记录；旧运行继续按已保存的锁定根及对应组成读取，不修改或补造历史记录。`contracts/src/run.ts:138-153,186-188` 的 `pack_digest` 是运行工作包摘要，`product_pack_digest` 是可选字段，历史运行可能没有；产品生产包的身份按旧组成记录核对，不能声称每个旧运行都直接锁了它。读旧根通常无需重跑目录规划。
2. **旧包重产**：单独测试用旧摘要重新运行同步和 seed。旧 `familyManual` 与 `addAdocSources` 在旧包内仍使用旧 `tree.ts`；不能将当前技能结果悄悄冒充旧包行为。若无法在受限沙箱复现旧路径，要明确缺少旧规划能力和下一步；是否允许经管理员追加迁移时点绑定，需所有者决定，不能改写旧锁。
3. **新旧差分**：用合成固定修订目录，分别跑迁移前和迁移后的同步计划、seed 与生产。逐项比较请求序列、角色、文件与目录外部号及顺序、修订、读取清单、parser、源摘要、引文和缺失/预算出口；覆盖同目录两主文件、分目录两书、根目录主文件、空主文件、兄弟目录不读、缺目录/文件、混修订、超预算和重复路径。再比较每条规范化 entry 字节与摘要、所有节点字节及根摘要。
4. **组成记录不是根内容**：`hub/knowledge/digest.ts:60-83` 按规范内容算条目及节点；`hub/knowledge/produce.ts:942-972` 的组成记录还含生产包版本、摘要和生产时间。新包重产不能一概承诺新旧组成记录逐字节相同。应验证旧记录原字节不变，新记录完整披露新包/技能摘要及迁移依据；逐字段比较来源、引用和决定，只有明示批准的版本、时间及新增锁定字段可不同，不能为了比较而抹去来源差异。
5. 现有 `hub/knowledge/seed.test.ts:372-403,429,556-579,665` 覆盖重复产出、声明解析器、缺失拒绝和双书目录；`packs/product/apv/functions/adoc/deployment.test.ts:104-173` 覆盖模板、两书与整组边界，`adoc/expand.test.ts` 覆盖正文展开。它们是基线，不是跨实现等价证明；需新增上述前后差分、旧摘要运行及新增技能缺失/错误/超限测试，不能以同版重复测试代替。

## 需要所有者决定

1. 是否接受方案二为目标，并允许先以方案一作为有期限的过渡；通用技能与生产期摘要冻结需要新增契约和实现，本任务不做这些改动。
2. 旧根和旧运行原样可读之外，是否要求**所有已发布旧产品包可重产**？若要求，选旧包计划兼容执行、追加管理员迁移时点绑定，还是保留有版本的兼容适配器；必须先证明或披露其适用范围。
3. 通用技能的声明位置、生产锁与旧组成记录的追加披露方式；组预算是否保持当前数值，及超限后的管理员出口。
4. 是否同步修订 C02、T01 的模型文字以纳入决定 72 的通用技能包；在同步前如何解释通用能力的发布归属。
