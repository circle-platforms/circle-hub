# Hub simplification: scope and decisions

## Actual use and essential boundaries

Hub serves colleagues in an internal laboratory. The high-cost failures are real credentials reaching a model or log, writing a real business system or device unexpectedly, and presenting invented content as a verified fact. Malicious pack authors, root tampering and multi-tenant isolation are not current design targets. Keep source access and user roles, read-only business connectors, controlled device dispatch and mutual exclusion, verbatim citations, append-only history, and content hashes for identity and deduplication.

## Inventory and proposed decisions

This is a concrete proposal, not a claim that any existing rule was removed. The owner must explicitly decide the changed mechanisms and corresponding tests before they or their governing model/AGENTS clauses change.

### Decisions required before changing existing contracts

1. **One authorization decision per request.** Proposed meaning: for a given reader, source and consumer, obtain the current decision once at the start of that request and use it for that request only; revocation applies to the next request. This replaces immediate visibility of a revocation partway through one request. It affects B03 R[0], B04 R[3], and the immediate-revocation assertions in `hub/runs/engine/exact-prefetch-budget.test.ts` and `hub/runs/engine/lazy-access-security.test.ts`. Permission changes across requests and credential withholding stay enforced. The first optimization in this task does not make this change.
2. **Model identity declared once.** Proposed meaning: an explicit start-run declaration may supply a submission's missing identity only when the Hub-observed session matches the run's session; a different session declares its identity itself. Preserve both the raw submitted bytes and the provenance of the effective declaration; no identity is inferred from a model name. This changes W07 F[0], which presently says each submission separately declares its identity, and requires schema, client and compatibility tests. Although W06 F[12] describes a start-run identity declaration, the current `StartRunInput` and `RunRecord` schemas have no such field: implementing reuse first needs to add it, not merely read an existing value. A missing declaration still means independence is unknown.
3. **Per-call isolation proof.** Proposed meaning: keep OS isolation for every call and tests that verify the actual isolation, but remove the per-call Linux attestation and its proof-only assertions in the affected sandbox tests. The exact tests are to be listed alongside the implementation before removal. An unavailable sandbox still fails closed. Decide this separately from changing isolation or resource limits.
4. **Sources and lease presentation.** First collapse presentation only, preserving B02 F[5], R[4] and R[6] and the underlying source decisions. Keep real device mutual exclusion and never present absence of a lease as authorized. The separate, unmerged operation-device-lease proposal should not be treated as current mainline behavior; decide its continuous-coverage rule and any changed tests before merging it.

## Baseline and real workflow priorities

At baseline `f3fcf38b`, tracked TypeScript under `hub`, `packs`, `contracts`, and `tests` comprises 857 non-test files / 136001 lines and 854 test files / 112597 lines, including generated code and fixtures. These counts measure scope, not mechanism complexity. The previous shared-lane report measured 539.7 seconds for one full unit run at another commit and concurrency 14; it is historical and not comparable to a new run at concurrency 2. No full run was started solely to refresh the baseline.

For the approved simplification batches, aim to reduce full unit-test wall time by at least 20% and the TypeScript lines in the specifically changed mechanism modules by at least 15%, measured on the same machine and concurrency with the baseline and final test outcomes reported. Count removed proof-only tests separately from added behavioral regressions; fewer tests alone is not success. These are targets rather than claims, and no useful behavior or necessary test is removed merely to meet them. The first quotation-read change reduced the synthetic 40-reference prefetch from 161 source reads to 81; this is an operation count, not a real-world latency measurement.

* The repository helper `node tools/prepare-packs.ts --changed <base>` runs each changed pack's own manifest generator in one step. It does not choose a version or publish; if files changed at the same version as the base it warns the author to check whether a new version is needed. Explicit pack directories may be supplied instead.
* T1-2: the current review still needs the client's explicit model family. The same source under a new locked root does not make the old and new roots equal. Reuse declarations without inventing them.
* T1-3: category claims require raw-source byte spans, and the client had to compute them manually. A future tool should derive spans from original bytes and the declared selector, preserve ambiguity and escaped/double-encoded input, and let Hub independently check the submitted quotation. The existing preview's fragment-relative ranges are not raw-source offsets.
* T2-1, T2-3 and T6-2: a client timed out while the server continued. Provide a queryable state for long operations rather than retrying blindly; the observed T2-3 failure's root cause remains unproven.
* T2-2, T2-5 and T2-6: show whether data was read, projection is unfinished, or a tree/index is missing. An empty interim view is not proof of an empty dataset.
* T4/T6: distinguish historical device results, actual restoration and synthetic tests. Keep exclusive occupancy and report a missing lease as unknown.
* T7-6: present each unresolved run with missing fact and next action; derive this display without changing stored receipts.

The integration head and the deployed core were different at the last handoff. Neither local tests nor an integration merge proves the live result. Deployment requires the owner's stop window and a fresh check for unfinished jobs and leases. After that, revisit the scenario list and distinguish real, synthetic, partial and unverified outcomes.
