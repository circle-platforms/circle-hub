# 对象标准：五要素检查单

> **2026-10-21 改写**：旧版把五要素（记录、资产、审批策略、证据、扩展点）当作四个对象各自的存储分区，这一点已被取代。按通用模型待定第 3 项的决定，五要素是设计检查单和记录页布局，不作存储分区。旧版的分区表、数据流和适配单见 [ca66002 的本页](https://github.com/circle-platforms/circle-hub/blob/ca66002fb6bfc3220547d0fdd895bfae83345943/docs/design/object-standard.md)。

## 一、四个对象就是四个家

四个对象就是通用模型 C01 的四个家，按内容的性质分，打包进哪个任务包不改变它所属的家：

| 家 | 放什么 | 怎么改 |
|---|---|---|
| 知识 | 描述某个版本的世界：知识树、知识条目、目录、事实表 | 按源复核 |
| 政策 | 决定什么可以发生：决定表、政策表 | 只能重新决定，并配样例 |
| 方法 | 怎么做、怎么判：规则、检查、规程、包内确定性函数 | 沙箱运行、锁定版本，以新包版本生效 |
| 资源 | 怎么连接一个系统：对接规范、系统类型档案、部署实例、执行器 | 由管理员配置，前提默认为假 |

归属另按四类分（C02），按子组件判，合同与实现分开：通用的进 Hub 核心；带产品方言的进产品包；带系统方言、不带产品语义的进系统包，由管理员实例化为资源；只服务一个工作流的进工作流包。“多个工作流在用”不等于通用。

## 二、存储只有一种形状

五要素不对应任何表、目录或编号前缀。按 [Hub r4 架构](../hub-r4-architecture.md)，Hub 存的是：

- 只追加的记录：一张记录表（id、kind、schema、digest、provenance、created_at、body）加一张小索引表，记录种类见合约里的 `RECORD_KINDS`；
- 按内容寻址的对象字节；
- 少量可变状态：用户、令牌哈希、当前根指针（比较并交换）、密钥库条目。

其余状态都由记录推出。记录的摘要是 `{kind, schema, provenance, created_at, body}` 按 RFC 8785 规范化之后的 SHA-256。

## 三、五要素：检查单与记录页布局

### 作设计检查单

设计一个组件、一个任务包或一次系统接入时，逐条回答下表；答不上来的那一格就是缺口。

| 要素 | 要回答的问题 | 模型里对应的元素 |
|---|---|---|
| 记录 | 它留下哪些记录？凡是“说了什么”，是否都写成主张，带根据、生产者和有效条件？ | B01–B08 |
| 资产 | 它用到的每条规则、每份目录、每个包文件，是否按内容寻址、带版本，并在运行开始时锁定？ | B02、T01、W03–W05、C04–C07、D01、D07、K01、K02 |
| 审批策略（现在只剩许可） | 谁在什么时刻许可它可以做？只有两种人作出许可：包的所有者发布（过发布校验），管理员分配与配置。没有审批流；许可不当证据，通过的检查也不当许可 | B04、T02、R01 |
| 证据 | 结果的根据是哪些引用？Hub 自己的动作记录和效果记录在哪里？规则自己的正例与反例在哪里？ | B01、B03、B05、B06、T01、C05 |
| 扩展点 | 它从哪里插进来：归属类、能力声明、包内函数、系统类型档案和产品方言档案、执行器登记？接一个新产品或新系统类型时，Hub 核心是否一行不改？ | C02、C08、T01、D01、D07 |

### 作记录页布局

控制台（只读）上的一条记录按同样五格排：

1. 记录本身：按合约的展示顺序 `DISPLAY_ORDER` 列出位置、陈述、性质与依据等级、限定、根据、生产者、解析状态、有效条件；
2. 资产：所依据的任务包版本、规则@版本、目录和知识根摘要；
3. 许可：相关的发布、分配、配置或分享记录，带决定人和时刻；
4. 证据：根据所指的源文件片段和 Hub 记录、Hub 的动作记录，以及规则的样例；
5. 扩展点：它来自哪个任务包、属于哪个归属类。

缺失与无权一律只显示“对你不可用”和同形的空集。

## 四、B 的原件与证据规则

> **已被取代**（2026-10-21）：旧版这一节的原件、证据与入库规则属于已退役的服务器。现在：源文件按内容寻址、原样保存并带出处，哈希一致只证明“就是这一份”（B02）；引用是主张根据的唯一形式（B03）；上传时做凭据扫描，提交时做边界校验（T03）；模型写下的精确值在边界解析成引用，引文与原文逐字核对（T04）。见[通用模型](generic-model.md)。
