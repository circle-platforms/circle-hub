# 角色与范围

主体两类：人、服务客户端。服务客户端是机器身份，只有 scope 串（例如 `jumphost:run`），没有角色。

## 三种角色，按范围授予

人的角色按范围授予：**管理员**、**成员**、**访客**。根范围的管理员就是 hub 管理员。按范围的角色是唯一的人权限源；今天散落的动作串（`assets.approve`、`decisions.approve`、`cases.execute`…）收进三个预设，只做一次迁移；界面只显示角色。预设是数据，以后可自定义。

| 能做什么 | 管理员 | 成员 | 访客 |
|---|---|---|---|
| 读资料、证据、登记簿、本范围任务状态 | ✓ | ✓ | ✓ |
| 交活、运行（走执行链，不审批）、回应自己的任务 | ✓ | ✓ | — |
| 推送技能包、上传原件、登记资源、建 bot | ✓（变更集） | ✓（变更集，需管理员批） | — |
| 批变更集 | ✓，不批自己 | — | — |
| 人员、角色、范围策略 | ✓（变更集） | — | — |
| worker、运行 profile、服务客户端 | ✓ | — | — |

原有的 targets / readers 继续限制具体资源和来源的可见范围；根管理员管角色与范围，不自动继承子范围的资料读取。

## 两人规则

范围策略 `twoPersonRule`（布尔，默认开）。审批资格：

- 成员的变更集永远要管理员决定。
- 管理员自己的变更集：规则开，要另一位管理员；规则关，或该范围只有一名管理员，允许本人决定，记录 `decisionMode: self`，带范围标志 `singleAdminMode`。自决不是静默放行：列表里和他决并排显示，页面顶部有提示。
- 角色变更本身是变更集：加管理员要现有管理员批，两人规则开时要另一位。

开源默认：两人规则开；首个管理员建范围时自动进入单管理员模式并提示。一句公式：**谁需要审批 = 成员，或管理员且该范围两人规则开。**

## 这回答了什么

- 「Circle 用管理员身份连 hub 就能自己批自己吗」：能，在单管理员模式或规则关时；但记录标注自决，决定仍绑定摘要，审计不变。
- 「用户提交才需要审批吗」：是，成员提交永远需要管理员。
- 「权限太散」：人只有角色，机器只有 scope 串，别的都是数据。
