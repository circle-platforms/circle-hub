# Hub r4 使用指南：七项用例能力

写给出任务的模型（在 Circle 里）和看它工作的人。Hub 是一个标准的 MCP 服务器：它核对结果、从不生成内容；能算的由它直接算，要判断的由模型判断、Hub 在边界上核对证据。每项能力一节；细节（决定、限制、对其他包的需求）以各任务包的 README 为准，本文只指路。

先读这三条，再按能力查：

- **结果在哪里看**：`start_run` 和 `submit_result` 的回答（回执）里有运行编号、条目摘要和计数；存下的校验结果用 `get_nodes` 按 `rec:` 引用读，条目多时分页（照回答末尾的说明接着读）。只读的控制台也能看运行、知识树和任务包。分区回答“交付了什么”（已交付、已拒收、已隔离、未完成，未知单独计数），终态回答“判定是什么”；未知保持未知，从不显示成通过或不通过。
- **Hub 核对的与模型判断的**：Hub 自己算的（事实检查）标“事实”，模型写的（判断）标“判断”并写声明的模型；独立复核要求换一个会话和一个不同家族的模型，否则 Hub 记“独立性未知”，复核不成立。
- **空是合法答案**：没有变更、没有要维护的用例、没有要追溯的缺陷时，结果是空的条目集，不是出错。

## 运行前要知道的

- **管理员**（详见 [交接页](hub-r4-progress.md)的部署与规则部分）：发布任务包（`pack publish <目录> --stage`）并把工作流包分配给要用的用户、激活产品包；用 `knowledge sync` 同步知识库（两个名称族的每个已发布构建各产出一个根）；系统包发布新版本后用 `resource update <资源> --system-pack <包名>` 改绑。包内容改了要先升版本号再发布，已发布的版本不改内容。
- **用户令牌**：Hub 只监听本机，调用带 Bearer 令牌；钥匙和操作令牌在钥匙串里，由管理员用 `circle-hub key …` 等命令管理。没有分配给你的任务包，和不存在看起来一样（对你不可用）。
- **模型家族**：初评和复核要用不同家族的模型（现在只有千问家族的端点时，Hub 不把名字里带共同词的模型认作独立；复核要换另一个家族的端点，由所有者配置）。这决定复核能不能成立。

## 用例评审（case-review 加 case-review-verify）

模型按团队的评审方法评审一份测试脑图：初评写出每个用例的发现和整份等级，另一个会话、另一个家族的模型用复核包独立复核，给出 PASS、PARTIAL 或 FAIL 和最终等级。

- **提示这样写**（编号都是占位）：「用 Hub 评审敏捷平台的脑图 `<文档编号>`，先初评；完成后另起会话换模型复核。」
- **Hub 自己核对**：字面问题（重复、空字段等）、引文逐字、位置存在、命令与参数按锁定构建的目录核对、复核的独立性；**模型判断**：发现的内容与严重程度、等级、复核结论。
- **已知限制**：一次运行最多 100 个条目，更多时按分组（`block`）或顺序（`slice`）分块，各块独立评审、整体取最差；命令的已验证测试事实（足迹）这一版没有，算证据缺口；初评的召回要靠独立复核补（真实测量见[进度](hub-r4-progress.md)）。
- 详见两个包的 README：[case-review](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/case-review/README.md)、[case-review-verify](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/case-review-verify/README.md)（复核的输入是初评的回执引用 `rec:<摘要>` 和前驱运行编号）。

## 模板缺口（template-gap）

按团队的用例模板 v3 查出每份脑图缺哪些类别（24 个类别：六个测试类型加命令增删改查、日志、配置同步、升级兼容、安全、数据库等），以及每个类别的证据用例。全是事实，开始运行时直接算出，不用模型提交。

- **提示这样写**：「用 Hub 检查脑图 `<文档编号>` 的模板缺口。」可以给多份，一次最多约 30 份。
- **Hub 自己核对**：类别的出现与否按规则（测试类型按标签，其余按关键词）——全部是事实；**模型判断**：只有用户明确声明的“跳过”才跳过（理由照用户原话记下）；模型自己的看法另标“模型转述，未经校验”。
- **已知限制**：关键词判定可能误报；没有标签、写法像用例的节点不计入，摘要里会写明有几个。
- 详见 [template-gap 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/template-gap/README.md)。

## 用例定位（case-location）

按敏捷平台的目录树定出每份脑图（或每个用例）的产品线、版本、版本线、发布火车和模块，列出定位到的版本线在两个名称族的已知构建候选（别名解析到它所依据的构建），核对目录和标题里写出的构建名，并列出标题关联的需求与缺陷编号。全是事实。

- **提示这样写**：「用 Hub 定位脑图 `<文档编号>`。」按用例定位时加参数 `granularity: "case"`，一次一份。
- **Hub 自己核对**：定位规则、构建候选（按运行开始时冻结的已知构建列表）、写出构建名的对照；**模型判断**：无（模型的评论只记为判断）。
- **已知限制与未知**：目录树定不准或自相矛盾时记未知并写明缺什么，从不记为不通过；知识库不认识的构建名记未知（知识库只收录构建站列出的构建）；写出的构建名属于另一条版本线时记提示档的不通过，写明属于哪条线。一次最多约 40 份（按用例定位一份），更多照回答末尾的说明分页读。
- 详见 [case-location 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/case-location/README.md)。

## 回归范围（regression-scope）

给出两个构建之间变了什么、哪些已索引用例落在变更的路径上：回归范围。全是事实。

- **提示这样写**：「用 Hub 算从 `<起始构建>` 到 `<目标构建>` 的回归范围。」（输入是知识库的影响视图：`knowledge:impact:<产品>:<起始构建>..<目标构建>`，构建名写两个名称族里任一个的写法都可以。）
- **Hub 自己核对**：范围按两个构建的知识树根的条目级差异算出；**模型判断**：无。
- **已知限制与未知**：变更路径上没有用例记为未知（缺输入）——用例索引本来就不完整，没有列出不等于没有；后一构建的索引有列出的文档没读到时，结论写明句数，未覆盖的路径可能是用例没被读到。没有变更时范围是空的，是合法结果。可选参数：`priorities` 只保留列出的优先级；`include_added` 写成 false 时新增路径不进入范围。
- 详见 [regression-scope 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/regression-scope/README.md)。

## 维护巡检（maintenance-sweep）

对一个新构建巡检较早构建的已索引用例：命令已删除的用例要维护（阻断档：改写或停用），命令定义有差异的是提示（按字段给出两边的值）。全是事实。

- **提示这样写**：「用 Hub 巡检 `<起始构建>` 到 `<目标构建>` 之间要维护的用例。」
- **Hub 自己核对**：命令是否还在、定义差异逐字段比对；**模型判断**：无。
- **已知限制与未知**：只改了行为说明、或路径是新增的，不是维护项；索引没有收录的用例不作结论；较早构建有没读到的文档时，没有维护项并不能证明没有过期的用例（结论照写句数）。可选参数 `ignore_fields` 列出比较定义时跳过的顶层字段名。没有维护项是合法的空结果。
- 详见 [maintenance-sweep 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/maintenance-sweep/README.md)。

## 追溯矩阵（traceability）

构建的缺陷到用例的追溯：release notes 列出的每个缺陷，有没有已索引的用例携带它的编号。全是事实。

- **提示这样写**：「用 Hub 算 `<构建>` 的缺陷追溯矩阵。」（输入是知识库的两个索引视图，指向同一个构建：`knowledge:index:<产品>:<构建>?kind=defect&key=bug` 和 `?kind=case&key=defects`，构建名写任一名称族的写法都可以。）
- **Hub 自己核对**：矩阵按两个索引视图算出；**模型判断**：无。
- **已知限制与未知**：没有已索引用例的缺陷记未知（缺输入）——用例索引按构造不完整，没有列出不等于没有，绝不显示成“没有追溯用例”的失败；来源里同一缺陷既列为已修复又列为已知的记提示档的状态矛盾；运行级计数（缺陷、已追溯、未追溯）在跨条目结论里。可选参数 `statuses` 只看已修复或已知。
- 详见 [traceability 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/traceability/README.md)。

## 质量看板（quality-board）

按（版本线、模块）分组的质量指标：用例数、无期望结果占比、只有含糊期望结果占比、负面用例占比，以及整个构建的合计；阈值越界是提示档的管理信号，从不是阻断。全是事实。

- **提示这样写**：「用 Hub 看 `<构建>` 的质量看板。」（输入是知识库的计数视图：`knowledge:facets:<产品>:<构建>?kind=case&by=line,module,has_expected,vague_expected,negative`。）
- **Hub 自己核对**：指标按计数视图的定义算出（无期望 = `has_expected` 为假；含糊期望 = `has_expected` 真且 `vague_expected` 真；占比是精确分数，展示值只在展示时取舍）；阈值参数 `max_missing_ratio`、`max_vague_ratio`（默认 0.05）、`min_negative_ratio`（默认 0.02），等于阈值不算越界；**模型判断**：无。
- **已知限制与未知**：看板只覆盖用例索引收录的用例（索引只收指到可解析命令的用例），描述的是已索引的用例，不是整套测试；视图有列出的来源没读或被截断时，合计的说明里照写。
- 详见 [quality-board 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/quality-board/README.md)。

## 缺陷转用例（defect-to-case）

模型从缺陷（现象、修复说明）起草回归测试用例，Hub 在边界与运行期核对。**模型起草（判断），Hub 核对（事实）**。

- **提示这样写**：「用 Hub 从缺陷 `<缺陷编号>` 起草回归用例。」
- **Hub 自己核对**：用例结构、命令与参数按锁定构建的目录核对（反向用例预期被反驳，被接受反而是违规）、期望结果的引文逐字取自修复说明或手册、与锁定构建已索引用例的去重；**模型判断**：用例内容本身；起草不了的缺陷（如无外部可测行为）由模型声明跳过并写明理由，不是失败。
- **已知限制**：去重比对只看已索引用例（索引不完整）；每缺陷最多起草数 `max_cases`（默认 6）和默认优先级 `priority`（默认 2）可调。
- 详见 [defect-to-case 的 README](https://github.com/circle-platforms/circle-hub/blob/main/packs/workflow/defect-to-case/README.md)。

## 转自动化（还没做）

把评审过的用例编译成执行工作簿并经实验室网关跑起来，需要设备台架。开始之前要所有者先确认台架、账号和允许的命令类（设备是共享实验室硬件）；在那之前不做。

## 读结果的手法（六项通用）

1. 开始运行的回答里，条目按摘要列出；完整结论在 `result.reference` 指向的校验结果里，用 `get_nodes` 按 `rec:` 引用读，条目多时分页。
2. 事实与判断分开列：检查算出的结论标“事实”，模型写的标“判断”并带声明的模型名；模型的补充看法用 `submit_result` 提交后只记为判断，不改变 Hub 算出的结果。
3. 未知永远写明原因（缺输入、检查出错等），不显示成通过或不通过；证据缺口（没读到、没绑定的来源）在回答和运行记录里单列。
4. 每个条目落在且只落在一个分区：已交付、已拒收、已隔离、未完成；计数如实，不写“全绿”。
5. 控制台是只读页面：运行、知识树、任务包都在那里能看。
6. 答非所问时不猜：目标没给（文档编号、构建名）先问用户。
