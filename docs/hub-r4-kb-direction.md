# 知识库改造：所有者定下的方向（2026-10-23）

这是所有者 10-23 下午给出的知识库方向，作为知识库改造各任务的依据。设计权威仍是通用模型：`docs/design/generic-model.md`、`contracts/model.json`，用 `node tools/show-element.ts K01 K02 K03 K04 K05 B01 B02 B03` 查元素；知识包的实现见 `hub/knowledge/README.md`。照这里办，不另造概念或词表。

前提：Hub 不调用任何模型，Hub 与 Circle 联动，统一处理平台接入的结构化与非结构化资料。

## 一、资料分三类

1. **机器结构**：命令树 XML、构建头、测试清单、缺陷导出。由 Hub 的生产器机械解析。
2. **作者结构**：adoc 手册、规格。由 Hub 直接把 adoc 转为结构化数据，不再接上游的 md。
   - 产出：章节路径、命令签名锚、取值域、示例。示例只作参考，不参与判定。
   - 同样的输入给出同样的字节。
3. **自由文本**：工单、纪要。由 Circle 读、Jev 排序。Jev 在 bot 侧，Hub 不调用它。

## 二、Circle 和 Jev 的产出放在哪

- **按文档的产出**存到 Hub 的候选层：分类、归位提议、声明、关系。
- **按任务的产出**只进运行记录：排序、取舍、分数。
- 层级和依据等级由来源决定（词表 `provenance_type`、`basis_rank`），模型的自信不改变等级。
- 归位提议由 Hub 按确定性规则核验：引文逐字出自源文件、路径可解析、不越过声明。这是 K04 R[6] 尚未实现的通道。

## 三、树（K01）

- 每个产品线@构建一个内容寻址的根。未变子树共享，版本差就是回归范围。
- 条目是原文片段，加上生产器声明的种类和适用条件（型号、平台、起止构建）；抽不出的记“未声明”。硬件平台是条目的适用条件，不是树的一个轴。
- 落点是结构规则：
  - 字面能定的直接挂。
  - 跨叶主张挂最近公共祖先，不造合成路径。
  - 无锚散文（APP 手册约四成）按源自身的章节层级挂到章节节点，再按命令字面做交叉链接，不能留在根下未归位。
- 没有产品线的源文件照样存、照样能引用，但不挂树。

## 四、三层写入（K03）

- 树只由生产器写。
- 观察层：Hub 在核实运行中采到的回显，只追加。
- 候选层：收 Circle 的产出。要不要改为团队可见，待所有者决定。
- 观察层和候选层不计入根摘要，重建只动树本身。

## 五、Hub 不裁决矛盾

- 矛盾主张只按 B01 R[2] 作为可机器检查的反驳条件打标：两条都返回，带来源和时间。
- 矛盾靠自动化测试和沉淀步骤（P10）逐渐消融。Circle 侧缺一个定时整合技能，这是待补项。
- “实际怎样”与“应该怎样”冲突时，不自动判谁胜。产物是缺陷候选或漂移记录，由用途决定。

## 六、环境信息和通用知识

- 环境信息（床位、主机、IP）是 D 的资源记录，不进知识树。
- 通用知识拆成三种：
  - 包规则：随包的版本。
  - 外部规范：独立对象，从节点链接。
  - 产品线根上的全版本事实：要负责人署名。
- 版本别名表（一个产品多个名称，APV 即 NSAE）的修改要留修订记录，并且可以回滚。

## 七、从 InfoTest 只取精髓，不搬形态

- 取：“语义判断归模型，结构操作和存在性核查归代码”的契约（InfoTest `docs/footprint.md`）；手册转换链的身份耦合、同批换代、fail-closed 纪律（InfoTest `docs/HANDOFF_manual_catalog_2.90.md`）。
- 不搬：不按版本复制节点目录；不 rebuild 加搬运；不用收据钉和双生常量；不用向量库；不用五层认知序。
- InfoTest 位于 `../InfoTest_Engine`，只读参考，禁止运行、导入或复制其代码、配置、凭据和业务数据。
- 新代码一律 TypeScript；生产器在沙箱内运行，没有网络。

## 八、待调研的四项（各自独立）

1. asciidoctor.js 能否在生产器沙箱内运行，并直接给出章节路径、签名块和表格。
2. 用 APP 手册的真实章节验证“章节路径与命令路径共存一棵树”的落点规则。
3. 在真实手册里找同一版本下按平台分叉的内容，验证适用条件的三个字段够不够用。
4. 统计现有知识库源文件中，手册、命令树、用例文档、发布说明之外的自由文本占比，决定派生数据机制是否推迟。

工作在各自的 worktree 分支上进行，不推送、不建 PR，提交只加显式路径并带 `-s` 签名。

## 集成者 10-23 核对到的事实

- 手册库里只有转换后的 md 和 InfoTest 生成的 catalog.json，没有 adoc 原件；catalog 的 identity 里记着各章 adoc 的 sha256 和行号。要直接接 adoc，先要所有者给出 adoc 的来源。
- 现在的手册生产器读 md 和 catalog.json，只把命令锚挂到 `/commands/...`，其余段落留在根下未归位。
- 候选层和观察层的记录形状已经有了（`hub/knowledge/layers.ts`），但运行里的提交还没有写候选层的通道，K04 R[6] 的归位提议核验也没有。
- 版本别名在产品包的 `names` 里，随包的版本发布，修改天然留版本、可以下架回滚。是否还要单独的别名修订记录，在任务里核对。
