## Isolation of pack functions

Following the [Hub r4 architecture](hub-r4-architecture.md), a task pack's functions run in a restricted child process (implemented by the rules package, under review): the Node permission model forbids file writes and child processes and allows reading only the extracted pack; the architecture brief records that on Node 24.17 the permission model was found not to restrict network access, so the child process also runs under macOS `sandbox-exec` with network denied; time, memory and input and output sizes are limited as well. On Linux this layer is bubblewrap with the Hub's AppArmor policy, which an administrator loads (see [the rules package](https://github.com/circle-platforms/circle-hub/blob/main/hub/rules/README.md)). Where no operating-system isolation works, pack functions are refused by default (`SANDBOX_UNAVAILABLE`). Equivalent isolation on other platforms is not decided yet.

Public CI runs on Ubuntu. A pull request runs only the fast checks (`Types`, `Generated contracts match the model`, `Docs and CI checks`; `Docs and CI checks` checks out full Git history with `fetch-depth: 0` and runs `npm run test:docs`, including `package-boundaries`, `package-cycles`, `core-names-no-pack`, `no-compat-paths`, `doc-set`, `contract-schema-freeze`, `tool-input-stability`, `test-suites`, `address-id-check` and a `pack-version` check that fails on a shallow clone; `Reference archive` also runs); the merge queue runs the full suite on the commit that becomes main, and every push to main runs it again. On a pull request the shards and their aggregates (`Unit tests`, `Acceptance on a temporary PostgreSQL`, `Linux isolation`) are skipped, which a required check counts as passed; in the merge queue and on main each aggregate requires all its shards to pass. Default unit tests (`npm run test:unit`) no longer include `scripts/**/*.test.ts` (`scripts/real` real-system and diagnostic scripts); the unit jobs install the PostgreSQL 18 client from the PostgreSQL apt repository, so backup, restore and deploy run there. The tests of the pack sandbox, including those that prove the network denial against a really listening loopback server, run in the `Linux isolation` jobs in the merge queue and on every push to main: they install bubblewrap and AppArmor, generate and load the Hub's AppArmor policy for the job's own Node, fail when the isolation is unavailable, and then run the unit and acceptance files selected from the sources by their skip guards. They leave `kernel.apparmor_restrict_unprivileged_userns` unchanged; the launcher profile's own `userns` rule is enough. The other unit and acceptance jobs have no isolation, and these tests skip there. Ubuntu has no `sandbox-exec`, plutil or launchd, so `sandbox-exec` itself, plutil and the launchd checks skip on Ubuntu; the key files are the same on every platform, so their tests run there. The `macOS-only paths` workflow runs them on `macos-15`, and the sandbox's tests again under `sandbox-exec`, on every push to main, nightly and on demand; pull requests do not trigger it and it is not a required check. The merge queue's checks are therefore evidence for the sandbox under bubblewrap and AppArmor, but not for `sandbox-exec`, plutil or launchd; a pull request's own checks are evidence for neither. A skip is not a pass; each phase still records a full local macOS run, with commands, counts and skipped tests, in the [Hub r4 progress](hub-r4-progress.md). The CI job summary lists every skipped test.

## Key storage

Since the owner's decision 137 (2026-11-03) the Hub no longer uses the macOS keychain: on macOS as on Linux, the vault master key and the operator token are each a 32-byte file under the data root's `keys` directory (the directory 0700, each file 0600 and owned by the service account), never in a backup. `CIRCLE_HUB_KEYCHAIN_SERVICE` and `CIRCLE_HUB_KEYCHAIN_ACCOUNT` are retired: a process that has either set, even empty, refuses to start and says where the keys are now. The deployment settings keep their `keychain_service` and `keychain_account` fields, which now name the key files, so a release rolled back to reads the same settings file. A macOS deployment whose key is still in the keychain moves it before it runs a release with this change: `circle-hub key export --confirm` of the earlier release piped into `circle-hub key import` of the new one, then `circle-hub operator-token reissue`.

The versions of each secret, its digest rule, length, setter and time are kept in the data root's `vault/`, authenticated by the vault, not in the records database; a reset and rebuild keeps both `keys/` and `vault/`.

## Release order

1. The Hub first: when the model or a contract changes, raise the major version of the affected schema (`name@major`) and update this page; a release needs a separate decision by the owner.
2. Circle does not release in step with the Hub: it is only an MCP client and depends on the MCP protocol and the tool schemas.
3. Task packs carry their own versions; an upload runs the pack's positive and negative samples automatically (the publish check), and a pack that fails is not published.

Changing compatibility baselines and renaming identifiers in each repository are separate decisions, each recorded in History below.
